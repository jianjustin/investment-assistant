# v2.3.0 数据底座与「数据」菜单

> 2026-10-26，基线 `main@e3837d9`（`v2.2.0` 之后）。路线见 [roadmap](../roadmap/roadmap.md#83-透明与认知-v23v252026-10-26)。
> 三项：数据族状态层（清单 + 只追加的拉取记录 + 读取接口）、单族手动拉取、「数据」菜单（状态总览 + 原始数据浏览）。
> 本文是设计，不是实施授权：真实库执行迁移 024、打 tag、推送都在执行时单独确认。

---

## 1. 目标

主线不变，只让数据**看得见**：每类数据为什么存在、覆盖了哪些标的、最新到什么时点、最近一次拉取成没成功、失败原因是什么，以及原始值本身。

成功标准（对应路线 v2.3 退出条件）：

- 「数据」菜单有六张卡，每张都显示用途、覆盖、最新时点、最近一次拉取的成败。
- 每族都能手动拉取（ATR 走日线、范围是重新加载文件），失败原因在卡片和详情页可见。
- 能浏览原始数据：某只票的日线、某条 FRED 序列的实际值等；用户验收过浏览可用。
- §11 的手动验收和定时验收都留下证据。

系统仍然只出研究候选：不下单、不接券商；所有规则都未经验证（Phase 0 Gate HOLD），数据完整不代表信号有效，页面照此标注。

## 4. 数据族清单

代码里一份静态注册表 `investment_assistant/workbench/families.py`（`FAMILIES`），字段：`id`、`title`、`purpose`（卡片用途文案，由后端下发，与 `tasks/catalog.py` 同一做法）、`kind`（`fetched` / `derived` / `manual`）、`job`、`per_ticker`（能否单只拉取）、`fetch_via`（派生族指向被派生的族）。

| `id` | 名称 | `kind` | 所属任务 | 用途（卡片文案要点） | 目标清单 | 覆盖口径 | 最新时点 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `bars` | 日线 | `fetched` | `workbench` | 规则 v1 信号、`plan-1` 价位、`screen-1` 筛选、区制广度、「标的」页 K 线 | SPY + 行业 ETF（`SMH`、`XLK`、`QQQ`）+ 当前观察池 + 持仓 + 纳指 100 范围，去重 | 目标中最新日线日期 = 最近已收盘交易日的数量；其余列为「滞后」 | `max(price_date)` |
| `sec_filings` | SEC 申报 | `fetched` | `filings`、`workbench` | `earnings_gap_up` 的财报事件、「标的」页 SEC 列表、SEC 监控通知 | 当前观察池 + 持仓 | 近 120 天有申报记录（`filings` 行或 `sec_8k` 列表）的标的数；注明「无申报 ≠ 缺数据」 | 最近一条申报日 |
| `news` | 资讯 | `fetched` | `workbench` | Agent 工具读取的资讯标题、「标的」页资讯列表（规则不读） | 当前观察池 + 持仓 | 近 7 天（`NEWS_LOOKBACK_DAYS`）有资讯标题的标的数 | `max(published_at)`（缺失时用 `fetched_at`） |
| `atr` | ATR | `derived`（`fetch_via = bars`） | 随 `bars` | `plan-1` 止损与仓位、`screen-1` 的 ATR 区间、移动止损 | 同 `bars` | 有 ≥ 15 根日线（`plans.MIN_BARS`）且最新一根是最近已收盘交易日的标的数 | 同 `bars` |
| `fred` | FRED 利差 | `fetched` | `workbench` | 区制的宏观部分（HY 利差 `BAMLH0A0HYM2`、2s10s `T10Y2Y`） | 两条序列 | 有观测值的序列数；最新观测早于 session 前 7 个自然日的列为「滞后」 | 每条序列的 `max(obs_date)` |
| `universe` | 纳指 100 范围 | `manual` | 随 `workbench` 加载 | `screen-1` 的筛选范围、区制广度样本 | 范围文件 `config/universes/nasdaq100.json` | 成员数（合法区间 90–105）；超过 120 天（`universe.STALE_DAYS`）未更新标「过期」 | 文件 `as_of` |

「当前观察池」= `watchlist_items` 的手动池 + `pool_tiers` 最新一行为 `source = screen` 且未移出的筛选成员；「持仓」= 未作废成交得出的未平仓标的。目标清单由 `families.targets(conn, family_id, now)` 一处计算，批处理的目标与手动拉取的目标都与它对齐（批处理沿用自己现有的循环，测试断言二者一致）。

覆盖口径与滞后阈值都是**展示定义**，不是规则参数，不用历史数据去调。

## 5. 拉取记录表与迁移 024

### 5.1 `data_fetch_runs`

每次「某族被拉取一次」追加一行，只追加、不更新、不删除：

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `BIGSERIAL` PK | |
| `family` | `TEXT NOT NULL` | `CHECK (family IN ('bars', 'sec_filings', 'news', 'fred', 'universe'))`；`atr` 从不单独拉取，没有行 |
| `job` | `TEXT NOT NULL` | 该次拉取走的任务路径：`workbench` / `filings` |
| `trigger` | `TEXT NOT NULL` | `CHECK (trigger IN ('scheduled', 'manual_batch', 'manual_family'))`：定时批处理 / 手动批处理 / 数据菜单手动拉取 |
| `run_id` | `TEXT` | `job_reports.run_id` 或 `tasks/runner` 的 `run_id` |
| `scope` | `TEXT NOT NULL` | `CHECK (scope IN ('family', 'ticker'))` |
| `ticker` | `TEXT` | `CHECK ((scope = 'ticker') = (ticker IS NOT NULL))` |
| `session` | `DATE` | 本次针对的最近已收盘交易日 |
| `status` | `TEXT NOT NULL` | `CHECK (status IN ('success', 'partial', 'failed', 'skipped'))` |
| `target_count` | `INTEGER NOT NULL` | `CHECK (target_count >= 0)` |
| `ok_count` | `INTEGER NOT NULL` | `CHECK (ok_count >= 0 AND ok_count <= target_count)` |
| `failures` | `JSONB NOT NULL DEFAULT '[]'` | `[{"target": "MU", "reason": "..."}]` |
| `detail` | `JSONB NOT NULL DEFAULT '{}'` | 新增 / 未变行数、`reason`（`skipped` 时必有）、范围文件元数据等 |
| `started_at` | `TIMESTAMPTZ NOT NULL` | |
| `finished_at` | `TIMESTAMPTZ NOT NULL` | |
| `created_at` | `TIMESTAMPTZ NOT NULL DEFAULT now()` | |

索引：`(family, created_at DESC)`。

**状态判定**（纯函数 `families.classify`）：有 `detail.reason` 且未执行 → `skipped`；`ok_count = target_count` → `success`；`ok_count = 0` → `failed`；其余 → `partial`。整族一次性调用失败（SEC 列表、范围文件加载）记 `failed`，`failures` 里只有一条 `{"target": "*", "reason": ...}`。

**失败原因**：截断到 300 字；经 `macro.redact` 去掉 `FRED_API_KEY`；不写 `SEC_USER_AGENT`、webhook 等任何凭据（沿用「凭据不进报告」）。

### 5.2 迁移 024

`migrations/024_data_fetch_runs.sql`：只建 §5.1 的表与索引，`IF NOT EXISTS` 可重跑；不改任何旧表，不加种子行。

`data_fetch_runs` **不加入** `repository.WORKBENCH_TABLES`：否则迁移执行前 `service._tx()` 会因缺表报 `Unavailable`，整条批处理停摆。数据菜单的读取用例单独检查这张表（§10）。

真实库执行**待用户授权后**进行，方式与 022、023 相同：代码提交并重启之后，先 `pg_dump` 全库备份，再 `psql --single-transaction -v ON_ERROR_STOP=1 -f migrations/024_data_fetch_runs.sql` 手动执行，每一步单独授权；结果追加到 `operations/migrations-and-backup.md`。

## 6. 共用采集函数与写入

### 6.1 抽取（行为不变的重构）

新模块 `investment_assistant/workbench/collect.py`，把 `run_batch` 与 `screening._collect` 里现有的逐只采集原样搬出来：

| 函数 | 内容（与现在完全相同） | 返回 |
| --- | --- | --- |
| `bars_one(ticker, *, session, now, deps, lookback_days)` | `bars.fetch_history` → `normalize_history` → 独立事务 `repository.store_bars` | `{counts, skipped}` |
| `news_one(ticker, *, now, deps)` | `news.fetch_yfinance` → `normalize_yfinance` → `store_news` | `{inserted…, fetched, skipped}` |
| `sec_listing(tickers, *, session, now, deps)` | `EdgarSource.discover`（回看 `FILING_LOOKBACK_DAYS`）→ `store_news(filing_news)` + `fill_filing_acceptance` | 现有 `summary['filings']` 结构 |
| `fred_series(series_id, *, session, now, deps, api_key)` | 无 key 返回 `not_configured`；否则 `fetch_series` → `store_macro` | 现有 `summary['macro'][id]` 结构 |
| `load_universe(deps)` | 现有 `screening._load_universe` | `Universe` |

异常照旧向上抛（`Unavailable` 仍穿透），调用方的 `try/except` 与写 `summary` 的代码保持原样。`lookback_days` 由调用方传入：批处理沿用 `HISTORY_DAYS`（420），筛选沿用 `COLLECT_LOOKBACK_DAYS`（400），手动拉取用 420。

唯一的行为补充：`screening._collect` 现在丢掉了失败原因（只记 ticker），改为同时返回 `{ticker: reason}`，`stage['fetch_failures']` 的形状不变，原因只供 §6.2 记账。

**护栏**：重构前先补「批处理 `summary` 特征测试」（假 fetcher，含 SPY 失败、一只 ETF 失败、一只池内股日线失败、资讯失败、SEC 失败、FRED 未配置），把现状的 `summary` 钉住；重构后逐字段一致，现有 `test_workbench_service`、`test_workbench_screening`、`test_workbench_scenarios` 全部照过。

### 6.2 批处理写拉取记录

- `run_batch` 新增参数 `record_trigger: str | None = None`；`tasks/workbench.run` 传 `scheduled`（定时）或 `manual_batch`（手动），其余调用方（测试、显式 `tickers`/`pool`）默认 `None`，不写记录。
- 调用共用函数时顺手记账（`collect.Tally`：`target_count`、`ok_count`、`failures`、`detail`），不从 `summary` 的字符串里反解析。
- 采集阶段结束后（FRED 之后、区制之前），按族各追加一行：`bars`（SPY + ETF + 筛选采集 + 逐股，「`collected_in_screen`」算成功一次、不重复计数）、`news`、`sec_filings`、`fred`、`universe`（由筛选阶段的范围加载结果得出；显式池跳过筛选时不写）。
- 写入在独立事务里；失败（包括迁移 024 尚未执行）只写进 `summary['data_status'] = {'written': n, 'error': '...'}`，**不进 `summary['errors']`**，不让一次记账失败把批处理标成失败。

### 6.3 `filings` 任务写拉取记录

`tasks/filings.run` 在下载器与监控两种模式结束后各追加一行 `sec_filings`（`job = filings`，`trigger` 按 `trigger_source`：`scheduled` / `manual_batch`）：`status` 由任务结果得出；`summary.errors` 若按标的给出则逐只记入 `failures`；`target_count` 是该任务自己的目标（`config.watchlist`），`detail.targets_source = 'config.watchlist'` 注明与批处理目标不同。写入失败同样只记、不改任务结果。

### 6.4 并发

每族一把会话级 advisory lock，键为 `hashtext('data_family:<id>')`，持锁连接单独开、用完即放：

- 手动拉取：`pg_try_advisory_lock`，拿不到 → 409「该族正在采集」。
- 批处理：采集阶段开始前按固定顺序（`bars`、`news`、`sec_filings`、`fred`）`pg_advisory_lock` 阻塞获取，采集阶段结束后释放。手动拉取只拿一把锁，没有环路，不会死锁。
- 锁跨进程有效（命令行运行的批处理也遵守）；`universe` 只读文件，不加锁。

目的：避免批处理与手动拉取同时为同一标的写 `price_bars` 而撞上 `(ticker, price_date, revision)` 唯一约束。

## 7. 单族手动拉取

`POST /api/data/families/{id}/fetch`，body 可选 `{"ticker": "MU"}`。

- 校验：未知族 → 404；`atr` → 400（「派生族，请拉取日线」，前端按 `fetch_via` 直接调 `bars`）；带 `ticker` 而族不支持单只（`fred`、`universe`）→ 400；`ticker` 必须通过 `data.identity.stock_id`，否则 400。单只拉取不要求在目标清单内。
- 执行：`tasks/runner.submit` 后台运行，立即返回 `{run_id, status: 'pending'}`；前端用现有 `GET /api/runs/{run_id}` 与 SSE 看结果。
- 锁：接口层提交前先 `try` 探测一次，被占就直接返回 409；真正持锁的是后台任务（会话级锁绑在它自己的连接上）。探测与持锁之间被别人抢先时，后台任务以 `{"status": "busy"}` 结束、不写任何行，前端同样显示「该族正在采集」。
- 范围：全族时目标 = `families.targets(...)`；单只时目标 = 那一只。逐只调 §6.1 的同一组函数，`session = bars.latest_closed_session(now)`。
- 写入：只写数据表与一行 `data_fetch_runs`（`trigger = manual_family`、`job` 取族的所属任务；`sec_filings` 取 `workbench`）。**不跑规则、不生成计划或候选、不改池、不推送、不写 `job_reports`**。
- `universe`：重新 `universe.load()` 并校验，成功 `ok_count = 1`、`detail` 记 `name`、`as_of`、成员数、是否过期；失败记 `UniverseError` 原文。不联网。
- 失败照旧按只记录、不重试风暴；yfinance 限流导致的失败就是 `partial` / `failed` 加原因。

## 8. 读取接口与只读性

分层：`api/routes/data.py`（薄封装）→ `workbench/data_view.py`（用例）→ `workbench/repository.py`（新增 SQL）。

| 接口 | 返回 | 读写 |
| --- | --- | --- |
| `GET /api/data/families` | 六张卡 | 只读 |
| `GET /api/data/families/{id}` | 卡片 + 最近 20 次拉取记录 + 逐目标覆盖表 | 只读 |
| `POST /api/data/families/{id}/fetch` | `{run_id, status}` | 写数据表 + `data_fetch_runs` |
| `GET /api/data/browse/{id}` | 原始值（`?ticker=` 或 `?series=`） | 只读 |

**卡片字段**：`id`、`title`、`purpose`、`kind`、`fetch_via`、`per_ticker`、`job`（`name`、`enabled`、`next_run_at`，读 `scheduled_jobs`）、`coverage`（`targets`、`covered`、`lagging`）、`latest_at`、`last_run`（`status`、`trigger`、`scope`、`ticker`、`finished_at`、`ok_count`、`target_count`、前 5 条 `failures`）、`last_success_at`（最近一次 `success` 或 `partial` 的 `finished_at`）、`evidence`（固定文案，见下）、`fetch_runs_ready`（迁移 024 是否已执行）。

**逐目标覆盖表**：每个目标一行——`target`、`latest_at`、`lagging`、最近一次失败原因（取该族最近 20 次记录里该目标的最后一条失败）。

**浏览窗口**（固定，不做日期筛选）：

| 族 | 参数 | 内容 |
| --- | --- | --- |
| `bars` | `ticker` | 最近 120 个交易日；每日取截至现在的最新修订（`repository.read_bars`），附该日修订次数与 `fetched_at`；OHLC 为拆股调整、未分红调整，`adj_close` 为全调整，表头注明 |
| `atr` | `ticker` | 同一份日线用 `plans.atr14` 逐日现算的最近 60 个值，附当日收盘与 ATR/收盘；标注「现算，与 `plan-1` 同一函数；不入库」 |
| `news` | `ticker` | 近 60 天标题、来源、发布者、链接、发布时间（`repository.read_news`） |
| `sec_filings` | `ticker` | 近 180 天 `filings` 行（`read_filings`）+ 未入 `filings` 表的 `sec_8k` 列表 |
| `fred` | `series` | 最近 120 个观测值（截至现在的最新修订）+ 修订次数 |
| `universe` | — | 文件元数据（`name`、`as_of`、`source`、`note`）+ 成员表，每只附最近日线日期 |

**只读性**：

- 所有 `GET` 用例在只读事务里执行（psycopg 连接 `read_only = True`），数据库层面写不进去。
- 读取从不调用外部数据源；缺数据显示「无数据」并提示去拉取，不在读取时补拉。
- 测试断言：调用 `GET` 前后各数据表行数不变。

**证据状态**：卡片 `evidence` 与页面顶部常驻一行——「这里只展示采集事实。所有规则都未经验证（Phase 0 Gate HOLD）：数据完整不代表信号有效。」ATR 卡与 ATR 浏览再标「`plan-1` 的计算输入，规则 `gate_hold`」。

## 10. 出错与降级

| 情况 | 行为 |
| --- | --- |
| 数据库未配置 / 不可达 | `GET` 与 `POST` 返回 503，沿用 `Unavailable` 文案；不返回空列表冒充「无数据」 |
| 工作台数据表缺失 | 同上，提示需执行的迁移 |
| 仅 `data_fetch_runs` 缺失（024 未执行） | `GET /api/data/families` 照常返回覆盖与时点，`fetch_runs_ready = false`、`last_run = null`；`POST .../fetch` 返回 503「需执行迁移 024」；批处理与 `filings` 任务写记录失败只记 `data_status.error` |
| 范围文件不可读 | `universe` 卡覆盖为 0、最新时点为空、最近拉取 `failed` 带原因；其他卡不受影响 |
| FRED 未配置 key | `fred` 记 `skipped`，`detail.reason = 'FRED_API_KEY 未配置'`，不发请求 |
| 手动拉取时锁被占 | 409 |
| 外部源单只失败 | 记入 `failures`，族状态 `partial`；不写库、不冒充「无数据」 |
