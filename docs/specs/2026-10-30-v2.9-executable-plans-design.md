## 1. 目标

对应路线成功标准 6：**每份计划都能照着执行：一只股票同一时间只有一条计划链，再次触发产生写明差异与理由的修订版；「今日」一张表回答「明早开盘落在区间内、跳空高开、跳空低开各做什么，本计划何时作废」；持仓每个交易日有一行持仓状态（距止损、距 T1、已持有与剩余天数、维持理由），到最长持有未到 1R 给出退出指令；采纳由成交推导，不再点按钮；「标的」页能读出该标的全部计划的来龙去脉。**

用户遇到的三个问题与对应交付：

| 问题（用户原话摘要） | 根因（核查） | 交付 |
| --- | --- | --- |
| 今天产生的信号明天不一定适用 | 计划只有入场区间与有效期；开盘落在区间外怎么办由人临场判断；影子模拟对「跳空低于止损」仍会成交 | §5 执行字段：入场类型、开盘三种情形、本计划何时作废，宿主按模板生成，影子按同一规则模拟（`plan-shadow-2`） |
| 同一只股票（如 MU）今天和明天都出现在计划里、入场价不同，不知道是什么关系 | 单元与 `agent-2` 链的键都是（标的，信号日），连续两天触发 = 两个单元、两条链，各自复查；首版提议的人类消息只有一行，看不到任何历史链（`graph.py:419-420`） | §4 一只股票一条活跃链：再次触发不开新链，作为 `retrigger` 信号进已有链的复查、产出修订版；首版能看到最近一条已结束链的摘要；§10.3「标的」页计划历史 |
| 入场后一周没等到退出信号，不知道继续等还是卖 | 计划与影子都没有时间止损，持仓会一直是 `open`；持仓期复查只写一句结论，没有状态输出 | §7 最长持有（默认 10 个交易日未到 1R 即退出）、`held_sessions_reached`、每日持仓状态 |

外加用户要求的两项：**取消「采纳 / 否决 / 降级」按钮**（§6，采纳由成交推导）与**失效计划分组置灰**（§10.1）。

**不改的口径**：规则 v1、`screen-1`、`regime-2`、`context-2`、`backcheck-2`、`derivation-1`、`stages-4`、`daily-1`、`fetch-1`、`siwc-1`、`agent-brief-1`、知识三件（`knowledge-1`、`my-knowledge-1`、`knowledge-perf-1`）。`plan-1` 的价位公式在 `plan-2` 里原样保留（§5.4）。所有规则与 Agent 照旧**未经验证**（Phase 0 Gate HOLD）。

## 2. 假设与决定

用户需求原文已定的不再重复。下表是本 spec 补定的设计决定；会改变范围或真实数据语义、需要你拍板的，列在 §19「待用户确认」，并按建议方案先写进本文。推翻任一条就改对应章节。

| # | 问题 | 决定 | 理由 | 放弃的备选 |
| --- | --- | --- | --- | --- |
| D1 | 链的身份 | 链键保持（标的，**首版信号日**）不变；「链」仍是 `agent_plan_versions` 的一组版本，不建链表、不存状态列，状态照旧每次现算（`timeline-2`，§4.1） | 只追加：状态由记录推出是 v2.5 起的做法；改键要迁移全部版本行与复查行 | 新建 `chains` 表带 `status` 列（状态可被改写，违背只追加） |
| D2 | 「活跃链」的判定 | 活跃 = `timeline-2` 状态为 `entry`、`holding` 或 `exiting`（§4.1）；**每个标的至多一条**（非旧链）。由宿主在 `plan` 节点按复查交易日 S 现算，`plan_review check` 每天核对 | 用户要的是「同一时间只有一条活跃链」；`exiting`（已发退出指令但仍持仓）也必须占位，否则持仓期就能再开一条入场链 | 只把 `entry` 算活跃（持仓时再触发会开出第二条链） |
| D3 | 再次触发在哪一步判定 | **`plan` 节点**：为买入单元算完规则基线后，若该标的已有活跃链，就写一行 `chain_retriggers`（§8.3），单元标「已有活跃链」；`agent` 节点对这些单元不提议（跳过原因 `active_chain`），`review` 节点据此给已有链触发 `retrigger` 信号 | `plan` 节点是宿主判定、不依赖模型：Agent 不可用时映射照样落库；`agent` 节点只读映射，不用再判一次；三处用同一张表，口径唯一 | 在 `agent` 节点判定（Agent 不可用时没有记录，次日复查看不到这次触发）；在 `review` 节点判定（`agent` 节点已经为它开了新链） |
| D4 | `retrigger` 在入场期怎么处理 | 入场期的链触发 `retrigger` 时**跳过单阶段复查，直接走修订流程**（提议 + 反方 + 校验，`mode = revise`），提示词带这次触发的规则、冻结取值与规则基线价位；修订输出 `pass` 仍按 v2.5 改为作废。价位与条件都不变时允许只「续期」（§4.3） | 用户要求「产出修订版并写明 diff 与理由」；再次触发的同时有效期要重新起算，维持旧版会让它很快过期；直接修订省一次复查调用 | 当作普通信号由模型选维持 / 修订（模型选维持时旧版照旧按原有效期过期，用户看不到「为什么又出现」） |
| D5 | `retrigger` 在持仓期与退出期 | 持仓期：只作为证据进单阶段复查（不加仓，白板 6.4「持仓期只能上移止损、改目标」）；退出期（`exiting`）：只记信号、不调用模型 | 持仓时再触发说明趋势仍在，可以是上移止损或维持的理由，但不是加仓指令 | 持仓期允许按仓位规则加仓（本版不做，§3） |
| D6 | 入场期上限 | `chain_entry_cap` 从「首版信号日后第 10 个交易日」改为「**最近一次触发**（首版或 `retrigger`）后第 10 个交易日」；新上限写进 `chain_retriggers.entry_cap` 与修订版 `inputs.chain_entry_cap` | 否则第 9 天再触发的链只剩 1 天入场期，修订版的有效期会被截断成当天 | 不延长（再次触发等于白触发） |
| D7 | 修订版的「续期」 | `agent-3` 的宿主差异 `diff` 多两个**宿主字段** `valid_until`、`entry_cap`（标 `host_only: true`），不要求出现在模型的 `changes` 里；`retrigger` 触发的修订若模型字段全无变化，允许成为新版（`changes = []`，页面与推送用宿主模板「再次触发（<规则>，<信号日>），沿用价位，有效期延至 <日期>」），其余修订照旧 `no_change` 作废 | 核查：`CHANGE_FIELDS` 不含有效期，同价位的修订会被 `no_change` 拒掉；而「再触发、价位不变、有效期顺延」正是用户想看懂的一类变化 | 把有效期加进模型必填的 `changes`（每次修订都要写一条「有效期顺延」，噪音） |
| D8 | 上线时已存在的多条活跃链 | 不改任何旧行。`timeline-2` 新增派生状态 `superseded`：入场期的链，若同标的存在信号日更晚的链 → `superseded`（终止）。持仓中的链不会被取代；两条都持仓的旧数据各自保留 `holding`，`check` 只对首版为 `agent-3` 的链核对唯一性 | 只追加；上线之后新链只在无活跃链时才开，所以 `superseded` 只会出现在旧数据上 | 迁移时写「合并」记录（改写历史语义） |
| D9 | 首版能看到什么历史 | `agent-3` 首版提示词加一段**「同标的上一条链」证据块**：最近一条已结束链的摘要（§4.6），只读、只用截止时间之前的记录；块内的模型文字加 `    │ ` 前缀；不可作为引用（价位与论点仍须引用本次工具调用） | 用户要求首版知道「上一条链怎么结束的」；做成证据块而不是新工具：工具集合（十个）与工具轮数上限不变，块长度可控（≤ 2000 字） | 新工具 `get_chain_history`（改工具集合与推理视图，且模型可能不调用） |
| D10 | 入场类型 | 三种（`entry-1`，§5.2）：`zone_limit`（区间限价，规则基线恒用）、`breakout_stop`（突破买入止损限价）、`next_open`（次一交易日开盘市价）。开盘三种情形的做法由宿主按入场类型从模板生成，**模型只选类型、不写情形文字** | 判定在宿主代码：情形文字与影子模拟必须同一份规则；白板 6.1 列了四种，分批（一半触发、一半确认）留 backlog | 让模型自由写开盘预案（无法模拟、无法校验） |
| D11 | 跳空低于区间 | 开盘 ≤ 止损 → **本计划作废**（当日起不买）；止损 < 开盘 < 区间下沿 → 不在开盘买，`zone_limit` / `breakout_stop` 盘中回到下沿时按下沿买入，`next_open` 当日不买、计划作废 | 白板 6.1「超出下沿视为失效」；`plan-shadow-1` 对「开盘低于止损、盘中反弹到下沿」照样成交、当根又触止损，是假成交 | 低开一律作废（与 `plan-shadow-1` 差异过大，规则基线的影子会大面积变成「作废」） |
| D12 | 跳空高于区间 | 一律不追：`zone_limit` 限价留在上沿，盘中回落到上沿才成交；`breakout_stop` 同（买入止损限价，限价 = 上沿）；`next_open` 当日不买、计划作废 | 白板 6.1「开盘超出上沿一定比例不追」；本版取比例 0，追高本来就是纪律四项之一 | 允许追 x%（新参数、新影子口径，样本还没有） |
| D13 | 规则基线 | 新版本 **`plan-2`** = `plan-1` 的价位、有效期、仓位、财报规则原样 + `entry_type = zone_limit` + `max_hold_sessions = 10`；上线后新单元只生成 `plan-2`，旧 `plan-1` 行不重算（§5.4） | 规则基线也要能照着执行（Agent 没有可用计划时表里只有它）；价位公式不变，规则 v1 与筛选口径不受影响 | 继续生成 `plan-1`、另算 `plan-2`（每单元两行规则计划，表格与三方对比都要选一个） |
| D14 | 影子 | 新版本 **`plan-shadow-2`**：入场按 §5.2 的开盘情形（含 D11 的作废）、`next_open` 只看第一根、持仓按最长持有退出（§7.1）。对带执行字段的计划（`plan-2`、`agent-3`、v2.9 的 `own`）**同时**算 `plan-shadow-1` 作反事实列（「无时间止损、旧入场规则」），旧计划只算 `plan-shadow-1` | 用户「与 `plan-1` 并列影子」；同一份计划两种口径并列，正是白板 7.3 的反事实：时间止损在自己的单元上是帮了还是害了 | 只算 `plan-shadow-2`（失去对照） |
| D15 | 最长持有的语义 | 计划必填 `max_hold_sessions`（规则基线 10；Agent 在 5–20 之间选，默认 10）；**时间止损成立** = 已持有交易日数 ≥ `max_hold_sessions`，且开仓以来没有一个收盘价 ≥ 成本 + 1R；成立时当天收盘后给出退出指令「次一交易日开盘卖出」，影子按次日开盘价退出（§7.1） | 白板 6.2「N 个交易日未达 1R 则退出（资金效率）」；按收盘判定、次日执行，与止损「按收盘判定、次日生效」一致；到过 1R 说明交易在走，交给移动止损 | 只看天数（会砍掉慢涨的好交易）；看当天收盘是否 < 1R（一次冲高回落就解除时间止损，又被拉回） |
| D16 | 条件 `held_sessions_reached` | `condition-2` 新增 `held_sessions_reached{sessions}`（3–30），语义同 D15（含「未到 1R」）；失效与复查两栏都可用；入场期判定为 `not_met`（不是 `unknown`）。宿主把计划的 `max_hold_sessions` 自动作为一条失效条件（`source = max_hold`）参与判定，模型不必也不能重复写 | 用户指定条件名；放进条件集合，失效条件的判定、文案、复查记录与推理视图全部复用 | 时间止损只做成宿主硬编码（推理视图与复查记录里看不到） |
| D17 | 持仓期的「作废」 | `timeline-2` 下，持仓期的链被作废（失效条件成立、时间止损、止损触及、Agent 判作废）**不再结束链**，而是进入 **`exiting`（退出期）**：最新版照旧，每日持仓状态给出退出指令，直到这些买入全部平仓 → `position_closed`。复查记录的 `outcome` 仍是 `invalidate`（不加新取值），页面按 `mode = holding` 显示为「退出指令」 | v2.5 的做法是持仓期作废即「不再复查」，持仓却还在——用户问「继续等还是卖」恰好落在这个空档；`outcome` 不加取值，推送、运行一览、复查计数的分支不用改 | 新增 `outcome = 'exit'`（十余处按 `outcome` 分支的代码要跟着改）；作废即结束（现状） |
| D18 | 持仓期止损触及 | `timeline-2` 下，持仓期当天最低价 ≤ 当前有效止损（含 T1 之后的移动止损）→ **宿主判定作废 → 退出期**，原因「止损触及（<价>）：应已按止损卖出；仍持有则次一交易日开盘卖出」，不调用模型；入场期的 `stop_touched` 照旧只是信号 | 止损是事先写好的退出规则，判定在宿主；现在要等模型复查才说「作废」，而模型可能「维持」 | 照旧交给模型 |
| D19 | 持仓状态存在哪 | 新表 **`holding_status`**（只追加，§8.4）：每个**持仓标的**每个复查交易日一行（有链、有规则 / 自定计划、无计划的持仓都有），由 `review` 节点在复查之后写入，**不论复查成功、跳过还是出错** | 用户要「每日都有一行持仓状态」；挂在 `plan_reviews` 上会在复查跳过或出错的日子缺行，也覆盖不到没有 Agent 链的持仓 | `plan_reviews` 加一列（缺行）；页面现算（推送与复盘读不到当天冻结的值） |
| D20 | 持仓的计划取哪一版 | `timeline-2` 下持仓的止损 / T1 取**链的最新版**（持仓期修订上移的止损随之生效），1R 的风险取**第一笔买入关联的那一版**的止损（初始止损）；没有链的持仓取买入关联的计划 | 核查：现在持仓止损取决定关联的那份计划，持仓期修订版上移的止损不生效；白板 6.2「止损只能上移」要求修订版能管到持仓 | 照旧取决定关联的计划 |
| D21 | 成交怎么关联计划 | `trades` 加列 **`plan_id`**（关联当时照着做的那一份计划版本）；录入成交时下拉列出该标的当时可执行的计划（活跃链的最新版、有效期覆盖成交日的规则基线、「自定」、「无计划」）；「自定」在同一事务里写一行 `own` 计划（带执行字段）。新成交不再接受 `decision_id`（§6.1） | 核查：成交与计划、版本、单元之间只有 `trades.decision_id` 一条路，纪律、实际轨、持仓止损、复盘卡、周报、链状态都靠它；取消决定后必须有直接关联 | 成交时由宿主按时间自动推断计划（同标的多份计划时会猜错，且你无法更正） |
| D22 | 链怎么从成交推出 | 成交关联的计划是 `agent-2` / `agent-3` 版本 → 它的链；是规则基线或 `own` 计划 → 该计划所属单元：单元自己开了链则是那条链，单元被并入（`chain_retriggers`）则是被并入的链，否则无链 | 映射全在已写入的记录里，纯函数可推；不额外存「成交所属链」列 | `trades` 再加 `chain_signal_date` 列（冗余，可能与 `plan_id` 矛盾） |

## 4. 一只股票一条活跃链（`timeline-2`）

### 4.1 链状态

纯函数 `timeline.chain_state(chain, *, session, now, facts)`，在复查交易日 S、截止时间 `now` 判定，按顺序取第一条成立的：

| 状态 | 条件 | 活跃 | 复查 |
| --- | --- | --- | --- |
| `legacy` | 单元只有 `agent-1` 计划 | 否 | 否 |
| `invalidated` | 最新版有一条有效复查的结论为 `invalidate`，且该复查的 `mode = entry`，或复查行的 `timeline_version = 'timeline-1'` | 否（终止） | 否 |
| `closed_by_decision` | 单元的**旧决定**链头 `final_action ≠ buy`（只可能来自 v2.9 之前的决定行） | 否（终止） | 否 |
| `exiting` | 链上关联的买入（§6.1）还有未平批次，且最新版有一条 `mode = holding`、`timeline_version = 'timeline-2'`、结论 `invalidate` 的有效复查 | **是** | 否（只写持仓状态，§7.2） |
| `holding` | 链上关联的买入还有未平批次 | **是** | **是**（持仓期） |
| `position_closed` | 有过关联的买入，现已全部平仓 | 否（终止） | 否 |
| `superseded` | 处于入场期，且同标的存在信号日更晚的 `agent-2` / `agent-3` 链（只会出现在 v2.9 之前开出的链上，D8） | 否（终止） | 否 |
| `expired` | `S ≥ 最新版 valid_until`，或 `S >` 当前入场期上限 | 否（终止） | 否 |
| `entry` | 其余 | **是** | **是**（入场期） |

- 「链上关联的买入」= `execution.chain_buys(chain)`：`trades.plan_id` 按 D22 映射到这条链的未作废买入，**并上**旧口径（`trades.decision_id` 属于该单元的决定，`repository.unit_decision_ids`），两者取并集、按成交 id 去重。
- `timeline-1` 的 `closed_by_decision → holding` 顺序（核查：仍持仓也先判成 `closed_by_decision`）在 `timeline-2` 里不变：旧决定否决的链即使后来有成交也照旧算终止，只是这类持仓的状态行由 §7.3 的「无链持仓」覆盖。
- 链视图（`GET /api/workbench/chains/...`）的 `state` 带 `{state, mode, basis, active, timeline_version}`；`basis` 写出判定依据（如 `{exit_review_id}`、`{superseded_by: '2026-10-29'}`）。

### 4.2 再次触发：`plan` 节点

`plan` 节点为每个**无冲突的买入单元**算完规则基线 `plan-2` 之后（同一个逐只循环、同一事务）：

1. 读该标的全部 `agent-2` / `agent-3` 链，按 §4.1 在 S 判定状态（与 `review` 节点同一个函数、同一份事实读取 `plan_review.read_chain_facts`）。
2. 有活跃链 → 写一行 `chain_retriggers`（§8.3）：`ticker`、`unit_signal_date = S`、`chain_signal_date`、`chain_state`、本单元的 `rule_ids`、`baseline_plan_id`（本单元的 `plan-2`）、`entry_cap`（入场期 = `add_trading_days(S, CHAIN_ENTRY_SESSIONS)`，持仓 / 退出期为空）、`run_id`。`(ticker, unit_signal_date)` 唯一，同一 session 重跑不重复写。
3. 没有活跃链 → 什么也不写，单元照旧进入 `agent` 节点开新链。

`plan` 节点 `detail.retriggers = {count, by_state: {entry, holding, exiting}, tickers: [...]}`。卖出、观察与冲突单元不参与（卖出单元对持仓标的照旧产生 `plan_stop` / `plan_target` 候选，与链无关）。

### 4.3 `retrigger` 信号与复查

- **`agent` 节点**：单元有 `chain_retriggers` 行 → 不提议、不写运行行，阶段 `skips` 记 `active_chain`（附链键）；这类单元的解读直接用规则版简报（不再单独跑 `agent-brief-1`，省一次调用）。`GET /api/workbench/agent-runs` 的覆盖率把它算作已覆盖（`coverage.merged`），不进 `coverage.missing`。
- **`review` 节点**：`timeline.signals` 加第八项（`timeline-2`）：

| `kind` | 触发判定 | `detail` / `evidence` |
| --- | --- | --- |
| `retrigger` | 有 `chain_retriggers` 行指向本链，且 `unit_signal_date ∈ (since_session, S]` | `[{unit_signal_date, rule_ids, baseline: {entry_low, entry_high, stop, target1}, frozen_values}]`（`frozen_values` 取候选行的冻结取值） |

- **入场期 + `retrigger` 触发**（D4）：跳过 §7.4 第 2 步「无事可看」与第 4 步单阶段复查，直接进修订流程；`plan_reviews` 照写一行（`outcome` 按修订结果：新版 → `revise`；`pass` → `invalidate`、`detail.via = revision_pass`；校验不过 → `revise` 且无新版、`detail.revision_status`），`decided_by = agent`、`review_agent_run_id` 为空、`detail.via = 'retrigger'`。为此放宽约束：`CHECK (decided_by = 'host' OR review_agent_run_id IS NOT NULL OR revision_agent_run_id IS NOT NULL)`（§8.6）。失效条件成立仍先由宿主作废（第 1 步不跳过）。
- **修订版的有效期**：`valid_from = S+1`、`valid_until = min(S+3, 新入场期上限)`，新入场期上限 = `chain_retriggers.entry_cap`（D6）。
- **续期**（D7）：模型字段（`CHANGE_FIELDS`）全无变化、只有宿主字段变化时，`agent-3` 校验在 `via = retrigger` 下放行，`changes = []`，宿主差异 `diff` 只含 `valid_until` / `entry_cap`；页面与推送的变化说明用宿主模板「再次触发（<规则简称>，<信号日>），沿用价位，有效期延至 <日期>」。其余触发下照旧 `no_change`。
- **持仓期**：`retrigger` 只是信号，进单阶段复查的证据块（D5）；**退出期**：记进持仓状态的 `detail.signals`，不调用模型。
- 同一天同一条链既有 `retrigger` 又有用户输入：只走一次修订流程（证据块里两者都有）。

### 4.4 入场期上限

- 首版：`chain_entry_cap = add_trading_days(signal_date, CHAIN_ENTRY_SESSIONS)`（同 v2.5）。
- `retrigger`：`entry_cap = add_trading_days(unit_signal_date, CHAIN_ENTRY_SESSIONS)`；之后的修订版取该链最近一行 `chain_retriggers.entry_cap` 与首版上限的较大者，写进新版 `inputs.chain_entry_cap`。
- `expired` 的判定用当前上限（§4.1）。推导（`('agent-3', 'agent')`）的有效期核对按同一规则从 `chain_retriggers` 读上限。

### 4.5 旧数据：多条活跃链

上线时可能已有同标的两条入场期链（例如 MU 10-28 与 10-29）。`timeline-2` 下旧的那条判为 `superseded`（D8），新的照常；两条都持仓的各自 `holding`。`plan_review check` 的唯一性核对只对**首版 `schema_version = 'agent-3'`** 的链执行（v2.9 上线后开出的链首版必为 `agent-3`，不依赖任何上线时间戳），并核对同标的 `agent-3` 链与仍活跃的旧链不重叠。不写任何合并记录。

### 4.6 首版的「同标的上一条链」证据块

`agent-3` 首版提议（`_run_agent_unit`）的人类消息在现有一行之后加一段，宿主在只读事务里按截止时间 `now` 组装（纯函数 `timeline.previous_chain_block(facts)`）：

```
同标的上一条链（只读背景，不可引用；价位与论点仍须引用本次工具调用）
- 链 MU·2026-10-21（共 3 版），结束：已过期未执行（2026-10-24）／作废：<理由>／已平仓（2026-10-27，实际 -1.0R）
- 最新版：入场 x–y · 止损 z · T1 w · 有效期至 <日期> · 入场类型 <类型>
- 最后一次复查：<结论>（Agent／系统规则，<日期>）：<理由>
- 影子（plan-shadow-2，截至本次截止时间）：<状态，R>
    │ 最后一版的变化说明：<changes 文本>
```

- 只取**已结束**（`invalidated` / `closed_by_decision` / `position_closed` / `superseded` / `expired`）且结束判定所用的全部记录 `created_at ≤ now` 的**最近一条**链；没有则写「同标的此前没有计划链」。
- 影子只用 `≤ as_of_session` 的日线；实际 R 只用 `executed_at ≤ now` 且 `recorded_at ≤ now` 的成交。
- 模型写的文字（`changes`、复查理由）每行加 `    │ ` 前缀，整块至多 2000 字（超出截断并注明）；块的全文与哈希写进 `agent_runs.input_digest.previous_chain`，推理阅读视图在「提议者读了什么」之前显示这一块。
- 同一标的的链之间不再是互不相关：计划历史（§10.3）的「为什么又开」就读这一块与开链单元的规则。

### 4.7 互斥

- `plan` 节点判定活跃链、写 `chain_retriggers` 时持事务级锁 `chain-open:<标的>`；`agent` 节点为某标的写首版之前在同一把锁下再核对一次「没有活跃链」（同一 session 的 `chain_retriggers` 不存在、该标的没有处于 `entry` / `holding` / `exiting` 的链），不满足则改记 `active_chain` 跳过。
- 手动「重新运行 Agent」（`POST /api/workbench/agent-runs`）同样先核对：已有活跃链 → 409 `active_chain`（「MU 已有进行中的计划链（10-29 第 n 版），这次触发已并入」）。
- 复查的两把锁（`review-run:<标的>:<信号日>`、`review:<标的>:<信号日>`）不变。

### 5.2 入场类型与开盘三种情形（`entry-1`）

记入场区间 [L, U]、止损 S、有效期 [F, E]。每个有效日按当日开盘价 O 分三种情形（纯函数 `entry_rules.scenarios(plan)` 返回 `[{case, action, text}]`，`entry_rules.simulate_entry(plan, bars)` 给影子用，两者同一张表）：

| 入场类型 | 开在区间内（L ≤ O ≤ U） | 跳空高于区间（O > U） | 跳空低于区间（O < L） |
| --- | --- | --- | --- |
| `zone_limit` 区间限价 | 开盘按开盘价买入（限价挂在 U） | 不追：限价留在 U，盘中回落到 U 才成交；当日未成交次日照旧 | O ≤ S → **本计划作废**；否则不在开盘买，盘中回升到 L 时按 L 买入（买入止损单 L），当日未成交次日照旧 |
| `breakout_stop` 突破买入 | 开盘按开盘价买入（已在突破价之上） | 不追：买入止损限价单的限价是 U，盘中回落到 U 才成交 | O ≤ S → **本计划作废**；否则挂买入止损单 L（限价 U），盘中升破 L 成交 |
| `next_open` 次日开盘 | 只在第一个有效日：开盘按开盘价买入 | 不买，**本计划作废** | 不买，**本计划作废** |

- 文案逐字（`entry_rules.TEXT`，前端同步）：
  - `in_zone`：「开在 L–U：开盘买入 N 股」；
  - `gap_up`：`zone_limit` / `breakout_stop`「高开过 U：不追，挂 U 限价等回落」，`next_open`「高开过 U：不买，本计划作废」；
  - `gap_down`：`zone_limit`「低开：≤ S 作废；否则回升到 L 时买入」，`breakout_stop`「低开：≤ S 作废；否则升破 L 时买入」，`next_open`「低开过 L：不买，本计划作废」。
  - L、U、S、N 按计划行的值原样替换（到分；股数缺资金快照时写「—」）。
- `zone_limit` 与 `breakout_stop` 在日线上的成交规则相同（区别只在你挂的单子类型），所以影子一致；`next_open` 只看第一个有效日。
- 同一根日线的成交价：开在区间内取 O；高开后回落取 U；低开后回升取 L（与 `plan-shadow-1` 相同，只多了「O ≤ S 作废」与 `next_open`）。

### 5.3 本计划何时作废（`void_when`）

宿主汇总（`entry_rules.void_when(plan, chain, conditions)`），按顺序列出，每条一个 `{source, text}`：

1. `validity`：「有效期至 <E> 收盘仍未成交」（入场期上限更早时写上限）；
2. `gap`：入场类型对应的开盘作废规则（上表加粗的格子）；
3. `invalidation`：最新版的每条失效条件（条件文案与 `agent/conditions.py` 模板逐字一致），附最近一次判定；
4. `max_hold`：持仓后「持有 n 个交易日仍未到 1R → 次日开盘卖出」（入场期显示为「持仓后：…」）；
5. `stop`：持仓后「收盘前触及止损 <S>（T1 之后为移动止损）」。

规则基线只有 1、2、4、5 四类。

### 5.4 规则基线 `plan-2`

- `plans.build_rule_plan` 改为生成 `plan_version = 'plan-2'`：价位、有效期、仓位、财报与市场环境规则**逐字沿用 `plan-1`**，另写 `entry_type = 'zone_limit'`、`max_hold_sessions = 10`（`RULE_MAX_HOLD_SESSIONS`）、`inputs.entry_rules_version = 'entry-1'`。
- 推导注册 `('plan-2', 'rule')`：与 `('plan-1', 'rule')` 相同的推导，另核对两个执行字段等于常量；旧 `plan-1` 行照旧按 `('plan-1', 'rule')` 推导。
- 「已有活跃链」的单元照常生成 `plan-2`，计划行 `inputs.active_chain = {ticker, signal_date}`，页面与推送标「已有活跃链，见 MU·10-29」。
- 重跑结果相同就返回原计划的规则不变（`plan-2` 与已有 `plan-1` 不比较：上线当天之前生成的 `plan-1` 不会被重算）。

### 5.5 Agent `agent-3`

- **输出**：在 `agent-2` 的形状上加 `entry_type`（三选一）与 `max_hold_sessions`（整数 5–20）；提议、修订都必填，缺 → `malformed`。
- **`CHANGE_FIELDS`**：`('action', 'entry', 'entry_type', 'stop', 'target1', 'max_hold_sessions', 'thesis', 'invalidation', 'review_when')`；宿主字段 `('valid_until', 'entry_cap')` 只进 `diff`（带 `host_only: true`），不进 `changes` 的相等核对。
- **持仓期的修订**（白板 6.4，宿主校验）：方向不变（`pass` 仍按 v2.5 改为作废 → `exiting`）；**止损只能上移**（新止损 < 上一版止损 → `stop_lowered` 作废这次修订）；入场类型与区间在持仓期改动不生效（照写进新版，但持仓状态与影子不用它们，页面标「持仓期不适用」）。入场期不限制。
- **条件集合**：`condition-2`；模型写 `held_sessions_reached` 进失效条件 → `invalid_condition`（由宿主从 `max_hold_sessions` 注入，D16），写进复查条件允许。
- **提示词**：提议与修订各加一段入场类型说明（三种类型的含义与上表）、最长持有说明；首版加 §4.6 证据块；修订（`retrigger`）加「再次触发」证据块。
- **作废原因（新增，`REASON_TEXT` 与前端同步）**：`invalid_entry_type`「入场类型不在允许的三种之内」、`invalid_max_hold`「最长持有须为 5–20 个交易日」、`stop_lowered`「持仓期不能下移止损」、`active_chain`「已有进行中的计划链，这次触发已并入」。
- 旧 `agent-2` 链在 v2.9 下照常复查；它们的修订版按 `agent-3` 生成（链里出现 `agent-2` 与 `agent-3` 混排，按版本行的 `schema_version` 区分），`agent-2` 版本没有执行字段时，计划表按 `zone_limit` + 10 日显示并标「旧版计划，执行字段按默认值显示」，影子只算 `plan-shadow-1`。

### 5.6 影子 `plan-shadow-2`

`plan_shadow.simulate_v2(plan, bars, spy_bars, *, splits)`（纯函数），在 `simulate`（`plan-shadow-1`）上改三处：

1. **入场**：按 §5.2 逐日判定；`O ≤ S` 的那一天起计划作废（`status = 'voided'`，`void_reason = 'gap_below_stop'`，计 0R、不计入有 R 的份数，汇总里单列 `voided`）；`next_open` 只看 F 那一根。
2. **时间止损**：成交后按交易日计数（成交日 = 第 1 天）；第 n 天收盘时 n ≥ `max_hold_sessions` 且自成交以来所有收盘 < 成交价 + 1R（R = 成交价 − 初始止损）→ 第 n+1 天开盘按开盘价退出余下仓位（`reason = 'time_stop'`）；当天若先触止损按止损算。T1 已触发（卖出一半）时 1R 必已到达，时间止损不再适用。
3. **到期未成交**：同 `plan-shadow-1`（`expired`）。

- `GET /api/workbench/plans/shadow` 每行加 `shadow_v1`（对带执行字段的计划，`plan-shadow-1` 的结果作反事实列）与 `shadow_version`；`agent_summary` 的 `first` / `latest` 照旧，另给 `counterfactual: {v1: …, v2: …}` 两套汇总（同一批计划、两种口径）。
- 周度 / 月度快照：`plans` 按 `plan-shadow-2`（新计划）与 `plan-shadow-1`（旧计划）分别汇总，页面标口径；不混算。

## 6. 采纳由成交推导（`execution-1`）

### 6.1 成交关联计划

- `POST /api/workbench/trades` 的 body 加 `plan_id?` 与 `own_plan?`（`{entry_low, entry_high, stop, target1, max_hold_sessions?}`），**去掉** `decision_id`（给了 → 400 `decision_link_retired`）。三选一：关联计划（`plan_id`）/ 自定（`own_plan`，同一事务写一行 `kind = 'own'`、`plan_version = 'plan-2'`、`entry_type = 'zone_limit'`、`max_hold_sessions` 缺省 10 的计划，`signal_date` = 该标的当时活跃链所在单元或最近一个单元，有效期 = 成交日当天）/ 都不给（无计划）。
- 校验：`plan_id` 必须是同一标的的计划；指向链上的**旧版**（成交时已有更新的版本）→ 409 `plan_stale`（「这条链已更新到第 n 版，请按最新版关联，或选自定」）；卖出成交可不关联（平仓按 FIFO 配对，链状态由买入决定）。
- **可关联的计划**（`GET /api/workbench/trades/linkable-plans?ticker=&executed_at=`）：该标的在成交时刻活跃链的最新版（默认选中）、有效期覆盖成交日的规则基线、最近 5 个交易日内的 `own` 计划；每项带标签「Agent MU·10-29 第 2 版（入场期，有效至 11-03）」。
- 前端「复盘 → 交易与持仓」的「关联决定」下拉改为「关联计划」，选项来自上面的接口；默认选中活跃链最新版，没有时默认「无计划」。

### 6.2 执行状态

纯函数 `execution.status(plan_version_row, chain_buys, *, session)`：

| 状态 | 判定 | 页面 |
| --- | --- | --- |
| `adopted` 采纳 | 有关联到这一版的未作废买入成交，成交的纽约日期 ∈ [`valid_from`, `valid_until`] | 「已采纳（<日期> 成交 n 股）」 |
| `out_of_validity` 有效期外成交 | 关联到这一版，但成交日在有效期外 | 「有效期外成交」 |
| `pending` 等待成交 | 没有关联成交，`S < valid_until`，链仍在入场期 | 「入场期，未成交」 |
| `not_executed` 未执行 | 没有关联成交，有效期已过或链已结束 | 「未执行」 |

- 链的执行状态 = 任一版本为 `adopted` / `out_of_validity` 即「已执行」，否则看最新版。
- 计划外：买入成交没有关联计划（`plan_id` 为空）且旧口径下决定也没带计划。
- 备注（§6.5）不影响执行状态。

## 7. 时间止损与持仓日报

### 7.1 最长持有与 `held_sessions_reached`（`condition-2`）

- **持有天数** `held_sessions`：当前未平仓位里**最早一笔**买入成交的纽约交易日到 S（含两端）的交易日数，成交日 = 第 1 天。
- **1R**：R = 成本 − 初始止损。成本 = 未平批次的加权平均成本（同 `positions`）；初始止损 = 第一笔关联买入所关联版本的 `stop`（D20）。R ≤ 0 或取不到初始止损 → 1R 判定为 `unknown`。
- **到过 1R** `reached_1r`：自最早一笔买入的交易日起（含）有任一日收盘 ≥ 成本 + R。
- `held_sessions_reached{sessions}`：持仓期 `held_sessions ≥ sessions` 且 `reached_1r = false` → `met`；`reached_1r = unknown` → `unknown`；入场期或其余 → `not_met`。模板文案「持有 {sessions} 个交易日仍未到 1R」。
- 宿主注入：持仓期的复查判定失效条件时，额外判定一条 `{source: 'max_hold', kind: 'held_sessions_reached', params: {sessions: 最新版 max_hold_sessions}}`，写进 `plan_reviews.conditions`（`list = 'invalidation'`、`index = 'max_hold'`）。最新版没有执行字段（旧 `agent-2`）时按 10 注入并在 `detail` 注明 `max_hold_default`。

### 7.2 持仓期的退出指令（`exiting`）

持仓期复查的宿主步骤在 v2.5 §7.4 的顺序上改为：

1. 算持仓状态的事实（§7.3，不写行）。
2. **止损触及**（D18）：当日最低价 ≤ 有效止损 → 结论 `invalidate`，`decided_by = host`，原因「止损触及（<价>）：应已按止损卖出；仍持有则次一交易日开盘卖出」。
3. **时间止损**：`max_hold` 条件 `met` → `invalidate`（host），原因「时间止损：持有 n 个交易日仍未到 1R，次一交易日开盘卖出」。
4. 其余失效条件成立 → `invalidate`（host），原因同 v2.5。
5. 其余照 v2.5（无事可看 → 维持；预算闸门；单阶段复查 `agent-review-2`；修订）；Agent 判 `invalidate` 也进入退出期。
6. 写复查行之后写持仓状态行（§7.3），指令按结论与事实取值。

退出期（`exiting`）的链不再复查（不调用模型、不写 `plan_reviews`），每个交易日只写持仓状态行：指令 `exit`，原因「退出指令自 <日期> 起（<原因>），仍持有 n 股」；全部平仓后链变为 `position_closed`。

### 7.3 持仓状态 `holding_status`

`review` 节点在全部复查之后，对**每个持仓标的**写一行（纯函数 `timeline.holding_status(facts)` 算值，§8.4 存储）：

| 字段 | 计算 |
| --- | --- |
| `quantity`、`avg_cost` | 未平批次（同 `positions`） |
| `last_close` | S 的收盘；缺日线 → 空，`detail.bars_missing` |
| `stop`、`stop_mode` | 有效止损：链最新版（或无链时成交关联的计划）的止损，T1 之后 = max(开仓以来最高收盘 − 3 ATR, 成本)（同 `exits.active_stop`）；`stop_mode` ∈ `initial` / `trail` / `breakeven` |
| `target1`、`t1_reached` | 最新版 T1；开仓以来是否触及 |
| `to_stop_pct` | (last_close − stop) ÷ last_close × 100，保留 2 位；已跌破为负 |
| `to_t1_pct` | (target1 − last_close) ÷ last_close × 100；已触及 T1 时为空 |
| `held_sessions`、`max_hold_sessions`、`remaining_sessions` | §7.1；`remaining = max(max_hold − held, 0)`；`reached_1r = true` 时 `remaining` 为空（页面写「已到 1R，时间止损解除」） |
| `r_now`、`reached_1r` | (last_close − avg_cost) ÷ R；§7.1 |
| `instruction` | `exit`（当天结论为持仓期作废，或链处于退出期）/ `sell_half`（当天首次触及 T1 且之后没有卖出过）/ `hold`（其余有计划的持仓）/ `no_plan`（没有任何计划的持仓） |
| `exit_reason` | `stop_touched` / `time_stop` / `invalidation` / `agent_invalidate`（`exit` 时必填） |
| `reason` | 维持理由（§7.4） |
| `review_id`、`plan_id`、`chain_signal_date` | 当天的复查行、有效计划、所在链（无链为空） |

- 指令文案（逐字，`timeline.INSTRUCTION_TEXT`）：`hold`「继续持有」、`sell_half`「到 T1：卖出一半，余下按移动止损」、`exit`「次一交易日开盘卖出」、`no_plan`「无计划持仓（回撤规则看护）」。
- 一行的展示（「今日」持仓组、推送）：「MU 持有 4/10 天 · 距止损 −5.20% · 距 T1 +8.10% · 现 +0.6R · 继续持有：<维持理由>」。
- 持仓状态只由批处理写（每个标的每个 S 一行）；重新复查不写新行，页面在当天行旁显示之后的重新复查结论。

### 7.4 维持理由

- Agent 复查（维持）：复查行的 `reason`。
- 宿主维持（无事可看）：模板「无新信号，复查条件未满足（<条件>）；收盘 <价> 在止损上方 <x>%，未到 T1，持有 n/m 天」。
- 复查跳过或出错：「今日复查未完成（<原因>），按第 n 版继续持有」——**持仓状态照写**（D19），这是「每天都有一行」的保证。
- 无链持仓：「无 Agent 链，按 <规则基线 / 自定计划> 的止损与最长持有看护」。
- 核查提醒：v2.5 起 `review_when` 缺省为 `next_session`，而 `next_session` 恒成立（`conditions.py:393`），所以「宿主静默维持」只在模型显式写了别的复查条件时才出现，实际上持仓期每天都调用模型。`agent-review-2` 不改这一点；持仓状态的价值在于把模型理由与宿主算出的距离、天数并排固定下来。

## 11. 推送

## 13. 出错与降级

| 情况 | 行为 |
| --- | --- |
| 迁移 029 未执行 | `daily` 拒绝运行（D36）；读接口 `plan-table`、`plan-history`、`holding-status`、`plan-notes`、`linkable-plans` 返回 503「迁移 029 未执行」；`POST /trades` 带 `plan_id` / `own_plan` 返回 503 |
| Agent 不可用 | `plan` 节点照写 `chain_retriggers`；`retrigger` 修订记 `skipped`；持仓状态照写（理由「今日复查未完成（Agent 不可用：<原因>）」）；计划表照常（链行状态写原因） |
| 当天日线缺失 | 持仓状态 `last_close` 等为空、`detail.bars_missing`，指令沿用前一日（`exit` 不会因缺数据解除），理由写「缺 S 的日线」；时间止损判定 `unknown` |
| 初始止损取不到（旧持仓、关联计划缺止损） | `reached_1r = null`、`remaining_sessions` 为空，指令 `hold`，理由注明「无法计算 1R」 |
| 一个标的的持仓状态计算出错 | 只影响该标的（进 `review` 行 `failures`），其余照写；`check` 报缺行 |
| `chain_retriggers` 写入冲突（同 session 重跑） | `ON CONFLICT DO NOTHING`，读回已有行 |
| 已并入的链当天被宿主作废（失效条件成立） | 这次触发只剩规则基线；计划表该标的出一行规则基线，标「所并入的链今日作废」；次日再触发即开新链（§16） |
| 旧 `agent-2` 版本没有执行字段 | 计划表按默认值显示并注明，影子只算 `plan-shadow-1`（§5.5） |

### 14.2 手动触发验收

1. 029 执行并重启后手动运行 `daily`：`stage_runs` 10 行；`plan_review check --session <当天>` 通过；「今日」计划表三组显示，没有任何决定按钮。
2. 找一只已有入场期链又触发的标的（或等它出现）：`chain_retriggers` 有一行；该链当天一条复查 `via = retrigger`，新版的 `diff` 与变化说明可读；计划表只有一行，「链与版本」下写再次触发；「标的」页计划历史能读出两次触发与版本变化。
3. 录一笔关联 Agent 最新版的买入（测试账户或真实成交）：链变为持仓期；次日 `holding_status` 一行，「今日」持仓组与推送都有；三方对比该单元 `version_basis = fill`。

## 16. 已知限制

- 开盘三种情形是收盘后写好的条件指令，系统不看盘前、盘中价格；你仍要自己挂单。
- 已并入的链当天被宿主作废时，这次触发不会补开新链（要等下一次触发）。
- 没有 Agent 链的持仓（成交只关联规则基线、或在 Agent 不可用时成交）不参与复查，只有宿主持仓状态；之后同标的再触发会开一条入场期的新链，与持仓并存（链与持仓不自动合并）。
- 旧 `agent-2` 版本没有执行字段，按默认值显示；旧 `plan-1` 计划不补 `plan-2`。
- 时间止损的 1R 以第一笔关联买入的版本为准；分次买入时以加权成本计，与影子（单笔成交）不完全一致。
- 备注不进 Agent；想让 Agent 参考要另写「我的补充」。
- `superseded` 只按「同标的有更晚的链」判定，不区分旧链当时是否真的被替代。

## 18. 与 roadmap 及用户需求文字的差异

| 原文 | 本 spec | 理由 |
| --- | --- | --- |
| 「无信号、无输入、复查条件未到」时宿主静默维持 | 核查：缺省复查条件 `next_session` 恒成立，持仓期实际每天都调模型；本 spec 不改这一点，持仓状态把模型理由与宿主算出的距离、天数固定在一起 | §7.4 |
