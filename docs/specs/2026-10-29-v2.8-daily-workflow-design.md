# v2.8.0 每日工作流

> 2026-10-29，基线 `main@ff9664e`（`v2.7.0` 之后）。路线见 [roadmap §4.6](../roadmap/roadmap.md#46-每日工作流v28)；用户 2026-10-28 重定义 v2.8（决策 #58–#66），2026-10-29 确认开工、范围不变（决策 #67–#68）。
> 五块内容：三个定时任务合成**一张 LangGraph 图** `daily`（北京 11:30、周二至周六）；**检查点与续跑**；**外部请求策略**（紧超时、按目标有限重试、节点级重试一次）；**运行详情页**；**模型层改走 Sign in with ChatGPT** 并删除智谱。
> 本文是设计，不是实施授权：真实库迁移 028、重启服务、一次性登录 ChatGPT、打 tag、推送都要在执行时单独确认。§17「核查结果」由你执行 [`scripts/siwc_precheck.py`](../../scripts/README.md) 后追加；模型层的实现路径以那一节为准（§8.7）。

## 1. 目标

对应路线成功标准 5：**每日运行是一条看得见的链：任一天打开运行详情，能看到每个节点做了什么、每个数据源对每个目标拿到或没拿到什么、失败卡在哪一步；失败的运行能从失败节点续跑而不重跑已完成的部分；Agent 用你的 ChatGPT 订阅运行，不依赖本地 CLI 与按量计费的 API key；截止时间与工具记录的保证不变。**

1. **一天一次、一条链**：`filings`（09:30）、`workbench`（06:30）、`workbench_review`（08:00）三个定时任务合成一个任务 `daily`，北京 11:30（周二至周六）跑一次：`sec_monitor → collect → screen → regime → signals → plan → agent → review → push → retro`，十个节点，每次运行恰好十条节点证据。
2. **出错有界、能续上**：每个外部请求连接 10 秒、总计 30 秒，网络错误 / 5xx / 429 按目标重试 2 次（退避 2 秒、8 秒），单个目标失败不拖住整条链；节点抛异常时等 60 秒自动重试 1 次，再失败就停在该节点，下游记 `skipped: upstream_failed`；你在运行详情页点「从此节点继续」，从检查点续跑，已完成的节点不重跑，截止时间沿用原运行。
3. **看得懂一次运行**：运行详情页顶部一句话 + 节点状态图，点开节点看「做了什么 / 拉取详情 / 结果详情」，底部折叠「原始摘要」。
4. **Agent 用你的 ChatGPT 订阅**：「设置 → Agent 连接」一次性登录（OAuth 动态注册 + PKCE + 本机回环回调），之后服务自己刷新；`ChatOpenAI` 切到 Responses 模式（或按核查结果退到 `openai` SDK 薄客户端）；智谱 provider、配置、额度错误码全部删除。

**不改计划口径**：规则 v1、`screen-1`、`regime-2`、`plan-1`、`agent-2` 的结构与校验、四张子图的提示词与判定（`citations.py`、`plan_check.py`、`growth_check.py`）、`plan-shadow-1`、`tracks-1`、`retro-1`、`review-7`、`monthly-3` 都不动。所有规则与 Agent 照旧**未经验证**（Phase 0 Gate HOLD）。

### 4.2 状态 `DailyState`

```python
class DailyState(TypedDict, total=False):
    # 运行身份（START 时写入，之后只读）
    run_id: str                 # 'daily-<UTC 时间戳>-<8 位 hex>'，= thread_id = job_reports.run_id
    graph_version: str          # 'daily-1'
    stages_version: str         # 'stages-4'
    trigger: str                # 'scheduled' | 'manual_batch'（续跑不改它）
    cutoff_at: str              # ISO 时间，= 原 run_batch 的 now；全部计算的截止时间
    session: str                # ISO 日期，bars.latest_closed_session(cutoff_at)
    ny_date: str                # cutoff_at 的纽约日期
    trading_day: bool           # is_trading_day(ny_date)；手动运行恒为 True（同 v2.7）
    explicit: bool              # 显式池（测试与 CLI 覆盖）
    # 上游交给下游的最小数据
    pool: dict                  # {'core': [...], 'extended': [...]}（collect 读到的池；screen 之后为合并后的池）
    held: list[str]             # 池外持仓
    chain_tickers: list[str]    # 池外活跃 agent-2 链（D21 of v2.5）
    collected: list[str]        # 本次采集过日线 / 资讯 / SEC 的股票
    universe: dict | None       # {'name', 'as_of', 'tickers', 'stale', 'fetched': [...], 'fetch_reasons': {...}}
    manual_pool: dict           # screen 之前的池（regime 广度样本用）
    timeline_ready: bool        # 迁移 026（028 之后恒为 True，仍保留以复用 v2.5 的分支）
    growth_ready: bool          # 迁移 027（同上）
    # 产出引用（每个节点写自己的键）
    refs: dict[str, dict]       # {'collect': {'data_fetch_runs': [...]}, 'screen': {'screen_run_id': ..}, 'agent': {...}, ...}
    agent_started_at: str | None   # agent 节点开始的墙钟时间（D24），review 用它
    summary: dict               # 与 job_reports.summary 同一份（推送与运行记录的输入）
    # 失败信息（执行器写，节点不写）
    failed_node: str | None
    failure: dict | None        # {'node', 'reason', 'first_error', 'retried': bool, 'at'}
```

- 只放 JSON 可序列化的值（日期、时间都是 ISO 字符串）；`PostgresSaver` 的 `JsonPlusSerializer` 原样存取。
- 节点返回「本节点写的键」的增量；`summary` 由节点返回整份新值（各节点只改自己负责的子键，与 v2.7 `run_batch` 对 `summary` 的写法一致）。
- `summary` 新增顶层键：`graph_version`、`run_status`（D13）、`failed_node`、`resumed`（续跑次数）。

### 4.3 节点函数与 `StageRecorder`

```python
# workbench/workflow.py
NODE_RETRY_WAIT_S = 60
NODES: tuple[str, ...] = stages.STAGE_IDS            # stages-4 的十个 id，顺序即边

def node(stage_id: str, body: Callable[[DailyState, NodeContext], dict], *, sleep=time.sleep) -> Callable[[DailyState], dict]:
    """建本节点的 StageAcc → 调 body → 异常时等 NODE_RETRY_WAIT_S 秒重试一次（新的 StageAcc，第一次的异常记进
    detail.retry = {'first_error': …, 'waited_s': 60}）→ 写一行 stage_runs → 返回状态增量；
    第二次仍异常 → 写 failed 行（reason = 'aborted: <脱敏后的异常>'）并抛 NodeFailed(stage_id, reason)。"""

def build_graph(*, checkpointer, deps: service.Deps, sleep=time.sleep) -> CompiledStateGraph: ...
def run(*, trigger: str, now: datetime, deps: service.Deps | None = None, explicit_pool=None,
        checkpointer_factory=None, sleep=time.sleep) -> dict: ...          # 新运行
def resume(run_id: str, node: str, *, now: datetime, deps=None, checkpointer_factory=None,
           sleep=time.sleep) -> dict: ...                                    # 续跑（§5.4）
```

- `NodeContext`：本次执行的 `StageRecorder`（`attempt` 已定）、`deps`、`clock`、`wall_now`、`notify_cfg`、是否续跑。
- `service.py` 把 `run_batch` 拆成九个模块级函数 `stage_collect(state, ctx, acc)`、`stage_screen`、`stage_regime`、`stage_rules`（产出 `signals` 与 `plan` 两个累加器）、`stage_agent`、`stage_review`、`stage_push`（从 `tasks/workbench.py` 搬来）、`stage_retro`；`sec_monitor` 的体在 `tasks/filings.py` 的 `stage_sec_monitor`。判定、写库与 `summary` 写法逐行搬移，不改语义；搬移后 `run_batch` 只是「依次调用这九个函数」的薄壳（测试与 `derivation` CLI 继续用它，`stages=None` 时行为与 v2.7 相同）。
- **`signals` 与 `plan`**：两个阶段在同一个逐只循环里（每只股票一个事务，信号与计划一起提交），拆成两个图节点会改变事务边界。做法：`signals` 节点跑整个循环并把 `plan` 的累加器冻结进状态 `refs['plan_acc']`（可序列化的计数、跳过、失败、产出引用）；`plan` 节点只做 `_check_derivations` 并写自己的一行。`plan` 的 `started_at` / `finished_at` 是这一步的真实起止，`detail.timings.in_signals_ms` 记循环里计划部分的累计耗时。这样每个节点仍是一行、事务边界不变（§22 Q4）。
- `StageRecorder` 的改动：构造参数加 `attempt: int = 1` 与 `job: str = 'workbench'`（`daily` 传 `'daily'`）；`_row` 写 `attempt`、`job`；`duration_ms` 改为 `round((finished_at − started_at).total_seconds() * 1000)`（D25），`acc.duration_ms` 改记进 `detail.timings.measured_ms`；`skip` / `close` 不变。`close(exc)` 不再由图使用（图的未执行节点由执行器按 D8 写 `upstream_failed`），保留给 `run_batch` 薄壳。

### 4.5 `collect` 与 `screen` 的细节（D4）

- `collect` 的采集名单与顺序：①SPY + 行业 ETF 日线；②`universe`：加载范围文件，对「范围 − 手动池 − QQQ」逐只采日线（400 天）与财报日（同 `screening._collect`）；③池（`watchlist` 表里的核心 + 扩展，即上一次筛选后的池）∪ 池外持仓 ∪ 池外活跃链：日线（420 天；已在②采过的跳过）、资讯、财报日；④③的名单逐只 SEC 列表（D21）；⑤FRED 两个序列。族锁 `bars`、`news`、`sec_filings`、`fred` 在本节点开始时按固定顺序取、结束时释放（同 v2.3 §6.4）。
- `collect` 的 `data_fetch_runs`：五行（`bars`、`news`、`sec_filings`、`fred`、`universe`），`job = 'daily'`、`run_id`、`session`；`bars` 的目标 = ①∪②∪③（范围成分的日线现在计在 `bars` 族里，与 v2.7 一样：v2.7 也把筛选阶段的取数记在 `bars`）。
- `screen` 节点：用库里的日线与财报日跑 `screen.evaluate` 与 `_pick_members`，写 `screen_runs`，`_sync_pool` 入池；新成员 = 今天的成员 − `collect` 读到的池。对新成员**补采**：资讯与 SEC 列表（同一套 `fetch_policy`），在本节点里取 `news`、`sec_filings` 两把族锁，写两行 `data_fetch_runs`（`detail.scope = 'screen_new_members'`）。补采失败只计进本节点 `failures`（`news:<T>`、`sec:<T>`），节点 `partial`，不失败。

## 5. 检查点与续跑

### 5.1 检查点

- 用现有 `agent_model.checkpointer(url)`（`PostgresSaver.from_conn_string`）；表已由 `setup_checkpoints` 建好（与 Agent 子图共用 `checkpoints` / `checkpoint_writes` / `checkpoint_blobs`）。
- `thread_id = run_id`（`daily-…`），`checkpoint_ns = ''`；Agent 子图的 `thread_id` 是 `agent_runs.id`（UUID），两者不会冲突。
- `graph.invoke(initial_state, config={'configurable': {'thread_id': run_id}}, durability='sync')`：每个节点结束同步落检查点（节点边界即检查点）。
- 保留：检查点不清理（与 Agent 子图一致；已知限制 §19）。

### 5.2 节点级重试

`workflow.node` 的体（D7）：

1. `acc1 = recorder.open(stage_id)`；调 `body(state, ctx, acc1)`。
2. 抛异常（`service.Unavailable` 除外——数据库不可达直接按失败处理，不等 60 秒）→ 记 `first_error = sanitize_reason(exc)`，`sleep(60)`，换新的 `acc2`，再调一次。第一次已写的业务行（例如 `screen_runs`、`agent_runs`）不回滚：各阶段函数本来就按 `session` 幂等（`already_completed`、`ON CONFLICT`、`already_pushed`），这是 v2.7 起「重跑同一天」的既有保证。
3. 第二次成功 → `acc2.detail['retry'] = {'first_error': first_error, 'waited_s': 60}`，写一行（状态按 `acc2` 判定）。
4. 第二次仍失败 → 写 `failed` 行（`reason = 'aborted: <脱敏异常>'`，`detail.retry` 同上），抛 `NodeFailed`。

「节点函数抛异常」只指阶段函数没有接住的异常；阶段内部已有的「单个目标 / 单元失败记 `failures`、整阶段照常结束」不触发节点重试（例如区制计算异常在 v2.7 是 `failed` 行、批处理继续——v2.8 改为：`regime` 体在记 `failed` 之后抛出，交给节点重试；这是唯一一个从「记失败继续」变成「停链」的阶段，因为 `signals` 依赖当天区制，§22 Q5）。

### 5.3 失败、下游与运行状态

- 执行器（`workflow.run` / `resume`）捕获 `NodeFailed`：对 `NODES` 里排在失败节点之后、本次执行尚未写行的节点各写一行 `skipped`、`reason = 'upstream_failed'`；`summary.run_status = 'failed'`、`summary.failed_node`、`summary.error = '<节点>: <原因>'`。
- 状态推导（D13）：读本 `run_id` 的有效行（每个 stage 最大 `attempt`）：任一 `failed` → `failed`；否则任一 `partial` / `degraded` → `degraded`；否则 `success`（`skipped` 不影响，如休市、`not_due`、`manual_run`）。

### 5.4 续跑接口

`POST /api/jobs/daily/resume`，body `{"run_id": "daily-…", "node": "collect"}`。前置检查同步做（不写任何行），通过后后台执行，返回 `202`：

```json
{"run_id": "daily-20261030033000-1a2b3c4d", "node": "collect", "status": "pending", "attempt": 2,
 "runner_id": "daily_resume-20261030050102-9f8e7d6c"}
```

| 条件 | 响应 |
| --- | --- |
| body 缺 `run_id` / `node`，或 `node` 不在 `stages-4` | 400 |
| 没有这个 `run_id` 的 `job_reports`（`task = 'daily'`）或检查点 | 404「没有这次运行」 |
| 迁移 028 未执行 / 数据库不可达 | 503 |
| 运行状态不是 `failed`（检查点 `next` 为空） | 409 `not_failed`「这次运行没有失败的节点」 |
| `node ≠ next[0]` | 409 `node_mismatch`「只能从失败的节点 <next> 继续」 |
| 现在 ≥ 续跑截止（§5.5） | 409 `resume_window_closed`「已过 <下一交易日> 纽约 17:00，只能整次重新运行」 |
| `daily:run` 锁被占 | 409 `daily_running` |

后台体：取锁 → `attempt = 该 run_id 已有的最大 attempt + 1`（全运行统一，一次续跑一个号）→ `graph.invoke(None, config)` 从检查点继续 → 同 §5.3 收尾 → 追加 `job_reports` 行（`trigger_source = 'resume'`，`summary` = 续跑后的完整 `summary`，`summary.resumed = n`、`summary.resume_node`）→ 失败则按 D14 通知。

### 5.5 续跑的截止时间与拒绝条件

- `resume_deadline(session) = datetime.combine(add_trading_days(session, 1), time(17, 0), NY)`；现在 ≥ 截止 → 拒绝（纯函数 `workflow.resume_deadline`，测试覆盖周五 → 周一、节假日前后、夏令时切换日）。
- 续跑沿用状态里的 `session`、`cutoff_at`、`trigger`；只有 `agent_started_at` 由 `agent` 节点（若重新执行）重写（D24）。
- 采集类节点在续跑时：日线只写 `trade_date ≤ session`（`collect.bars_one` 现有行为，测试确认）；资讯丢掉 `published_at > cutoff_at` 的条目；SEC 列表与监控丢掉 `acceptance_datetime > cutoff_at` 的申报（监控模式下这些申报不归档、不通知，留给下一次运行）；财报日照常取（已知限制 §19）。被丢掉的数量记 `detail.after_cutoff_dropped`。
- 原则：续跑产生的每一行，其 `fetched_at` / `cutoff_at` 字段仍是原运行的 `cutoff_at`，与已完成节点一致。

### 5.6 「已完成节点不重跑」的证明

- 自动：`test_resume_skips_completed_nodes`（让 `screen` 第二次也失败 → 续跑 → `sec_monitor`、`collect` 的体调用次数仍为 1，`stage_runs` 里它们只有 `attempt = 1`；`screen` 及下游有 `attempt = 2`）；`test_derivation_stages_accepts_resumed_runs`（守护对续跑后的运行通过、对伪造的「已完成节点 attempt 2」报错）。
- 人工：§16.2 第 3 条（造一次节点失败并续跑）。

### 5.7 `agent` 节点续跑与 `max_attempts` 重跑

- 续跑重新执行 `agent` 节点时，已完成的单元由现有 `already_completed` 守卫跳过（`acc.skip('already_completed', T)`），失败的单元按尝试次数再试；`agent_runs.attempt` 继续递增。
- 尝试次数闸（D26）：`prior` = 该单元、该 mode 在**最近一次重置之后**的运行；`max_attempts` 跳过行只在重置之后出现才拦截；`attempt` 字段 = 全部历史运行数 + 1（不清零，便于对账）。
- 「重新运行 Agent」：`POST /api/workbench/agent-runs/rerun` body `{ticker, signal_date, mode}`（`mode` ∈ `propose` / `interpret`；`review` 的尝试闸照旧按天，不在本版范围）→ 写一行 `agent_attempt_resets`（`request_id` 幂等）→ `propose` 立即后台跑一次（`service.run_agent`，同手动单元运行）；`interpret` 只重置，由下一次运行或续跑执行。条件：该单元最近的运行是 `skipped / max_attempts` 或 `error`，否则 409「这个单元不需要重跑」。

### 5.8 Agent 预算

- `agent` 节点开始时写 `state.agent_started_at = wall_now()`；`_agent_stage`、`plan_review.run_stage` 的 `started` / `clock` 改由节点用 `agent_started_at` 换算（单调时钟不跨进程，所以存墙钟、在节点内换算成 `clock() − (wall_now() − agent_started_at)`）。
- `retro` 节点用自己的起点（D24）。
- `BATCH_BUDGET_S = 1800` 与 `batch_over_budget` 删除（不再有整批预算；每个外部请求有上界、Agent 有预算，整链上界见 §19）。

### 5.9 `job_reports` 与运行记录

- `task = 'daily'`；`started_at` / `finished_at` = 本次执行的起止；`target_start_date = target_end_date = session`；`status` 映射：`success` → `success`，`degraded` → `degraded`，`failed` → `error`；`summary` 增加 `graph_version`、`run_status`、`failed_node`、`resumed`、`stage_status`（`StageRecorder` 写入报告）。
- 运行记录列表每次执行一行；同一 `run_id` 的多行在详情页的「执行记录」里按时间列出。

## 6. 外部请求策略（`fetch-1`）

### 6.1 策略

```python
# data/fetch_policy.py
FETCH_POLICY_VERSION = 'fetch-1'
CONNECT_TIMEOUT_S = 10
TOTAL_TIMEOUT_S = 30
RETRY_BACKOFF_S = (2, 8)            # 重试 2 次
RETRY_STATUSES = frozenset({429, 500, 502, 503, 504})

@dataclass(frozen=True)
class FetchPolicy:
    connect_s: float = CONNECT_TIMEOUT_S
    total_s: float = TOTAL_TIMEOUT_S
    backoff_s: tuple[float, ...] = RETRY_BACKOFF_S
    retry_post: bool = True          # 推送类调用传 False（D23）

class FetchError(RuntimeError):
    kind: str            # 'timeout' | 'network' | 'http_5xx' | 'http_429' | 'http_4xx' | 'empty' | 'parse' | 'other'
    status: int | None
    attempts: list[dict] # [{'n', 'kind', 'status', 'elapsed_ms'}]

def fetch(target: str, fn: Callable[[], T], *, policy: FetchPolicy = FetchPolicy(), sleep=time.sleep,
          classify: Callable[[BaseException], tuple[str, int | None]] = classify_exception) -> Fetched[T]
    """调 fn；可重试的 kind（timeout、network、http_5xx、http_429）按 backoff 重试，其余立即失败。
    返回 Fetched(value, attempts, elapsed_ms)；最终失败抛 FetchError（带 attempts）。"""

def policy_session(policy=FetchPolicy()) -> requests.Session   # 挂一个 HTTPAdapter：timeout=(connect_s, total_s)、不自动重试
def hard_deadline(fn, *, seconds: float) -> T                     # 线程跑 fn，超过 seconds 抛 FetchError(kind='timeout')
def yf_session(policy=FetchPolicy()) -> 'curl_cffi.requests.Session'  # impersonate='chrome'、timeout=total_s、CONNECTTIMEOUT=connect_s
```

- 429 带 `Retry-After` 时等待 `min(Retry-After, backoff[n])`；总等待不超过 10 秒。
- 单个目标的最坏耗时 = 3 × 30 秒 + 2 + 8 秒 = 100 秒 < 2 分钟（退出条件「没有任何外部请求的真实耗时超过 2 分钟（含重试）」）。`hard_deadline` 对 yfinance 取 35 秒，最坏 3 × 35 + 10 = 115 秒。
- `classify_exception`：`requests.Timeout` / `curl_cffi` 超时 / `FetchError(timeout)` → `timeout`；连接、TLS、代理错误（含代理 503 的 `ProxyError`）→ `network`；`HTTPError` 按状态码；yfinance 的空结果 → `empty`（不重试）；JSON / 解析错误 → `parse`（不重试）。
- 错误文本照旧经 `families.sanitize_reason`（FRED key 脱敏、截断 300 字）。

### 6.3 为什么 yfinance 要两层截止

- `curl_cffi` 的 `timeout` 浮点数映射为 libcurl 的总超时（`CURLOPT_TIMEOUT_MS`），能真正中断卡住的传输；`CURLOPT_CONNECTTIMEOUT` 管连接。yfinance 内部某些请求（时区、cookie、crumb）不经过 `history(timeout=…)`，用自建会话就能统一。
- `hard_deadline(35)` 是兜底：yfinance 若在某处自己 `sleep` 或解析卡住，线程截止让目标按 `timeout` 失败、节点继续；被放弃的线程最多再活到 libcurl 的 30 秒总超时。
- 测试用本地假服务器（`http.server` 在 `127.0.0.1` 上随机端口，按路径返回慢响应 / 5xx / 429 / 4xx / 断开），对 `policy_session` 与 `curl_cffi` 会话各跑一遍；yfinance 本身用注入的 fetcher（`Deps`）测，不连 Yahoo。

### 6.4 族状态与目标级明细

- 族状态判定不变：`skipped`（未配置）> `failed`（`'*'` 且 `ok = 0`）> `families.classify`（全成功 `success`、零成功 `failed`、其余 `partial`）。
- 节点不因单个目标失败而失败：目标失败 → `Tally.fail`、`acc.fail('<族>:<目标>', reason)`，节点 `partial`。
- `Tally` 增加 `record(target, fetched_or_error, *, rows=None, latest=None)`，`detail.targets` 每项：

```json
{"target": "NVDA", "ok": false, "attempts": 3, "error_kind": "timeout", "http_status": null,
 "reason": "timeout after 30s (3 attempts)", "rows": null, "latest": null, "elapsed_ms": 100412}
{"target": "AAPL", "ok": true, "attempts": 1, "error_kind": null, "http_status": 200,

```

  - `rows`：日线 = 本次新写入行数（`counts.inserted`）；资讯 = 新写入条数；SEC = 发现的申报数；FRED = 新写入观测数；`latest`：日线最新 `trade_date`、资讯最新 `published_at`、SEC 最新 `filing_date`、FRED 最新观测日。
  - `detail.policy = 'fetch-1'`；`detail.targets` 按目标名排序；一族至多 600 项（纳指 100 + 池上限 100 + ETF，远低于此），超出截断并记 `detail.targets_truncated`。

- 财报日不是族：`collect` 节点的 `detail.earnings = {'targets', 'ok', 'failed', 'items': [同上形状]}`。

## 8. 模型层：Agent 走你的 ChatGPT 订阅

### 8.1 OAuth 流程（`workbench/agent/chatgpt.py`，`siwc-1`）

常量（逐字，与 devkit 一致）：`ISSUER = 'https://auth.openai.com'`、`RESOURCE = 'https://api.openai.com/v1'`、`SCOPES = 'openid profile email offline_access resource.invoke chatgpt.tokens.use.direct'`、`SHARING_SCOPE = 'chatgpt.tokens.use.direct'`、`CALLBACK_PATH = '/auth/callback'`、`DYNAMIC_CLIENT = 'dynamic_agent_client'`、`APP_NAME = 'investment-assistant'`、`LOGIN_TTL_S = 600`。

1. **发现**：`GET {ISSUER}/.well-known/openid-configuration`（`fetch_policy`），要求 `issuer == ISSUER`，`authorization_endpoint`、`token_endpoint`、`jwks_uri`、`revocation_endpoint`（可选）的 origin 都是 `ISSUER`；结果进程内缓存。
2. **开始连接**（`POST /api/settings/agent-connection/login`）：没有 `host_id` 就生成 `urn:uuid:<uuid4>` 并写入 `agent_connections`（之后永不改）；生成 `state`、`nonce`、`code_verifier`（各 32 字节随机，base64url）；在 `127.0.0.1:<WORKBENCH_CHATGPT_CALLBACK_PORT 或 0>` 起一次性 HTTP 监听（D31）；构造授权 URL：`client_id`（已有注册用保存的 `client_id`，否则 `dynamic_agent_client`）、`response_type=code`、`redirect_uri=http://127.0.0.1:<端口>/auth/callback`、`scope`、`resource`、`state`、`nonce`、`code_challenge_method=S256`、`code_challenge`、`ext_agent_host_id=<host_id>`；首次加 `agent_name_hint=investment-assistant`；已知邮箱加 `login_hint`。待定事务记在进程内存（D30），连接状态写 `pending`。返回 `{authorize_url, expires_at}`，前端新标签打开。
3. **回调**：监听只接受 `GET /auth/callback`，`Host` 必须是 `127.0.0.1:<端口>`，`state` 唯一且常数时间相等；不符的请求 400 / 404 但不结束事务。带 `error` → 事务失败（`access_denied` 等）。取 `code`（唯一）与 `client_id`（回调里带的优先，否则保存的；必须匹配 `^[A-Za-z0-9_-]{1,200}$` 且不是 `dynamic_agent_client`；已保存的与回调的不同 → `registration_incomplete`）。先把 `client_id` 写库（「一次性 code 可能换失败，注册结果先存」），回浏览器一页「已完成，可以关闭此标签页」（`Cache-Control: no-store`、`Referrer-Policy: no-referrer`、CSP 同 devkit）。
4. **换令牌**：`POST token_endpoint`（表单）：`grant_type=authorization_code`、`client_id`、`code`、`code_verifier`、`redirect_uri`、`resource`。要求 `token_type` 为 bearer、`expires_in > 0`、有 `access_token` 与 `refresh_token`（含 `offline_access`）、`scope` 字符串；`id_token` 按 D28 校验（`iss`、`aud`、`exp`、`nonce`、`sub`），取 `email`；再次连接时 `sub` 必须与已保存的相同，否则 `account_mismatch`。
5. **落库**：一个事务里 `UPDATE agent_connections`（`status = 'connected'`、令牌、`access_expires_at = now + expires_in`、`refresh_expires_at = now + 30 天`、`earliest_refresh_at`、`subject`、`email`、`scopes`、`connected_at`）+ 插 `agent_connection_events(kind = 'connected')`。`scopes` 不含 `chatgpt.tokens.use.direct` → 状态 `connected` 但 Agent 记 `not_configured`、设置页提示「已登录，但这个账号没有开启计划用量共享」。
6. **超时与取消**：10 分钟没有回调 → 关监听、状态回到原值（`disconnected` 或 `needs_login`）；「取消」按钮同。

### 8.2 刷新与断开

- `access_token(conn) -> str`（D32）：剩余 ≥ 300 秒直接用；否则若 `earliest_refresh_at` 已过 → `POST token_endpoint`：`grant_type=refresh_token`、`client_id`、`refresh_token`、`resource`；整个过程在 `SELECT … FROM agent_connections WHERE id = 1 FOR UPDATE` 的事务里，成功即写新令牌与 `agent_connection_events(kind = 'refreshed')` 并提交，**提交之后**才把新 access token 交给调用方。响应省略 `scope` 时沿用旧值；带 `id_token` 时校验 `sub` 不变。未到 `earliest_refresh_at` 但已过期 → `refresh_not_ready`（记 `model_error`，下个单元再试）。
- 刷新失败：`invalid_grant`、`invalid_refresh_token`、`token_expired`、`refresh_token_expired`、`refresh_token_invalidated`、`refresh_token_reused`、`invalid_id_token`、`account_mismatch` → 清空令牌、`status = 'needs_login'`、`last_error`、事件 `refresh_failed`；其余（网络、5xx）→ 不改状态，本单元 `model_error`。
- 断开（`DELETE /api/settings/agent-connection`）：向 `revocation_endpoint` 撤销 refresh token（`token_type_hint=refresh_token`、`client_id`；5xx 重试一次）；不论撤销成功与否都清空令牌、`status = 'disconnected'`、保留 `host_id` 与 `client_id`；撤销未确认时返回 `{revoked: false}`，页面提示「本机凭据已删除，但远端断开未确认，请到 ChatGPT 设置里断开这个应用」。
- 令牌不进日志：`chatgpt.py` 里的异常一律重新构造为 `ChatGPTError(code, message)`（`code` 只取 `^[A-Za-z0-9_.:-]{1,100}$` 的安全标识符，消息为固定中文），原始响应体不进异常；`classify_error` 的脱敏同时去掉当前 access / refresh token 与 `Bearer …` 片段。

### 8.3 模型清单与选择

- `GET {RESOURCE}/models`（Bearer），取 `models[]` 里 `visibility == "list"` 的项，保持服务器顺序，返回 `[{slug, display_name}]`；接口 `GET /api/settings/agent-connection/models`（未连接 409）。
- 选择 `PUT /api/settings/agent-connection/model` body `{slug}`：必须在当前清单里，写 `model`、`model_display_name` 与事件 `model_selected`。

- `chat_model(s)`：取 `access_token()`（可能刷新）→ 构造路径 A 或 B 的模型（§8.7）。

### 8.5 路径 A：`ChatOpenAI` Responses 模式

读 `langchain-openai` 1.7.2 源码（`chat_models/base.py`）的结论：

| 问题 | 结论 | 处理 |
| --- | --- | --- |
| 请求体从哪来 | `_get_request_payload` = `_default_params`（`model`、`stream`、`store`、`include`、`reasoning`、`truncation`、`temperature`、`max_tokens` 等，值为 `None` 的去掉）+ `model_kwargs` + 调用参数，再经 `_construct_responses_api_payload` | 子类覆写 `_get_request_payload`，在父类结果上做 §8.5 的改写 |
| `temperature=None` | 不进请求体 | 构造时 `temperature=None` |
| `max_tokens` / `max_output_tokens` | 不设就不发 | 不设；改写时兜底删除 |
| `store=False` | 进请求体；同时让输入里的助手消息去掉 `msg_*` id、丢掉不带 `encrypted_content` 的推理块 | 构造时 `store=False` |
| `stream` | `streaming=True` 时走 `_stream_responses`，`stream: true` | 构造时 `streaming=True`；`stream_usage` 对 Responses 路径不加 `stream_options` |
| `user`、`previous_response_id` | 只在显式传入（`model_kwargs` / `use_previous_response_id=True`）时出现 | 不设；改写时兜底删除 |
| `parallel_tool_calls` | 只在 `bind_tools(parallel_tool_calls=…)` 时出现 | 不传；若核查发现必须显式 `false` 再加 |
| `disabled_params` | 只在 `bind_tools` / `with_structured_output` 里过滤参数（`_filter_disabled_params`），**不作用于** `_default_params`、`model_kwargs` 与最终请求体 | 不能靠它；用子类改写 |
| system 消息 | `SystemMessage` 转成 `input` 里的 `{"role": "system"}`（`additional_kwargs.__openai_role__ = 'developer'` 时为 `developer`）；**从不**写进 `instructions` | 改写：把 `input` 开头所有 `role ∈ {system, developer}` 且内容为纯文本的项取出，按顺序用两个换行拼成 `instructions`；其余位置的 system 项改为 `developer` |
| `output_version` | 1.x 默认 `responses/v1`：`AIMessage.content` 是内容块列表，而子图用 `message.content` 当字符串 | 构造时 `output_version='v0'`；若 v0 下文本仍是块列表，`SiwcChatOpenAI` 覆写 `_generate` / `_stream` 末尾把纯文本块合并为字符串（只改返回的消息、不改子图） |
| 工具形状 | `bind_tools` 产出 Chat Completions 形状，`_construct_responses_api_payload` 改成顶层 `{"type": "function", "name", "description", "parameters"}` | 官方限制页写明「函数与自定义工具必须放进 namespace，或经 `additional_tools` 输入项提供」：核查结果决定 `TOOL_SHAPE ∈ {'top_level', 'namespace', 'additional_tools'}`（§17）。`namespace`：改写时把顶层函数工具包成 `{"type": "namespace", "name": "workbench", "description": "投研工作台的只读数据工具", "tools": [...]}`；`additional_tools`：改写时移出 `tools`，在 `input` 开头插一项 `{"type": "additional_tools", "role": "developer", "tools": [...]}` |
| 被禁字段兜底 | 官方限制页列出 `background`、`conversation`、`max_output_tokens`、`max_tool_calls`、`metadata`、`moderation`、`multi_agent`、`prompt`、`prompt_cache_retention`、`safety_identifier`、`temperature`、`top_logprobs`、`top_p`、`truncation`、`user`、`previous_response_id` | `FORBIDDEN_FIELDS`（逐字为上列）在改写最后一步删除；`REQUEST_OVERRIDES`（可配置，默认空）由核查结果补充（例如必须显式 `parallel_tool_calls: false`） |
| `usage` | `response.completed` 事件里的 `response.usage`（`input_tokens`、`input_tokens_details.cached_tokens`、`output_tokens`、`output_tokens_details.reasoning_tokens`）→ `AIMessage.usage_metadata`（`input_tokens`、`output_tokens`、`input_token_details.cache_read`、`output_token_details.reasoning`） | 子图的 `usage_delta` 已读 `usage_metadata.input_tokens / output_tokens`，不改；缓存与推理 token 本版只记进 `agent_runs.detail`（见下） |
| 客户端 | `ChatOpenAI(api_key=<access token>, base_url=RESOURCE, max_retries=0, timeout=httpx.Timeout(180, connect=10))`，`default_headers` 不带 organization / project | 每个单元构造一次（D32） |

`SiwcChatOpenAI` 只做上表的改写，不改 `ToolNode`、四张子图与校验。`citations.py`、`plan_check.py`、`growth_check.py` 一行不改。

### 8.6 路径 B：`openai` SDK 薄客户端

- `workbench/agent/responses_model.py`：`ResponsesChatModel(BaseChatModel)`，`_generate(messages, stop=None, **kw)`：把 LangChain 消息转成 Responses `input`（system → `instructions`；`AIMessage.tool_calls` → `function_call` 项；`ToolMessage` → `function_call_output` 项），`client.responses.create(model, instructions, input, tools, store=False, stream=True)`，按事件累积文本与函数调用，`response.completed` 才算成功；`response.failed` / `error` 事件按 `event.response.error.code` 抛 `ChatGPTError`；`response.incomplete` → `ChatGPTError('response_incomplete')`；流在 `response.completed` 之前结束 → `stream_interrupted`。返回 `AIMessage(content=<文本>, tool_calls=[…], usage_metadata=…)`。
- `bind_tools(tools)`：用 `convert_to_openai_tool` 生成函数定义，按 `TOOL_SHAPE` 组装，返回绑定了工具的 `RunnableBinding`；`ToolNode` 照旧执行工具。
- **自写循环（最后的退路）**：只有当 `ToolNode` 与 Responses 的函数调用 id（`call_id`）无法对上、导致工具结果不能回传时，才在 `graph.py` 里把 `ToolNode` 换成 `_run_tools(message, tools)`（逐个执行 `tool_calls`、产出 `ToolMessage`），子图的节点与边不变。roadmap 说的「放弃 `ToolNode`」指这一步。

### 8.7 选路规则

1. §17 的核查结果里，路径 A 的「带函数工具、两轮（调用 → 回传结果 → 最终回答）」用例成功、被拒字段都能由改写去掉 → **选 A**。
2. A 失败但同一用例用 `openai` SDK 原生调用成功 → **选 B**（保留 `ToolNode`）；B 的 `ToolNode` 回传失败 → B + 自写循环。
3. 两者都失败 → 本版模型层停在「连接与设置页」，`agent` 节点记 `agent_unavailable: not_configured`，向你汇报后再定（其余 v2.8 内容照常交付）。
4. 若实现时 §17 仍为空：先按路径 A 实现，`TOOL_SHAPE`、`FORBIDDEN_FIELDS`、`REQUEST_OVERRIDES`、`INSTRUCTIONS_FROM_SYSTEM` 都做成 `chatgpt.py` 里的常量 + 环境变量覆盖（`WORKBENCH_CHATGPT_TOOL_SHAPE` 等，仅供核查期使用），并向编排者汇报。

`agent_runs.provider = 'chatgpt'`、`model = <slug>`；`agent_runs.detail`（已有列）在 `ok` 运行里追加 `usage: {cached_input_tokens, reasoning_tokens}`（没有时省略）。每日 token 上限（`WORKBENCH_AGENT_DAILY_TOKENS`）照旧按 `input + output` 计。

### 8.8 错误分类

`classify_error(exc, secret) -> (reason, detail)`（`detail` 脱敏、截断 300 字；不含请求体）：

| 来源 | 条件 | `reason` | 影响 |
| --- | --- | --- | --- |
| Responses（HTTP 或 `response.failed`） | `code == 'subscription_sharing_usage_limit_exceeded'` | `quota_exhausted` | 本次运行其余单元跳过（同现在）；推送里如实标注 |
| 同上 | `subscription_sharing_usage_unavailable`、`subscription_sharing_user_unavailable` | `model_error` | 走尝试次数闸 |
| 同上 | `model_not_found` | `model_unavailable` | 本节点其余单元跳过（`agent_unavailable: model_unavailable`）；设置页提示重新选模型；通知一次 |
| 同上 | `subscription_sharing_user_not_eligible`、`subscription_sharing_invalid_user`、`chatpass_v2_scope_not_authorized`、`chatpass_v2_invalid_authorization_context`、`invalid_token`、`invalid_api_key`、HTTP 401 | `not_connected` | 同 `model_unavailable` 的处理，状态改 `needs_login`（401 只在刷新后仍 401 时） |
| 同上 | `subscription_sharing_unsupported_capability`、`subscription_sharing_route_not_supported`、HTTP 400 / 422 | `model_error`，`detail` 带安全的 `param` | 走尝试次数闸；三次后 `max_attempts` |
| 刷新（§8.2） | 需重新登录的那几种 | `not_connected` | 设置页红条「ChatGPT 连接已失效，请重新连接」+ 失败通知一次（同一次失效只通知一次：上一次 `refresh_failed` 之后没有 `connected` / `refreshed` 事件就不再发） |
| 网络、5xx、429（非额度）、`stream_interrupted`、`response_incomplete`、超时 | — | `model_error` | 走现有尝试次数闸 |
| 检查点表缺失 | 同现在 | `checkpoint_unavailable` | 同现在 |

- `agent/__init__.REASON_TEXT` 新增（逐字，前端 `AGENT_REASON_TEXT` 同步）：`'not_connected': 'ChatGPT 未连接'`、`'model_unavailable': '所选模型不可用'`；`'not_configured'` 文案不变（「未配置」）。删除：无（`quota_exhausted` 等沿用）。
- 「不可用」在节点开头判断一次（`unavailable_reason`），整节点 `skipped: agent_unavailable: not_connected`；单元运行中途发现的 `not_connected` / `model_unavailable` 让本节点其余单元记 `skipped` 同一原因。

### 8.9 「设置 → Agent 连接」

- 新区块（`Settings.svelte` 里「系统」之后），组件 `AgentConnection.svelte`。

## 15. 出错与降级

| 情况 | 行为 |
| --- | --- |
| 迁移 028 未执行 | `daily` 拒绝运行：`job_reports` 记 `error / migration_028_missing`，失败通知一次；新接口 503；运行详情对旧运行照常 |
| 单个目标取数失败 | 该目标重试 2 次后记失败，族 `partial` / `failed`，节点 `partial`，链继续 |
| 节点抛异常 | 60 秒后重试 1 次；再失败停链、下游 `upstream_failed`、通知一次、可续跑 |
| 数据库不可达（`Unavailable`） | 不重试，节点失败、停链；`job_reports` 若也写不进，只剩运行日志文件（`_record` 现有兜底） |
| 纽约休市 | `push` 之前九个节点 `skipped: not_trading_day`，`push` 只发休市一行，`retro` 判断周 / 月复盘是否到期（不到期 `not_due`） |
| ChatGPT 未连接 / 失效 | `agent`、`review` 整节点 `skipped: agent_unavailable: not_connected`，`retro` 照常建卡、起草跳过；规则计划与推送照常（推送里 Agent 行显示「Agent 未给出计划（ChatGPT 未连接）」）；通知一次 |
| 额度用尽 | `quota_exhausted`，本次其余单元跳过（同 v2.7） |
| 所选模型不可用 | `model_unavailable`，同「未连接」的节点处理；设置页提示 |
| 续跑窗口已过 | 409 `resume_window_closed`；只能整次手动重新运行（新的 `run_id`、新的截止时间） |
| 两次执行重叠 | 后到的 409 / `error: daily_running` |
| 登录中服务重启 | 待定事务丢失，连接状态从 `pending` 在下次读取时按「超时」恢复为原状态 |
| 刷新时进程被杀 | 新令牌在提交后才使用；若在 HTTP 返回后、提交前被杀，旧 refresh token 已失效 → 下次刷新 `refresh_token_reused` → `needs_login`（已知限制，概率很低） |
| 检查点表缺失 | `daily` 拒绝运行（`checkpoint_unavailable`），不做无检查点的降级运行 |

## 19. 已知限制

- **整链没有硬上限**：每个外部请求 ≤ 2 分钟、Agent + 复查 ≤ 25 分钟、复盘起草 ≤ 25 分钟，但目标数 × 最坏耗时理论上仍可很长（例如 Yahoo 全面超时时 230 个目标 × 100 秒）；本版只保证「卡住的请求有界」，v2.9 的备源解决「整族不可用」。
- **续跑只能从失败节点开始**；要「重跑某个已成功的节点」只能整次重新运行。
- **财报日在续跑时取到的是当时的值**（Yahoo 不提供按时点的财报日），与原运行可能不同。
- **检查点不清理**（同 Agent 子图），每次运行约十个检查点；量很小，留待以后。
- **`attempt` 之前的旧运行**（`stages-1/2/3`）没有续跑，详情页只读。
- **单账号**：换账号要断开再连；断开时远端撤销可能无法确认。
- **ID token 不验签名**（D28）；只从令牌端点经 TLS 取得。
- **令牌明文存于本机数据库**（与 `.env` 同级）；数据库备份文件同样含令牌，`pg_dump` 的备份放 `.local/`（不入库）。
- **周日、周一不运行**：这两天到期的复盘推送顺延到周二 11:30。
- **v2.7 起的「推送前复盘卡」改到推送后**：当天新建的卡在下一次推送里报数（D3）。
- 链内拆股换算、`get_trigger` / `get_position` 不按截止时间过滤等沿用 v2.5–v2.7 的已知限制。
