# v2.6.0 看懂系统

> 2026-10-28，基线 `main@842d4aa`（`v2.5.0` 之后）。路线见 [roadmap §4.4](../roadmap/roadmap.md#44-看懂系统v26)；用户 2026-10-28 按 §4.4 授权开工（决策 #55）。
> 五块内容：「今日」顶部的**运行一览**（今天批处理八个阶段各一句人话）；仓库内版本化的**概念卡**与「知识」菜单、**就地展开**；「知识」菜单下的**「原理」页**；计划卡展开后的 **Agent 推理阅读视图**；**「标的」页重排与 K 线标注**。另给 Agent 加一个工具 `get_concept`。
> 本文是设计，不是实施授权：重启服务、打 tag、推送都要在执行时单独确认。本版**没有迁移**。

## 1. 目标

对应路线成功标准 3：**不读仓库文档，在系统里能看懂**——

1. **今天批处理跑了什么**：「今日」顶部一段运行一览，八个阶段各一句人话（扫了多少只、触发几只、几份计划、Agent 跑了几个单元、复查了几份、推了几条）加计数和跳过原因；可选日期看往日。
2. **任一概念是什么意思**：每个数据族、指标、规则项、`plan-1` 字段、Agent 计划字段、复盘指标都有一张概念卡；「知识」菜单可浏览、互链；「数据」菜单、推导视图、「标的」页、计划卡上的概念名点一下就地展开摘要，一跳到完整卡。「原理」页把系统每天怎么跑串成一篇，每一步链到概念卡和当天的阶段行。
3. **任一份 Agent 计划的每个字段和数字从哪来**：计划卡展开后按时间顺序读——提议者读了什么（工具调用的参数与返回值，字段用概念卡解释）→ 论点与价位 → 反方读了什么、提了哪些反证 → 之后的回应（复查与修订）→ 校验结果；版本链上每一版、每次复查都能这样读。

另外两件配套：「标的」页按投资流程重排（信号与计划 → 关键数据 → 背景 → 历史），首屏回答「今天该关注什么、为什么」，K 线上标出候选、各版本计划价位与你的成交；Agent 可以用 `get_concept` 读概念卡。

**不改任何计算口径与 Agent 流程**：规则 v1、`plan-1`、`screen-1`、`regime-2`、`agent-2` 的提议 / 反方 / 校验 / 复查、影子与复盘口径都不动；新增的只是只读的解释层，加一个只读工具。系统仍然只出研究候选，所有规则与 Agent 都**未经验证**（Phase 0 Gate HOLD）——概念卡和原理页都要如实写这一点。

## 2. 假设与决定

roadmap §4.4 已定的不再重复（五项交付、数据来源、退出条件、不做清单）。下表是本 spec 补定的设计决定，由 spec 作者按 roadmap 与 v2.3–v2.5 的做法自行确定；没有一条新增数据族、新建数据库表或改动口径，所以没有回头问用户。推翻任一条就改对应章节。

| # | 问题 | 决定 | 理由 |
| --- | --- | --- | --- |
| D1 | 概念卡与原理页放哪 | `docs/knowledge/concepts/<id>.md`（一卡一文件）与 `docs/knowledge/principles.md`；系统运行时从仓库读取 | 仓库内、随代码版本走（roadmap #37）；放在 `docs/` 下可直接在仓库里读，相对链接由 `tests/test_docs_links.py` 校验 |
| D2 | 概念 id 的形式 | `<分组>.<名字>`，分组取七个固定值（§4.1），名字用代码里的标识符（如 `rule.trend_reclaim`、`plan.stop`）；文件名 = id | 带分组避免撞名（`stop` 在规则计划和 Agent 计划里都有）；用代码标识符方便就地展开按字段挂卡 |
| D3 | 卡的版本 | frontmatter `version` 为正整数；**定义或口径变了**才加 1，改措辞、补例子不加；系统不保存旧版正文（看 git 历史） | 概念卡随代码走（roadmap §4.4）；Agent 实际读到的正文连同 SHA-256 已存在 `agent_tool_calls`，旧版内容可回看 |

| D5 | 卡内链接 | 只允许两种：指向其它概念卡的相对链接（`plan.stop.md`；原理页里写 `concepts/plan.stop.md`），以及原理页里指向阶段行的 `#stage-<阶段 id>`。外链、图片、指向仓库其它文档的链接一律校验失败 | 「不读仓库文档也能看懂」：系统里的知识不能把人引回仓库；两种形式在仓库里也都能通过链接检查 |

| D7 | 加载与缓存 | 首次使用时整目录加载并校验，结果在进程内缓存到重启；服务启动时不加载。校验失败：知识接口返回 503 并附问题清单，`get_concept` 返回错误信封，批处理与其它页面不受影响 | 卡只随代码部署变化，而部署本来就重启；坏卡不能拖垮服务启动；`knowledge check` CLI 与测试保证提交的卡合法 |
| D8 | 迁移 | **不需要**。运行一览只读 `stage_runs`；推理视图只读 `agent_runs`、`agent_tool_calls`、`agent_plan_versions`、`plan_reviews`；「标的」页只读已有表；概念卡与原理页是仓库文件 | roadmap「不另建表」「不新增数据」 |
| D9 | 运行一览的句子在哪拼 | 后端纯函数按 §7.3 的模板表拼好中文句子与原因文案，前端只显示；**数据只来自 `stage_runs` 行本身**（计数、`skips`、`failures`、`degradations`、`outputs`、`detail`），不顺着 `outputs` 里的 id 去读其它表 | 「计数与 `stage_runs` 逐项一致」可直接测；与 `families.py` / `stages.py` 由后端下发说明文字的做法一致 |
| D10 | 一个交易日跑了多次 | 默认显示该交易日**最后开始的、不是休市空跑**的那次运行（休市空跑 = `push` 之前的阶段全部 `skipped` 且原因为 `not_trading_day`）；只有休市空跑时才默认显示它。页面可切换到同日其它运行（定时 / 手动 / 休市、开始时间） | 手动补跑很常见；纽约休市日的定时运行会记到前一个交易日名下且开始得更晚，不能把真实运行盖住 |
| D11 | 推理视图里的「回应」 | `agent-2` 流程没有单独的「回应」步骤，**不新增**。阅读视图的「回应」一段 = 本版之后对它的复查记录（结论、理由、信号），若因此修订，附新版的「相对上版变化」并链到新版；本版之后还没有复查就写「本版之后还没有复查」 | 不改 Agent 流程；版本链里后一版对前一版的修改，就是系统里真实存在的回应 |
| D12 | 推理视图按什么取 | 按 Agent 运行取：`GET /api/workbench/agent-runs/{run_id}/reasoning`，覆盖 `propose`（首版）、`revise`（修订）、`review`（单阶段复查）、`interpret`（解读）四种 `mode`。计划卡链到生成这一版的运行，版本链每版、复查记录每条各自链到对应运行 | 运行是工具调用与输出的归属单位；同一接口服务计划卡、版本链与复查记录 |
| D13 | 「校验结果」怎么显示 | 列出该运行适用的检查项（§8.4）。`ok` / `pass` → 全部通过；`rejected` → 原因集合含该作废原因的检查项都标「可能未通过」（同一原因可能来自几项），其余标「未单独记录」，**不推断**哪些通过了；反方过滤结果与计划推导一致性另成一步 | 校验器遇到第一个失败就停，没有逐项记录；如实显示 |

## 4. 概念卡

### 4.1 源文件与格式

每张卡一个 UTF-8 文件 `docs/knowledge/concepts/<id>.md`，开头是 `---` 包起来的 YAML frontmatter，后面是 Markdown 正文。

**id**：`^(family|indicator|rule|plan|agent|review|system)\.[a-z0-9_]+$`，文件名去掉 `.md` 必须等于 `id`。七个分组：

| 分组 | 页面标题 | 内容 |
| --- | --- | --- |
| `family` | 数据族 | 「数据」菜单的六个数据族 |
| `indicator` | 指标 | 规则、计划、区制与筛选用到的指标 |
| `rule` | 规则 v1 | 八条规则 |
| `plan` | 规则计划 `plan-1` | 规则计划的字段与推导 |
| `agent` | Agent 计划 | `agent-2` 计划的字段、版本链与复查 |
| `review` | 复盘 | R、影子、纪律、三方对比、链状态、周 / 月复盘 |
| `system` | 系统运作 | 阶段、截止时间、只追加、证据状态、观察池、决定、推送、版本号、概念卡本身 |

**frontmatter 字段**（多余字段校验失败）：

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| `id` | ✓ | 同上 |
| `title` | ✓ | 中文名，1–30 字 |
| `group` | ✓ | 等于 id 的分组前缀 |
| `version` | ✓ | 正整数（D3） |
| `applies_to` | ✓ | 代码版本号列表，可为空 `[]`；每项必须在 `knowledge.KNOWN_VERSIONS` 里（§4.3） |
| `summary` | ✓ | 一句话摘要，1–120 字，不含换行；就地展开显示的就是它 |
| `related` | ✓ | 互链的概念 id 列表，可为空；每项必须存在，不能是自己 |
| `sources` | | 仓库内路径列表（如 `investment_assistant/workbench/plans.py`），每项必须存在；只给维护者看「改这些文件时要回看这张卡」 |

示例：

```markdown
---
id: plan.stop
title: 止损
group: plan
version: 1
applies_to: [plan-1]
summary: 参考价减 2 倍 ATR14，四舍五入到分；之后任一交易日最低价触及即按止损处理。
related: [indicator.atr14, plan.ref_price, plan.trailing_stop, review.r_multiple]
sources: [investment_assistant/workbench/plans.py]
---

## 是什么
…
```

**正文模板**（四个二级标题，按需省略，不另加一级标题）：`## 是什么`（一两句定义）、`## 怎么算 / 从哪来`（公式、阈值、数据来源，数字与代码常量一致）、`## 在系统里哪里看到`（页面与字段名）、`## 注意`（边界、缺数据时怎么显示、证据状态）。正文 1–6000 字。

**链接**（D5）：`[文字](<id>.md)` 指向其它卡；其余任何链接（外链、图片、`../` 路径、锚点）都校验失败。原理页另允许 `concepts/<id>.md` 与 `#stage-<阶段 id>`（§5.2）。

### 4.2 引用形式

`concept:<id>@<version>`（如 `concept:plan.stop@1`）；`concept:<id>` 表示当前版。解析规则：`knowledge.parse_ref(text) -> (id, version | None)`，格式不对抛 `ValueError`。用在：

- 知识接口的每张卡都带 `ref`（当前版的完整引用）；卡片页地址可带版本 `#knowledge/plan.stop@1`。
- `get_concept` 的结果带 `concept_ref`（§10）。
- 就地展开的摘要里显示引用，方便抄进笔记；v2.7「我的知识」挂到概念上也用它。

请求的版本不等于当前版时（D4）：返回当前版，带 `stale: {requested: n, current: m, note: '该引用指向第 n 版，当前为第 m 版；概念卡不保存旧版正文'}`。

### 4.4 卡写什么

## 7. 运行一览

### 7.1 数据与接口

`GET /api/workbench/run-overview?session=YYYY-MM-DD[&run_id=…]`（`session` 缺省 = 最近已收盘交易日），只读事务，只读 `stage_runs`（复用 `repository.stage_runs_for_session` / `stage_runs_ready`）。返回：

```json
{
  "session": "2026-10-27",
  "ready": true,
  "note": null,
  "runs": [{"run_id": "...", "trigger": "scheduled", "trigger_text": "定时", "stages_version": "stages-2",
            "started_at": "...", "finished_at": "...", "rows": 8}],
  "selected_run_id": "...",
  "headline": "定时运行 · 06:30 开始 · 用时 3 分 12 秒 · 8 个阶段：成功 6 · 降级 1 · 跳过 1",
  "stages": [{"id": "collect", "title": "数据采集", "purpose": "…", "status": "partial", "status_text": "部分失败",
              "sentence": "采集 141/174 个目标（按族计）；财报日 120/120；1 处失败",
              "input_count": 174, "output_count": 141,
              "skips": [{"reason": "…", "text": "…", "count": 3, "samples": ["ABC"]}],
              "failures": [{"target": "sec_filings:*", "reason": "…"}],
              "degradations": [{"kind": "…", "text": "…", "detail": "…"}],
              "reason": null, "reason_text": null, "duration_ms": 1234, "concepts": ["family.bars", "…"]}]
}
```

- **选哪次运行**（D10）：`run_id` 给了就用它（不属于该 `session` → 404）；没给取该 `session` 里开始最晚的**非休市空跑**运行（运行的开始时间 = 它最早一行的 `started_at`；休市空跑见 D10），没有非休市运行时取开始最晚的休市空跑。`runs` 每项另带 `closed: bool`，`trigger_text` 对休市空跑写「休市」。
- `stages` 按该运行的 `stages_version` 的阶段集合（`stages.STAGE_IDS_BY_VERSION`）排列；`title` / `purpose` 取注册表。
- 数字字段与 `stage_runs` 行**逐字段相同**（`input_count`、`output_count`、`skips`、`failures`、`degradations`、`reason`、`duration_ms`），只新增文本字段（`*_text`、`sentence`、`headline`）与 `concepts`。

### 7.2 边界情况

| 情况 | 显示 |
| --- | --- |
| `stage_runs` 表不存在（迁移 025 未执行） | `ready: false`，`note`「迁移 025 未执行，暂无阶段证据」，`stages: []` |
| 这一天没有任何阶段行 | `note`「这一天没有阶段证据：当天没有运行，或运行早于 v2.4（2026-10-27 起才记录）」，`stages: []` |
| 运行按 `stages-1` 记账（迁移 026 前） | 七行；在 `push` 之前插一行占位 `{id: 'review', status: 'not_recorded', sentence: '这次运行按 stages-1 记账（早于 v2.5 或迁移 026 未执行），没有每日复查阶段'}`，计数字段为 `null` |
| 该运行缺某个阶段行（只可能是记账失败） | 该阶段 `status: 'missing'`，句子「这一阶段没有证据行（记账失败，见运行报告）」，计数为 `null` |
| 行里出现注册表之外的阶段 id | 照原样排在最后，句子「未知阶段」 |
| `skipped` | 句子 = 「跳过：<原因文案>」（§7.4），计数照显示 |
| `failed` | 句子 = 「失败：<原因文案>」，若有计数照显示 |
| 选中的是休市空跑（D10） | `headline` 改为「纽约休市，未运行（只推送一行休市说明）」，各行照常列出 |

`status_text`：`success` 成功、`partial` 部分失败、`degraded` 降级、`failed` 失败、`skipped` 跳过、`missing` 缺证据、`not_recorded` 未记录。

## 8. Agent 推理阅读视图

### 8.1 接口

`GET /api/workbench/agent-runs/{run_id}/reasoning`，只读事务。读：`agent_runs` 一行、它的全部 `agent_tool_calls`、`agent_plan_versions`（`agent_run_id = run_id` 的版本，迁移 026 就绪时）、`plan_reviews`（`review_agent_run_id` 或 `revision_agent_run_id` 等于 `run_id` 的行，以及 `head_plan_id` 等于本版计划的后续复查）、生成计划的推导一致性（复用 `derivation_view` 的推导，同一只读事务）。`run_id` 不是 UUID → 400；不存在 → 404。

返回：

```json
{
  "run": {"id": "...", "ticker": "...", "signal_date": "...", "mode": "propose", "agent_version": "agent-2",
          "status": "ok", "reason": null, "reason_text": null, "model": "...", "cutoff_at": "...",
          "started_at": "...", "finished_at": "...", "input_tokens": 0, "output_tokens": 0},
  "legacy": false,
  "version": {"plan_id": "...", "version_no": 1, "origin": "review"} ,
  "review": null,
  "steps": [ ... ],
  "notes": ["…"]
}
```

### 8.2 步骤（按时间顺序）

每一步 `{kind, title, concept, ...}`，`concept` 是这一步的概念卡。

| `mode` | 步骤顺序 |
| --- | --- |
| `propose`（首版） | ① `read`（提议者读了什么：`phase = propose` 的调用）→ ② `proposal`（动作、摘要、价位、论点、失效条件、下次复查条件）→ ③ `check`（§8.4；图里校验在反方之前执行）→ ④ `read`（反方读了什么：`phase = counter` 的调用）→ ⑤ `counter`（逐条反证、其他风险、丢弃数、无反证的论点）→ ⑥ `response`（D11）→ ⑦ `outcome`（生成的计划行状态与推导一致性，只对生成了计划的运行） |
| `revise`（修订） | 先 ⓪ `evidence`（触发这次修订的复查：复查交易日、信号、条件判定、给模型的用户输入 id，取自 `revision_agent_run_id = run_id` 的复查行；并链到该复查自己的单阶段运行）→ 其后同 `propose`，② 另含 `changes` 与宿主 `diff` |
| `review`（单阶段复查） | ⓪ `evidence`（同上，取自 `review_agent_run_id = run_id` 的复查行）→ ① `read`（`phase = review`）→ ② `verdict`（结论、理由、引用）→ ③ `check` |
| `interpret`（解读） | ① `read` → ② `interpretation`（输出原样）→ ③ `check` |

- **`read`**：每个调用 `{seq, ref: 'call:N', tool, tool_text, args, result, result_sha256_8, called_at, concept, fields: {<结果顶层键>: <概念 id>}, cutoff_exempt}`。`concept` 与 `fields` 取自 §8.3 的表；`get_concept` 调用 `cutoff_exempt: true`，页面标「概念卡随代码版本走，不受截止时间约束」。
- **`proposal`**：价位 `[{key, value, refs, concept}]`（`entry_low` / `entry_high` → `plan.entry_zone`，`stop` → `plan.stop`，`target1` → `plan.target1`）；论点 `[{id: 'T1', text, refs}]`；失效 / 复查条件 `[{kind, params, text, refs}]`（`text` 用 `conditions.describe`）。引用 `refs` 原样给出，页面点开跳到 ① / ④ 里对应的调用。
- **`response`**（D11）：本版之后以本版为 `head_plan_id` 的复查记录，按时间：`[{review_id, session, trigger, outcome, decided_by, reason, signals_fired, new_plan_id, new_version_no, changes}]`；没有 → `items: []`，`title`「回应：本版之后还没有复查」。`agent-1` 运行和没有生成计划的运行没有这一步。
- **结果为 `rejected` / `error` / `skipped`** 的运行：照样给出已记录的调用；`output` / `counter` 存了就照常显示（例如入场期修订版因计划行作废而 `rejected / plan_invalid` 时两者都在），没存的那一步写「这次运行作废：<原因文案>，只保留工具调用」；`check` 照给。

### 8.4 校验项

| 适用 | 检查项（`id` · 文案 · 对应作废原因） |
| --- | --- |
| `propose` / `revise`（`agent-2`） | `json` 输出是合法 JSON 且字段齐全（`malformed`）· `refs` 引用都存在（`invalid_citation`）· `price_refs` 每个价位至少引用一次价格类工具（`invalid_citation`）· `level_order` stop < entry_low ≤ entry_high < target1（`level_check`）· `level_range` 价位在最近收盘 ±50% 内（`level_check`）· `thesis_count` 论点 1–3 条（`thesis_count`）· `conditions` 失效与复查条件合法（`invalid_condition`）· `changes` 变化说明与宿主差异一致（`changes_mismatch` / `no_change` / `malformed` / `invalid_citation`，仅修订）· `plan_status` 入场期修订的新计划行必须有效（`plan_invalid`，仅修订）· `tool_rounds` 工具轮数不超过 8（`tool_rounds_exceeded`） |
| `propose`（`agent-1`） | 同上去掉 `thesis_count`、`conditions`、`changes`、`plan_status` |
| `review` | `json` 复查输出格式（`review_malformed`）· `refs` 修订 / 作废必须有引用且都存在（`invalid_citation`）· `tool_rounds` |
| `interpret` | `json`（`malformed`）· `refs`（`invalid_citation`）· `tool_rounds`（`tool_rounds_exceeded`） |

每项 `result`：运行 `ok` / `pass` → `pass`；运行 `rejected` → 作废原因出现在该项原因集合里的**全部**项标 `implicated`（页面写「未通过的检查在这几项之中：A、B；校验器遇到第一处失败就停，不记录是哪一项」），其余 `not_recorded`（D13）；`error` / `skipped` → 全部 `not_run`，附原因文案。反方过滤（`dropped`、`uncountered`）放在 `counter` 步骤；计划行状态与推导一致性放在 `outcome` 步骤。

### 8.5 `agent-1` 旧运行的降级

`legacy: true`；`notes` 加「agent-1（旧版）：没有失效条件、下次复查条件与逐条对应的反证，也不参与复查；以下按原样显示」。步骤：① `read` → ② `proposal`（动作、摘要、价位、`thesis` 作为「理由」）→ ③ `check`（`agent-1` 检查项）→ ④ `read`（反方）→ ⑤ `counter`（只有 `risks`）→ ⑦ `outcome`；没有 ⑥ `response`。

### 8.6 页面

`AgentReasoning.svelte`（props `{ runId: string }`，展开时才请求）。挂在：

- `AgentPlanCard` 底部「看推理过程」（取生成这一版的运行 id；「今日」与计划页共用，所以版本链里点开的每一版都有）。
- `PlanTimeline` 每条复查记录：「看复查推理」（`review_agent_run_id`）与「看修订推理」（`revision_agent_run_id`），有才显示。

显示：每一步一个小节，标题带 `ConceptTerm`；`read` 里每个调用一行「call:N · 工具中文名 · 参数」，点开看返回值（列表默认只显示条数与首尾各 2 行，可展开全部）与哈希前 8 位，字段名旁挂 `ConceptTerm`；论点、价位、反证里的 `call:N` 可点，滚动并高亮到那次调用；`user:<id>` 只显示。

### 9.2 「今天该关注什么」（`instrument_view.focus`，纯函数）

按顺序生成，每条 `{kind, text, link, concepts}`：

4. **临近财报**（已知财报日在 10 个交易日内）：「{n} 个交易日后发布财报（{date}）」。
5. 以上都没有：「今天没有触发，也没有进行中的计划或持仓」。

### 9.3 K 线标注（`chart.annotate`，纯函数）

`chart.annotate(*, bars, candidates, plans, versions, trades) -> {markers, segments, omitted}`，只用图上已保留的日线日期：

| 情况 | 行为 |

## 15. 风险

| 风险 | 应对 |
| --- | --- |
| 概念卡与代码口径脱节 | 守护测试（§4.6）在代码集合变化时失败；`sources` 指出要回看的文件；卡写「改了口径同提交改卡」进 `docs/README.md` 维护规则 |
| 卡写错数字或阈值 | 内容 Task 的审查逐张对照代码常量；「要点」列给出必须写清的事实；用户验收时发现就同提交修正卡（措辞不加版本，口径加版本） |
| `get_concept` 让 Agent 读到「未来的定义」 | 这是明示的例外（D19）：卡是定义不是数据；结果与记录里写明 `point_in_time: false`，推理视图标出；卡不含任何价格、标的或日期相关数据（校验禁止外链，内容审查禁止写具体行情） |
| 新增工具改变 Agent 行为 | 输出结构与校验不变；工具调用照常计入轮数与 token；影子与三方对比照常检验结果 |
| `{@html}` 注入 | 源文件只来自仓库；`markdown-it-py` 关闭原始 HTML；链接只允许两种形式并在加载时校验 |
| 运行一览被读成「全部成功」 | 状态徽标与跳过 / 失败 / 降级逐条显示；`partial` / `degraded` 不合并成成功；没有证据时明说没有 |
| 「标的」页变慢 | 新增读取都是按标的、按窗口的索引查询；指标现算只用已读出的日线；`MAX_PLANS` 限制线段数 |
| 推理视图的「回应」被误读成 Agent 自我辩护 | 标题写「回应：本版之后的复查与修订」，说明 `agent-2` 没有单独的回应步骤 |
