# v2.5.0 计划时间线

> 2026-10-28，基线 `main@53d9ed5`（`v2.4.0` 之后）。路线见 [roadmap §4.3](../roadmap/roadmap.md#43-计划时间线v25)；用户 2026-10-28 按 §4.3 授权开工。
> 三块内容：Agent 计划结构化为可复查的论点（`agent-2`）并成为「今日」与推送的默认复查对象；同一单元的 Agent 计划有只追加的版本链，批处理新增第 8 个阶段做每日复查，系统信号与你的输入触发修订；每个版本独立影子跟踪，三方对比取你决定时看到的那一版。
> 本文是设计，不是实施授权：真实库执行迁移 026、重启服务、打 tag、推送都要在执行时单独确认。

---

## 1. 目标

主线不变（`screen-1` → 规则候选 → 计划 → 你复查、决定、自己下单 → 复盘），只改两件事：

1. **你复查的对象**：每个买入单元先看 Agent 计划。计划写清为什么现在值得做（论点）、反方找到的反证、什么情况下这份计划就不成立（失效条件，程序可检查）、什么时候该再看一次（下次复查条件），以及相对上一版改了什么。`plan-1` 照常计算，折叠为「规则基线」。
2. **计划会随时间更新**：信号日之后，每个交易日批处理对每份有效 Agent 计划做一次复查，结论是维持、修订或作废；新 8-K、异常波动、止损或 T1 触及、临近到期、区制变化，以及你贴进来的材料，都会让复查认真看一次。修订出新版，旧版不改，每版截止时间各自固定、各自影子跟踪。

成功标准（对应路线成功标准 1、2 与 §4.3 退出条件）：

- 每个买入单元，只读 Agent 计划就能决定做不做：计划有论点、证据（引用）、反证、失效条件、价位依据、下次复查条件。
- 每份有效 Agent 计划每个交易日恰有一条复查记录；新信号或你的输入能产生新版，差异可读；所有版本可回放，截止时间各自固定。
- §14 的手动验收与连续 10 个交易日的定时验收都留下证据。

系统仍然只出研究候选：不下单，不接券商。**Agent 成为默认复查对象不等于 Agent 有效**：规则 v1、`plan-1` 与 Agent 都**未经验证**（Phase 0 Gate HOLD），不因界面默认展示 Agent 解除 Gate HOLD，不做自动晋升。

## 2. 假设与决定

roadmap §4.3 已定的不再重复（版本链、每日复查阶段、五类系统信号、用户输入、每版影子、计划更新段、预算、退出条件、不做清单）。下表是本 spec 补定的设计决定，均由 spec 作者按 roadmap 与 v2.0–v2.4 的做法自行确定；没有一条新增数据族或改动 `plan-1` 口径，所以没有回头问用户。推翻任一条就改对应章节。

| # | 问题 | 决定 | 理由 |
| --- | --- | --- | --- |
| D1 | 新结构的版本号 | Agent 计划 `plan_version = agent_version = 'agent-2'`；首版与修订版同一版本号，靠版本链区分第几版。复查调用 `agent-review-1`；失效 / 复查条件集合 `condition-1`；链状态与信号判定规则 `timeline-1` | 与 `plan-1`、`agent-1` 同一命名方式；改了结构或口径就发新版本 |
| D2 | 旧 `agent-1` 计划 | 保留只读、照常展示与影子跟踪，标「agent-1（旧版，不参与复查）」；不迁移、不回填、不进复查。v2.5 上线后新生成的 Agent 计划一律 `agent-2` | 只追加；旧版没有论点 / 失效条件等字段，补写就是改历史 |
| D3 | 版本存在哪里 | 每一版都是 `trade_plans` 的一行（`kind = 'agent'`、`plan_version = 'agent-2'`、`signal_date` 仍是单元的信号日），链关系存在新表 `agent_plan_versions` | 决定（`signal_decisions.plan_id`）、影子、推导、纪律都按 `trade_plans` 工作，每版一行就能原样复用 |
| D4 | 版本的有效期 | 首版 = 信号日后 T+1 至 T+3（同 `agent-1`）。修订版 = 复查交易日 S 之后 S+1 至 S+3，入场期的链另设上限：不晚于信号日后第 `CHAIN_ENTRY_SESSIONS = 10` 个交易日 | 每版截止时间 = 生成时刻，影子从生成之后才可能成交；上限防止靠修订无限延期 |
| D5 | 有效计划（复查对象） | 链处于「入场期」或「持仓期」。入场期：未决定或决定买入但未成交，且 S 早于最新版 `valid_until`；持仓期：该单元的决定链上有未平的买入成交。终止：复查作废、过期未成交、决定为不买、持仓平仓（§5.3） | roadmap「未过期、未作废 + 关联持仓的计划」的可判定写法 |
| D6 | 扩展池的链 | 扩展池单元的链同样每日复查（roadmap「所有有效的 Agent 计划」），排在持仓与主列表之后，受同一预算与对象上限约束；结果只影子跟踪、不推送 | 不缩小 roadmap 授权的复查范围；扩展池本来就只影子跟踪 |
| D7 | 「关联持仓的计划」怎么读 | 读作「已过入场有效期、但关联了持仓的 Agent 计划」：持仓期的链不受 `valid_until` 限制，照常复查。只有规则 / 自定计划、单元没有 `agent-2` 链的持仓，不为它新建链；阶段 `detail.holdings_without_chain` 列出，「今日」持仓行标「此持仓无 Agent 计划，不参与复查」 | 版本链的对象是 Agent 计划；从规则计划生成 Agent 计划是新的生成入口，不在 v2.5 |
| D8 | 失效条件命中 | 宿主判定：任一失效条件 `met` → 复查结论直接为作废（`decided_by = host`），不调用模型 | 判定始终在宿主代码；失效条件是 Agent 自己声明的，程序执行 |
| D9 | 没有新信号的日子 | 没有任何系统信号、没有新的用户输入、下次复查条件都不满足 → 宿主写「维持」（`decided_by = host`），不调用模型。默认下次复查条件是「下一交易日」，即默认每天调用一次模型 | 让「下次复查条件」有实际作用，又不违背「每日一条复查记录」 |
| D10 | 修订未通过校验 | 复查记录照写（结论 `revise`、`new_plan_id` 为空、写明原因），最新版不变，不推送；当天不自动重试，可点「重新复查」 | 如实记录模型想改但没改成；不伪装成维持 |
| D11 | 修订时模型改口 `pass` | 视为作废（`decided_by = agent`，`detail.via = 'revision_pass'`） | 修订版必须是可执行的计划；不想做就是作废 |
| D12 | 用户输入怎么给模型 | 宿主把输入原文连同 `user:<id>` 与时间戳写进提示词，作为证据块；**不新增工具**，八个工具与截止时间机制不变 | 满足「工具层不动」；引用 `user:<id>` 由宿主校验 |
| D13 | 用户输入的更正 | 只追加：更正或撤回 = 新一行指向旧行（`supersedes_id`）；旧版计划引用过的旧行永远可读 | 只追加；新经验不回填到旧计划 |
| D14 | 「重新复查」怎么跑 | 后台执行（同「立即运行批处理」的 `runner.submit`），截止时间 = 点击时刻；同一条链与批处理复查互斥（advisory lock），撞上返回 409 | 一次复查加修订可能要几分钟；不能和批处理同时改同一条链 |
| D15 | 决定记录存哪一版 | `signal_decisions` 新增 `agent_plan_id`（决定时页面显示的 Agent 版本，后端核对必须等于当时的最新版，否则 409）与 `review_view`（布局、是否展开过规则基线） | 三方对比取「你决定时看到的那一版」；退出条件「只读 Agent 计划就能决定」需要可查的证据 |
| D16 | 三方对比 | `tracks-1` 口径不变；Agent 轨道取的计划由「该单元唯一的 Agent 计划」推广为「决定时看到的那一版」，未决定的单元取首版。`agent-1` 单元结果与现在完全相同，所以不发新版本号；行上新增 `version_no`、`version_basis` | roadmap §4.3「三方对比 `tracks-1` 不变」与「取你决定时看到的那一版」同时成立 |
| D17 | 周 / 月复盘的计划影子 | `_plan_summary` 的 `agent` 改为每条链只算首版（`agent-1` 计划就是自己的首版），新增 `agent_latest`（快照生成时的最新版）；`review-5` → `review-6`、`monthly-2` → `monthly-3` | 否则每版都计入 `agent`，样本被修订次数放大；改了冻结快照的口径必须发新版本 |
| D18 | 阶段顺序 | 第 8 个阶段 `review`（每日复查）放在 `agent` 之后、`push` 之前；`STAGES_VERSION = 'stages-2'` | 推送的「计划更新」段要用当天的复查结果 |

## 4. Agent 计划结构 `agent-2`

### 4.1 字段

| 字段 | 来源 | 内容 | 校验（任一不过，整版作废，原因见 §4.4） |
| --- | --- | --- | --- |
| 动作与价位 | 提议 | `action`（`buy` / `pass`）、`summary`、`levels.{entry_low, entry_high, stop, target1}`，每个价位 `{value, refs}` | 原样沿用 `citations.check_proposal`：JSON 形状、引用存在、每个价位至少一个价格类工具引用、`stop < entry_low ≤ entry_high < target1`、价位在最近收盘 ±50% 内 |
| 论点 `thesis` | 提议 | 1–3 条 `{text, refs}`：为什么现在值得做；宿主按顺序编号 `T1…T3` | 条数 1–3（`thesis_count`）；每条 `refs` 非空且都存在（工具调用或本次给出的用户输入） |
| 关键反证 `counter` | 反方 | `counter: [{thesis: n, text, refs}]` 逐条对应论点，另可有 `risks: [{text, refs}]` | 只保留引用存在、`thesis` 编号存在的条目，其余丢弃并计数（`dropped`）；没有对应反证的论点列入 `uncountered`；反方**不改**价位和动作（代码层忽略） |
| 失效条件 `invalidation` | 提议 | 1–5 条 `{kind, params, text, refs}`，取自 §4.2 的条件集合 | 条数 1–5；`kind` 已登记且可用于失效；`params` 合法；`refs` 非空且存在（`invalid_condition`） |
| 下次复查条件 `review_when` | 提议 | 0–3 条 `{kind, params, text}`；空 = `[{kind: next_session}]`（默认「下一交易日」） | `kind` 已登记且可用于复查；`params` 合法（`invalid_condition`） |
| 相对上版变化 `changes` | 提议（修订） | 首版不填；修订版 `[{field, text, refs}]`，`field ∈ {action, entry, stop, target1, thesis, invalidation, review_when}` | 首版出现非空 `changes` → `malformed`；修订版必填，`refs` 非空且存在；字段集合必须**等于**宿主算出的差异字段集合（`changes_mismatch`）；宿主差异为空 → `no_change` |

宿主差异（`timeline.diff(prev, new)`，纯函数）按字段比较：`entry`（两端任一到分不同）、`stop`、`target1`（到分）、`action`、`thesis`（文本序列逐字）、`invalidation` / `review_when`（`(kind, params)` 序列的规范 JSON；只改 `text` 不算变化）。差异与模型写的 `changes` 一起存进版本记录，页面两者并列显示。

`agent_runs.output` 存提议的完整输出（含 `thesis`、`levels`、`invalidation`、`review_when`、`changes`），`agent_runs.counter` 存 `{status, counter, risks, dropped, uncountered}`，与 `agent-1` 一样是唯一的内容来源；`trade_plans` 只存价位、有效期、仓位等计划字段。

### 4.2 条件集合 `condition-1`

失效条件与下次复查条件共用一份注册表（`agent/conditions.py`，纯函数）。每个条件对给定事实（§7.3）判定为 `met` / `not_met` / `unknown`；数据缺失时一律 `unknown`，**不当作满足**，并如实记录。

| `kind` | `params` | 含义（页面文案模板） | 判定 | 失效 | 复查 |
| --- | --- | --- | --- | --- | --- |
| `close_below` | `price` | 收盘跌破 {price} | 判定窗口内任一交易日收盘 < `price` | ✓ | ✓ |
| `close_above` | `price` | 收盘突破 {price} | 任一交易日收盘 > `price` | ✓ | ✓ |
| `no_entry_by` | `date` | {date} 收盘前未进入入场区 | S ≥ `date`，且自版本生成后到 `date` 没有一根日线与入场区间相交（`low ≤ entry_high` 且 `high ≥ entry_low`）；仅入场期有效，持仓期恒 `not_met` | ✓ | |
| `no_entry_before_earnings` | — | 财报前未进入入场区 | 已知下次财报日 E，`S+1 ≥ E`，且自版本生成后没有日线与入场区间相交；财报日未知 → `unknown`；仅入场期 | ✓ | |
| `earnings_within` | `sessions`（1–10） | 距财报不足 {sessions} 个交易日 | 已知财报日 E 且 `S < E ≤ S + sessions` 个交易日 | ✓ | ✓ |
| `regime_is` | `label` ∈ `risk_on` / `neutral` / `risk_off` | 区制变为 {label} | S 的 `regime-2` 标签 = `label`；没有快照或 `insufficient` → `unknown` | ✓ | ✓ |
| `sector_weak` | — | 所属行业转弱 | S 的区制快照里该标的行业 ETF 的状态为 `weak`；未映射 → `unknown` | ✓ | ✓ |
| `rs_below` | `window` ∈ 20 / 60，`value` ∈ [−1, 1] | 相对 SPY {window} 日强弱低于 {value} | 按 `tools.indicators` 的同一公式（截止时间内日线）计算 `rs{window}` < `value` | ✓ | ✓ |
| `new_filing` | `form` ∈ `8-K` / `10-Q` / `10-K` | 出现新的 {form} | 判定窗口内有该类 SEC 文件（按受理时间，缺受理时间按 `filing_date`） | ✓ | ✓ |
| `date_reached` | `date` | 到 {date} 再看 | S ≥ `date` | | ✓ |
| `next_session` | — | 下一交易日 | 恒 `met` | | ✓ |

参数校验：价格为正且在生成时最近收盘的 ±50% 内；日期晚于版本的生成交易日、且不超过其后 60 个日历日；`sessions` 为 1–10 的整数；`label` 与 `form` 取上表枚举；`value` 为有限数。未知 `kind`、多余或缺少参数都是 `invalid_condition`。

### 4.3 提示词

- **`PROPOSE_PROMPT_V2`**（首版与修订版共用）：在 `agent-1` 的提议提示词上增加论点 1–3 条、失效条件与下次复查条件（把 §4.2 的 `kind` / `params` / 含义整表写进提示词）、修订时的 `changes` 要求。修订时附上上一版全文（价位、论点、反证、失效与复查条件、生成时间）、信号日的原始触发（D24）、本次复查的理由、系统信号与新的用户输入。

## 5. 版本链

### 5.1 链与版本

- **链** = 一个单元（`ticker`、`signal_date`）的全部 `agent-2` 版本，按 `version_no` 从 0 起连续编号；**最新版**（head）是编号最大的一版。
- **首版**（`version_no = 0`，`origin = 'signal'`）由信号日批处理的 `agent` 阶段生成，即现有提议 + 反方 + 校验流程，输出换成 `agent-2`。手动「重新运行 Agent」（`POST /api/workbench/agent-runs`）也只生成首版。
- **修订版**（`version_no ≥ 1`，`origin = 'review'` 或 `'recheck'`）只由复查生成：`supersedes_plan_id` 指向上一版，`changes` 必填；同一版不能被两版指向（链不分叉）。
- **截止时间**：每一版的截止时间 = 生成时刻（`agent_runs.cutoff_at`，也写进 `agent_plan_versions.cutoff_at`）；`as_of_session` = 该时刻最近已收盘的交易日。工具层照旧只读截止时间之前的数据。
- 旧版不改：`trade_plans`、`agent_runs`、`agent_plan_versions` 的行写入后不更新。

### 5.2 版本计划行

新版的计划行由 `timeline.build_version_plan(...)` 生成（纯函数，复用 `plans.size`、`plans.earnings_flags`、`plans.context_flags`、`plans.atr14`，**不改 `plans.py`**）：

- 价位 = 模型价位（到分）；参考价 = `as_of_session` 收盘；`atr` 能算就算，不能算为 0（移动止损退化为保本，同 `agent-1`）。
- 有效期按 D4：首版 `plans.validity(signal_date)`；修订版 `valid_from = S+1`，`valid_until = S+3`，入场期另取 `min(S+3, signal_date + 10 个交易日)`。
- 仓位按入场区间中点、生成时刻的资金快照与敞口计算（同 `agent-1`）。持仓期的敞口包含已持有的这只股票，所以修订版可能因 `no_room` 而 `status = invalid`——这只说明「按仓位规则不能再加仓」，**链照常有效**、照常复查（Review Focus 6）。
- 财报：有效期内有财报 → `earnings_in_validity` 作废，与 `plan-1` 同一规则。
- `inputs` 在 `agent-1` 的形状上增加 `as_of_session`、`version_no`、`supersedes_plan_id`、`chain_entry_cap`（入场期上限日，持仓期为 `null`）。

推导链为 `('agent-2', 'agent')` 注册推导：与 `agent-1` 相同地核对价位等于 `agent_runs.output.levels`，有效期改按 `inputs.as_of_session` 与 `chain_entry_cap` 推导，并核对 `agent_plan_versions` 里有这一版、`version_no` 一致；缺版本行 → `incomplete`（`missing: agent_plan_versions:<plan_id>`）。

### 5.3 链状态（`timeline-1`，纯函数 `timeline.chain_state`）

在复查交易日 S、截止时间 `now` 判定，按顺序取第一条成立的：

| 状态 | 条件 | 是否复查 |
| --- | --- | --- |
| `legacy` | 单元只有 `agent-1` 计划 | 否 |
| `invalidated` | 最新版有一条有效复查记录的结论为 `invalidate` | 否（终止） |
| `closed_by_decision` | 单元最新决定的 `final_action ≠ buy` | 否（终止） |
| `holding` | 单元的决定链上有未作废的买入成交，且这些成交还有未平批次 | **是**（持仓期） |
| `position_closed` | 有过这类买入成交，现已全部平仓 | 否（终止） |
| `expired` | `S ≥ 最新版 valid_until` | 否（终止） |
| `entry` | 其余（未决定，或决定买入尚未成交） | **是**（入场期） |

「决定链上的买入成交」与三方对比的口径相同（`repository.unit_decision_ids` + `trades.decision_id`）。终止状态由已有记录推出，不另写状态行；`GET` 接口返回的链视图带上状态与判定依据。

## 7. 每日复查阶段 `review`

### 7.1 阶段定义（`stages-2`）

`stages.py` 注册表在 `agent` 与 `push` 之间加一行，`STAGES_VERSION = 'stages-2'`，每次运行恰好 8 行：

| 顺序 | `id` | 名称 | `input_count` | `output_count` | `outputs` | 跳过 / 降级 / 失败 |
| --- | --- | --- | --- | --- | --- | --- |
| 7 | `review` | 每日复查 | 本次复查对象数（§7.2） | 写入的有效复查记录数 | `{"review_ids": […], "plan_ids": [新版…], "agent_run_ids": […]}` | 逐链跳过原因（`stage_budget`、`quota_exhausted`、`token_budget`、`max_attempts`、`already_reviewed`、`review_in_progress`、`object_cap`、`fresh_version`）进 `skips`；`error` 记录与异常进 `failures`；修订未通过 → `degradations`（`revision_failed`）；Agent 不可用但有对象 → 宿主能判定的照写、其余记 `skipped`、阶段 `degraded`（`agent_unavailable`）；Agent 不可用且没有对象 → `skipped`（`agent_unavailable: <原因>`）；迁移 026 未执行 → 本次按 `stages-1` 记账，没有这一行（D22） |

`detail`：`{"outcomes": {maintain, revise, invalidate, skipped, error}, "decided_by": {agent, host}, "signals": {<kind>: 触发次数}, "modes": {entry, holding}, "ended": {expired, closed_by_decision, position_closed}, "holdings_without_chain": [ticker…], "tokens": {input, output}, "derivation": {…}}`。`derivation` 同 v2.4：对本次新版做推导核对，`mismatch` / `incomplete` 记 `degraded` 并进 `summary['errors']`。

非交易日：与其余阶段一起记 `skipped`（`not_trading_day`）。`summary` 新增 `review` 键（`{objects, outcomes, tokens}`），没有复查对象时为 `{objects: 0, …}`；这是 `summary` 唯一的结构新增，现有键不变。

`derivation stages` CLI 改为按 `stages_version` 核对行数（`stages-1` 7 行、`stages-2` 8 行）；`RUN_STAGE_COUNT` 改为按版本的映射。

### 7.2 复查对象

在 `agent` 阶段之后，读全部 `agent-2` 链，按 §5.3 判定状态：

- 对象 = 状态为 `entry` 或 `holding` 的链，排除：最新版 `as_of_session == S`（当天刚生成，生成本身就是当天的记录，`fresh_version`）、本 S 已有有效批处理复查（`already_reviewed`）。
- 顺序：持仓期在前；然后主列表入场期、最后扩展池入场期（按首版运行的 `pool`），各自按最新版 `valid_until` 升序、再按标的。超过 `REVIEW_MAX_OBJECTS = 20` 的记 `object_cap`。
- **链标的只采集**（D21）：处于有效状态的链，其标的若不在观察池与持仓里，在逐只循环之后单独采集日线、资讯、财报日，并计入 SEC 列表的标的，**不跑规则**；`summary['pool']` 新增 `chains` 计数，`collect` 阶段计数照常包含它们。

### 7.3 输入、信号与条件

对每个对象，在同一截止时间 `now`、复查交易日 S 下由宿主只读取：

- **上一版全文**：最新版的计划行、`agent_runs.output` 与 `counter`、`changes` 与 `diff`、生成时间、上一次有效复查的结论与理由。
- **「上次复查之后」**：`since_session = max(最新版 as_of_session, 本版最近一次有效复查的 session)`，`since_at = max(最新版 cutoff_at, 该复查的 cutoff_at)`。
- **系统信号**（`timeline.signals`，纯函数，六项都写进记录）：

| `kind` | 触发判定 |
| --- | --- |
| `new_8k` | 该标的有 8-K，受理时间在 `(since_at, now]`（缺受理时间按 `filing_date > since_session`） |
| `abnormal_move` | `signal_candidates` 里该标的 `abnormal_move` 候选的 `signal_date ∈ (since_session, S]` |
| `stop_touched` | `(since_session, S]` 内有日线 `low ≤ 最新版 stop` |
| `t1_touched` | `(since_session, S]` 内有日线 `high ≥ 最新版 target1` |
| `expiry_near` | 入场期，且 `S+1 == 最新版 valid_until`（到期前 1 个交易日） |
| `regime_change` | S 的区制标签 ≠ 最新版 `inputs.context.regime.label`；任一侧缺失 → 不触发，`detail = 'unknown'` |
| `user_input` | 有 `created_at ∈ (since_at, now]` 的有效用户输入（标的级或本链） |

- **条件判定**：最新版的失效条件（窗口从 `as_of_session` 次日到 S）与下次复查条件（窗口从 `since_session` 次日到 S），每条记 `met` / `not_met` / `unknown`。

### 7.4 结论

按顺序：

1. **失效条件成立**：任一失效条件 `met` → 结论 `invalidate`，`decided_by = host`，原因「失效条件成立：<条件文案>」，不调用模型（D8）。
2. **无事可看**：没有任何信号触发、没有新的用户输入、下次复查条件没有一条 `met` → 结论 `maintain`，`decided_by = host`，原因「无新信号，复查条件未满足（<条件文案>）」，不调用模型（D9）。重新复查（§8.2）跳过这一步。
3. **预算闸门**（同 `agent` 阶段，顺序不变）：批处理开始 `AGENT_DEADLINE_S` 秒后 → `stage_budget`；Agent 不可用 → `<不可用原因>`；本次已遇额度用尽 → `quota_exhausted`；同链同 S 已尝试 `REVIEW_MAX_ATTEMPTS` 次 → `max_attempts`；当日 token（含复查与修订运行）已达上限 → `token_budget`。命中 → 写 `outcome = skipped` 的复查行（原因同上）。
4. **单阶段复查**：`agent-review-1` 调用（`mode = 'review'`，`ToolContext(ticker, session = S, cutoff_at = now)`，工具轮数上限同 `MAX_TOOL_ROUNDS`）。输出经 `plan_check.check_review` 校验：JSON 形状与 `outcome` 枚举（`review_malformed`）、`revise` / `invalidate` 必须有引用、引用必须是本次工具调用或本次给出的 `user:<id>`（`invalid_citation`）。校验不过或模型出错 → `outcome = error`，原因为作废原因或错误分类，阶段记 `failures`。
5. **`maintain` / `invalidate`**：照写，`decided_by = agent`。
6. **`revise`**：走完整的提议（修订提示词）+ 反方 + 校验（`mode = 'revise'`）：
   - `buy` 且通过 §4.1 全部校验（入场期另要求新计划行 `status = 'ok'`，否则按 D23 视为修订未通过）→ 新计划行 + 新 `agent_plan_versions` 行 + 修订运行与工具调用 + 复查行（`new_plan_id` 指向新版），**同一事务**写入；
   - `pass` → 结论改为 `invalidate`（D11）；
   - 校验不过或出错 → 复查行 `outcome = revise`、`new_plan_id = NULL`、`detail.revision_status = '<status>: <reason>'`，最新版不变（D10）。

每条链在 advisory lock `review:<ticker>:<signal_date>` 下执行；拿不到锁（重新复查正在跑）→ 本次跳过（`review_in_progress`），不写行。单条链出任何意外只影响这条链，不中断阶段（同 `agent` 阶段的隔离）。

### 7.5 预算

复查对象通常是个位数。沿用：批处理时间预算（`AGENT_DEADLINE_S = 1500` 秒后不再启动新的复查调用）、每日 token 上限 `WORKBENCH_AGENT_DAILY_TOKENS`（复查与修订运行都是 `agent_runs`，自动计入）、额度用尽即停。新增常量：`REVIEW_MAX_OBJECTS = 20`、`REVIEW_MAX_ATTEMPTS = 3`、`CHAIN_ENTRY_SESSIONS = 10`。每条链每次复查至多一次修订流程。宿主判定的维持 / 作废不消耗 token。

## 8. 用户输入与「重新复查」

### 8.1 用户输入

- **入口**：「标的」页（默认作用于该标的所有链，可选一条链）与计划页 `#plan/<id>`（作用于这一条链）各有一个输入框：类型（研报要点 / 新闻 / 我的判断 / 其他）、正文、可选链接。提交后列在同页，带 `user:<id>` 与时间；每条可「更正」或「撤回」（都是新一行指向旧行）。
- **API**：`POST /api/workbench/user-inputs`（body `{request_id, ticker, signal_date?, kind, body, source_url?, supersedes_id?}`；同一 `request_id` 同内容返回原行，不同内容 409；`signal_date` 给了但单元没有候选 → 404；`supersedes_id` 不属于同一标的 → 400）；`GET /api/workbench/user-inputs?ticker=&signal_date=`（含被更正 / 撤回的标记）。
- **给模型**：复查与修订的提示词里附「用户输入」证据块：截止时间之前的有效输入中，`created_at > since_at` 的新输入全部给出（最多 10 条、合计 8000 字，超出的写「另有 n 条未纳入」并记进 `detail`）；更早的有效输入只给标题行（id、类型、时间、前 80 字）。引用 `user:<id>` 只能引用块里出现的 id。
- 用户输入只是证据：不授予权限，不改规则、价位口径或校验；用户输入本身不触发修订，只触发一次认真复查（`user_input` 信号）。

### 8.2 重新复查

- **入口**：计划页与「今日」进行中的链各有「重新复查」按钮；贴入输入后页面提示可以重新复查。只对状态为 `entry` / `holding` 的链可用。
- **API**：`POST /api/workbench/chains/{ticker}/{signal_date}/recheck` → 前置检查（迁移就绪、链存在且有效、Agent 可用、没有正在进行的复查），不过分别返回 503 / 404 / 409（`chain_not_active`、`agent_unavailable: <原因>`、`review_in_progress`），不写行；通过后 `runner.submit` 后台执行，返回 `{run_id, status: 'pending'}`，页面用 `/api/runs/{run_id}` 轮询。
- **执行**：`trigger = 'recheck'`，截止时间 = 点击时刻（请求进入时取，不是后台开始执行的时刻），S = 该时刻最近已收盘交易日；跳过 §7.4 第 2 步（你要求看就一定调用模型），其余同批处理（失效条件成立仍由宿主作废）。新版 `origin = 'recheck'`。不受 `REVIEW_MAX_ATTEMPTS` 限制，受 token 上限与额度限制。
- **CLI**：`python -m investment_assistant.workbench.plan_review recheck --ticker X --date YYYY-MM-DD`（同步执行，打印复查行与新版 id）。

## 9. 影子跟踪与三方对比

### 9.1 每版独立影子

- 每一版是一行 `trade_plans`，`plan-shadow-1` 原样按它自己的价位与有效期模拟；修订版 `valid_from = S+1`，所以影子只可能在生成之后成交，不回溯到信号日。
- `GET /api/workbench/plans/shadow` 的每行增加 `chain: {version_no, origin, is_head, supersedes_plan_id}`（`agent-1` 与规则 / 自定计划为 `null`），并新增 `agent_summary: {first, latest}`：`first` 只算每条链的首版（`agent-1` 计划算自己的首版），`latest` 只算每条链当前的最新版；每项给 `count`、`determined`、`expired`、`r_mean`、`r_median`，样本少于 5 个不给均值与中位数（同 roadmap 口径）。
- 周度 `review-6` 与月度 `monthly-3`：`plans.agent` = 首版，新增 `plans.agent_latest` = 快照生成时的最新版（D17）。其余口径不变。

### 9.2 三方对比

`tracks-1` 的单元集合、R 口径、状态集合不变。Agent 轨道取哪一版：

1. 单元有决定且 `agent_plan_id` 非空 → 这一版（`version_basis = 'decision'`）；
2. 有决定但 `agent_plan_id` 为空（v2.5 之前的决定）→ 该单元唯一的 `agent-1` 计划，没有则首版（`'first'`）；
3. 未决定 → 首版（`'first'`），防止用事后修订的版本美化结果。

`agent_track` 的 `run` 取生成这一版的运行。行上新增 `version_no`、`version_basis`。实际轨道（`plan_kind` 照规则 / 照 Agent / 自定）不变：照 Agent 执行时 `plan_id` 本来就是那一版。

### 9.3 决定

- `POST /api/workbench/decisions` 新增可选字段 `agent_plan_id` 与 `review_view`。单元有 `agent-2` 链时：`agent_plan_id` 缺省由后端填为当时的最新版；给了但不等于当时的最新版 → 409（`agent_plan_stale`：「Agent 计划已更新到第 n 版，请刷新后再决定」）。执行依据选「Agent 计划」时 `plan_id` 必须等于最新版且其 `status = 'ok'`。
- `review_view` = `{layout: 'agent_first' | 'legacy', baseline_expanded: bool, agent_version_no: int | null}`，由页面如实上报，只用于验收统计，不影响校验。
- 两个字段都进 `request_hash`；同一 `request_id` 重放照旧幂等。

## 10. 「今日」与推送

### 10.1 「今日」决策单元卡

默认布局「Agent 优先」：

1. **Agent 计划块**（在最前）：「Agent 计划 · 第 n 版 · 生成于 <北京时间> · 截止 <北京时间>」；动作与价位（每个价位带引用编号，可展开工具调用，同现在）、建议股数；论点 T1–T3（带引用）；每条论点下的关键反证（没有的标「反方未对此论点给出反证」）；失效条件（每条带最近一次判定：成立 / 未成立 / 无法判定）；下次复查条件；修订版显示「相对第 n−1 版」：宿主差异与模型说明并列；最近一次复查（结论、`decided_by`：「Agent」/「系统规则」、理由、时间）；「展开推导」；**常驻「证据：未验证」**。
2. **规则基线**（折叠为一行）：「规则基线 `plan-1`：入场 x–y · 止损 z · T1 w · 建议 N 股（有效 / 已作废）」+「展开」；展开后是现在的规则计划块（含「展开推导」）。
3. Agent 没有可用计划时，Agent 块只写原因，规则基线**自动展开**，不伪装成有 Agent 计划：
   - 没有成功的运行 →「Agent 未给出计划：<原因>」+「重新运行 Agent」；
   - `pass` →「Agent 不建议买入：<摘要>」；
   - 链已作废 →「Agent 已作废此计划（第 n 版）：<理由>」；
   - `agent-1` 单元 → 原样展示，标「agent-1（旧版，不参与复查）」，规则基线不折叠。
4. 决定表单：执行依据顺序改为「Agent 计划（第 n 版）/ 规则计划 / 自定价位」，Agent 可用时默认选 Agent；提交时带 `agent_plan_id` 与 `review_view`。
5. **切换回旧布局**：页头「布局：Agent 优先 / 规则优先（旧）」开关，存浏览器本地（`localStorage`，读写失败按默认布局）；旧布局 = v2.4 的顺序（规则计划块在前、Agent 块在后、都不折叠），结构化字段照样显示在 Agent 块里。

### 10.2 「今日」进行中的 Agent 计划

单元列表之后新增一段「进行中的 Agent 计划」：已决定买入（入场期等待成交）与持仓期的链，每条一行：标的 · 入场期 / 持仓期 · 第 n 版 · 最近复查（结论、时间、理由前 40 字）· 今日触发的信号 ·「查看」（`#plan/<最新版 id>`）·「重新复查」。没有链的持仓在「持仓止损」行尾标「此持仓无 Agent 计划，不参与复查」。

### 10.3 推送

- **新计划**消息：每个单元的字段改为 Agent 行在前（「Agent 第 n 版：区间 · 止损 · T1 · 股数 · 摘要 · 首条反证」），规则基线行在后（「规则基线：区间 · 止损 · T1 · 股数」）；Agent 没有可用计划时写「Agent 未给出计划（原因）」，再写规则基线。证据状态照旧。
- **新增「🔁 计划更新 · <session>」消息**：时间窗按 D25（上一次成功推送之后写入的复查记录，批处理与重新复查都算），只推结论为 `invalidate`、或 `revise` 且产生了新版的记录；维持、修订失败、跳过都不推；扩展池入场期的链不推（只影子跟踪），持仓链总是推。每条一个字段：
  - 修订：「<标的> 第 n−1 → n 版：<变化说明逐条，每条一句> · 新价位 区间 · 止损 · T1 · 有效期至」；
  - 作废：「<标的> 作废（Agent / 系统规则）：<理由>」。
  - 没有更新时不发这条消息；概览加一行「计划更新 修订 a · 作废 b」。
- 推送顺序：概览、新计划、计划更新（有时）、持仓、待处理与异常、筛选报告。`push` 阶段 `output_count` 照旧是实际发送的消息数。字段与消息的截断规则不变。

## 13. 出错与降级

| 情况 | 行为 |
| --- | --- |
| 迁移 026 未执行 | 本次按 `stages-1` 记 7 行（D22）；`agent` 阶段首版单元逐个 `skipped`（`migration_026_missing`）、解读照常、阶段 `degraded`；`errors` 一条；规则计划与推送照常；新接口 503；「今日」隐藏复查控件 |
| Agent 不可用（未配置 / 关闭） | `agent` 阶段照旧 `skipped`；`review` 阶段：宿主可判定的（失效成立、无事可看）照写，其余写 `skipped` 行，阶段 `degraded`；重新复查 409 |
| 额度用尽 / token 上限 / 超时 | 其余链写 `skipped` 行（原因同 `agent` 阶段），阶段计入 `skips` |
| 复查调用出错或输出无效 | 该链 `outcome = error`，进 `failures`；同 S 后续批处理可重试，最多 3 次 |
| 修订未通过校验 | 复查行 `revise` + `new_plan_id = NULL` + 原因；阶段 `degraded`（`revision_failed`）；不推送；「今日」与计划页显示「Agent 建议修订，但修订未通过校验（原因），当前仍为第 n 版」 |
| 重新复查与批处理撞上同一条链 | 后到的一方：批处理跳过（`review_in_progress`），重新复查 409 |
| 决定时 Agent 已出新版 | 409 `agent_plan_stale`，页面提示刷新 |
| 链标的当天日线缺失 | 信号与条件按缺失如实为 `unknown` / 不触发，`detail` 写 `bars_missing`；照常走 §7.4 |
| 某条链意外异常 | 只影响这条链（`failures` + `summary['errors']` 一条），阶段继续 |
| 新版推导核对不一致 | 同 v2.4：阶段 `degraded`，`errors` 加 `derivation_mismatch: <ticker> <plan_id>` |

### 14.1 自动化测试

- **条件集合（离线）**：每个 `kind` 在 `met` / `not_met` / `unknown` 三种事实下的判定；参数校验的边界（价格 ±50%、日期 60 天、`sessions` 1–10、未知 `kind`、多余参数）；失效专用与复查专用的使用范围。
- **`agent-2` 校验（离线）**：沿用 `check_proposal` 的六步后，论点条数、失效 / 复查条件、反证的编号对应与丢弃计数、`uncountered`、首版不得有 `changes`、修订版 `changes` 与宿主差异相等 / 不等 / 差异为空、`user:<id>` 引用存在与不存在、复查输出的三种结论与 `review_malformed`。
- **时间线纯函数（离线）**：链状态七种的判定与优先级；版本计划行的有效期（首版、入场期修订含上限、持仓期修订）、持仓期 `no_room` 时链仍有效；宿主差异；六项信号的触发与「上次复查之后」窗口（同一 T1 触及第二天不再触发）；§7.4 第 1、2 步的宿主结论；用户输入的「截止时间之前有效」（更正、撤回、晚于截止时间）。
- **Agent 图（离线，脚本化模型）**：`agent-2` 提议 + 反方产出结构化输出；修订提示词带上一版全文与用户输入；复查单阶段的工具轮数上限；提示词里用户输入块的注入防护文案。
- **批处理集成（假 fetcher + 脚本化模型，SQL）**：
  - 信号日生成首版（`agent-2`、`version_no = 0`、版本行与计划行同一事务），当次 `review` 阶段 `fresh_version`；
  - 次日：无信号 → 宿主维持（不调用模型）；默认 `next_session` → 调用模型维持；8-K / `abnormal_move` / 止损触及 / T1 触及 / 临近到期 / 区制变化各触发一次修订，新版 `supersedes` 正确、截止时间 = 运行时刻、`valid_from = S+1`、推导 `consistent`；失效条件成立 → 宿主作废，之后不再是对象；
  - 修订失败（`changes_mismatch`）→ 最新版不变、记录 `revise` + 空 `new_plan_id`；修订 `pass` → 作废；
  - 持仓期：决定买入并录入成交后链进入持仓期并照常复查；平仓后 `position_closed`；决定否决后 `closed_by_decision`；过期 `expired`；
  - 预算：超时、额度用尽、token 上限、`max_attempts` 各自的记录与阶段计数；同 session 再跑一次 → `already_reviewed`，不重复写行；
  - 每次运行恰好 8 行 `stage_runs`（定时、手动、非交易日、显式池、中途异常）；`review` 阶段计数与复查记录一致；
  - 迁移 026 未执行（测试里删掉三张表）→ 本次 `stages-1` 7 行、首版单元 `skipped`、解读与规则计划照常、`errors` 一条；
  - 链标的不在观察池时只采集、不产生候选；扩展池入场期的链排在最后复查、不推送；
  - 入场期修订版 `earnings_in_validity` → 修订未通过，最新版不变。
- **用户输入与重新复查（SQL）**：幂等与 409；更正 / 撤回后新复查只看到新行、旧版引用的旧行仍可读；重新复查截止时间 = 请求时刻、跳过第 2 步、与批处理互斥（锁被占 → 409 / `review_in_progress`）；`recheck` CLI。
- **决定与三方对比（SQL）**：`agent_plan_id` 缺省填最新版、过期版本 409、执行依据为 Agent 时 `plan_id` 必须是最新版；三方对比 `version_basis` 三种情况；`agent-1` 单元的三方对比结果与 v2.4 逐字段相同（特征测试）。
- **影子与复盘（离线 + SQL）**：每版一行影子、`agent_summary.first / latest`、样本少于 5 不给均值；`review-6` / `monthly-3` 的 `agent` 只含首版、`agent_latest` 为最新版。
- **推送（离线 + SQL）**：新计划 Agent 行在前、规则基线在后、Agent 无计划时的写法；「计划更新」只含修订（有新版）与作废、无更新时不发、概览计数；推送之后的重新复查进入下一次推送（D25）；消息顺序。
- **迁移（SQL，一次性库）**：从 001 跑到 026；三张新表的每个 `CHECK` 与唯一约束（含部分唯一索引：同链同 S 第二条有效批处理复查被拒、`skipped` 行可多条）；放宽后的约束接受新值、旧值照旧；`agent-1` 唯一索引仍生效、`agent-2` 同单元可多行；重复执行不报错；新表不在 `WORKBENCH_TABLES`。
- **CLI**：`plan_review check` 在完整、缺一条、`fresh_version`、引用不成立四种情况下的输出与退出码；`derivation stages` 对 `stages-1` 7 行、`stages-2` 8 行都通过。
- **API 契约**：新接口与新字段进 `tests/test_api_contract.py`；错误码。
- **前端（Vitest）**：Agent 计划卡各字段与「证据：未验证」常驻；规则基线折叠 / 展开 / Agent 失败时自动展开；布局开关与本地存储失败时的默认；决定带 `agent_plan_id` 与 `review_view`、409 提示；进行中的链；计划页版本链、复查记录、旧版提示；用户输入的提交、更正、撤回；重新复查按钮的可用条件与轮询；`AGENT_REASON_TEXT` 与后端一致。

### 14.2 手动触发验收

迁移 026 经授权执行、服务重启跑 v2.5 代码之后：

1. **阶段**：手动运行一次批处理 → `stage_runs` 8 行，`review` 行计数与 `plan_reviews` 一致。
2. **首版**：有新的无冲突买入单元时（没有就等下一个），「今日」Agent 计划在前，论点、反证、失效条件、下次复查条件、引用齐全；规则基线折叠一行，可展开；「证据：未验证」可见。
3. **用户输入触发**：任选一条有效链，在计划页贴入一段文本 → 点「重新复查」→ 复查记录出现，`user_input` 信号为触发；若产生新版，「相对上版变化」可读、引用 `user:<id>` 可点开、截止时间 = 点击时刻。
4. **系统信号触发**：等到一次由系统信号触发的修订（定时验收期间出现即可），核对信号证据（8-K id、候选 id 或日线）、差异与说明一致。
5. **决定**：在 Agent 优先布局下对一个单元做决定，`signal_decisions.agent_plan_id` 等于当时的最新版、`review_view` 如实；三方对比该单元 `version_basis = decision`。
6. **推送**：第一次定时运行后，Discord 的新计划 Agent 行在前；有修订或作废的那天出现「计划更新」消息，内容与 `plan_reviews` 一致。
7. **CLI**：`plan_review check --session <当日>` 通过；`derivation check --since <首日> --kind agent` 对 `agent-2` 版本全部 `consistent`。

证据追加到 `docs/roadmap/v2.5-acceptance.md`（新建，格式同 [v2.4-acceptance.md](../roadmap/v2.4-acceptance.md)）。

### 14.3 定时验收与退出条件（roadmap §4.3）

迁移执行之后：

- **连续 10 个交易日**：每天 `plan_review check --session <当日>` 通过（每份有效 Agent 计划恰有一条复查记录）；`derivation stages --session <当日>` 通过（每次运行恰好 8 行）。
- **至少一次由系统信号触发、一次由用户输入触发的修订版**：「相对上版变化」可读且引用成立（`plan_review check` 的引用核对通过）。
- **每个版本有自己的影子跟踪行**；三方对比能指出决定用的是哪一版（`version_basis`）。
- **你确认**：连续两周只读 Agent 计划（不展开规则基线）就能做决定；`signal_decisions.review_view.baseline_expanded` 的统计作为辅助证据，没有你的确认记录就不算过。

## 15. 风险

| 风险 | 应对 |
| --- | --- |
| 修订把影子结果「修好看」 | 每版独立影子、修订版只能在生成之后成交；汇总首版与最新版分开；三方对比取决定时看到的那一版，未决定取首版 |
| 模型借用户输入越权（提示词注入） | 用户输入只进证据块，提示词写明不是指令；判定（引用、价位、条件、差异）全在宿主代码；没有读写工具可被诱导 |
| 调用量上升，智谱额度先成瓶颈 | 宿主判定的维持 / 作废不调模型；扩展池排在最后、超预算即跳过；对象上限 20；沿用每日 token 上限；`detail.tokens` 每日可查（为 v2.8 运行时切换提供用量数据） |
| 失效条件写得过宽或过窄 | 条件集合有限且可判定；`unknown` 不当作成立；每条判定结果写进复查记录，复盘时可回看 |
| 同一事件天天触发修订 | 信号与复查条件只看「上次复查之后」 |
| 入场期靠修订无限延期 | 链入场上限：信号日后 10 个交易日 |
| 修订后持仓的止损与 Agent 新版不一致 | v2.5 不重新关联持仓；页面并列「当前止损（按你决定的计划）」与「Agent 第 n 版建议止损」，由你决定是否改券商单 |
| 改约束的迁移在真实库出错 | 026 只新增与放宽；单事务执行，失败整体回滚；执行前 `pg_dump` |
| 链内拆股导致修订版换算偏差 | 已知限制：影子与纪律以信号日为拆股基准；10 个交易日内拆股少见，出现时在验收记录如实标注，留 backlog |
| 「Agent 在前」被误读为「Agent 有效」 | 「证据：未验证」常驻 Agent 块与推送；规则基线始终可展开、可切回旧布局；不做自动晋升 |
