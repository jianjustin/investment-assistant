# v2.4.0 计划推导链与批处理 workflow 底座

> 2026-10-27，基线 `main@5e59705`（`v2.3.0` 之后）。路线见 [v2-visibility.md §3.2 / §3.3](../roadmap/v2-visibility.md#32-批处理-workflow-化v24-工程底座)。
> 两块内容：批处理拆成显式阶段，并只追加写入阶段证据 `stage_runs`（工程底座）；每份计划都能展开推导链，并自动校验推导与重算一致（主交付）。
> 本文是设计，不是实施授权：真实库执行迁移 025、打 tag、推送都要在执行时单独确认。

## 1. 目标

主线不变，只让计划**看得懂**：一份计划由哪条规则、哪个版本触发，当时用了哪些输入，每个价位和股数按什么公式、代入了哪些值算出来，校验结果如何。同时，批处理的每个阶段都留下证据：处理了多少、产出多少、跳过多少及原因、失败与降级、耗时、产出引用，并且挂在正确的 `run_id` 下。

成功标准（对应路线 v2.4 退出条件）：

- 每份 `status = ok` 的计划都能展开完整推导链，推导结果与已存价位逐项一致（`consistent`）。
- 每次 `workbench` 任务恰好写出 7 行阶段证据，`run_id` 等于该次运行的 `job_reports.run_id`。
- §12 的手动验收与连续 5 个交易日的定时验收都留下证据。

系统仍然只出研究候选：不下单，不接券商。所有规则都**未经验证**（Phase 0 Gate HOLD）。推导一致只说明算术正确，不说明规则有效，页面照此标注。

## 4. 阶段定义

代码里一份静态注册表 `investment_assistant/workbench/stages.py`（`STAGES`），顺序即展示顺序。字段：`id`、`title`、`purpose`（一句话说明，由后端下发，做法同 `families.py`），以及输入、输出计数的口径说明。阶段定义的版本号是 `STAGES_VERSION = 'stages-1'`：改了阶段集合或计数口径，就发新版本。

| 顺序 | `id` | 名称 | `input_count` | `output_count` | `outputs`（产出引用） | 跳过 / 降级 / 失败 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | `collect` | 数据采集 | 本次记账各族 `target_count` 之和（`bars`、`news`、`sec_filings`、`fred`），财报日的目标数单列在 `detail.earnings` | 各族 `ok_count` 之和 | `{"data_fetch_runs": [id…]}`（写入成功时） | 单只失败进 `failures`（`target` 为 `<族>:<ticker>`）；FRED 未配置进 `degradations`；SEC 整族失败进 `failures`（`target = sec_filings:*`） |
| 2 | `screen` | 筛选 `screen-1` | 范围成员数 | 当日入选数 | `{"screen_run_id": …}` | 显式池 → `skipped`（`explicit_pool`）；范围文件加载失败或 QQQ 缺当日数据、沿用成员 → `degradations`；阶段报错 → `failed` |
| 3 | `regime` | 市场环境 `regime-2` | 广度样本数 | 写入或已存的快照数（0 或 1） | `{"market_regime_id": …}` | 标签为 `insufficient` 或任一宏观序列不是 `ok` → `degradations`；快照冲突 → `degradations`（`conflict`）；异常 → `failed` |
| 4 | `signals` | 信号与候选（规则 v1） | 参与评估的标的数（池 + 持仓） | 候选数（新增 + 已存） | `{"inserted": [id…], "existing": [id…]}` | 规则跳过按 `rule_id:reason` 分组进 `skips`；单只评估异常进 `failures`；候选冲突进 `degradations`；`detail.units` 按建议动作计数 |
| 5 | `plan` | 规则计划 `plan-1` | 无冲突、未决定的买入单元数 | 计划数（新增 + 已存，含 `invalid`） | `{"inserted": [plan_id…], "existing": [plan_id…]}` | `atr_unavailable` 进 `skips`；计划冲突进 `degradations`；`detail.status` 计 `ok` / `invalid`；`detail.derivation` 见 §8 |
| 6 | `agent` | Agent 建议 | 待提议与待解读的单元数 | `ok` / `pass` 运行数 | `{"agent_run_ids": […], "plan_ids": […]}` | 逐单元跳过原因（`stage_budget`、`quota_exhausted`、`max_attempts`、`token_budget`、已完成）进 `skips`；`error` 运行与异常进 `failures`；Agent 不可用（缺 key 等）→ `skipped`（`agent_unavailable: <原因>`）；`detail.tokens`、`detail.derivation` |
| 7 | `push` | 复核与推送 | 待发消息数 | 成功发送数 | `{"push": {sent, messages, reason}}` | 手动运行 → `skipped`（`manual_run`）；今日已推送 → `skipped`（`already_pushed`）；通知关闭 → `skipped`（`task_disabled`）；没有可发消息（`no_notifications`）→ `success`，计数 `0 / 0`；发送失败（含部分失败）→ `failed`，`reason` 取 notifier 返回的原因 |

说明：

- **嵌套与交错**：筛选阶段嵌在采集窗口里（它自己采集范围日线，这部分日线记在 `collect` 的 `bars` 计数里，与 v2.3 记账一致），所以 `collect` 的时间窗口包住 `screen`。信号与计划在同一个逐只循环里交替执行，两者的 `duration_ms` 分别累计各自那段代码的耗时，`started_at` / `finished_at` 都取循环的起止。展示顺序以注册表为准，不以时间戳为准。
- **空跑**：输入为 0（例如当天没有买入单元）时记 `success`，计数 `0 / 0`，不记 `skipped`。
- **非交易日**（定时运行、纽约休市）：前 6 个阶段记 `skipped`（`not_trading_day`）；`push` 照常发休市一行（`push_closed`），按发送结果记 `success` 或 `failed`，`detail.closed = true`。
- **「复核与推送」**：包括组装今日视图（主列表、筛选单元经 `plan-1` 复核后的进入与否）与推送摘要。筛选单元的 `plan-1` 复核计划本身在 `plan` 阶段生成，这里只记推送了什么。

## 5. 阶段证据表与迁移 025

### 5.1 `stage_runs`

每次 `workbench` 任务、每个阶段追加一行，只追加，不更新，不删除：

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `BIGSERIAL` PK | |
| `run_id` | `TEXT NOT NULL` | 该次运行的 `job_reports.run_id`（harness 生成） |
| `job` | `TEXT NOT NULL` | `CHECK (job = 'workbench')` |
| `trigger` | `TEXT NOT NULL` | `CHECK (trigger IN ('scheduled', 'manual_batch'))` |
| `session` | `DATE` | 本次针对的最近已收盘交易日；非交易日同样填 `latest_closed_session(now)` |
| `stage` | `TEXT NOT NULL` | `CHECK (stage IN ('collect', 'screen', 'regime', 'signals', 'plan', 'agent', 'push'))` |
| `stages_version` | `TEXT NOT NULL` | `'stages-1'` |
| `status` | `TEXT NOT NULL` | `CHECK (status IN ('success', 'partial', 'degraded', 'failed', 'skipped'))` |
| `reason` | `TEXT` | `CHECK (status NOT IN ('skipped', 'failed') OR reason IS NOT NULL)` |
| `input_count` | `INTEGER NOT NULL` | `CHECK (input_count >= 0)` |
| `output_count` | `INTEGER NOT NULL` | `CHECK (output_count >= 0)` |
| `skips` | `JSONB NOT NULL DEFAULT '[]'` | `[{"reason": "trend_reclaim:insufficient_history", "count": 3, "samples": ["ABC", …]}]`，`samples` 最多 10 个 |
| `failures` | `JSONB NOT NULL DEFAULT '[]'` | `[{"target": "bars:MU", "reason": "…"}]` |
| `degradations` | `JSONB NOT NULL DEFAULT '[]'` | `[{"kind": "fred_not_configured", "detail": "…"}]` |
| `outputs` | `JSONB NOT NULL DEFAULT '{}'` | 产出引用，形状按阶段（§4） |
| `detail` | `JSONB NOT NULL DEFAULT '{}'` | 阶段特有的计数与说明 |
| `started_at` | `TIMESTAMPTZ NOT NULL` | 真实墙钟（可注入，同 v2.3 `wall_now`） |
| `finished_at` | `TIMESTAMPTZ NOT NULL` | `CHECK (finished_at >= started_at)` |
| `duration_ms` | `INTEGER NOT NULL` | `CHECK (duration_ms >= 0)`；来自 `deps.clock`（单调时钟），跳过的阶段为 0 |
| `created_at` | `TIMESTAMPTZ NOT NULL DEFAULT now()` | |

约束与索引：`UNIQUE (run_id, stage)`（每次运行每阶段一行，同时充当按 `run_id` 查询的索引）；`(session, stage)` 索引。

**状态判定**（纯函数 `stages.classify`）：未执行 → `skipped`（必须有 `reason`）；执行了但整体报错、没有产出 → `failed`（必须有 `reason`）；`failures` 非空 → `partial`；`degradations` 非空 → `degraded`；否则 `success`。优先级：failed > partial > degraded > success。

**原因文本**：沿用 `families.sanitize_reason`，截断到 300 字，去掉 `FRED_API_KEY`，不写任何凭据。

## 6. run_id 接通与阶段记账

### 6.1 harness 把 run_id 交给任务

根因：`tasks/_harness.run_task` 在内部生成 run_id，而 `fn()` 没有参数，任务函数拿不到它。

- `run_task` 新增参数 `pass_run_id: bool = False`。为 `True` 时，在调用之前生成 run_id 并调用 `fn(run_id)`；生成规则、记录与通知都不变。其余任务保持 `fn()`。
- `tasks/workbench.run` 用 `pass_run_id=True`，把 run_id 交给 `run_batch(run_id=…)` 与推送阶段的记账。
- `run_batch` 已有的 `run_id` 参数原本就会传给 `signal_candidates` 与 `screen_runs`，接通后它们的新行自动带上 run_id。v2.3 写 `data_fetch_runs` 时硬编码的 `run_id=None` 改为传入的 run_id。
- 手动批处理（`POST /api/workbench/run`）经 `tasks/runner.submit` 后台执行，runner 自己的 `run_id` 只用于页面轮询；所有记录一律用 harness 的 run_id，也就是 `job_reports.run_id`。CHANGELOG 写明这一点。

### 6.2 阶段记账器

新增 `stages.StageRecorder(run_id, trigger, session, wall_now, clock)`，由 `tasks/workbench.run` 创建，并作为新参数 `stages=` 传给 `run_batch`；`None`（测试、显式 `tickers` / `pool` 的调用）时完全不记，批处理行为与现在一致。`record_trigger` 继续只管 `data_fetch_runs` 与锁；`tasks/workbench.run` 两者都传。

- `recorder.stage(id)` 返回该阶段的累加器（`input` / `output` / `skip(reason, sample)` / `fail(target, reason)` / `degrade(kind, detail)` / `ref(key, value)` / `detail`），**挨着现有代码记账**，不从 `summary` 的字符串里反解析（同 v2.3 `Tally`）。
- 每个阶段结束时立即在独立事务里写这一行（写入函数仿 `collect.write_runs`），所以后面的阶段出了事，前面的证据也已经落库。
- `recorder.skip_rest(reason)`：非交易日、手动运行不推送等场景，用它把剩余阶段记为 `skipped`。
- `recorder.close(exc)`：`tasks/workbench.run` 在 `finally` 里调用。凡是没写过的阶段：有异常时记 `failed`（`reason = 'aborted: <异常摘要>'`），没有异常时记 `skipped`（`not_reached`）。保证每个 `run_id` 恰好 7 行（数据库不可达时尽力而为，见 §11）。
- 写入失败（包括迁移 025 未执行）不抛出，只汇总进 `summary['stage_status'] = {'written': n, 'error': '…'}`，**不进 `summary['errors']`**，不让记账失败把批处理标成失败。
- `_generate_rule_plan` 改为返回 `store_plan` 的结果（`status` 与记录 id），供 `plan` 阶段记账。它写 `summary` 的方式不变，这是不改行为的小重构。Agent 计划的 id 取自 `agent_runs.plan_id`。

### 6.3 护栏

- 重构前先扩展 v2.3 的批处理 `summary` 特征测试。重构后，`summary` 除新增的 `stage_status` 键之外逐字段一致；`stages=None` 时完全一致。
- 现有 `test_workbench_service`、`test_workbench_screening`、`test_workbench_scenarios` 与 v2.3 的记账测试全部照过。

## 7. 推导链

### 7.1 模块与版本

新模块 `investment_assistant/workbench/derivation.py`：

- **纯函数部分**：`derive_plan(plan, rows) -> Derivation`，输入是计划行与按 ID 回读来的原始行，输出推导结构；`derive_unit(candidates) -> Derivation`，只有触发段。不访问数据库，不调用外部源。
- **回读部分**：`load_rows(conn, plan)` 按 `inputs` 里的 ID 读取所需原始行，只读。
- **推导按代入值独立计算**：每一步都由「公式 + 已显示的代入值」直接算出结果，取整规则显式写出；**不调用** `plans.rule_levels` / `plans.size` 等计算路径，也不修改 `plans.py`。这样推导与 `plans.py` 是两份独立实现，彼此对照才有意义。
- **推导定义按 `plan_version` 注册**：`plan-1`（规则计划与自定计划）、`agent-1`（Agent 计划）。遇到未注册的版本，结论为 `incomplete`（`unknown_plan_version`）。
- **常量对齐**：推导里的常量（`ENTRY_ATR = 0.5`、`STOP_ATR = 2`、`TARGET_ATR = 4`、`TRAIL_ATR_MULTIPLE = 3`、`VALID_SESSIONS = 3`、`EARNINGS_WARN_SESSIONS = 10`、`ATR_PERIOD = 14`）在 `derivation.py` 里单独声明；测试断言它们等于 `plans.py` 的同名常量。改了公式或常量而不发新 `PLAN_VERSION`，测试就会失败。
- 推导结构自身的版本 `DERIVATION_VERSION = 'derivation-1'`，随接口返回。

### 7.2 四段结构

**① 触发**：该单元（`ticker`、`signal_date`）的全部候选，取自 `signal_candidates`，逐条给出 `rule_id`、`rule_version`、动作，以及条件逐句复核。每条规则一份条件表（来自 `rules.py` 的定义，`rule_version = '1'`），例如：

| 规则 | 条件句 | 复核用的冻结取值 |
| --- | --- | --- |
| `trend_reclaim` | `close > ma50 > ma200`；`close > ma20`；此前连续 3 日收于 MA20 之下 | `values.close`、`ma20`、`ma50`、`ma200`；第三句没有冻结取值 |
| `volume_breakout` | `close > prior_high`；`volume ≥ 1.5 × avg_volume_50`；`close > ma50` | `values.*`、`thresholds.volume_multiple` |
| `earnings_gap_up` | `gap = open / prev_close − 1 ≥ 0.03`；`close ≥ open` | `values.*`、`thresholds.gap`、`filing_ids` |

其余规则（`trend_break`、`earnings_gap_down`、`position_drawdown`、`abnormal_move`、`plan_stop`、`plan_target`、`new_filing`）同样列出条件表，用于没有计划的单元。每句条件的结果是 `holds`（冻结取值满足条件）、`violated`（冻结取值不满足）或 `not_frozen`（候选没有冻结该句所需的取值，如实标「未冻结，无法复核」）。

**限度**：候选只冻结了信号日 bar id 与取值，因此触发段只复核「已存取值满足阈值」，不从 200 根日线重算均线。`violated` 计入一致性结论（存下来的候选自称触发，取值却不满足，是缺陷）；`not_frozen` 不计入。

**② 输入快照**：按 `inputs` 里的 ID 回读，只读。这些表都只追加，按 ID 读到的就是计划生成时用的那一行（日线修订是新行，不覆盖旧行）。

| 输入 | 来源 | 展示 |
| --- | --- | --- |
| 15 根日线 | `inputs.bar_ids` → `price_bars` 按 id | 日期、开高低收、修订号；注明「拆股调整、未分红调整」 |
| 参考价 `ref_price` | 最后一根的 `close`，冻结到 6 位 | 值与来源 bar |
| 财报日 | `inputs.earnings_date_id` → `earnings_dates` | `status`、`earnings_date`、`fetched_at`；为空时显示「无记录」 |
| 资金快照 | `inputs.snapshot_id` → `account_snapshots` | `as_of`、`equity`；为空时显示「无快照（`no_equity`）」 |
| 敞口 | `inputs.exposure`（冻结值） | 该票市值、总持仓市值；注明「生成时冻结，不重算」 |
| 仓位参数 | `sizing.risk_pct`、`single_cap`、`total_cap`（冻结值） | 注明「取计划冻结值，不读当前配置」 |
| 市场环境 | `inputs.context`：`regime.id` → `market_regimes`；`sector`；`next_earnings`；`pool_tier`；`source` | 区制标签与版本、行业 ETF 与 RS20 / RS60 / 状态 |
| 筛选分组 | `inputs.context.screen`（`screen_run_id`、分组、RS、排名） | 来源为 `screen` 时显示 |
| Agent 运行（仅 Agent 计划） | `inputs.agent_run_id` → `agent_runs` | 模型、`agent_version`、`output.levels` 与引用 |

**③ 逐项计算**：每一项是一行 `{key, label, formula, substitutions, result, stored, consistent}`。`plan-1` 规则计划的计算项：

| 项 | 公式（展示文本） | 取整 |
| --- | --- | --- |
| `tr_1 … tr_14` | `max(H − L, |H − C前|, |L − C前|)`，取 15 根里的后 14 根 | 不取整 |
| `atr` | `(tr_1 + … + tr_14) / 14`（`plan-1` 只取最后 15 根日线，恰好 14 个 TR，所以 Wilder 递推退化为算术平均） | 6 位，四舍五入 |
| `ref_price` | `close(最后一根)` | 6 位，四舍五入 |
| `entry_low` / `entry_high` | `ref_price ∓ 0.5 × atr` | 分，四舍五入 |
| `stop` | `ref_price − 2 × atr` | 分，四舍五入 |
| `target1` | `ref_price + 4 × atr` | 分，四舍五入 |
| `trail_atr_multiple` | 常量 3 | — |
| `valid_from` / `valid_until` | 信号日后第 1 / 第 3 个交易日 | — |
| 财报标记 | 有效期内有已知财报 → `earnings_in_validity`（作废）；10 个交易日内 → `earnings_within_10d`；未知 → `earnings_unknown` | — |
| `per_share_risk` | `ref_price − stop` | 不取整 |
| `risk_amount` | `equity × risk_pct` | 不取整 |
| `cap_risk` / `cap_single` / `cap_total` | `⌊risk_amount / per_share_risk⌋`；`⌊(equity × single_cap − ticker_value) / entry_high⌋`；`⌊(equity × total_cap − total_value) / entry_high⌋` | 向下取整 |
| `shares` 与 `applied_cap` | 三者取最小，并给出是哪一个 | — |
| `sizing.status` | `no_equity` / `no_room`（≤ 0）/ `sized`（风险上限生效）/ `capped` | — |
| `status`、`invalid_reasons`、`warnings` | 作废原因 = 财报作废 + `no_room`；提示 = 财报提示 + 区制 / 行业提示（`regime_risk_off`、`regime_unavailable`、`sector_weak`） | — |

自定计划（`kind = own`，`plan-1`）：四个价位标「你的输入」，不重算，只校验顺序；`per_share_risk` 用入场区间中点 `(entry_low + entry_high) / 2` 作参考价；规则计划的作废原因降级为提示，`status` 恒为 `ok`；`atr` 能从日线算出就算，否则取规则计划的值，再否则为 0，并标出取自哪一种。

Agent 计划（`kind = agent`，`agent-1`）：四个价位标「Agent 引用」，核对已存价位等于 `agent_runs.output.levels.<key>.value`，并列出每个价位的引用；仓位同样用入场区间中点；`atr` 无法计算时为 0，并注明「移动止损退化为保本」。

**④ 校验**：价位顺序 `stop < entry_low ≤ entry_high < target1`、作废原因、提示，以及由③得出的 `status`。

**证据状态**（每份推导都带，页面常驻）：「规则 v1 与 `plan-1` 都未经验证（Phase 0 Gate HOLD）。推导一致只说明算术正确，不说明规则有效。」

**运行证据**：查 `plan` / `agent` 阶段行里 `outputs` 新增计划 id 包含该计划的那一行，给出 `run_id`、阶段状态与 `detail.derivation`。不用候选的 `run_id` 去找，因为候选可能在更早一次运行就已写入。v2.4 之前生成的计划显示「v2.4 之前生成，无阶段证据」；迁移 025 未执行时显示「迁移 025 未执行」。

### 7.3 一致性结论

`consistency = {status, mismatches, missing}`：

- `consistent`：③ 的每个可重算项（以及 Agent 计划的引用核对）`result == stored`，并且触发段没有 `violated`。
- `mismatch`：至少一项不相等，`mismatches` 列出 `{key, result, stored}`。
- `incomplete`：缺少推导所需的行（日线 id 回读不到、`bar_ids` 不是 15 个、`snapshot_id` 或 `earnings_date_id` 指向的行不存在、Agent 运行不存在），或版本没有推导定义；`missing` 列出缺什么。

比较口径：数值都转成 `Decimal` 后精确比较（`trade_plans` 的 `NUMERIC(18,6)`、`sizing` JSON 里的数值字符串），`shares` 比整数，日期比日期，原因与提示比集合。

## 8. 一致性校验（三处共用 `derive_plan`）

1. **接口**：每次展开都现算并返回 `consistency`（§9）。
2. **批处理**：`plan` 阶段结束后，对本次 `outputs` 里的全部计划（新增 + 已存）在只读事务中回读并推导，计数写进 `detail.derivation = {checked, consistent, mismatch, incomplete, items: [{plan_id, status}]}`；`agent` 阶段对本次新增的 Agent 计划同样处理。出现 `mismatch` 或 `incomplete` 时，该阶段至少记 `degraded`（`degradations` 加 `derivation_mismatch`），并在 `summary['errors']` 追加 `derivation_mismatch: <ticker> <plan_id>`。这是缺陷，应该进运行报告。校验自身抛异常同样处理（原因写进 `degradations`）。校验只读，不改变已存计划，也不影响推送内容。
3. **CLI**（只读）：
   - `python -m investment_assistant.workbench.derivation check --since 2026-10-28 [--until …] [--kind rule|own|agent]`：逐份输出 `plan_id`、标的、日期、`kind`、`status`、一致性结论；末行汇总；有任何 `status = ok` 的计划不是 `consistent` 时退出码为 1。
   - `python -m investment_assistant.workbench.derivation stages --session 2026-10-28`：按 `run_id` 分组列出该 session 的阶段行（阶段、状态、计数、原因）。检查两件事：每个 `run_id` 恰好 7 行，且在 `job_reports` 里存在；该 session 收盘之后、下一交易日收盘之前开始的 `workbench` 运行报告，都有阶段行（没有的列为「缺证据」）。任一项不满足时退出码为 1。

## 9. 接口与只读性

分层：`api/routes/workbench.py`（薄封装）→ `workbench/derivation.py` 与 `workbench/stages.py`（用例与纯函数）→ `workbench/repository.py`（新增 SQL）。

| 接口 | 返回 | 读写 |
| --- | --- | --- |
| `GET /api/workbench/plans/{plan_id}/derivation` | 完整推导结构（§7）+ `consistency` + `run` + `evidence` + `derivation_version` | 只读 |
| `GET /api/workbench/units/{ticker}/{signal_date}/derivation` | 只有触发段（无计划单元用）+ 该单元已有计划的 id 列表 | 只读 |
| `GET /api/workbench/stage-runs?session=YYYY-MM-DD` 或 `?run_id=…` | 原样返回证据行，按运行分组、按注册表顺序排列；附 `STAGES` 定义与 `stage_runs_ready` | 只读 |

- 错误码：`plan_id` 不是合法 UUID → 400；计划不存在 → 404；`ticker` 不过 `data.identity.stock_id` 或日期非法 → 400；单元没有候选 → 404；`stage-runs` 两个参数都缺或都给 → 400；数据库不可用 → 503（沿用 `Unavailable` 文案）。
- **只读性**：用例都在只读事务里执行（psycopg `read_only = True`）；读取从不调用外部数据源，缺行如实标 `incomplete`，不在读取时补拉。测试断言：调用前后各表行数不变；在只读连接上尝试写入会失败。
- 推导接口不依赖 `stage_runs`：迁移 025 未执行时照常返回推导，`run = {"ready": false}`。

## 10. 前端

- **类型与格式化**：`lib/derivation.ts`（接口类型、结论文案、条件句结果的文案、取整说明）；接口函数加进 `lib/api.ts`。

- **降级**：接口 503 时显示后端给的原因；404 显示「计划不存在」；`run.ready = false` 显示「迁移 025 未执行，暂无阶段证据」。

## 11. 出错与降级

| 情况 | 行为 |
| --- | --- |
| 数据库未配置 / 不可达 | 三个接口返回 503；批处理照旧抛 `Unavailable`；`recorder.close` 尽力补写，写不进去就只记 `stage_status.error`（此时 `job_reports` 也写不进，两者一致缺失） |
| 仅 `stage_runs` 缺失（025 未执行） | 批处理照常完成，`summary['stage_status'].error` 说明原因、`errors` 不变；推导接口照常，`run.ready = false`；`stage-runs` 接口返回 `stage_runs_ready = false` 与空列表 |
| 推导所需的行缺失 | 该计划结论为 `incomplete`，列出缺失项；页面照常展示能展示的部分 |
| 计划版本未注册推导 | `incomplete`（`unknown_plan_version`） |
| 批处理中推导校验不一致 / 校验异常 | 阶段记 `degraded`，`summary['errors']` 加一条，运行报告状态随之为 `error`；计划与推送不受影响 |
| 某阶段中途抛异常 | 已完成的阶段已落库；该阶段与后续阶段由 `recorder.close` 记 `failed`（`aborted: …`） |
| 阶段证据写入失败 | 只记 `stage_status`，不改批处理成败 |

### 12.1 自动化测试

- **推导纯函数（离线）**：用 `plans.build_rule_plan` / `build_own_plan` / `build_agent_plan` 生成多组计划（`sized`、`capped`（单票上限与总上限各一）、`no_room`、`no_equity`、财报作废、10 日内财报提示、财报未知、区制 `risk_off`、行业偏弱、筛选来源、自定计划在规则计划作废时的降级、Agent 计划 `atr = 0`），推导逐项与生成结果一致，结论为 `consistent`。篡改一个已存价位 / 股数 / 原因 → `mismatch` 且指出该项；去掉一根日线或资金快照行 → `incomplete`；未知版本 → `incomplete`。推导常量等于 `plans.py` 常量。触发段：每条规则的条件表在满足、不满足、取值未冻结三种情况下的结果。

## 13. 风险

| 风险 | 应对 |
| --- | --- |
| 在批处理里插记账代码引入回归 | 特征测试先行；`stages=None` 时完全不记；记账只读局部变量，不改控制流；写入失败不抛出 |
| 推导与 `plans.py` 是两份实现，日后改公式时漂移 | 常量对齐测试；推导按 `plan_version` 注册，未注册即 `incomplete`；批处理每天校验，漂移当天就进运行报告 |
| 推导「复用」`plans.py` 导致自证循环 | 规定推导按代入值独立计算，不调用 `plans` 的计算函数（只允许复用交易日历等基础设施） |
| 新表误入 `WORKBENCH_TABLES`，迁移前停掉主线 | 明确不加，有测试断言 |
| 一致性校验把旧计划的数据问题报成缺陷 | 批处理只校验本次 `outputs` 里的计划；历史计划经 CLI 逐份核对并如实记录，不改历史数据 |
| 不一致进 `errors` 让运行报告变 `error`、触发告警 | 这是有意为之：不一致就是缺陷；只限推导校验，记账写入失败不进 `errors` |
| 触发段被误读为「规则已重算」 | 条件句逐句标 `holds` / `violated` / `not_frozen`，并在页面说明只复核冻结取值 |
