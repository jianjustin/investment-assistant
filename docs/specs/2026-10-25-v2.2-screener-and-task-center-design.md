# v2.2.0 每日筛选（纳指 100）与任务中心自描述

> 2026-10-25，基线 `main@691641c`（`v2.1.0` 之后）。两项：任务中心统一北京时间、每个定时任务自带说明；工作台批处理每天从纳指 100 筛出一批适合波段交易的股票，自动进扩展池，用 `plan-1` 复核，出筛选报告。
> 本文是设计，不是实施授权：真实库执行迁移 023、打 tag、推送都在执行时单独确认。

---

## 1. 目标

1. **任务中心自描述**：所有定时任务按 `Asia/Shanghai` 调度和显示；每个任务都有 `?` 说明，说明由后端注册表下发。
2. **每日筛选**：观察名单现在只有 8 只（全在核心池），规则 v1 很少触发，大多数日子只有「观察」。批处理每天收盘后从纳指 100 筛出一批，触发买入规则的优先，形态好的补齐，自动进扩展池；`plan-1` 复核通过的可以直接在「今日」决定；推送和页面给出筛选报告。

成功标准：

- 任务中心、运行记录、「设置 → 定时任务」显示的时间都是北京时间，标「北京」；三个任务的 `timezone` 都是 `Asia/Shanghai`；每个注册任务都有说明，缺说明的测试会失败。
- 每个交易日的批处理都写一份 `screen_runs`，推送多一条「筛选报告」；筛选来源、当天有有效规则计划的单元进待决定列表，标「筛选」。
- 区制改按纳指 100 ∪ 手动名单计算广度，脱离「样本不足」。
- §9 的手动验收和定时验收都留下证据。

系统仍然只出研究候选：不下单、不接券商；价位是规则的算术结果，不是投资建议，推送照旧标注「证据：未验证」。

## 4. 任务中心：北京时间与自描述

### 4.1 时区

- 迁移 023 把 `filings` 改为 `Asia/Shanghai 09:30`，并重算 `next_run_at`，只改 `timezone = 'America/New_York'` 的行：

  ```sql
  UPDATE scheduled_jobs
     SET timezone = 'Asia/Shanghai', time_local = '09:30',
         next_run_at = (
           SELECT min(ts) FROM (
             SELECT (((now() AT TIME ZONE 'Asia/Shanghai')::date + d) + time '09:30') AT TIME ZONE 'Asia/Shanghai' AS ts
               FROM generate_series(0, 7) AS d) s
            WHERE ts > now() AND extract(isodow FROM ts AT TIME ZONE 'Asia/Shanghai') BETWEEN 1 AND 5)
   WHERE name = 'filings' AND timezone = 'America/New_York';
  ```

  不把 `next_run_at` 置空：置空会让调度器在下一个 tick 立即运行一次。这里直接写入下一个北京 09:30（周一至周五）。北京 09:30 全年都落在美东 20:30 之后（夏令时 21:30、冬令时 20:30），盘后 SEC 披露都能赶上。
- 迁移种子 007 的默认值不改（新装库从 001 跑到 023 也会被 023 改掉）。
- 改完后：`workbench` 06:30 周二至周六，`workbench_review` 08:00 每天，`filings` 09:30 周一至周五，都是 `Asia/Shanghai`。

### 4.2 显示

- `web/src/lib/format.ts` 新增 `fmtBeijing(value)`：用 `Intl.DateTimeFormat('zh-CN', {timeZone: 'Asia/Shanghai', hour12: false, ...})` 格式化为 `YYYY-MM-DD HH:mm:ss 北京`。浏览器在哪个时区都显示同样的值。
- 「工具」的任务中心（下次 / 上次 / 最近调度检查 / 本轮开始）、运行记录（运行时间、详情里的开始和结束）、「设置 → 定时任务」改用它。其他页面的 `fmtTime` 不动。
- 任务中心「计划」列显示为「06:30 北京 · 周二至周六」：`weekday_mask` 转成中文（`1-5` → 周一至周五，`1-7` → 每天，`2-6` → 周二至周六，其他写法逐个列出）；`timezone` 不是 `Asia/Shanghai` 时显示原时区名并标「非北京时区」。

### 4.3 自描述

- 新增 `investment_assistant/tasks/catalog.py`：

  ```python
  JOB_INFO: dict[str, dict] = {
      'workbench': {'title': ..., 'goal': ..., 'details': [...], 'manual_note': ...},
      ...
  }
  ```

  每个 `REGISTRY` 里的任务一条。`GET /api/jobs/scheduled` 每个任务加 `description`（没有条目时为 `null`，前端不显示 `?`）。
- 内容按现状写：
  - `workbench`（每日批处理）：采集日线、资讯、财报日、SEC 列表、行业 ETF、FRED → 纳指 100 筛选 → 市场环境 → 规则 v1 → 规则计划 → Agent 轨道 → 推送 Discord；纽约休市日跳过并推一行；手动运行针对最近一个已收盘交易日、不推送。
  - `workbench_review`（复盘）：影子跟踪、三方对比、纪律指标、周度复盘、月度收益；周 / 月复盘推送；手动运行不推送。
  - `filings`（SEC 监控）：按 [SEC 采集](../features/sec-filings.md) 的现状写监控范围、正文事实、Bot 直发、历史去重；按日期运行可回补。实施时以 `tasks/filings.py` 的实际行为为准，不沿用前端旧文案。
- 前端删掉 `JOB_HELP` 常量，`?` 弹窗读 `description`。
- 测试：`REGISTRY` 的每个键在 `JOB_INFO` 里都有非空的 `goal` 和至少一条 `details`。

## 5. 筛选范围与 `screen-1`

### 5.1 范围文件

- `config/universes/nasdaq100.json`：`{"name": "nasdaq100", "as_of": "YYYY-MM-DD", "source": "<官方名单出处>", "tickers": [...]}`。实施时按纳斯达克官方成分股名单填写，`as_of` 写名单日期。
- 同一公司的多类股票只留一个（`GOOGL` 留，`GOOG` 去掉），文件注释写明。
- 加载时校验：每个代码过 `data/identity.py`；去重后不足 90 只或多于 105 只视为文件错误。
- `as_of` 距批处理日超过 120 天，记 `universe_stale` 提示，照常运行。
- 已在手动观察名单里的股票不参加筛选，它们本来就每天在跑。

### 5.2 采集

- 对范围内、不在观察池里的股票只采**日线**和**财报日**，复用 `workbench/bars.py`、`earnings.py` 的增量采集和修订规则，写进 `price_bars`、`earnings_dates`。
- 入选进池之后，按观察池的现有流程补采资讯和 SEC 列表；同一次运行里已采过的日线不重复采。
- 首次运行回补约 300 根日线（一次性，报告里记耗时）。

### 5.3 `screen-1`

阈值事先固定，不调参；改阈值就发新版本，旧结果保留原版本。

| 步骤 | 条件 | 未通过时 |
| --- | --- | --- |
| 数据 | ≥ 200 根日线、截止时间前有当日日线、复权因子正常 | 记跳过原因（同规则 v1），不算「未通过」 |
| 流动性 | 20 日平均成交额（`close × volume`）≥ 5000 万美元 | `illiquid` |
| 财报 | 截止时间前已知的下次财报日落在之后 5 个交易日内 | `earnings_soon`；财报日未知只加提示 `earnings_unknown`，不排除 |
| 触发组 | 规则 v1 中 `trend_reclaim` 或 `volume_breakout` 当日触发，且没有卖出候选 | — |
| 形态组 | 不在触发组；收盘 > MA50 > MA200，且 ATR14 / 收盘 ∈ [2%, 6%] | `no_setup` |
| 排序键 | RS = ½(r20 − r20(QQQ)) + ½(r60 − r60(QQQ))，r 用 `adj_close` | QQQ 缺数据时整次筛选记 `benchmark_missing`，按 §9.3 处理 |
| 入选 | 触发组按 RS 降序全部优先，再按 RS 降序从形态组补齐；当天新入选 ≤ 20 只 | 落选记 `rank_cut` |

- MA、ATR 的口径和规则 v1、`plan-1` 一致（同一份 `price_bars` 当前修订，ATR14 Wilder）。
- 范围内的规则只用来判断触发组：结果写进 `screen_results.trigger_rules`，**不写** `signal_candidates`。入选进池之后，规则 v1 在池内照常运行，写候选和计划。
- 理由（写进功能文档）：纳指 100 的成分股流动性好、数据稳定；财报前不开新仓，因为跳空会穿过止损；ATR 太小吃不到波段，太大会让 2 ATR 止损过宽、仓位被压到很小；RS 同时看 20 日和 60 日，兼顾近期势头和中期持续性；每天 ≤ 20 只控制 Agent 消耗和推送长度。

## 6. 池成员与轮换

### 6.1 筛选成员

当天的筛选成员 = 下列三类的并集，减去手动观察名单里已有的：

1. 今天新入选的（≤ 20 只）；
2. 保留期内的：最近一次入选距今 ≤ 10 个交易日（含当天）；
3. 锁定的：有有效期内、未作废的规则计划或自定计划，或者当前有持仓。

### 6.2 上限与挤出

- 筛选成员 ≤ `min(40, 100 − 手动观察池数)`。
- 超出时按优先级保留：锁定 → 今天入选 → 保留期内按最近入选日由新到旧、同日按当日排名。挤出的记入 `summary.screen.evicted`。
- 锁定的股票永远不挤出。锁定数本身超过上限时，照常保留并记 `screen_locked_over_cap`，当天不新增。

### 6.3 分层

- 筛选成员一律 `tier = extended`、`source = screen`，不占核心池名额。
- 观察池 = `pool.from_watchlist(...)` 的结果并上筛选成员；`Pool` 增加 `sources: dict[str, str]`，`tier_changes` 在 `tier`、`sector_etf`、`source` 任一变化时追加一行。
- 手动加入观察名单的股票，`source` 从 `screen` 变成 `watchlist`（追加一行）；之后从名单删除，就按 §6.1 重新判断是否仍是筛选成员。
- 移出写 `tier = removed`，和现有逻辑一致。某只股票某天在不在池里、因为什么在，按「`effective_session <= 该日` 且 `recorded_at <= 截止时间`」的最新一行还原。

## 7. 复核与决定

### 7.1 复核

筛选成员进池之后和其他扩展池股票一样：补采资讯和 SEC 列表，跑完整的规则 v1、`plan-1` 和 Agent 轨道。复核结论就是 `plan-1` 的结果：

| 结论 | 条件 |
| --- | --- |
| 有效计划 | 规则计划写入且 `invalid_reasons` 为空 |
| 作废 | 写入但有 `invalid_reasons`（`earnings`、`no_room` 等），原样列出 |
| 冲突 / 回避 | 决策单元标记冲突或回避，不生成计划 |
| 等待触发 | 只有观察候选，或没有候选 |

### 7.2 决定资格

- `_unit_is_extended` 改为：信号日 `tier = extended`、不是持仓，并且**不是**「`source = screen` 且当日规则计划有效」。
- 结果：筛选来源一旦出现有效规则计划，就按主列表对待：进待决定列表和推送，Agent 排进 `main_buy` 做「提议 + 反方」，页面和推送里标「筛选」。保留期内的成员哪天触发，也一样。
- Agent 在规则计划全部写入之后才分组，所以资格在 Agent 之前就已经确定。

### 7.3 冻结与复盘

- 计划 `inputs.context` 增加 `source` 和 `screen`（`screen_run_id`、分组、RS、排名）。
- `review.pool_of` 从 core / extended 扩成 **core / screen / extended**：`source = screen` 的计划归 `screen`，不论它有没有进主列表。周度复盘、三方对比、纪律指标按三类分组。没有 `source` 的旧计划按原规则归类。
- 影子跟踪不改。

## 8. 市场环境 `regime-2`

- 观察池每天会变，池内广度会跟着名单波动。广度的样本改为**纳指 100 范围 ∪ 手动观察池**（当日有 K 线的），`adj_close` 口径、MA50 / MA200 / 52 周新高新低的算法不变。
- 区制阈值不变（样本 < 20 只为「样本不足」，60% / 50% 进攻，40% / 30% 防守）。
- `REGIME_VERSION` 升到 `regime-2`，`inputs.tickers` 记录实际样本；旧快照保留 `regime-1`。
- 范围文件加载失败时，退回只用手动观察池，记 `regime_universe_missing`。

## 9. 报告、推送、页面与出错

### 9.1 推送：第 5 条消息「筛选报告」

放在现有 4 条之后，同一交易日推送成功就不重复推；手动运行不推送；字段截断 1024、单条 ≤ 6000 字符的规则照旧。

- 概览：`screen-1` · 范围 n · 通过过滤 m · 今日入选 k（触发 a / 形态 b）· 筛选成员 j / 上限 · 移出 r；提示（`universe_stale` 等）。
- **今日触发 → 复核**：每只一行，代码 · 规则 · RS · 复核结论；有效计划写「入场 x–y · 止损 z · T1 w · 建议 N 股」，作废写原因。有效计划同时出现在「新计划」消息里，标「筛选」。
- **形态候选（等待触发）**：按 RS 前 10 只，代码 · RS · ATR%；其余写「另 N 只见页面」。
- 筛选未运行时，这条消息写「筛选未运行：原因」，并列出沿用的成员数。

### 9.2 页面与 API

- 「今日」：市场环境卡片下加「筛选」卡片，内容同推送，形态候选列全；可决定的筛选单元在待决定列表里带「筛选」标签。
- 「设置 → 关注列表」：表头加「· 筛选 j / 上限」。
- API：
  - `GET /api/workbench/screen?session=`：当次 `screen_runs` 与全部 `screen_results`（含未入选），缺省为最近一次。
  - `POST /api/workbench/screen/replay`，body `{"sessions": N}`（1 ≤ N ≤ 20，默认 5）：§11.2 的只读回放。
  - `GET /api/workbench/today` 增加 `screen` 摘要。
- 命令行：`python -m investment_assistant.workbench.screen replay [--sessions N]`。
- 运行报告 `summary.screen`：`status`、`run_id`、入选、各步过滤计数、跳过原因、`evicted`、提示、耗时。

### 9.3 出错

| 情况 | 处理 |
| --- | --- |
| 范围文件缺失或校验失败 | 跳过筛选，`screen.status = error`；成员只保留锁定和保留期内的，不新增；批处理继续；推送如实写原因 |
| QQQ 缺当日数据 | 同上，原因 `benchmark_missing` |
| 单只股票采集失败 | 记入 `summary.sources` 和该股跳过原因，不算「未通过过滤」 |
| 筛选步骤耗时 > 600 秒 | 记 `screen_over_budget`，不中断；总预算仍是 1800 秒 |

### 11.2 手动触发验收

1. **真实批处理**：执行迁移 023 后，「今日」点「立即运行批处理」（针对上一交易日，不推送）。核对：`summary.screen.status = success`；`pool_tiers` 出现 `source = screen` 的行；「今日」筛选卡片和 `GET /api/workbench/screen` 一致；有效计划的筛选单元进待决定列表并标「筛选」；`summary.regime` 为 `regime-2` 且不再是「样本不足」。
2. **回放（只读）**：真实批处理之后（第一次批处理才会回补范围内的日线），在真实库上 `POST /api/workbench/screen/replay {"sessions": 5}`（或命令行）。对上一交易日及之前共 N 个交易日，逐日只用当日及以前的日线跑 `screen-1`，返回 N 份筛选报告；**不写** `screen_runs`、`pool_tiers`、计划，不推送。核对：每份都有范围数、过滤计数、触发组与形态组、RS 排名；同一股票相邻日的入选变化说得通。已知局限：财报日用的是当前已知值，不是当时的时点值，报告里标注。
