# 每日计划：规则 → 交易计划 → 推送

每天早上收到一份交易计划：价位能追溯到规则和数据，由你决定采纳还是否决、自己下单并录入成交。系统只给研究候选，不自动下单、不接券商；所有规则都**未经验证**（Phase 0 Gate HOLD），推送里会如实标注。

设计：[工作台](../specs/2026-10-23-us-research-workbench-design.md)、[P1 规则计划与推送](../specs/2026-10-23-p1-rule-plans-and-push-design.md)。

## 每日流程

| 时间（北京） | 发生什么 | 你要做的 |
|---|---|---|
| 周二至周六 06:30 | 任务 `workbench`：采集日线、资讯、财报日、SEC 列表、行业 ETF、FRED；跑纳指 100 筛选（成员自动进扩展池，见[观察池](pool-and-context.md)）；记录各数据族拉取结果；生成市场环境；对最近收盘交易日跑规则；生成规则计划；跑 Agent 轨道；对每份有效 Agent 计划做每日复查（见下文[每日复查](#每日复查)）；推送；记录 8 个阶段的证据（`stage_runs`，每次运行恰好 8 行；迁移 026 未执行时按 `stages-1` 记 7 行，见[调度与通知](../operations/scheduling-and-notifications.md)）。纽约休市日跳过，推一行「纽约休市，未运行」 | 无 |
| 早上 | 打开「今日」：每只股票每天一个决策单元，显示候选规则、输入值、Agent 计划（默认在前，见下文[「今日」：Agent 优先](#今日agent-优先)）、规则基线、解读（支持 / 反证 / 冲突，带引用）、近期财报与资讯；筛选来源的单元带「筛选」标记；单元列表之后是进行中的 Agent 计划 | 采纳 / 否决 / 降级为观察，写一句理由；采纳时选执行依据：Agent 计划（第 n 版）、规则计划或自定价位 |
| 成交后 | 「复盘 → 交易与持仓」录入成交（本机时区），关联当时的决定 | 录错就「作废」并写理由，再重新录入 |

「今日」右上可「立即运行批处理」：手动运行总是针对最近一个已收盘的交易日（纽约 17:00 后算当天收盘），**不推送**。

## 规则 v1

阈值事先固定，不用历史数据调参；改阈值就发新版本，旧信号保留原版本和输入。

| 规则 | 动作 | 条件 |
|---|---|---|
| 趋势回踩修复 `trend_reclaim` | 买入 | 收盘 > MA50 > MA200，且收盘重新站上 MA20，此前至少连续 3 天在 MA20 下方 |
| 放量突破 `volume_breakout` | 买入 | 收盘创前 20 日收盘新高，成交量 ≥ 前 50 日均量 × 1.5，收盘 > MA50 |
| 财报跳空向上 `earnings_gap_up` | 买入 | 8-K Item 2.02 后第一个交易日，开盘较前收盘跳空 ≥ +3%，收盘 ≥ 开盘 |
| 跌破 MA50 `trend_break` | 卖出 | 此前至少连续 10 天收在 MA50 上方，当日跌破 |
| 财报跳空向下 `earnings_gap_down` | 卖出 | 财报后第一个交易日跳空 ≤ −3%，收盘 ≤ 开盘 |
| 持仓回撤 `position_drawdown` | 卖出 | 仅限没有计划的持仓：收盘较成本跌 ≥ 8%，或较持仓以来最高收盘回撤 ≥ 12% |
| 新财报 `new_filing` | 观察 | 当日出现新的 10-Q / 10-K / 8-K |
| 异常波动 `abnormal_move` | 观察 | 日收益绝对值 ≥ 近 20 日波动率 × 2.5，且当日无新财报 |

- 财报时点按 SEC 受理时间（UTC）判断：盘后发布算下一个交易日，盘前算当天，盘中发布不触发跳空规则。批处理用 SEC 列表补全缺失的受理时间和 Item，只补空值、不覆盖；仍缺受理时间的财报只能触发「新财报」。
- 不足 200 根日线、当日缺日线或复权因子异常时，价格规则不产出候选，并在运行报告记录跳过原因，不写成「无信号」。
- 同一天同时出现买入和卖出候选，标记「冲突」，默认观察；没有持仓的卖出候选标记「回避」。

## 交易计划 `plan-1`

为「建议买入、无冲突、未决定」的单元生成：

| 字段 | 规则 |
| --- | --- |
| 参考价 | T 日收盘 |
| ATR | ATR14（Wilder，拆股调整口径） |
| 入场区间 | 参考价 ± 0.5 ATR |
| 止损 | 参考价 − 2 ATR |
| 目标 T1 | 参考价 + 4 ATR（2R） |
| 有效期 | T+1 至 T+3 个交易日 |
| 建议仓位 | min(资金 × `risk_pct` ÷ 每股风险，单票上限，总持仓剩余空间)；缺资金快照时只给每股风险并标 `no_equity`；没有空间就作废（`no_room`） |
| 财报 | 有效期内有财报则计划作废；之后 10 个交易日内有财报，或日期未知、已过，则加提示 |
| 市场环境 | 冻结进 `inputs.context`；防守区制、快照失败、行业弱势只加提示，不改价位 |

价位四舍五入到 0.01。重跑结果相同就返回原计划；结果不同则记入运行报告的冲突列表，不覆盖原计划。采纳时提交自定价位，会另存一份 `own` 计划，和决定在同一事务里写入，建议股数按新价位重算。

## 计划推导

每份计划的价位都能只用它 `inputs` 指向的已存行重算出来（只读回读，按 id 取行，修订过的新行不会被误取）。批处理在 `plan`、`agent` 与 `review` 阶段结束前对本阶段产出的计划（`review` 为本次修订出的新版）做一次核对，计数写进阶段行的 `detail.derivation`；有计划判为 `mismatch` / `incomplete` 时该阶段记 `degraded`，运行报告的 `errors` 多一条 `derivation_mismatch: <标的> <计划id>`——已存计划、推送内容与其他阶段不受影响。

页面入口在「今日」：规则计划块与 Agent 计划块各有「展开推导」，没有计划的单元显示「触发依据」（只渲染触发段），都是点开后才请求，展开状态不进地址。展开后顶部是一致性结论（一致 / 不一致 / 不完整，后两者列出差异与缺失项）与常驻的证据状态说明，下面四段——①触发（每条候选一张条件表：条件句 · 冻结取值 · 结果）、②输入快照（参考价、财报、资金快照、敞口、仓位参数、区制与行业，15 根日线表默认折叠）、③逐项计算（项目 · 来源 · 公式 · 代入 · 结果 · 已存 · 一致，TR 明细默认折叠）、④校验——底部是生成这份计划的运行证据（`run_id`、阶段状态、推导核对计数；迁移 025 未执行或 v2.4 之前生成的计划会如实说明）。数字按后端字符串原样显示，前端不重算、不再取整。

- API（只读）：`GET /api/workbench/plans/{plan_id}/derivation`、`GET /api/workbench/units/{ticker}/{signal_date}/derivation`。错误码：输入非法 400、计划或单元不存在 404、数据库不可用 503（页面直接显示后端原因）。

命令行核对（只读，两个子命令都在只读事务里执行，时间按北京时间显示）：

```bash
.venv/bin/python -m investment_assistant.workbench.derivation check --since 2026-10-28 [--until 2026-10-31] [--kind rule|own|agent]
.venv/bin/python -m investment_assistant.workbench.derivation stages --session 2026-10-28
```

- `check`：逐份列出 `plan_id`、标的、信号日、种类、`status`、一致性结论（`consistent` / `mismatch` / `incomplete`）与差异明细，末行汇总；`--until` 按信号日截止（含当日），`--kind` 只看一种计划。任何 `status = ok` 的计划不是 `consistent` 时退出码 1（作废计划照常列出，不影响退出码）。
- `stages`：按 `run_id` 分组列出该 session 的阶段行（阶段、状态、计数、推导计数、原因）。核对三件事：每个运行按自己的阶段版本行数齐全（`stages-1` 7 行、`stages-2` 8 行，阶段集合也按版本核对）、每个运行都在 `job_reports` 里、时间窗（当日纽约 16:00 到下一交易日纽约 16:00 之间开始）内的 `workbench` 运行报告都有阶段行——没有的列为「缺证据」。任一项不满足，或 `stage_runs` 表还没建（迁移 025 未执行），退出码 1。
- 两个子命令参数错误或数据库不可用时退出码 2。
- 验证一次推导：手动运行批处理后，在「今日」任选一份计划点「展开推导」，顶部显示「推导与重算一致」，触发段每条条件标「成立」或「未冻结，无法复核」，底部运行证据的 `run_id` 与该次运行报告一致；CLI `check --since <当日>` 对同一计划的结论相同。
- 已知限制：触发段只复核冻结取值——候选没有冻结的取值如实标「未冻结，无法复核」，不从原始日线重算均线；「推导一致」只说明算术正确，不说明规则有效（证据状态说明常驻每份推导）。

## 每日复查

批处理的第 7 个阶段 `review`（「每日复查」，在 `agent` 之后、`push` 之前，设计见 [v2.5 计划时间线 §7](../specs/2026-10-28-v2.5-plan-timeline-design.md#7-每日复查阶段-review)）对每条有效的 `agent-2` 计划链做一次复查，每条链每个交易日至多一条有效批处理复查记录（`plan_reviews`）。

- **对象**：链状态为入场期（`entry`）或持仓期（`holding`）的链；当天刚生成的版本不复查（`fresh_version`，生成本身就是当天的记录），当天已有有效批处理复查的不再复查（`already_reviewed`）。顺序：持仓期在前，然后主列表入场期，扩展池入场期最后，各自按最新版截止日、再按标的；超过 20 条的记 `object_cap`。已作废、已否决、已平仓、已过期的链不复查，计入阶段 `detail.ended`；持仓所在单元完全没有 `agent-2` 链的列在 `detail.holdings_without_chain`（链在持仓期间被作废等已结束的不算「无链」）。
- **链标的只采集**：有效链的标的若已不在观察池与持仓里，批处理在逐只采集之后单独采集它的日线、资讯、财报日，并计入 SEC 列表，**不跑规则**（不产生候选、单元、计划或推送）；运行报告 `pool.chains` 记这类标的数，`collect` 阶段计数照常包含它们。
- **信号与条件**：宿主只读取截止时间之前的数据，判定七项系统信号（`new_8k`、`abnormal_move`、`stop_touched`、`t1_touched`、`expiry_near`、`regime_change`、`user_input`，窗口是「上次有效复查之后」）以及最新版的失效条件与下次复查条件（`met` / `not_met` / `unknown`，数据缺失不当作成立；当天日线缺失时 `detail.bars_missing`），全部写进复查记录。
- **结论顺序**：① 任一失效条件成立 → 系统规则作废（「失效条件成立：<条件文案>」），不调用模型；② 没有信号、没有新的用户输入、复查条件都未满足 → 系统规则维持（「无新信号，复查条件未满足（<条件文案>）」），不调用模型；③ 预算闸门（批处理开始 1500 秒后 `stage_budget`、Agent 不可用、本次已遇额度用尽 `quota_exhausted`、当日 token 上限 `token_budget`）→ 写 `skipped` 记录；同链同日已有 3 条 `skipped` / `error` 记录后不再写行，只在阶段 `skips` 记 `max_attempts`；④ 一次 `agent-review-1` 单阶段复查（`agent_runs.mode = review`，工具按复查交易日取数，信号日的原始触发由宿主写进证据块），输出无效或模型出错 → `error` 记录；⑤ 维持 / 作废照写；⑥ 修订 → 完整的提议 + 反方 + 校验（`mode = revise`）：通过则新计划行、新版本行（`origin = review`，有效期复查日 S+1 至 S+3，入场期不晚于信号日后第 10 个交易日）、修订运行、复查运行与复查记录同一事务写入；校验不过、入场期新版按规则作废（如有效期内有财报，`plan_invalid: earnings_in_validity`）或出错 → 记录为 `revise`、没有新版、`detail.revision_status` 写原因，最新版不变，阶段 `degraded`（`revision_failed`）；修订时改口不买（`pass`）→ 作废（`detail.via = revision_pass`）。持仓期的新版即使按仓位规则作废（`no_room`）也成为最新版，链照常复查。
- **互斥**：每条链的复查全程（读取、调用模型、写入）在一条不经连接池的专用连接上持有会话级 advisory lock `review-run:<标的>:<信号日>`，读取与写入事务里另有事务级锁 `review:<标的>:<信号日>`；任一把被占（正在重新复查）时本次跳过（`review_in_progress`），不写行，也不调用模型。写入前核对链仍有效、最新版没变；模型调用期间链被改动（如提交了不买的决定）时不写复查记录，但模型运行记为 `skipped`（`review_in_progress`）并带 token，计入每日上限。模型调用期间不占用数据库事务。阶段 `detail.excluded` 逐链记下未复查的链与原因（`fresh_version`、`already_reviewed`、`object_cap` 与无行跳过），供 `plan_review check` 核对。
- **阶段证据**：`review` 行的输入 = 复查对象数，产出 = 有效复查记录数，`outputs` 列出复查记录、新版计划与复查 / 修订运行的 id，`detail` 有各结论与 `decided_by` 计数、信号触发次数、入场 / 持仓对象数、`ended`、`holdings_without_chain`、token 与新版推导核对；Agent 不可用但有对象时宿主可判定的照写、其余写 `skipped`、阶段 `degraded`（`agent_unavailable`），没有对象时整阶段 `skipped`（`agent_unavailable: <原因>`）。迁移 026 未执行时本阶段不运行，本次按 `stages-1` 记账。
- **验证一次**：手动运行批处理后，`stage_runs` 该 `run_id` 有 8 行，`review` 行的输出计数等于 `plan_reviews` 里该交易日 `trigger = batch` 的有效记录数；信号日当天的新链只出现在 `review` 行的 `skips`（`fresh_version`）里，次一交易日才有复查记录。

## 「今日」：Agent 优先

「今日」的决策单元卡默认按「Agent 优先」排列（设计见 [v2.5 §10](../specs/2026-10-28-v2.5-plan-timeline-design.md#10-今日与推送)；链、版本与复查的含义见 [Agent 轨道 · 计划时间线](agent-track.md#计划时间线)）：

- **Agent 计划块在前**：「Agent 计划 · 第 n 版 · 生成于 <北京时间> · 截止 <北京时间>」；动作与价位（每个价位带引用编号，点开看工具调用）、建议股数；论点 T1–T3（带引用，`user:<id>` 引用只显示、不可点）；每条论点下的关键反证，反方没有给出的标「反方未对此论点给出反证」；其他风险；失效条件，每条带最近一次复查的判定（成立 / 未成立 / 无法判定；还没复查过、或最近一次复查正是产生本版的那次时写「尚未复查」）；下次复查条件（空 = 「下一交易日」）；修订版显示「相对第 n−1 版」：宿主差异（如「止损 95.00 → 96.00」）与模型的变化说明并列；最近一次复查（结论、「Agent」/「系统规则」、理由、时间）；修订未通过时写「Agent 建议修订，但修订未通过校验（原因），当前仍为第 n 版」；持仓期的新版按仓位规则作废（如 `no_room`）时写「本版按仓位规则不能加仓（原因）」，不当作计划作废；「展开推导」；「证据：未验证」常驻。条件文案与后端 `agent/conditions.py` 的模板逐字一致（区制标签保留 `risk_on` / `neutral` / `risk_off` 原值），数字按后端字符串原样显示。
- **看推理过程**：计划卡底部「看推理过程」（取生成这一版的 Agent 运行 id，「今日」与计划页共用，版本链里点开的每一版都有）展开 Agent 推理阅读视图，展开时才请求。按时间顺序一步一个小节，标题带概念：提议者读了什么（每次工具调用一行「call:N · 工具 · 参数 · 哈希前 8 位」，「看返回值」展开，列表默认只显示条数与首尾各 2 行，结果字段名旁可展开概念）→ 提议（动作、价位、论点、失效 / 复查条件）→ 校验结果 → 反方读了什么 → 反方（逐条反证、其他风险、丢弃数、无反证的论点）→「回应」（本版之后的复查记录；没有写「回应：本版之后还没有复查」）→ 生成的计划（状态与推导一致性）。论点、价位、反证里的 `call:N` 可点，滚动并高亮到那次调用；`user:<id>` 只显示。修订运行与复查运行前面多一步「触发这次运行的复查」（信号、条件判定、给模型的用户输入，并可再展开那次复查 / 修订自己的运行）。`get_concept` 调用标「概念卡随代码版本走，不受截止时间约束」；被作废的运行只保留已记录的工具调用，没存的步骤写「这次运行作废：<原因>，只保留工具调用」；校验项逐项列出，作废时只标「可能未通过」的范围，不推断哪些通过了；`agent-1` 旧运行按原样降级显示。后端接口与步骤定义见 [Agent 轨道 · 推理阅读视图](agent-track.md#推理阅读视图)。
- **计划卡上的概念**：版本、截止时间、动作与价位、引用编号、论点、反方、失效 / 下次复查条件、相对上版、最近复查、「证据：未验证」、`agent-1` 旧版、修订未通过原因、「本版按仓位规则不能加仓」旁各有一个可点开的概念名（`ConceptTerm`），规则基线与版本链（来源、链状态、复查结论、信号、条件判定、用户输入、影子状态）、推导视图（一致性、证据说明、每张候选表的规则名、输入快照、逐项计算的项目列、运行证据）同样；「今日」决定表单的「执行依据」也挂了。版本链每条复查记录另有「看复查推理」（`review_agent_run_id`）与「看修订推理」（`revision_agent_run_id`），有才显示。
- **规则基线折叠为一行**：「规则基线 `plan-1`：入场 x–y · 止损 z · T1 w · 建议 N 股（有效 / 已作废）」+「展开」，展开后是原来的规则计划块（含「展开推导」）与「收起」。
- **Agent 没有可用计划时规则基线自动展开、不能收起**，Agent 块只写原因：没有成功的运行 →「Agent 未给出计划：<原因>」+「重新运行 Agent」；`pass` →「Agent 不建议买入：<摘要>」；链已作废 →「Agent 已作废此计划（第 n 版）：<理由>」；Agent 计划行按规则作废时同样展开；`agent-1` 单元原样展示、标「agent-1（旧版，不参与复查）」，规则基线不折叠。没有 Agent 运行的单元（卖出、观察）只显示规则计划。
- **解读不重复**：`agent-1` 与 `agent-2` 的解读只显示「解读见 Agent 建议」，摘要与首条反证已在 Agent 块里。
- **执行依据**：顺序为「Agent 计划（第 n 版）/ 规则计划 / 自定价位」；Agent 计划可用时默认选 Agent，否则规则计划，再否则自定价位。
- **提交决定**：迁移 026 就绪时带上页面显示的 `agent_plan_id` 与 `review_view`（当前布局；本次会话里该单元的规则基线是否展开过，自动展开与旧布局都算展开；Agent 版本号），字段含义见下文[决定记录看到的 Agent 版本](#决定记录看到的-agent-版本)；迁移 026 未执行（`today.timeline_ready = false`）时两项都不带。返回 409 `agent_plan_stale` 时只显示冒号后的文案「Agent 计划已更新到第 n 版，请刷新后再决定」并给「刷新」：刷新后保留草稿理由，换一个新的 `request_id`（页面换成新版后请求内容也变了）。
- **布局开关**：页头「布局：Agent 优先 / 规则优先（旧）」，存在浏览器本地（`localStorage` 键 `workbench.today.layout`，值 `agent_first` / `legacy`）；读写失败（隐私模式、禁用存储）一律按默认「Agent 优先」，切换只在本页生效。旧布局 = v2.4 的顺序：规则计划块在前、Agent 块在后，都不折叠，结构化字段照样显示在 Agent 块里。

- **重新复查**（「今日」与计划页同一做法）：提交后轮询 `/api/runs/<run_id>`，最长 900 秒（复查加修订常超过 2 分钟）；完成显示「复查完成：<结论>」（跳过或出错时附原因，如「复查完成：跳过（超出 token 上限）」）并刷新；轮询到时限仍未结束时显示「复查仍在后台进行，稍后刷新查看」，按钮保持不可点，不当作失败；409 显示「不能重新复查：<原因>」（正在复查 / 这条链不在入场期或持仓期 / Agent 不可用：<原因>）。

- **降级**：迁移 026 未执行（`timeline_ready = false`）时隐藏「进行中的 Agent 计划」、「重新复查」与无链持仓的标注，规则计划与 Agent 原有内容照旧显示。

## 决定记录看到的 Agent 版本

决定（`signal_decisions`）另记两项（设计见 [v2.5 §9.3](../specs/2026-10-28-v2.5-plan-timeline-design.md#93-决定)），都进 `request_hash`（只在提交了才进，v2.5 之前的请求重放仍幂等），同一 `request_id` 重放照旧返回原决定：

- `agent_plan_id`：决定时页面显示的 Agent 版本。单元有 `agent-2` 链时不填就由后端填为当时的最新版；填了但不是最新版 → 409，不写决定，返回 `{"error": "agent_plan_stale: Agent 计划已更新到第 n 版，请刷新后再决定"}`（n 为最新版的版本号）；不属于该单元 → 400。没有链的单元（`agent-1` 或只有规则计划）不自动填，填了必须是该单元自己的 Agent 计划。
- `review_view`：`{layout: agent_first | legacy, baseline_expanded: bool, agent_version_no: int | null}`，页面如实上报，只用于验收统计，不影响校验；多余字段或取值不对 → 400。
- 执行依据选「Agent 计划」时，`plan_id` 必须是链的最新版且 `status = ok`；指向链上的旧版同样按过期返回 409，最新版已作废（如持仓期 `no_room`）→ 400，改选规则计划或自定价位。
- 迁移 026 未执行时，带这两个字段的决定返回 503「迁移 026 未执行」；不带的规则 / `agent-1` 决定照常写入（这时还不可能有 `agent-2` 链）。

## 持仓止损

持仓的计划取「当前未平仓批次中最近一笔、且其决定关联了计划的买入」。有计划的持仓用 `plan_stop`（T 日最低价 ≤ 当前止损）和 `plan_target`（开仓以来首次触及 T1，卖出一半，只触发一次）；触及 T1 之后，当前止损 = max(开仓以来最高收盘 − 3 ATR, 持仓成本)，收盘后更新、次日生效。没有计划的持仓仍按 `position_drawdown` 判断。

## 推送

定时运行在批处理之后，把当日简报推到 Discord（默认 `signals` 频道），按顺序发：概览（含市场环境、扩展池新计划数、「计划更新 修订 a · 作废 b」）、新计划（核心池 + 持仓与可决定的筛选单元；筛选来源的计划字段名带「【筛选】」前缀）、计划更新（有更新时才发）、持仓、待处理与异常、筛选报告（概览 / 今日触发 → 复核 / 形态候选前 10 只，形态列全要看页面；筛选未运行时写原因与沿用成员数）。平常五条，有计划更新时六条；`push` 阶段的产出计数是实际发送的消息数。没有新计划也推送；同一交易日已成功推送就不再重复；推送失败只写进运行报告，下次推送附「上次推送失败」。单个字段截断到 1024 字符，单条消息不超过 6000 字符（超出的整字段丢弃，末尾注明「其余 n 条见系统」）。

- **新计划的字段**（设计见 [v2.5 §10.3](../specs/2026-10-28-v2.5-plan-timeline-design.md#103-推送)）：有 Agent 结果的单元，Agent 行在前、规则计划作为「规则基线：区间 · 止损 · T1 · 股数」在后（不写风险金额）。`agent-2` 写「Agent 第 n 版：区间 · 止损 · T1 · 股数 · 摘要 · 反证：<首条反证>」（n 是链的最新版）；链已作废写「Agent 已作废此计划（第 n 版）：<理由>」；Agent 没有可用计划（出错、跳过、校验作废等）写「Agent 未给出计划（<原因>）」；不建议买入照旧写「Agent（模型）不建议买入；摘要」；`agent-1` 单元保留原来的 Agent 行，末尾标「agent-1（旧版，不参与复查）」。Agent 简报（`agent-1`、`agent-2`）的摘要和反证已经在 Agent 行里，不再重复附在计划后面。没有 Agent 结果的单元（卖出、观察等）照旧只写规则计划。证据状态「证据：未验证」照旧。
- **「🔁 计划更新 · <交易日>」**：列出时间窗内写入的复查记录（批处理与重新复查都算），只推作废和产生了新版的修订，每条一个字段：
  - 修订：「<标的> 第 n−1 → n 版：<变化说明逐条> · 新价位 区间 · 止损 · T1 · 有效期至 <日期>」，变化说明取修订运行输出的 `changes`；
  - 作废：「<标的> 作废（Agent / 系统规则）：<理由>」。
  - 维持、修订失败（没有新版）、跳过、出错都不推；扩展池入场期的链不推（只影子跟踪），持仓期的链总是推。
  - 时间窗（D25）：起点是上一次成功的、交易日早于本次的每日推送读取复查记录的时刻（`job_reports` 里 `workbench` 的 `summary.push.sent = true`，取 `summary.push.reviews_until`；没有这个键的旧记录取报告时间 `created_at`；休市日那一行不算），终点是本次推送读取复查记录的时刻（写进本次的 `summary.push.reviews_until`），只取复查交易日不晚于本次的记录；从未成功推送过时只取本交易日的记录。推送之后才做的重新复查——包括推送发送期间、运行报告落库之前写入的——下一次推送照样会推。手动「重新推送今日计划」（`POST /api/workbench/push`）不写运行报告，不移动时间窗；同一交易日重推时起点不变，内容只会多出此后新写入的记录。迁移 026 未执行时不发这条消息，概览也不写「计划更新」一行。

## 入口与验证

- 页面：「今日」（决策单元、Agent 计划块与折叠的规则基线、布局开关、进行中的 Agent 计划与「重新复查」、持仓止损、市场环境、「重新推送今日计划」）；「标的」（单只股票的 K 线图（MA20/50/200 与成交量，最多 250 根日线）、日线、候选、计划与决定历史，页尾「Agent 计划」与「我的补充」）；计划页 `#plan/<id>`（`agent-2` 计划另有版本链、复查记录、「重新复查」与「我的补充」）。
- API：`GET /api/workbench/today`、`POST /api/workbench/decisions`（`plan_id` 与 `own_plan` 二选一；可选 `agent_plan_id`、`review_view`，见上文）、`GET /api/workbench/instruments/{ticker}`、`GET/POST /api/workbench/trades`、`POST /api/workbench/trades/{id}/void`、`POST /api/workbench/push`。
- 运行报告：`job_reports` 中 `workbench` 的 `summary`，包括 `tickers.<T>`（日线、资讯、候选、跳过原因）、`plans`（`inserted` / `existing` / `conflict` / `skip: 原因`）、`earnings`、`push`、`sources`（按数据源列出失败）、`timings`、`pool.chains`（只采集不跑规则的链标的数）、`review`（复查对象数、各结论条数、token）。
- 验证一次：手动运行批处理后，运行报告里 `plans.<T> == "inserted"`；「今日」显示「入场区间 x–y · 止损 z · T1 w · 建议 N 股」和「证据：未验证」；点「重新推送今日计划」，页面提示「已推送 N 条」，`push.sent == true`。
- 验证 Agent 优先：有 `agent-2` 链的单元，「今日」先显示「Agent 计划 · 第 n 版」块，下面是一行「规则基线 plan-1：…」；点「展开」看到完整规则计划；页头切到「规则优先（旧）」后顺序反过来、都不折叠，刷新页面仍保持；提交决定后 `signal_decisions.review_view` 记下当时的布局与是否展开过。

## 数据与时点

- 日线保存 yfinance `auto_adjust=False` 的开高低收（已按拆股调整、未按分红调整）和全复权收盘价；数据源改了数值就追加一个修订版本，不覆盖旧值。
- 规则、计划和解读只用运行截止时间之前已入库的数据；资讯发布时间未知时显示「发布时间未知」，不用获取时间代替。
- 资讯只存标题和链接，不抓正文。
- 这不是严格的历史时点回测：yfinance 的历史数据会被修订，只能保证「本系统开始采集之后」的记录能按时点还原。

## 已知限制

- 免费资讯源不稳定：`Ticker.get_news` 已被 Yahoo 改成 404，现在改用搜索接口；运行报告里 `news.fetched` 为 0 时，说明它又失效了。
- 样本小、信号重叠多，统计没有推断意义。
- 价位是你所设规则的算术结果，不是投资建议。
