# 每日计划：规则 → 交易计划 → 推送

每天中午前（北京时间周二至周六 11:30 开始运行）收到一份交易计划：价位能追溯到规则和数据，由你自己下单并录入成交（v2.9 起没有采纳 / 否决按钮，采纳由成交推出）。系统只给研究候选，不自动下单、不接券商；所有规则都**未经验证**（Phase 0 Gate HOLD），推送里会如实标注。

设计：[工作台](../specs/2026-10-23-us-research-workbench-design.md)、[P1 规则计划与推送](../specs/2026-10-23-p1-rule-plans-and-push-design.md)。

## 每日流程

| 时间（北京） | 发生什么 | 你要做的 |
|---|---|---|
| 周二至周六 11:30 | 任务 `daily`（一张 LangGraph 图，十个节点，见下文[十个节点](#十个节点)）：SEC 监控 → 数据采集（含纳指 100 范围成分的日线与财报日）→ 筛选（成员自动进扩展池，为新成员补采资讯与 SEC，见[观察池](pool-and-context.md)）→ 市场环境 → 规则信号 → 规则计划 → Agent 轨道 → 每日复查（见下文[每日复查](#每日复查)）→ 推送 → 复盘（复盘卡检测与周 / 月复盘，见下文[复盘卡检测](#复盘卡检测)）。每个节点写一行证据（`stage_runs`，每次运行十条有效行；续跑追加 `attempt` 行，见[调度与通知](../operations/scheduling-and-notifications.md)）。纽约休市日 `push` 之前的八个节点跳过，推一行「纽约休市，未运行」，`retro` 仍判断周 / 月复盘 | 无；出错时会收到一条「每日工作流失败」通知 |
| 早上 | 打开「今日」：一张计划表（入场期 / 持仓中 / 已结束三组，见下文[「今日」：计划表与 Agent 计划卡](#今日计划表与-agent-计划卡)），每行写明开盘落在区间内 / 高开 / 低开各做什么、本计划何时作废；展开一行看候选规则、输入值、Agent 计划（默认在前）、规则基线、解读（支持 / 反证 / 冲突，带引用）、近期财报与资讯；筛选来源的单元带「筛选」标记 | 照着计划在券商下单；想给自己留句话就写备注（备注不进 Agent）；想让 Agent 参考用「我的补充」 |
| 成交后 | 「复盘 → 交易与持仓」录入成交（本机时区），关联当时照着做的计划（见[成交与备注](#成交与备注v29)） | 录错就「作废」并写理由，再重新录入 |
| 交易结束后 | 「复盘 → 复盘卡」出现新卡（待审定），下一次每日推送概览写「复盘卡 上次推送后新增 a · 待审定 b」 | 逐条审定教训草稿（可改、可不采纳），采纳的进「知识 → 我的知识」 |

「今日」右上可「立即运行批处理」（也就是手动运行 `daily`）：总是针对最近一个已收盘的交易日（纽约 17:00 后算当天收盘），**不推送**（`push` 记 `skipped: manual_run`），周 / 月复盘只生成不推送。另一次执行正在进行时返回「每日工作流正在运行」（409）。

### 十个节点

| # | 节点 | 做什么 | 整节点跳过 |
|---|---|---|---|
| 1 | `sec_monitor` | 扫描 SEC 观察名单的申报、归档原文、提取正文事实，Bot 直发通知并去重（见 [SEC 采集](sec-filings.md)） | 休市 |
| 2 | `collect` | 日线、资讯、财报日、SEC 列表、行业 ETF、FRED、纳指 100 成分；每个请求连接 10 秒、总 30 秒，失败按目标重试 2 次 | 休市 |
| 3 | `screen` | 读库选取成员入扩展池；为当天新入池的成员补采资讯与 SEC | 显式池、休市 |
| 4 | `regime` | 市场环境 `regime-2` | 休市 |
| 5 | `signals` | 规则 v1 信号（与 `plan` 在同一个逐只循环里、每只一个事务） | 休市 |
| 6 | `plan` | 规则计划 `plan-1`；本节点重新推导核对，循环里计划部分的耗时在 `detail.timings.in_signals_ms` | 休市 |
| 7 | `agent` | Agent 建议；时间预算从本节点开始计 | 休市、Agent 不可用 |
| 8 | `review` | 每日复查，与 `agent` 共用预算窗口 | 休市 |
| 9 | `push` | 推送每日计划 / 休市一行 | `already_pushed`、`task_disabled`、`manual_run` |
| 10 | `retro` | 复盘卡与周 / 月复盘 | `not_due` |

**两层自动重试**：每个外部请求按目标重试 2 次（退避 2 秒、8 秒，4xx 不重试，见[外部请求策略](data-menu.md)），单个目标失败不拖住节点；节点抛出没人接住的异常时，等 60 秒自动重试一次，第一次的错误记进该行 `detail.retry`；再失败就停在该节点，它后面的节点各记一行 `skipped / upstream_failed`，运行状态为失败，并发一条失败通知。数据库连不上不重试。区制计算出错也会停链（信号依赖当天区制）。

**续跑**：失败的运行可以从失败的节点继续（运行详情页的「从此节点继续」，`POST /api/jobs/daily/resume`，命令行 `python -m investment_assistant.tasks.daily resume --run-id … --node …`）：已完成的节点不重跑，截止时间和交易日沿用原运行，只给重新执行的节点追加 `attempt` 更大的行；下一个交易日纽约 17:00 之后只能整次重新运行。只有「停链」的失败才能续跑：节点重试后仍失败而停在检查点上。节点自己记了 `failed` 行、链却照常跑完的失败（Discord 推送没发出去、整段 `review` 失败、复盘卡或筛选整段失败）检查点没有下一个节点，运行状态是失败，但详情页写「这一步记了失败但链已跑完，不能续跑；需要时整次重新运行」，失败通知里也没有「续跑」一行。

**运行状态**：由十个节点的有效行推出：有失败 → 失败；有 `partial` / `degraded` → 降级；否则成功。降级是常态（例如 FRED 没配置），不发通知；失败发通知。

## 运行详情

每次运行都有一页详情（`#tools/runs/<run_id>`），回答「这次运行每个节点做了什么、出了什么错、能不能接着跑」。设计见 [v2.8 每日工作流 §7](../specs/2026-10-29-v2.8-daily-workflow-design.md)。

**入口**：「工具 → 运行记录」每一行的「详情」；「今日」运行一览标题旁的「运行详情」链接；「立即运行」后出现的「运行详情」链接；失败通知里的链接（`workbench.public_url` 配置了才带）。命令行 `python -m investment_assistant.tasks.daily show --run-id …` 打印同一份节点表（状态、耗时、`attempt`、失败目标数，不含原始摘要）。

**页面**：
- 顶部一句话 `headline`（与「今日」运行一览是同一个函数：失败时「10 月 29 日的运行在「数据采集」失败（已自动重试 1 次）：…；其后 8 个节点未执行」，续跑后加「（第 2 次执行，从「…」续跑）」）、元信息（任务、触发、交易日、截止时间、`daily-1` / `stages-4`）和执行记录（一次运行有多次执行时逐次列出：首次执行与每次续跑，各一行 `job_reports`）。
- 节点状态图：十个格子，颜色之外有图标与文字（成功 / 降级 / 部分成功 / 失败 / 跳过 / 未开始 / 运行中）；重新执行过的节点角标「×2」；点格子展开下面的三块。
- ①做了什么：运行一览同一套句子、输入与产出、跳过与降级原因、自动重试说明；失败节点下方是「从此节点继续」。
- ②拉取详情（`sec_monitor`、`collect`、`screen` 三个节点）：按数据族分组，每个目标一行——结果、尝试次数、失败类别与原文、行数、最新时点、耗时；默认只展开失败目标。
- ③结果详情：每类至多 200 项（`total` 是真实数，超出标「只显示前 n 项」）——SEC 申报、入选成员、区制快照、信号候选、规则计划、Agent 运行（链到推理视图与计划，失败或次数用完的单元有「重新运行 Agent」）、每日复查、推送、复盘卡与周 / 月复盘。
- 底部折叠的「原始摘要」就是该运行最新一行 `job_reports.summary`。

**续跑与重跑**：
- 「从此节点继续」只在 `resume.allowed` 时出现（失败的运行、检查点停在该节点、还没过下一个交易日纽约 17:00、没有别的执行占着锁）；点开确认后每 5 秒刷新直到状态不再是「运行中」。不能续跑时页面给出原因：这次运行没有失败的节点 / 只能从失败的节点继续 / 已过截止时间只能整次重新运行 / 每日工作流正在运行；运行中途中断（节点没写完行，或还留着「上游节点失败」的旧行）时原因是 `interrupted`，只能整次重新运行。
- 「重新运行 Agent」：某个单元最近一次 Agent 运行是 `error`，或因次数用完（`max_attempts`）跳过时出现；另一次每日工作流正在运行时按钮不出现（那次执行可能正在处理同一个单元），`propose` 重跑也会被拒绝（409 `daily_running`）。点击重置这个单元该模式的尝试次数（只追加一条记录，`request_id` 幂等），`propose` 立即重跑一次，`interpret` 只重置，由同一交易日的续跑或手动运行执行（下一次定时运行已是新的交易日，不会用到）。该单元已经在重置之后就不再显示按钮。「今日」计划页上同样有这个入口。

**状态**：`success` / `degraded` / `failed` 由有效行推出；有行但还没有这次执行的运行报告、而 `daily:run` 锁被占时是 `running`（页面轮询）；本进程正在执行的运行（定时、手动、续跑都在 API 进程里）一进入执行就算 `running`，不必等它写出下一行；执行到一半进程被杀、没有写完十个节点的运行显示 `failed`，不能续跑，只能整次重新运行。

**旧运行**：v2.8 之前的批处理运行（`stages-1` 到 `stages-3`，7 / 8 / 9 个阶段）按各自的阶段列表画，拉取详情只有失败的目标（注明「这次运行早于目标级明细」），没有续跑与重跑按钮；SEC、回补等没有节点证据的运行只显示原始摘要。

**只读**：详情接口（`GET /api/runs/{run_id}/detail`，`run_id` 形如 `daily-20261030033000-1a2b3c4d`；格式不对 400、没有这次运行 404、库没就绪 503）全程在只读事务里读已经记下的行和检查点的下一个节点，不调用任何外部数据源，不碰 Agent 连接，也不会改变任何东西。

## 规则 v1

阈值事先固定，不用历史数据调参；改阈值就发新版本，旧信号保留原版本和输入。

| 规则 | 动作 | 条件 |
|---|---|---|
| 趋势回踩修复 `trend_reclaim` | 买入 | 收盘 > MA50 > MA200，且收盘重新站上 MA20，此前至少连续 3 天在 MA20 下方 |
| 放量突破 `volume_breakout` | 买入 | 收盘创前 20 日收盘新高，成交量 ≥ 前 50 日均量 × 1.5，收盘 > MA50 |
| 财报跳空向上 `earnings_gap_up` | 买入 | 8-K Item 2.02 后第一个交易日，开盘较前收盘跳空 ≥ +3%，收盘 ≥ 开盘 |
| 跌破 MA50 `trend_break` | 卖出 | 此前至少连续 10 天收在 MA50 上方，当日跌破 |
| 财报跳空向下 `earnings_gap_down` | 卖出 | 财报后第一个交易日跳空 ≤ −3%，收盘 ≤ 开盘 |
| 持仓回撤 `position_drawdown` | 卖出 | 仅限没有计划的持仓：收盘较成本跌 ≥ 8%，或较持仓以来最高收盘回撤 ≥ 12% |
| 新财报 `new_filing` | 观察 | 当日出现新的 10-Q / 10-K / 8-K |
| 异常波动 `abnormal_move` | 观察 | 日收益绝对值 ≥ 近 20 日波动率 × 2.5，且当日无新财报 |

- 财报时点按 SEC 受理时间（UTC）判断：盘后发布算下一个交易日，盘前算当天，盘中发布不触发跳空规则。批处理用 SEC 列表补全缺失的受理时间和 Item，只补空值、不覆盖；仍缺受理时间的财报只能触发「新财报」。
- 不足 200 根日线、当日缺日线或复权因子异常时，价格规则不产出候选，并在运行报告记录跳过原因，不写成「无信号」。
- 同一天同时出现买入和卖出候选，标记「冲突」，默认观察；没有持仓的卖出候选标记「回避」。

## 交易计划 `plan-1`

为「建议买入、无冲突、未决定」的单元生成：

| 字段 | 规则 |
| --- | --- |
| 参考价 | T 日收盘 |
| ATR | ATR14（Wilder，拆股调整口径） |
| 入场区间 | 参考价 ± 0.5 ATR |
| 止损 | 参考价 − 2 ATR |
| 目标 T1 | 参考价 + 4 ATR（2R） |
| 有效期 | T+1 至 T+3 个交易日 |
| 建议仓位 | min(资金 × `risk_pct` ÷ 每股风险，单票上限，总持仓剩余空间)；缺资金快照时只给每股风险并标 `no_equity`；没有空间就作废（`no_room`） |
| 财报 | 有效期内有财报则计划作废；之后 10 个交易日内有财报，或日期未知、已过，则加提示 |
| 市场环境 | 冻结进 `inputs.context`；防守区制、快照失败、行业弱势只加提示，不改价位 |

价位四舍五入到 0.01。重跑结果相同就返回原计划；结果不同则记入运行报告的冲突列表，不覆盖原计划。录入成交时选「自定」并提交自己的价位，会另存一份 `own` 计划，和成交在同一事务里写入，建议股数按新价位重算。

### `plan-2`：规则基线带执行字段（v2.9）

自 v2.9 起每个无冲突的买入单元生成的规则计划是 `plan-2`：价位、有效期、仓位、财报与市场环境规则**逐字沿用 `plan-1`**（推导里这些步骤与 `plan-1` 一一相同），另写入两个执行字段 `entry_type = zone_limit`（区间限价，见[入场类型](../knowledge/concepts/plan.entry_type.md)）与 `max_hold_sessions = 10`（见[最长持有](../knowledge/concepts/plan.max_hold.md)），`inputs.entry_rules_version = 'entry-1'`。推导注册 `('plan-2', 'rule')`，除 `plan-1` 的步骤外多核对这两个字段等于常量。上线之前生成的 `plan-1` 行不重算、不补字段，仍按 `('plan-1', 'rule')` 推导；同一单元重跑不比较 `plan-1` 与 `plan-2`。

该标的已有活跃链时，单元照常生成 `plan-2`，计划行 `inputs.active_chain = {ticker, signal_date}` 标出并入了哪条链（见下节）。

## 计划推导

每份计划的价位都能只用它 `inputs` 指向的已存行重算出来（只读回读，按 id 取行，修订过的新行不会被误取）。批处理在 `plan`、`agent` 与 `review` 阶段结束前对本阶段产出的计划（`review` 为本次修订出的新版）做一次核对，计数写进阶段行的 `detail.derivation`；有计划判为 `mismatch` / `incomplete` 时该阶段记 `degraded`，运行报告的 `errors` 多一条 `derivation_mismatch: <标的> <计划id>`——已存计划、推送内容与其他阶段不受影响。

页面入口在「今日」：规则计划块与 Agent 计划块各有「展开推导」，没有计划的单元显示「触发依据」（只渲染触发段），都是点开后才请求，展开状态不进地址。展开后顶部是一致性结论（一致 / 不一致 / 不完整，后两者列出差异与缺失项）与常驻的证据状态说明，下面四段——①触发（每条候选一张条件表：条件句 · 冻结取值 · 结果）、②输入快照（参考价、财报、资金快照、敞口、仓位参数、区制与行业，15 根日线表默认折叠）、③逐项计算（项目 · 来源 · 公式 · 代入 · 结果 · 已存 · 一致，TR 明细默认折叠）、④校验——底部是生成这份计划的运行证据（`run_id`、阶段状态、推导核对计数；迁移 025 未执行或 v2.4 之前生成的计划会如实说明）。数字按后端字符串原样显示，前端不重算、不再取整。

- API（只读）：`GET /api/workbench/plans/{plan_id}/derivation`、`GET /api/workbench/units/{ticker}/{signal_date}/derivation`。错误码：输入非法 400、计划或单元不存在 404、数据库不可用 503（页面直接显示后端原因）。

命令行核对（只读，两个子命令都在只读事务里执行，时间按北京时间显示）：

```bash
.venv/bin/python -m investment_assistant.workbench.derivation check --since 2026-10-28 [--until 2026-10-31] [--kind rule|own|agent]
.venv/bin/python -m investment_assistant.workbench.derivation stages --session 2026-10-28
```

- `check`：逐份列出 `plan_id`、标的、信号日、种类、`status`、一致性结论（`consistent` / `mismatch` / `incomplete`）与差异明细，末行汇总；`--until` 按信号日截止（含当日），`--kind` 只看一种计划。任何 `status = ok` 的计划不是 `consistent` 时退出码 1（作废计划照常列出，不影响退出码）。
- `stages`：按 `run_id` 分组列出该 session 的阶段行（阶段、状态、计数、推导计数、原因）。核对三件事：每个运行按自己的阶段版本行数齐全（`stages-1` 7 行、`stages-2` 8 行、`stages-3` 9 行，阶段集合也按版本核对）、每个运行都在 `job_reports` 里、时间窗（当日纽约 16:00 到下一交易日纽约 16:00 之间开始）内的 `workbench` 运行报告都有阶段行——没有的列为「缺证据」。任一项不满足，或 `stage_runs` 表还没建（迁移 025 未执行），退出码 1。
- 两个子命令参数错误或数据库不可用时退出码 2。
- 验证一次推导：手动运行批处理后，在「今日」任选一份计划点「展开推导」，顶部显示「推导与重算一致」，触发段每条条件标「成立」或「未冻结，无法复核」，底部运行证据的 `run_id` 与该次运行报告一致；CLI `check --since <当日>` 对同一计划的结论相同。
- 已知限制：触发段只复核冻结取值——候选没有冻结的取值如实标「未冻结，无法复核」，不从原始日线重算均线；「推导一致」只说明算术正确，不说明规则有效（证据状态说明常驻每份推导）。

## 每日复查

每日工作流的第 8 个节点 `review`（「每日复查」，在 `agent` 之后、`push` 之前，设计见 [v2.5 计划时间线 §7](../specs/2026-10-28-v2.5-plan-timeline-design.md#7-每日复查阶段-review)）对每条有效的 `agent-2` 计划链做一次复查，每条链每个交易日至多一条有效批处理复查记录（`plan_reviews`）。

- **对象**：链状态为入场期（`entry`）或持仓期（`holding`）的链；当天刚生成的版本不复查（`fresh_version`，生成本身就是当天的记录），当天已有有效批处理复查的不再复查（`already_reviewed`）。顺序：持仓期在前，然后主列表入场期，扩展池入场期最后，各自按最新版截止日、再按标的；超过 20 条的记 `object_cap`。已作废、已否决、已平仓、已过期的链不复查，计入阶段 `detail.ended`；持仓所在单元完全没有 `agent-2` 链的列在 `detail.holdings_without_chain`（链在持仓期间被作废等已结束的不算「无链」）。
- **链标的只采集**：有效链的标的若已不在观察池与持仓里，批处理在逐只采集之后单独采集它的日线、资讯、财报日，并计入 SEC 列表，**不跑规则**（不产生候选、单元、计划或推送）；运行报告 `pool.chains` 记这类标的数，`collect` 阶段计数照常包含它们。
- **信号与条件**：宿主只读取截止时间之前的数据，判定七项系统信号（`new_8k`、`abnormal_move`、`stop_touched`、`t1_touched`、`expiry_near`、`regime_change`、`user_input`，窗口是「上次有效复查之后」）以及最新版的失效条件与下次复查条件（`met` / `not_met` / `unknown`，数据缺失不当作成立；当天日线缺失时 `detail.bars_missing`），全部写进复查记录。
- **结论顺序**：① 任一失效条件成立 → 系统规则作废（「失效条件成立：<条件文案>」），不调用模型；② 没有信号、没有新的用户输入、复查条件都未满足 → 系统规则维持（「无新信号，复查条件未满足（<条件文案>）」），不调用模型；③ 预算闸门（`agent` 节点开始 1500 秒后 `stage_budget`，与 `agent` 共用一个窗口、采集的重试不占；Agent 不可用、本次已遇额度用尽 `quota_exhausted`、当日 token 上限 `token_budget`）→ 写 `skipped` 记录；同链同日已有 3 条 `skipped` / `error` 记录后不再写行，只在阶段 `skips` 记 `max_attempts`；④ 一次 `agent-review-1` 单阶段复查（`agent_runs.mode = review`，工具按复查交易日取数，信号日的原始触发由宿主写进证据块），输出无效或模型出错 → `error` 记录；⑤ 维持 / 作废照写；⑥ 修订 → 完整的提议 + 反方 + 校验（`mode = revise`）：通过则新计划行、新版本行（`origin = review`，有效期复查日 S+1 至 S+3，入场期不晚于信号日后第 10 个交易日）、修订运行、复查运行与复查记录同一事务写入；校验不过、入场期新版按规则作废（如有效期内有财报，`plan_invalid: earnings_in_validity`）或出错 → 记录为 `revise`、没有新版、`detail.revision_status` 写原因，最新版不变，阶段 `degraded`（`revision_failed`）；修订时改口不买（`pass`）→ 作废（`detail.via = revision_pass`）。持仓期的新版即使按仓位规则作废（`no_room`）也成为最新版，链照常复查。
- **互斥**：每条链的复查全程（读取、调用模型、写入）在一条不经连接池的专用连接上持有会话级 advisory lock `review-run:<标的>:<信号日>`，读取与写入事务里另有事务级锁 `review:<标的>:<信号日>`；任一把被占（正在重新复查）时本次跳过（`review_in_progress`），不写行，也不调用模型。写入前核对链仍有效、最新版没变；模型调用期间链被改动（如提交了不买的决定）时不写复查记录，但模型运行记为 `skipped`（`review_in_progress`）并带 token，计入每日上限。模型调用期间不占用数据库事务。阶段 `detail.excluded` 逐链记下未复查的链与原因（`fresh_version`、`already_reviewed`、`object_cap` 与无行跳过），供 `plan_review check` 核对。
- **阶段证据**：`review` 行的输入 = 复查对象数，产出 = 有效复查记录数，`outputs` 列出复查记录、新版计划与复查 / 修订运行的 id，`detail` 有各结论与 `decided_by` 计数、信号触发次数、入场 / 持仓对象数、`ended`、`holdings_without_chain`、token 与新版推导核对；Agent 不可用但有对象时宿主可判定的照写、其余写 `skipped`、阶段 `degraded`（`agent_unavailable`），没有对象时整阶段 `skipped`（`agent_unavailable: <原因>`）。迁移 026 未执行时本阶段不运行，本次按 `stages-1` 记账。
- **验证一次**：手动运行后，`stage_runs` 该 `run_id` 有 10 条有效行，`review` 行的输出计数等于 `plan_reviews` 里该交易日 `trigger = batch` 的有效记录数；信号日当天的新链只出现在 `review` 行的 `skips`（`fresh_version`）里，次一交易日才有复查记录。

### v2.9：一只股票一条活跃链、再次触发与退出期

- **活跃链**：`timeline-2` 的链状态有九种，`entry`（入场期）、`holding`（持仓期）、`exiting`（退出期）三种算活跃，同一个标的至多一条（见[一只股票一条活跃链](../knowledge/concepts/system.active_chain.md)）。复查的对象仍是 `entry` 与 `holding`；`exiting` 的链不复查、不调用模型，只写当天的持仓状态。`detail.ended` 的计数改为「过期 · 作废 · 平仓 · 被取代 · 否决（旧决定）」，`detail.exiting` 列出退出期的链。
- **`plan` 节点写再次触发**（设计 R2：这件事在 `signals` 节点的规则循环里做，与规则基线同一事务、同一把事务级锁 `chain-open:<标的>`；`plan` 节点的证据行写出 `detail.retriggers = {count, by_state, tickers}`）：为每个无冲突的买入单元生成 `plan-2` 之后，若该标的已有活跃链（入场期最后一个有效日或入场期上限那天触发的，算可续期的活跃链，R5），就写一行 `chain_retriggers`（`created_at` 取本次批处理的截止时间，所以同一次运行与之后的重新复查都按截止时间读到它）；没有活跃链则什么也不写，单元照常进 `agent` 节点开新链。同一 session 重跑读回已有的行，不重复写；已并入的单元重跑仍是并入。
- **`agent` 节点**：有 `chain_retriggers` 行的单元不提议、不写运行行，阶段 `skips` 记 `active_chain`（附链键，如 `MU·2026-10-21`），解读直接用规则版简报（`prompt_version = rules-1`，不单独跑 `agent-brief-1`）；`summary.agent.merged` 与阶段 `detail.merged` 记并入数，`GET /api/workbench/agent-runs` 的 `coverage.merged` 把它算作已覆盖。写首版之前在同一把锁下再核对一次：期间另一条链已经活跃，就把这次提议记为 `skipped / active_chain`（保留 token）并补写并入行，不开第二条链。手动「重新运行 Agent」遇活跃链 → 409 `active_chain`；已并入、但所并入的链已结束的单元可以开自己的链（R17）。
- **首版带「同标的上一条链」证据块**：提议者的人类消息在现有一行之后加最近一条已结束链的摘要（只读背景、不可引用；模型写的文字每行前缀 `    │ `；至多 2000 字；只用截止时间之前的记录），块全文与哈希存进该次运行的 `output.input_digest.previous_chain`。首版是 `agent-3`：计划行 `plan_version = agent-3`，必填 `entry_type` 与 `max_hold_sessions`。
- **入场期 `retrigger`**：该信号（第八项）触发时，复查跳过单阶段复查，直接走修订流程（提议 + 反方 + 校验）：复查行 `decided_by = agent`、`review_agent_run_id` 为空、`detail.via = 'retrigger'`，新版有效期 `S+1…min(S+3, 入场期上限)`，入场期上限取最近一次触发后第 10 个交易日（D6）。模型字段全无变化时允许「续期」版（`changes = []`，宿主差异只有 `valid_until` / `entry_cap`，标 `host_only`）；修订输出 `pass` 仍作废。失效条件成立仍先由宿主作废。持仓期的 `retrigger` 只是证据，进单阶段复查的证据块（不加仓）；退出期的记进持仓状态的 `detail.signals`。
- **持仓期的宿主步骤**（D18，顺序固定）：① 止损触及（当天最低价 ≤ 有效止损，含 T1 之后的移动止损）→ 作废，原因「止损触及（<价>）：应已按止损卖出；仍持有则次一交易日开盘卖出」；② 时间止损（宿主把计划的 `max_hold_sessions` 注入为 `source = max_hold` 的失效条件）成立 → 作废，原因「时间止损：持有 n 个交易日仍未到 1R，次一交易日开盘卖出」；③ 其余失效条件成立 → 作废。三者都不调用模型。持仓期的作废**不再结束链**，而是进入退出期（复查行 `mode = holding`、`timeline_version = timeline-2`，`detail.exit_reason` 为 `stop_touched` / `time_stop` / `invalidation` / `agent_invalidate`），直到这些买入全部平仓 → `position_closed`。其余照旧：无事可看由宿主维持、预算闸门、单阶段复查（`agent-review-2`，证据块加「再次触发」与「持仓状态」）、修订；持仓期修订的止损只能上移、必须低于复查日收盘，入场区间照抄上一版（止损可以高于入场区间下沿，计划行 `inputs.chain_mode = holding`）。退出期点「重新复查」→ 409 `chain_exiting`。
- **持仓状态 `holding_status`**（D19）：`review` 节点在全部复查之后，对**每个持仓标的**写一行——复查成功、跳过、出错、Agent 不可用、无链持仓、退出期的链都有；有链的取链最新版的止损 / T1，1R 的风险取第一笔关联买入所关联版本的止损（D20），无链的取成交关联的计划；字段、指令（`hold` / `sell_half` / `exit` / `no_plan`）与维持理由模板见[持仓状态](../knowledge/concepts/review.holding_status.md)。同一 session 重跑不写新行（先写的为准）；持仓事实只用截止时间之前的成交（`list_trades(cutoff=now)`，R11）。阶段 `detail.holding_status = {rows, by_instruction}`。
- **核对**：`python -m investment_assistant.workbench.plan_review check --session D` 另有三项（任一不过退出码 1）：① 首版为 `agent-3` 的链所在标的至多一条活跃链；② 当天每个 `chain_retriggers` 行指向的链有一条带 `retrigger` 信号的复查记录（被 `object_cap` 等排除、或已进退出期的除外）；③ 每个当天有未平批次的标的恰有一行 `holding_status`。`chain` 命令另打印并入的单元、持仓状态行与备注。
- **迁移 029 门**：`daily` 在 029 未执行时拒绝运行（`job_reports` 记 `error / migration_029_missing`，失败通知一次，不跑图），手动运行入口返回 503；在读取任何计划或成交之前检查。

## 复盘卡检测

每日工作流的第 10 个节点 `retro`（「复盘」，在 `push` 之后，设计见 [v2.7 §9](../specs/2026-10-28-v2.7-growth-loop-design.md#9-批处理阶段-retro)；卡的含义、审定与命令行见 [复盘](review.md#复盘卡)）。v2.8 起它做两件事：交易日检测并起草复盘卡（下面的内容，自己的 1500 秒窗口）；任何日子判断周 / 月复盘是否到期，到期就生成并推送（手动运行只生成不推送，`detail.weekly.push = manual_run`）。两件都没做记 `skipped / not_due`，交易日不会记 `not_due`。复盘卡在推送之后才建，所以推送概览报的是上一次推送之后的新卡数：

- **执行**（`retro_cards.run_stage`）：只读事务里枚举对象与结束事件并冻结事实；一个写事务插入新卡（`event_key` 唯一，同一 session 重跑不重复建卡）；之后对没有成功草稿的卡按结束日升序起草，每张卡一个写事务，每次批处理至多 5 张，预算闸门与 `agent` 阶段同一顺序。单个标的或单张卡出错只影响它自己（进 `failures`），阶段继续。
- **阶段证据**：`input_count` = 本次需要起草的卡数（新卡加之前没起草成功、且失败不足 3 次的），`output_count` = 本次成功的草稿数，`outputs` 有 `card_ids` / `draft_ids` / `agent_run_ids`，`skips` 逐卡记原因（`stage_budget`、`quota_exhausted`、`token_budget`、`max_attempts`、`draft_cap`、`agent_unavailable: <原因>`），草稿作废进降级 `draft_rejected`、出错进 `failures`，`detail` = `{events, new_cards, by_end_kind, no_plan, drafts: {ok, rejected, error, skipped}, to_review, tokens}`；运行报告 `summary.retro = {new_cards, drafts, to_review}`。Agent 不可用时照常检测与建卡，起草全部跳过，阶段 `degraded`（`agent_unavailable`）；没有需要起草的卡时阶段 `success`。
- **迁移 027 未执行**：`daily` 要求迁移 028，028 之后 027 一定已执行；v2.7 的 `run_batch` 外壳（命令行与测试用）遇到缺 027 时仍按 `stages-2` 记 8 行。
- **每日推送**：概览字段末尾的「复盘卡 上次推送后新增 a · 待审定 b」（a 是上一次每日推送之后新建的卡数，b 是推送时的待审定数；a、b 都为 0 时不加），不新增消息。
- **验证一次**：手动运行后 `stage_runs` 该 `run_id` 有 10 条有效行，`retro` 行计数与 `review_cards` / `review_card_drafts` 一致；`python -m investment_assistant.workbench.retro_cards check --since <首次批处理交易日 S 之前的第 4 个交易日（= S−4，检测窗口起点）>` 通过；「运行一览」最后一行读作「新结束 n 笔（平仓 a · 止损 b …），新建复盘卡 n 张；起草 x/y 张；待审定 z 张」。

## 「今日」：计划表与 Agent 计划卡

### v2.9：计划表（`GET /api/workbench/plan-table`）

v2.9 起「今日」不再有单元卡区、决定表单和「进行中的 Agent 计划」「持仓止损」两段，换成**一张计划表**（设计 [v2.9 §9.1、§10.1](../specs/2026-10-30-v2.9-executable-plans-design.md)）。页面顺序：运行一览 → 筛选 → 市场环境 → 计划表 → 其他触发（卖出 / 观察 / 冲突单元，一行一个只读解读）→ 扩展池（`include_extended` 开关，默认关；开关只管入场期 / 已结束组和其他触发里的扩展池单元，**持仓组永远全列**，扩展池标的的持仓和退出指令不会从「今日」消失，行上 `pool = extended`）。**没有任何决定按钮**，采纳由成交推出（见下文[成交与备注](#成交与备注v29)）。

- **只读、不调外部数据源**：`GET /api/workbench/plan-table?session=&include_extended=`，`session` 缺省 = 最近一个已收盘交易日；读更早的日子时整张表按那一天结束时已知的记录读——版本（链头是当时的那一版）、复查、并入、成交都按截止时间截断，之后才开出的链不在，入场期里后来才被作废的链仍是入场期，返回 `{session, groups: {entry, holding, ended}, other_units, counts, errors}`；某个标的读不出来只进 `errors.<标的>`，其余行照常。迁移 029 未执行返回 503「migration_029_missing」（页面写「迁移 029 未执行」），不给空表。后端把文案全部拼好，前端只排版。
- **入场期组**：每个处于入场期的链一行（再次触发并入的单元不单独成行，写在这一行的 `chain.retriggers`，每项带 `unit_signal_date`、`rule_ids` 与它产出的 `version_no`），加没有链的买入单元（Agent 出错 / 不可用 / `pass`，或所并入的链今日作废）——这类行以规则基线为计划、`chain = null`、`status.label` 写原因；单元所并入的链已结束时写「所并入的链 MU·10-21 已于 10-24 过期未执行（作废 / 平仓 / 被取代）」；标的已有活跃链、而这个更早的单元从未并入它时，只在其他触发里留一行。行内容：`plan`（入场类型与区间、止损、T1、建议股数、有效期、最长持有；`agent-2` 旧版没有执行字段，按 `zone_limit` + 10 天显示并标 `defaults_applied`）、`baseline`（规则基线一行；并入了这条链的单元其基线 `active_chain` 记 `{ticker, signal_date}`）、`open_scenarios`（开盘区间内 / 高开 / 低开各做什么，`entry-1` 模板）、`void_when`（本计划何时作废：有效期、开盘情形、每条失效条件及最近一次判定、最长持有、止损）、`status`（`label`、链级 `execution` 与 `execution_basis`「照 Agent 第 n 版」、最近一次复查、今日触发的信号、相对上一版的 `diff` 与 `changes_text`）、`notes`（有效备注）、`links`。
- **持仓组**：每个持仓一行，`holding` = 当天的[持仓状态](../knowledge/concepts/review.holding_status.md)行（距止损、距 T1、持有天数、现在几 R、指令与维持理由）；有链的取链的最新版，没有链的取成交关联的规则基线 / 自定计划（`chain = null`，写「无 Agent 链，按规则基线看护」）。当天没有 `holding_status` 行（`review` 节点整体失败）时现算一行并标 `holding.stale = true`，页面写「今日持仓状态未写入（每日复查失败），以下为现算」，现算的行不落库，持仓不会从「今日」消失（R18）。排序：指令 `exit` → `sell_half` → `hold` → `no_plan`，再按标的。
- **已结束组**：最近 5 个交易日内（`ENDED_WINDOW_SESSIONS`）结束的链与规则基线，`status.label` 为「已过期（未执行）」「已作废：<理由>」「已平仓（+1.2R）」「被取代」「旧决定不买」，带 `ended_at`；更早的去「标的」页计划历史。默认收起、整组置灰。
- **其他触发**：`other_units` 只带标的、信号日、建议动作、标签、规则与简报，不再有单元卡。
- **排序**：入场期按池（核心 → 筛选 → 扩展）再按标的；已结束按结束日倒序。
- **命令行**：`python -m investment_assistant.workbench.plan_table show [--session D]`（薄壳，转到 `plan_views.main`；只读）打印三组各一行与读取失败；退出码 0，数据库不可用或 029 未执行为 2。
- **持仓状态接口**：`GET /api/workbench/holding-status?session=` → `{session, rows}`（当天全部持仓状态行，缺行的现算并标 `stale`）。
- **`GET /api/workbench/today`**：`units` 与 `extended_units` 退役为空列表并带 `retired: true`；`holdings`、`chains`（按 `timeline-2` 判定，含退出期）、`market`、`screen`、`timeline_ready` 照旧。单元卡数据只剩推送在用（`service.unit_cards`）。

下面各条描述的是行展开里的 Agent 计划卡（`AgentPlanCard`，去掉了决定表单）和计划页，设计见 [v2.5 §10](../specs/2026-10-28-v2.5-plan-timeline-design.md#10-今日与推送)；链、版本与复查的含义见 [Agent 轨道 · 计划时间线](agent-track.md#计划时间线)：

- **Agent 计划块在前**：「Agent 计划 · 第 n 版 · 生成于 <北京时间> · 截止 <北京时间>」；动作与价位（每个价位带引用编号，点开看工具调用）、建议股数；论点 T1–T3（带引用，`user:<id>` 引用只显示、不可点）；每条论点下的关键反证，反方没有给出的标「反方未对此论点给出反证」；其他风险；失效条件，每条带最近一次复查的判定（成立 / 未成立 / 无法判定；还没复查过、或最近一次复查正是产生本版的那次时写「尚未复查」）；下次复查条件（空 = 「下一交易日」）；修订版显示「相对第 n−1 版」：宿主差异（如「止损 95.00 → 96.00」）与模型的变化说明并列；最近一次复查（结论、「Agent」/「系统规则」、理由、时间）；修订未通过时写「Agent 建议修订，但修订未通过校验（原因），当前仍为第 n 版」；持仓期的新版按仓位规则作废（如 `no_room`）时写「本版按仓位规则不能加仓（原因）」，不当作计划作废；「展开推导」；「证据：未验证」常驻。条件文案与后端 `agent/conditions.py` 的模板逐字一致（区制标签保留 `risk_on` / `neutral` / `risk_off` 原值），数字按后端字符串原样显示。
- **看推理过程**：计划卡底部「看推理过程」（取生成这一版的 Agent 运行 id，「今日」与计划页共用，版本链里点开的每一版都有）展开 Agent 推理阅读视图，展开时才请求。按时间顺序一步一个小节，标题带概念：提议者读了什么（每次工具调用一行「call:N · 工具 · 参数 · 哈希前 8 位」，「看返回值」展开，列表默认只显示条数与首尾各 2 行，结果字段名旁可展开概念）→ 提议（动作、价位、论点、失效 / 复查条件）→ 校验结果 → 反方读了什么 → 反方（逐条反证、其他风险、丢弃数、无反证的论点）→「回应」（本版之后的复查记录；没有写「回应：本版之后还没有复查」）→ 生成的计划（状态与推导一致性）。论点、价位、反证里的 `call:N` 可点，滚动并高亮到那次调用；`user:<id>` 只显示。修订运行与复查运行前面多一步「触发这次运行的复查」（信号、条件判定、给模型的用户输入，并可再展开那次复查 / 修订自己的运行）。`get_concept` 调用标「概念卡随代码版本走，不受截止时间约束」；被作废的运行只保留已记录的工具调用，没存的步骤写「这次运行作废：<原因>，只保留工具调用」；校验项逐项列出，作废时只标「可能未通过」的范围，不推断哪些通过了；`agent-1` 旧运行按原样降级显示。`agent-1` 计划没有版本链与计划卡，计划页 `#plan/<id>` 另给一段「Agent 推理」（标「agent-1（旧版，不参与复查）」），「看推理过程」按生成它的运行展开同一个视图。后端接口与步骤定义见 [Agent 轨道 · 推理阅读视图](agent-track.md#推理阅读视图)。
- **计划卡上的概念**：版本、截止时间、动作与价位、引用编号、论点、反方、失效 / 下次复查条件、相对上版、最近复查、「证据：未验证」、`agent-1` 旧版、修订未通过原因、「本版按仓位规则不能加仓」旁各有一个可点开的概念名（`ConceptTerm`），规则基线与版本链（来源、链状态、复查结论、信号、条件判定、用户输入、影子状态）、推导视图（一致性、证据说明、每张候选表的规则名、输入快照、逐项计算的项目列、运行证据）同样；「今日」决定表单的「执行依据」也挂了。版本链每条复查记录另有「看复查推理」（`review_agent_run_id`）与「看修订推理」（`revision_agent_run_id`），有才显示。
- **规则基线折叠为一行**：「规则基线 `plan-1`：入场 x–y · 止损 z · T1 w · 建议 N 股（有效 / 已作废）」+「展开」，展开后是原来的规则计划块（含「展开推导」）与「收起」。
- **Agent 没有可用计划时规则基线自动展开、不能收起**，Agent 块只写原因：没有成功的运行 →「Agent 未给出计划：<原因>」+「重新运行 Agent」；`pass` →「Agent 不建议买入：<摘要>」；链已作废 →「Agent 已作废此计划（第 n 版）：<理由>」；Agent 计划行按规则作废时同样展开；`agent-1` 单元原样展示、标「agent-1（旧版，不参与复查）」，规则基线不折叠。没有 Agent 运行的单元（卖出、观察）只显示规则计划。
- **解读不重复**：`agent-1` 与 `agent-2` 的解读只显示「解读见 Agent 建议」，摘要与首条反证已在 Agent 块里。
- **布局开关**（行展开里，只影响展开内容的顺序）：「布局：Agent 优先 / 规则优先（旧）」，存在浏览器本地（`localStorage` 键 `workbench.today.layout`，值 `agent_first` / `legacy`）；读写失败（隐私模式、禁用存储）一律按默认「Agent 优先」，切换只在本页生效。旧布局 = v2.4 的顺序：规则计划块在前、Agent 块在后，都不折叠，结构化字段照样显示在 Agent 块里。
- **运行一览**：「今日」最顶部（筛选、市场环境之前）一段，默认展开，自己取数（`GET /api/workbench/run-overview`），不依赖下面的批处理视图。页头：一行摘要（运行方式 · 开始时间 · 用时 · 各状态阶段数）· 日期选择 · 同日多次运行时的运行切换（定时 / 手动 / 休市 + 开始时间）·「原理」链接（`#knowledge/principles`）· 折叠按钮（折叠状态不保存）。下面九行，每行：阶段名 · 状态（成功 / 部分失败 / 降级 / 失败 / 跳过 / 缺证据 / 未记录）· 一句话 · 「输入 I · 产出 O」· 用时；有跳过 / 失败 / 降级时可「展开明细」看原因文案与样本标的。`stages-1` 运行的第 7 项（每日复查）与 `stages-1` / `stages-2` 运行的第 8 项（复盘卡）是「未记录」占位；没有阶段证据或迁移 025 未执行时只显示后端给的说明。日期改了只重新请求这一段。句子与原因文案由后端按模板拼好（见 [调度与通知](../operations/scheduling-and-notifications.md)）。
- **引用的知识与讨论**（v2.7）：Agent 计划卡与版本链每一版多一段「引用的知识」（`knowledge_refs`：`know:<id>@<版本>` + 引用时那一版的标题 + 引用的字段，点开到引用时的版本，该条目之后有新版时附「当前已是第 n 版」），以及「就此讨论」按钮（新建一次讨论并跳到 `#discuss/<id>`，见 [Agent 轨道 · 就此计划讨论](agent-track.md#就此计划讨论)）；「看推理过程」里 `get_knowledge` 的调用与返回的 `know:` 引用也链到条目页，推理视图顶部同样列出这次运行引用的知识（提议 / 修订运行取它的计划的引用，复查运行取它的复查行的引用，形状同计划卡的 `knowledge_refs`；其余运行没有这个键）。
- **进行中的 Agent 计划**：v2.9 起并入计划表的入场期组与持仓组（同一份 `timeline-2` 判定，退出期的链也在持仓组）。
- **重新复查**（「今日」与计划页同一做法）：提交后轮询 `/api/runs/<run_id>`，最长 900 秒（复查加修订常超过 2 分钟）；完成显示「复查完成：<结论>」（跳过或出错时附原因，如「复查完成：跳过（超出 token 上限）」）并刷新；轮询到时限仍未结束时显示「复查仍在后台进行，稍后刷新查看」，按钮保持不可点，不当作失败；409 显示「不能重新复查：<原因>」（正在复查 / 这条链不在入场期或持仓期 / Agent 不可用：<原因>）。
- **持仓**：没有 Agent 链的持仓行写「无 Agent 链，按规则基线 / 自定计划看护」，只有宿主的持仓状态；链在持仓期被作废进入退出期，行上写「退出期 · 退出指令自 <日期> 起」，不再复查，每天只写持仓状态。
- **降级**：迁移 029 未执行时计划表返回 503；迁移 026 未执行（`timeline_ready = false`）时隐藏「重新复查」，规则计划与 Agent 原有内容照旧显示。

### 计划页与「标的」页

- **计划页 `#plan/<id>`**：`agent-2` 计划在推导之上显示「版本链」：v0…vn 每版一行（第几版、来源：信号日 / 每日复查 / 重新复查、生成与截止时间、价位、有效期、宿主差异、影子状态，标出最新版与当前查看的版本），点「第 k 版」展开该版的 Agent 计划块（同「今日」）；打开的是旧版时页头写「这是第 k 版，最新为第 n 版」并链接最新版。下面是「复查记录」：每条写复查交易日、触发方式（批处理 / 重新复查）、结论、决定方、`第 k 版 → 第 n 版`、理由（跳过 / 出错写原因）、触发的信号、条件判定、给模型的新输入（`user_input_ids`）、引用的 `user:<id>`、修订未通过的原因。链在入场期或持仓期时可「重新复查」（同上）。推导下方是作用于这条链的「我的补充」。规则计划与 `agent-1` 计划的页面不变。
- **「我的补充」**（计划页作用于本链；「标的」页作用于整个标的，可选一条入场期或持仓期的链）：类型（研报要点 / 新闻 / 我的判断 / 其他）、正文 1–4000 字（按字符码位计，与后端一致）、可选 `http(s)://` 链接（≤ 500 字），提交前先在页面校验；提交带 `request_id`，失败时保留草稿与 `request_id`，重试幂等。列表每条显示 `user:<id>`、类型、北京时间、作用范围、已更正 / 已撤回与指向的旧行；有效的输入可「更正」（预填原文，新行指向旧行）或「撤回」。用户输入只是证据，不是指令（规则见 [Agent 轨道 · 计划时间线](agent-track.md#计划时间线)）。
- **页头链接**：计划页页头加「标的页」链接（`#instrument/<标的>`），「标的」页的计划行与焦点计划都链回 `#plan/<id>`。
- **「标的」页（v2.6 四段）**：标的选择与页头不变，下面按投资流程分四段，每段一个二级标题，设计见 [v2.6 §9](../specs/2026-10-28-v2.6-understanding-the-system-design.md#9-标的页重排与-k-线标注)。
  - **信号与计划**：首屏先放「今天该关注什么」（后端 `focus`：持仓 → 进行中的 Agent 计划 → 今日触发 → 临近财报，什么都没有时是后端给的兜底句「今天没有触发，也没有进行中的计划或持仓」，每条带链接和概念）；今日触发（规则名、动作、冻结取值，「触发依据」展开单元推导的触发段）；进行中的 Agent 计划（入场期 / 持仓期的链：第几版、价位、最近复查、「查看」、「重新复查」，做法同「今日」）与折叠的「已结束的链」；当前有效的规则 / 自定计划（有效期覆盖今天或之后，附「推导」）；持仓（股数、成本、开仓时间，其下一行是当前止损 / T1：止损标移动或初始、T1 是否已触、距止损与距 T1，没有计划的持仓写「无计划持仓（回撤规则看护）」，旁挂止损、T1、移动止损的概念）；「我的补充」。迁移 026 未执行时 Agent 计划一栏写原因、不显示补充表单。

  - **背景**：下次财报日（距今几个交易日）、区制、行业强弱（未映射写「未映射行业 ETF」）、基本面、近期资讯与 SEC 文件。
  - **我的知识**（v2.7，「信号与计划」之后）：挂在该标的上的有效条目（标题、适用范围、版本、被引用次数），点开到条目页；空时写「还没有挂在 <标的> 上的经验」并给「写一条」（预填标的）；`knowledge` 读取失败（含迁移 027 未执行）时显示 `errors.knowledge`。
  - **历史**：K 线（250 根日线、MA 三线）加标注——候选（信号日的箭头，买入在线下、卖出与观察在线上，文字为规则简称）、各份计划的入场上下沿 / 止损（虚线）/ T1 短线段（规则、自定、Agent 各版本分色）、你的成交（B / S）；作废（`invalid`）计划的线段淡显；图下列「计划价位」（种类、第几版、入场、止损、T1、有效期、「推导」），超出 12 份的写「另有 n 份未画」；最后是候选、决定、成交的完整时间线。`CandleChart` 不传标注时与以前完全一样。
  - **接口新增的键**（`GET /api/workbench/instruments/{ticker}`，旧键不变，只有 `candidates` 的窗口变宽：读取起点由信号日前 120 天改为图上第一根日线，约 250 个交易日）：`holding`（持仓的当前止损与 T1：与「今日」持仓止损同一函数，字段 `quantity` / `avg_cost` / `plan_id` / `stop` / `mode` / `t1_reached` / `target1` / `last_close` / `to_stop_pct` / `to_target_pct`；没有持仓为 null，没有计划的持仓 `stop` 为 null）、`focus`、`key_data`、`context`、`plans`、`chart.annotations`，另有 `errors`：某个新键读取失败时该键为 null、原因写在 `errors.<键>` 里，页面在对应段落显示原因，其余段落照常。
- **「标的」页的旧内容**：Agent 计划列表、「我的补充」、基本面、资讯与 SEC 时间线、K 线与成交量、候选 / 决定 / 成交时间线都在，只是归入上面四段。

## 成交与备注（v2.9）

**取消决定按钮**（设计 [v2.9 §6](../specs/2026-10-30-v2.9-executable-plans-design.md)）：你的交易日志本身就是采纳的证据，由成交推出每份计划的执行状态（口径 `execution-1`，纯函数 `execution.status`，含义与四种状态见[执行状态与备注](../knowledge/concepts/review.execution_status.md)）。

- **`POST /api/workbench/decisions`** 一律返回 **410** `{"error": "decisions_retired: v2.9 起不再记录决定，采纳由成交推出；可在计划上写备注"}`（`service.decide` 抛 `Gone`，不写任何记录）；`ledger.record_decision` 已删除，`repository` 里写决定的函数改为模块私有 `_insert_decision_for_tests`，只有 `tests/` 在用（`tests/legacy_decisions.py` 保留旧流程给需要旧数据的测试，有静态测试守护）。`signal_decisions` 表与旧行只读保留：旧链照旧按旧决定终止、旧复盘卡与旧周报照旧显示。
- **`POST /api/workbench/trades`** body 加 `plan_id?` 与 `own_plan?`（`{entry_low, entry_high, stop, target1, max_hold_sessions?}`，最长持有 3–30、默认 10），**去掉** `decision_id`：给了返回 400 `decision_link_retired: v2.9 起成交不再关联决定，请改为关联计划`。三选一：关联计划（`plan_id`）、自定（`own_plan`，同一事务里写一行 `kind = own`、`plan-2` 的计划，有效期只有成交当天，`signal_date` 按顺序取：成交时刻活跃链所在单元 → 成交日前 20 个交易日内该标的最近一个有候选的单元 → 成交日本身）、都不给（无计划）。同一 `request_id` 重放返回原成交，`plan_id` / `own_plan` 只在给了才进 `request_hash`，v2.9 之前的请求重放仍幂等；卖出可不关联（平仓按先进先出配对，链状态由买入决定），`own_plan` 只用于买入。
- **关联哪一版**（R6）：`plan_id` 必须是同一标的的计划；指向 Agent 链的版本时必须是**成交时刻的链头**——`agent_plan_versions.created_at ≤ executed_at` 且下一版不存在或晚于成交——比它旧的返回 409 `plan_stale: 成交时这条链已是第 n 版，请关联第 n 版`，生成于成交之后的返回 409 `plan_after_fill: 这一版生成于成交之后，不可能是你照着做的那一版`，所以补录昨天的成交时关联的仍是照着做时看到的那一版。迁移 029 未执行时带 `plan_id` / `own_plan` 返回 503「migration_029_missing」。
- **`GET /api/workbench/trades/linkable-plans?ticker=&executed_at=`**（`executed_at` 为带时区的 ISO 时间）→ `{ticker, plans, default_plan_id}`：成交时刻活跃链的链头（默认选中；退出期的链不列，R10）、有效期覆盖成交日的规则基线、最近 5 个交易日内的自定计划，每项 `{plan_id, label, kind, chain_signal_date, version_no}`，链头与活跃链都按成交那一刻已知的记录读（成交之后才有的版本、复查、作废都不影响；成交时刻之后才开的链不在），标签形如「Agent MU·10-29 第 2 版（入场期，有效至 11-03）」。前端「复盘 → 交易与持仓」的「关联计划」下拉来自它，默认选中链头，没有时「无计划」。
- **备注 `plan_notes`**：`POST /api/workbench/plan-notes` body `{request_id, ticker, body, chain_signal_date | plan_id, kind?, supersedes_id?}`——作用于一条链（`chain_signal_date`，该链必须存在）或一份非链计划（`plan_id`，规则基线 / 自定计划；链上的版本请用 `chain_signal_date`，否则 400），正文 1–1000 字（按字符码位），`request_id` 幂等（同 id 不同内容 409）；更正 = 带 `supersedes_id` 的新备注，撤回 = `kind: "retract"`；更正 / 撤回必须指向同一范围的备注。`GET /api/workbench/plan-notes?ticker=&chain_signal_date=&plan_id=` 只返回有效备注。给了 `plan_id` 时 `ticker` 可以省略（取计划的 `ticker`；计划不存在 404，`ticker` 与计划对不上 400），页面写 / 读规则基线与自定计划的备注就是这样。备注显示在计划表、计划页、计划历史和复盘卡（`facts.execution.notes`，建卡时冻结）；**不进任何 Agent 提示词、不触发复查**（`test_notes_not_in_any_agent_input` 守护），页面在输入框下写明「备注只给你自己看；要让 Agent 参考，请用『我的补充』」。

## 持仓止损

持仓的计划（v2.9，D20 / D22）：持仓属于某条持仓期 / 退出期的链时取**链的最新版**（持仓期修订上移的止损随之生效，1R 的风险取第一笔关联买入所关联那一版的止损）；否则取「当前未平仓批次中最近一笔、且其成交关联了计划（`trades.plan_id`，旧成交再看它的旧决定）的买入」的计划。有计划的持仓用 `plan_stop`（T 日最低价 ≤ 当前止损）和 `plan_target`（开仓以来首次触及 T1，卖出一半，只触发一次）；触及 T1 之后，当前止损 = max(开仓以来最高收盘 − 3 ATR, 持仓成本)，收盘后更新、次日生效。没有计划的持仓仍按 `position_drawdown` 判断。

## 推送

`push` 节点把当日简报推到 Discord（默认 `signals` 频道），按顺序发：概览（含市场环境、扩展池新计划数、「计划更新 修订 a · 作废 b」、「复盘卡 上次推送后新增 a · 待审定 b」、有数据族没拿全时一行「数据：日线 118/131（13 个目标没拿到，见运行详情）」，多个族用「；」连接、至多 3 个）、新计划（核心池 + 持仓与可决定的筛选单元；筛选来源的计划字段名带「【筛选】」前缀）、计划更新（有更新时才发）、持仓、待处理与异常、筛选报告（概览 / 今日触发 → 复核 / 形态候选前 10 只，形态列全要看页面；筛选未运行时写原因与沿用成员数）。平常五条，有计划更新时六条；`push` 阶段的产出计数是实际发送的消息数。没有新计划也推送；同一交易日已成功推送就不再重复；推送失败只写进运行报告，下次推送附「上次推送失败」。单个字段截断到 1024 字符，单条消息不超过 6000 字符（超出的整字段丢弃，末尾注明「其余 n 条见系统」）。

- **新计划的字段**（设计见 [v2.5 §10.3](../specs/2026-10-28-v2.5-plan-timeline-design.md#103-推送)）：有 Agent 结果的单元，Agent 行在前、规则计划作为「规则基线：区间 · 止损 · T1 · 股数」在后（不写风险金额）。`agent-2` 写「Agent 第 n 版：区间 · 止损 · T1 · 股数 · 摘要 · 反证：<首条反证>」（n 是链的最新版）；链已作废写「Agent 已作废此计划（第 n 版）：<理由>」；Agent 没有可用计划（出错、跳过、校验作废等）写「Agent 未给出计划（<原因>）」；不建议买入照旧写「Agent（模型）不建议买入；摘要」；`agent-1` 单元保留原来的 Agent 行，末尾标「agent-1（旧版，不参与复查）」。Agent 简报（`agent-1`、`agent-2`）的摘要和反证已经在 Agent 行里，不再重复附在计划后面。没有 Agent 结果的单元（卖出、观察等）照旧只写规则计划。证据状态「证据：未验证」照旧。
- **「🔁 计划更新 · <交易日>」**：列出时间窗内写入的复查记录（批处理与重新复查都算），只推作废和产生了新版的修订，每条一个字段：
  - 修订：「<标的> 第 n−1 → n 版：<变化说明逐条> · 新价位 区间 · 止损 · T1 · 有效期至 <日期>」，变化说明取修订运行输出的 `changes`；
  - 作废：「<标的> 作废（Agent / 系统规则）：<理由>」。
  - 维持、修订失败（没有新版）、跳过、出错都不推；扩展池入场期的链不推（只影子跟踪），持仓期的链总是推。
  - 时间窗（D25）：起点是上一次成功的、交易日早于本次的每日推送读取复查记录的时刻（`job_reports` 里 `workbench`（v2.7 及以前）或 `daily` 的 `summary.push.sent = true`，取 `summary.push.reviews_until`；没有这个键的旧记录取报告时间 `created_at`；休市日那一行不算），终点是本次推送读取复查记录的时刻（写进本次的 `summary.push.reviews_until`），只取复查交易日不晚于本次的记录；从未成功推送过时只取本交易日的记录。推送之后才做的重新复查——包括推送发送期间、运行报告落库之前写入的——下一次推送照样会推。手动「重新推送今日计划」（`POST /api/workbench/push`）不写运行报告，不移动时间窗；同一交易日重推时起点不变，内容只会多出此后新写入的记录。迁移 026 未执行时不发这条消息，概览也不写「计划更新」一行。

- **v2.9 的推送格式**（设计 §11）：
  - **新计划**（每个入场期链一项，加当天没有链的规则基线；扩展池不推）三行：「<标的> <月-日> 第 n 版：<入场类型> L–U · 止损 S · T1 W · N 股 · 有效至 E」、「开盘：区间内买 / 高开不追挂 U / 低开 ≤S 作废、否则回到 L 买」（`next_open`：「开盘：仅 <首个有效日> 开盘在 L–U 买，否则作废」）、「最长持有 n 天未到 1R 即退出 · 摘要 · 反证：…」；本次窗口内由再次触发产生的版本，第一行写「（再次触发，第 n−1 → n 版）」；规则基线行照旧在 Agent 行之后，当天并入这条链的单元另附其规则基线。
  - **持仓**消息每个持仓标的一行持仓状态「MU 持有 4/10 天 · 距止损 −5.20% · 距 T1 +8.10% · 现 +0.6R · 继续持有：<维持理由>」，**维持也推**；`exit` 行前加「⚠」。某个持仓当天没有状态行（`review` 节点整体失败）时按旧字段现算并写明「今日持仓状态未写入（每日复查失败），以下为现算」。
  - **计划更新**：持仓期作废写「<标的> 退出指令（<原因>）」；再次触发的修订写「<标的> 第 n−1 → n 版（再次触发）：<变化说明>」，续期版没有模型变化说明时写宿主模板「再次触发（<规则>，<信号日>），沿用价位，有效期延至 <日期>」。
  - **待处理与异常**：不再有「未决定单元」，改为「入场期可执行 n · 持仓 m（退出指令 k）」；概览的「待处理」= 入场期可执行 + 退出指令；Agent 建议计数把并入已有链的单元单列（「并入已有链」），不算「未给出」。

## 入口与验证

- 页面：「今日」（计划表三组、行展开里的 Agent 计划块与折叠的规则基线、布局开关、「重新复查」、市场环境、「重新推送今日计划」）；「标的」（单只股票的 K 线图（MA20/50/200 与成交量，最多 250 根日线）、日线、候选、计划历史与旧决定，页尾「Agent 计划」与「我的补充」）；计划页 `#plan/<id>`（`agent-2` 计划另有版本链、复查记录、「重新复查」与「我的补充」）。
- API：`GET /api/runs/{run_id}/detail`（运行详情）、`POST /api/jobs/daily/run`（手动运行，等价于 `POST /api/workbench/run`，返回 `{run_id, daily_run_id, status}`）、`POST /api/jobs/daily/resume`（续跑，body `{run_id, node}`，202）、`POST /api/workbench/agent-runs/rerun`（重新运行 Agent）、`GET /api/workbench/today`、`GET /api/workbench/plan-table`、`GET /api/workbench/holding-status`、`GET /api/workbench/instruments/{ticker}/plan-history`（计划历史：`include_reviews`、`include_baselines`，返回 `{ticker, rows, chains}`）、`POST /api/workbench/decisions`（410，见上文）、`GET /api/workbench/instruments/{ticker}`、`GET/POST /api/workbench/trades`（`plan_id` / `own_plan`；成交列表每行另带 `plan_label`，格式同可关联计划的标签）、`GET /api/workbench/trades/linkable-plans`、`GET/POST /api/workbench/plan-notes`、`POST /api/workbench/trades/{id}/void`、`POST /api/workbench/push`。
- 运行报告：`job_reports` 中 `daily` 的 `summary`（每次执行一行，续跑另追加 `trigger_source = resume` 的行；v2.7 及以前是 `workbench`），额外有 `graph_version`、`run_status`、`failed_node`、`resumed`、`stage_status`，以及 `retro`（`{new_cards, drafts, to_review}`，v2.7）、`tickers.<T>`（日线、资讯、候选、跳过原因）、`plans`（`inserted` / `existing` / `conflict` / `skip: 原因`）、`earnings`、`push`、`sources`（按数据源列出失败）、`timings`、`pool.chains`（只采集不跑规则的链标的数）、`review`（复查对象数、各结论条数、token）。
- 验证一次：手动运行后，运行报告里 `plans.<T> == "inserted"`；「今日」显示「入场区间 x–y · 止损 z · T1 w · 建议 N 股」和「证据：未验证」；点「重新推送今日计划」，页面提示「已推送 N 条」，`push.sent == true`。
- 验证计划表：手动运行后 `GET /api/workbench/plan-table` 的入场期组有当天的链；展开一行先看到「Agent 计划 · 第 n 版」块，下面是一行规则基线；在展开里切到「规则优先（旧）」后顺序反过来，刷新仍保持；录一笔关联该链最新版的买入后，次日 `holding-status` 有这个标的一行，计划表把它放进持仓组。

## 数据与时点

- 日线保存 yfinance `auto_adjust=False` 的开高低收（已按拆股调整、未按分红调整）和全复权收盘价；数据源改了数值就追加一个修订版本，不覆盖旧值。
- 规则、计划和解读只用运行截止时间之前已入库的数据；资讯发布时间未知时显示「发布时间未知」，不用获取时间代替。
- 资讯只存标题和链接，不抓正文。
- 这不是严格的历史时点回测：yfinance 的历史数据会被修订，只能保证「本系统开始采集之后」的记录能按时点还原。

## 已知限制

- 免费资讯源不稳定：`Ticker.get_news` 已被 Yahoo 改成 404，现在改用搜索接口；运行报告里 `news.fetched` 为 0 时，说明它又失效了。
- 样本小、信号重叠多，统计没有推断意义。
- 价位是你所设规则的算术结果，不是投资建议。
