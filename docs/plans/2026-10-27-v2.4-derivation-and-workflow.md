# v2.4.0 计划推导链与批处理 workflow 底座 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 批处理每个阶段都在正确的 `run_id` 下留下只追加的证据（`stage_runs`），每份计划都能展开推导链，并自动校验推导与重算一致。

**Architecture:** `workbench/stages.py` 是 7 阶段注册表、状态判定和挨着现有代码记账的 `StageRecorder`；harness 新增 `pass_run_id`，把 `job_reports.run_id` 交给 `run_batch`，由它写 `stage_runs`（迁移 025）、`data_fetch_runs`、`signal_candidates`、`screen_runs`。`workbench/derivation.py` 是纯函数：按代入值独立推导，不调用 `plans.py` 的计算函数，并给出一致性结论；`workbench/derivation_view.py` 在只读事务里按 ID 回读原始行，供接口、批处理后校验与 CLI 共用。前端新增 `PlanDerivation` 组件，挂在「今日」与独立页 `#plan/<id>`。

**Tech Stack:** Python 3.11 / FastAPI / psycopg 3 / PostgreSQL；Svelte 5 + Vitest；pytest（离线，数据库用一次性 schema）。

**Spec:** [docs/specs/2026-10-27-v2.4-derivation-and-workflow-design.md](../specs/2026-10-27-v2.4-derivation-and-workflow-design.md)

## Global Constraints

- 只在 `main` 上开发和提交（项目约定），不开分支或 worktree。
- 功能、架构、运维文档与对应代码同一个提交更新；spec 和本 plan 写成后不改正文。
- 不改计算口径：规则 v1、`plan-1`、`agent-1`、`screen-1`、`regime-2`、Agent 流程（提议、反方、引用校验、预算）一律不动；`plans.py`、`rules.py` 只读不改。
- `summary` 只新增 `stage_status` 一个键；`stages=None` 时 `run_batch` 与现状逐字段一致。唯一的新 `errors` 条目是 `derivation_mismatch: <ticker> <plan_id>`。
- 阶段 id 与顺序（逐字）：`collect`、`screen`、`regime`、`signals`、`plan`、`agent`、`push`；`STAGES_VERSION = 'stages-1'`。
- 取值：`status ∈ {success, partial, degraded, failed, skipped}`（优先级 failed > partial > degraded > success）；`trigger ∈ {scheduled, manual_batch}`；`job = 'workbench'`。
- 原因文本经 `families.sanitize_reason`（截断 300 字、FRED key → `***`）；`skips[].samples` 最多 10 个。
- 跳过原因（逐字）：`not_trading_day`、`explicit_pool`、`manual_run`、`already_pushed`、`task_disabled`、`not_reached`、`agent_unavailable: <原因>`；异常中断记 `failed`，原因为 `aborted: <异常摘要>`。
- `stage_runs` 只 `INSERT`，不进 `repository.WORKBENCH_TABLES`；写入失败只进 `summary['stage_status'] = {'written': n, 'error': ...}`，不进 `errors`。
- 推导常量（与 `plans.py` 相同，测试断言相等）：`ENTRY_ATR = 0.5`、`STOP_ATR = 2`、`TARGET_ATR = 4`、`TRAIL_ATR_MULTIPLE = 3`、`VALID_SESSIONS = 3`、`EARNINGS_WARN_SESSIONS = 10`、`ATR_PERIOD = 14`、`MIN_BARS = 15`；`DERIVATION_VERSION = 'derivation-1'`；注册版本 `plan-1`、`agent-1`。
- 取整：`atr`、`ref_price` 6 位 `ROUND_HALF_UP`；四个价位到分 `ROUND_HALF_UP`；三个股数上限 `ROUND_FLOOR`；比较一律 `Decimal` 精确相等。
- 文案（逐字）：证据状态「规则 v1 与 `plan-1` 都未经验证（Phase 0 Gate HOLD）。推导一致只说明算术正确，不说明规则有效。」；触发段说明「触发段只复核候选冻结的取值是否满足阈值，不从原始日线重算均线。」；运行证据「v2.4 之前生成，无阶段证据」「迁移 025 未执行，暂无阶段证据」。
- 读取用例都在只读事务里（`SET TRANSACTION READ ONLY`），从不调用外部数据源。
- 测试命令：离线 `env -u INVESTMENT_ASSISTANT_DATABASE_URL -u INVESTMENT_ASSISTANT_TEST_DATABASE_URL -u TEST_DATABASE_URL .venv/bin/python -m pytest tests/ -q`；SQL 测试另设 `INVESTMENT_ASSISTANT_TEST_DATABASE_URL=postgresql://test@127.0.0.1:55433/workbench_test`（一次性库，做法见 memory「Disposable Postgres for SQL tests」）；前端 `cd web && npm test && npm run build`（本机 Node 若报 webstorage 错，加 `NODE_OPTIONS=--no-experimental-webstorage`）。
- 真实库执行迁移 025、重启服务、打 tag、推送 `origin` 都要用户单独授权，不属于自动步骤。

## Review Focus

1. **日线值的 float 与 Decimal 两条路径**：`plans.atr14` 读的是 `repository.read_bars` 转成的 `float`，再 `Decimal(str(x))`；推导按 id 回读的是 `NUMERIC`。对 6 位小数的真实价格（如 `187.123457`），两条路径得到的 `atr` 与价位必须相同，结论为 `consistent`。→ Task 8 `test_derivation_float_and_decimal_paths_agree`。
2. **同一 session 先手动、后定时各跑一次**：第二次运行的 `plan.outputs.existing` 也包含这份计划，但运行证据必须指向**新增**它的那次运行。→ Task 8 `test_run_evidence_points_to_inserting_run`。
3. **用户打开 `#plan/<坏 id>` 或不存在的 id**：页面显示「计划不存在」或后端给的 400 原因，不白屏，也不回落到别的页面。→ Task 12 `shows not-found for unknown plan id`、Task 10 `test_derivation_bad_uuid_is_400`。
4. **自定计划提交时日线不足 15 根**：`atr` 取规则计划的值，没有就为 0；推导标出 `atr` 取自哪一种，结论仍为 `consistent`，不报 `incomplete`。→ Task 7 `test_own_plan_atr_fallback_sources`。
5. **Agent 未配置，当天又没有待处理单元**：`agent` 阶段记 `skipped`（`agent_unavailable: …`），而不是 `success 0/0`。不可用优先于空跑。→ Task 5 `test_agent_unavailable_beats_empty`。
