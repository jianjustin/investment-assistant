# v2.3.0 数据底座与「数据」菜单 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 让每类数据看得见：六个数据族的用途、覆盖、最新时点、最近拉取成败在「数据」菜单可见，可单族手动拉取，可浏览原始值。

**Architecture:** 静态注册表 `workbench/families.py` 定义六族与纯函数（状态判定、原因脱敏、覆盖口径、目标清单）；`workbench/collect.py` 是从 `run_batch` / `screening._collect` 原样抽出的逐只采集函数、记账用的 `Tally` 与每族 advisory lock，批处理与手动拉取共用；只追加表 `data_fetch_runs`（迁移 024）记每次拉取的成败与原因，覆盖与最新时点读取时从数据表实算；`workbench/data_view.py` 是只读用例与手动拉取用例，`api/routes/data.py` 薄封装；前端新增 zone `data`。

**Tech Stack:** Python 3.11 / FastAPI / psycopg 3 / PostgreSQL；Svelte 5 + Vitest；pytest（离线，数据库用一次性 schema）。

**Spec:** [docs/specs/2026-10-26-v2.3-data-foundation-design.md](../specs/2026-10-26-v2.3-data-foundation-design.md)

## Global Constraints

- 只在 `main` 上开发和提交（项目约定），不开分支或 worktree。
- 功能、架构、运维文档与对应代码同一个提交更新；spec 和本 plan 写成后不改正文。
- 业务数据只追加：`data_fetch_runs` 只 `INSERT`；不改任何旧表结构与写入语义（`store_bars`、`store_news`、`store_macro` 的修订规则不动）。
- 不改计算口径：规则 v1、`plan-1`、`screen-1`、`regime-2`、影子跟踪与复盘；批处理阶段顺序、事务边界、`summary` 结构与推送内容不变（只新增 `summary['data_status']` 一个键）。
- 族 id：`bars`、`sec_filings`、`news`、`atr`、`fred`、`universe`（顺序即卡片顺序）；`data_fetch_runs.family` 只允许前述除 `atr` 外的五个。
- 取值：`trigger ∈ {scheduled, manual_batch, manual_family}`；`scope ∈ {family, ticker}`；`status ∈ {success, partial, failed, skipped}`；`job ∈ {workbench, filings}`。
- 口径常量（spec §4、§8）：SEC 覆盖看近 120 天；资讯看近 7 天（`service.NEWS_LOOKBACK_DAYS`）；ATR 需 ≥ 15 根（`plans.MIN_BARS`）；FRED 最新观测早于 session 前 7 个自然日为滞后；范围超 120 天（`universe.STALE_DAYS`）为过期；失败原因截断 300 字；卡片最多 5 条失败；详情最近 20 次记录；浏览窗口：日线 120、ATR 60、资讯 60 天、SEC 180 天、FRED 120。手动拉取日线回看 `service.HISTORY_DAYS`（420）。
- 证据文案（逐字）：「这里只展示采集事实。所有规则都未经验证（Phase 0 Gate HOLD）：数据完整不代表信号有效。」；ATR 补充：「`plan-1` 的计算输入，规则 `gate_hold`」。
- 锁键：`hashtext('data_family:<id>')`，会话级 `pg_advisory_lock` / `pg_try_advisory_lock` / `pg_advisory_unlock`；批处理固定顺序 `bars`、`news`、`sec_filings`、`fred`。
- `data_fetch_runs` 不进 `repository.WORKBENCH_TABLES`。
- 凭据不进记录：失败原因经 `macro.redact(text, os.environ.get('FRED_API_KEY'))`。
- 测试命令：离线 `env -u INVESTMENT_ASSISTANT_DATABASE_URL -u INVESTMENT_ASSISTANT_TEST_DATABASE_URL -u TEST_DATABASE_URL .venv/bin/python -m pytest tests/ -q`；SQL 测试另设 `INVESTMENT_ASSISTANT_TEST_DATABASE_URL` 指向端口 55433 的一次性库（见 memory「Disposable Postgres for SQL tests」）；前端 `cd web && npm test && npm run build`（本机 Node 若报 webstorage 错，用 `NODE_OPTIONS=--no-experimental-webstorage npm test`）。
- 真实库执行迁移 024、重启服务、打 tag、推送 `origin` 都要用户单独授权，不属于自动步骤。

**与 spec 的两处实现偏差**（不改 spec 正文，在 CHANGELOG 与 features 文档里如实写）：

1. 批处理与 `filings` 任务的 `run_id`：`tasks/_harness.run_task` 在调用任务函数之前生成 `run_id` 但不传入。`filings` 任务在 `run_task` 返回后写记录，能带上 `run_id`；批处理的记录在采集阶段末尾写，`run_id` 为空，靠 `job` + `started_at` 对应运行报告。不为此改 harness 签名。
2. 手动拉取的 `run_id`：给 `tasks/runner.submit` 加关键字参数 `with_run_id: bool = False`，为真时以 `fn(run_id)` 调用，记录带上 runner 的 `run_id`。现有调用方不变。

## Review Focus

1. **手动拉取传小写或带空格的 ticker（` mu `）**：规范为 `MU` 再校验、采集、记录；记录里的 `ticker` 与写入 `price_bars` 的一致。→ Task 7 `test_fetch_normalizes_ticker`。
2. **同一交易日批处理跑两次（手动一次、定时一次）**：每次各追加五行，不去重；卡片取最新一行，`last_success_at` 取最近的 `success`/`partial`。→ Task 5 `test_rerun_appends_new_status_rows`、Task 8 `test_card_uses_latest_run`。
3. **浏览一只从没采过数据的 ticker**：返回 200、`rows = []`、`has_data = false`，不是 404 或 500，也不触发外部请求。→ Task 8 `test_browse_unknown_ticker_is_empty_not_error`。
4. **全族手动拉取耗时数分钟**：前端轮询上限 15 分钟（`pollRun(..., {timeoutMs: 900_000})`）；超时显示「仍在后台运行，稍后刷新」而不是失败；按钮恢复可点，再点会拿到 409。→ Task 10 `shows still-running on poll timeout`。
5. **外部源异常文本里带 FRED key**：`failures[].reason` 里是 `***`，`data_fetch_runs` 与接口都看不到原文。→ Task 2 `test_sanitize_reason_redacts_and_truncates`、Task 5 `test_fred_failure_reason_is_redacted`。
