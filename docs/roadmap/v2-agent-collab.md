# Roadmap v2 后续 — 知识与 Agent 协作

> 状态：**草案（2026-10-27），待用户审阅，未开工**。接在 [v2-visibility.md](v2-visibility.md)（v2.3–v2.5）之后，覆盖 v2.6–v2.9。
> 这是方向和排序，不是实施授权。每版开工前另写 spec 和 plan，按 [交付标准（DoD）](README.md#交付标准dod) 交付。

## 1. 目标与成功标准

**目标**：系统能指导你的交易，并且**你的知识和系统共同成长**。知识双向流动：系统把每个数据概念的含义讲给你听；你的判断、经验和复盘教训写进系统，被 Agent 引用，再由影子结果检验。

**主线不变**：扫描 / 研究找标的 → 规则主计划 `plan-1` + 并列 Agent 建议 → 你决定是否下单 → 复盘。Agent 仍是**并列挑战者**，不改主计划；晋升机制照旧暂缓。

**成功标准**：

| # | 标准 |
|---|---|
| 1 | 任何一个数据概念（数据族、指标、规则项）都有一张卡讲清含义、口径和常见误读，**在系统内展示**：有独立的「知识」菜单，也在概念出现的地方（「数据」菜单、推导链、「标的」页、计划卡）就地查看 |
| 2 | 你写下的经验 / 判断进入系统，Agent 能引用；每份 Agent 计划记录引用了哪些知识，以后可以回看「这条知识被引用过的计划表现如何」 |
| 3 | Agent 运行时以本地 CLI 为主，可在 Claude Code、codex CLI、pi 之间按配置切换，批处理和对话都适用；需要按 token 计费的 API 模型时统一挂在 pi 上；不论哪个运行时，截止时间、工具记录、引用校验的保证不变 |
| 4 | 有一个 Agent 一级入口：能就任一计划问「怎么来的」，补充信息后得到新版 Agent 计划；已结束的计划能沉淀出一条经验 |
| 5 | 多 agent 对抗式生成的 `agent-2` 全程可回放，与 `agent-1` 并列影子跟踪后，由你按证据二选一占用批处理位置 |

## 3. 设计要点

### 3.1 知识层（v2.6）

两类知识，存放和生命周期不同：

| 类 | 内容 | 存放 | 谁写 | 引用形式 |
|---|---|---|---|---|
| **概念卡** | 系统定义的概念：含义、算法 / 口径、在本系统哪里用、常见误读、相关概念 | 源文件是仓库内版本化 Markdown，随代码走；**由系统读取并渲染展示** | 手写，代码改了口径就同提交改卡 | `concept:<id>@<版本>` |
| **我的知识** | 你的经验、规则心得、对某标的 / 行业的判断、复盘教训 | 数据库，只追加；修改 = 新版本指向旧版本；归档 = 状态记录 | 你在系统里写；v2.8 起也可由 Agent 起草、你审定 | `know:<id>@<版本>` |

**系统内展示**（知识不留在仓库或文档里，而是你日常用系统时就看得到）：

| 位置 | 展示什么 |
|---|---|
| 一级菜单「知识」 | 概念卡浏览（按数据族 / 指标 / 规则项分组，卡与卡互链）；我的知识列表（按概念 / 标的筛选），写、改、归档、看版本历史 |
| 「数据」菜单卡片、v2.4 推导链每一步、「标的」页字段、「今日」计划卡 | 概念名可就地展开概念卡摘要，一跳到完整卡；挂在该概念上的我的知识条数与入口 |
| 「标的」页 | 挂在该标的上的我的知识 |
| Agent 计划卡 / 运行详情 | Agent 引用了哪些概念卡和我的知识，点开看引用时的那个版本 |

- **概念范围**：数据族（日线、SEC 财报、资讯、FRED 利差、纳指 100 范围…）、指标（ATR、均线、相对强弱、广度、区制…）、规则项（`screen-1` 各条、`plan-1` 入场 / 止损 / 目标 / 仓位）。spec 定稿清单。
- **我的知识**挂到概念或标的上（可多挂），带写入时间。
- **Agent 工具**：`get_concept(id)` 读概念卡；`get_knowledge(ticker 或 concept)` 读我的知识。都受截止时间约束——**批处理为信号日 T 生成计划时，只能看到截止时间之前写入的知识条目**，否则事后学到的教训会污染影子结果。
- **引用归因**：Agent 计划引用的知识条目随调用记录写库，为成功标准 #2 的回看提供数据；回看页面本轮不做，等有引用积累再议。

### 3.2 运行时可切换（v2.7）

**分层**：

| 层 | 现在 | v2.7 之后 |
|---|---|---|
| 编排：阶段顺序、分支、代码校验节点、检查点 | LangGraph `StateGraph` + PostgresSaver | **保留在 LangGraph** |
| 单阶段执行：模型调工具的内循环 | LangGraph `ToolNode` + 智谱 | 本地 CLI 运行时适配器 `run_phase(提示词, 工具范围) → 输出 + token 用量`；`ToolNode` 循环与智谱一并删除 |
| 工具 | 进程内 Python 函数 | 同一组函数，另以本地 stdio MCP 服务暴露 |
| 判定（引用、价位、基本校验） | `citations.py` | 不变，始终在宿主代码里，不交给任何运行时 |

- **适配器**：`claude-code`（`claude -p` + MCP 配置）、`codex`（`codex exec` + MCP）、`pi`（pi 不内置 MCP，通过扩展注册同一组工具）。三者都是本地 CLI，用各自的登录态 / 订阅。
- **API 模型统一走 pi**：以后需要按 token 计费的 API 模型（含智谱等），在 pi 里配置 provider，系统侧只认 `pi` 一个适配器，不再为某家 API 单写接入。
- **删除智谱运行时**：删 `zhipu` provider、`ToolNode` 循环、`ZHIPU_API_KEY` / `WORKBENCH_AGENT_BASE_URL` 等配置与额度错误码分类；已有的 Agent 运行记录与计划保留，只读。v2.7 上线前批处理照旧用智谱。
- **宿主注入、模型不可改**：截止时间、允许查询的标的范围、`run_id` / 阶段写进 MCP 服务的启动参数；每次调用照旧写 `agent_tool_calls`（参数、返回值、SHA-256）。
- **关掉运行时自带能力**：CLI 自带的 shell、文件读写、联网、网页搜索一律禁用，只允许本 MCP。否则模型能绕过截止时间读到「未来数据」。spec 里逐个运行时写清禁用方式，并有测试证明禁用生效。
- **配置**：按「用途 × 阶段」选运行时（如批处理提议用 `claude-code`、反方用 `codex`），另给一条降级顺序（如 `claude-code → codex → pi`）。单元级失败（CLI 不可用、未登录、超时、订阅额度用尽）按单元换降级顺序里的下一个运行时，全部失败记 `skipped` 并写明原因；运行记录新增运行时与模型字段。
- **开工第一步是可行性验证**：逐个运行时核实能否①无人值守运行（LaunchAgent 环境下登录态可用）②禁用自带工具 ③接上本工具集 ④报告 token 用量 ⑤在批处理时间预算内完成。不满足的运行时不进本版，留 backlog；至少两个运行时通过才能删除智谱，否则本版暂缓删除。
- **检查点粒度**：CLI 运行时只能在节点边界续跑，不能从一次 CLI 会话中途恢复；接受这一代价。
- backlog 的 Agent 工具 `get_fundamentals` 并入本版工具集。

### 3.3 Agent 一级入口（v2.8）

- **入口**：前端一级菜单「Agent」；从「今日」的计划卡、「标的」页、「复盘」里的计划都能「就此计划讨论」进入，带上计划上下文。
- **问「怎么来的」**：Agent 读 v2.4 推导链、计划依据与输入快照、相关概念卡，给出带引用的解释；不改任何东西。
- **补充信息**：你贴入的研报要点、新闻、自己的判断，存为带时间戳的**用户输入**（只追加），Agent 可引用为 `user:<id>`。
- **更新计划**：你确认后，Agent 生成一份**新版 Agent 计划**：来源标记为对话，`supersedes` 指向旧计划，价位和理由走同一套引用校验，失败照旧整条作废。
  - **截止时间 = 对话时刻**，**影子跟踪从生成时刻起算，不回溯到信号日**；三方对比里对话版计划单列，不并入 `agent-1` 统计。
  - 规则主计划 `plan-1` 不受影响。
- **沉淀经验**：对已结束的计划（止损、达标、过期）发起对话，Agent 依据计划结果起草一条带引用的经验；你审定（可改）后才进入「我的知识」，未审定的草稿不被任何 Agent 引用。
- **运行时**：对话可选运行时（§3.2）；对话历史与阶段记录持久化，可回看。

### 3.4 多 agent 对抗 `agent-2`（v2.9）

- **流程**（LangGraph 多节点图）：
  1. 2 个提议者各自独立给出计划（可配置为不同运行时，避免同一模型自我印证）；
  2. 代码校验节点逐份校验，作废的不进入下一步；
  3. 反方逐条反驳两份提议，并核对引用与数字；
  4. 提议者各回应一轮（可修订价位，修订后重新校验）；
  5. 裁决者合成最终 Agent 计划，每个价位引用支撑它的工具调用；
  6. 代码校验最终计划。
- 每一步都写阶段记录，回放复用 v2.8 的展示；每个价位能追溯到是哪个提议者提出、反方如何质疑、裁决为何采纳。
- 读取知识层（概念卡 + 截止时间前的我的知识）。
- **成本与时限**：每单元调用数约为 `agent-1` 的 3–4 倍；沿用每单元尝试上限、批处理时间预算和每日 token 上限，超限记 `skipped` 并写明原因。
- **样本有限，不长期并存**：一年几十笔交易，变体越多越难分出高下。`agent-2` 与 `agent-1` 并列跟踪满 4 周后，你按影子结果决定哪个保留在批处理里，另一个停跑（历史记录保留）。

## 4. 边界

- 沿用：不接券商、不自动下单、不做盘中自动交易；只追加写入、按时点可还原；价位是规则算术结果并标注证据状态（Phase 0 Gate HOLD 照旧）；每版 spec → plan → DoD；真实库迁移先 `pg_dump` 备份并单独授权；push 单独授权；与 #投研-工作（Team B）不衔接。
- Agent 仍是并列挑战者：对话版计划、`agent-2` 都只做影子跟踪和并列展示，不改 `plan-1`；晋升机制照旧暂缓。
- **截止时间覆盖一切 Agent 输入**：工具数据、概念卡、我的知识、用户输入，都只能看到截止时间之前的内容。
- 凭据只从各 CLI 自身的登录态 / 配置读取（API key 配在 pi 里），系统不保存，不进报告、不进运行记录；错误文本照旧脱敏。
