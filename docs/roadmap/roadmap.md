## 1. 最终目标与成功标准

**最终目标**（用户 2026-10-27）：Agent 生成交易计划，你复查并实施；Agent 的计划能沿时间链路反思、吸收后来的信号出新版；系统把它做了什么、为什么讲给你听；你的交易能力随系统一起进化。

**你的角色**：阅读 Agent 的计划与理由，决定是否下单、何时止盈止损，自己下单并录入成交，审定复盘得出的经验。
**Agent 的角色**：从规则候选出发给出可复查的计划，每日复查并修订，计划结束后起草复盘；远期扩展到主动研究（§5）。
**程序的角色**：数据、计算、校验、风险限制、记录；判定始终在宿主代码，不交给模型。

**主指标：月度账户收益率**

| 档位 | 月度收益率 |
|---|---|
| 非常优秀 | > 20% |
| 优秀 | 10% – 20% |
| 可行 | 0% – 10% |
| 需关注 | < 0% |

- 口径：（本月末资金快照 − 上月末资金快照 − 区间净出入金）÷ 上月末资金快照；同一行显示同月 SPY。
- **流程复查触发**：滚动 3 个月复合收益 < 0 **且**跑输 SPY。
- 优先级：收益 > 纪律 > 认知 > 省时间。一年约几十笔交易，第一年做到「收益口径算得准、算得诚实」，不以「已证明跑赢」为验收。

**主线（v2.5–v2.10 完成后）**：扫描 `screen-1` → 规则候选 → **Agent 计划（默认复查对象）+ `plan-1`（规则基线）** → 你复查、决定、自己下单 → **每日复查与版本更新** → 计划结束后**复盘卡讲给你听** → 你审定的经验进「我的知识」→ 被后续 Agent 引用、被影子结果检验。

**成功标准**：

| # | 标准 | 版本 |
|---|---|---|
| 1 | 每个买入单元，你只读 Agent 计划就能决定做不做：计划有论点、证据、反证、失效条件、价位依据、下次复查条件 | v2.5 |
| 2 | 每份有效 Agent 计划每个交易日有一条复查记录（维持 / 修订 / 作废）；新信号或你的输入能产生新版，差异可读；所有版本可回放，截止时间各自固定 | v2.5 |
| 3 | 不读仓库文档，在系统里能看懂：今天批处理跑了什么、任一概念是什么意思、任一份 Agent 计划的每个字段和数字从哪来 | v2.6 |
| 4 | 每笔结束的交易有复盘卡（预期 vs 实际、三条轨道的 R、你的决定与纪律判定、教训草稿）；教训经你审定进「我的知识」；每条知识被引用后能回看表现 | v2.7 |
| 5 | 每日运行是一条看得见的链：任一天打开运行详情，能看到每个节点做了什么、每个数据源对每个目标拿到或没拿到什么、失败卡在哪一步；失败的运行能从失败节点续跑而不重跑已完成的部分；Agent 用你的 ChatGPT 订阅运行，不依赖本地 CLI 与按量计费的 API key；截止时间与工具记录的保证不变 | v2.8 |
| 6 | 单一数据源故障不再让当日采集失败：每个数据族有主源与备源，用了备源有记录、口径差异可见 | v2.9 |

## 2. 原则与边界

**沿用原则**（自 v1 [00](../archive/roadmap-v1/00-principles-and-direction.md) 起有效）：

1. **闭环优先于回测**：价值在「计划、执行、结果」的归因，不在小样本上的组合回测。
2. **证伪优先于建设**：规则和 Agent 都要有影子跟踪证据，没有证据不宣称有效。
3. **诚实优先于漂亮**：统计带样本量；区分「没算」和「无信号」；不用历史反推参数。
4. **人在环路**：系统出计划，人决定是否下单；不接券商、不自动下单。
5. **只追加写入**：按时点可还原，更正用新记录指向旧记录。
6. **截止时间覆盖一切 Agent 输入**：工具数据、概念卡、我的知识、用户输入，都只能看到截止时间之前的内容；新经验不回填到旧计划。

**边界**：

- 不接券商、不自动下单、不做盘中自动交易；只做美股波段；本地单进程运行。
- 价位是规则或算术结果并标注证据状态；所有规则都未经验证（Phase 0 Gate HOLD），推送里如实标注。**Agent 成为默认复查对象不等于 Agent 有效**：`plan-1` 继续计算、影子跟踪、三方对比；不因界面默认展示 Agent 解除 Gate HOLD；不做自动晋升。
- **版本只追加**：旧版计划、当时的决定和成交不改写；修订版指向旧版并列出差异；影子跟踪按版本记录，汇总时首版与最新版分开。
- 证据不够时停住：数据缺失、计划超限、Agent 引用无效，都显式标出，不写成「无信号」。
- 每版 spec → plan → DoD；真实库迁移先 `pg_dump` 备份并单独授权；push 单独授权；与 #投研-工作（Team B）不衔接。
- 凭据只从环境变量或各 CLI 自身的登录态读取，系统不保存、不进报告；错误文本脱敏。
- 工程纪律：路由层薄封装（`api/routes` → `services` → `db` / `tasks`）；外部失败结构化返回，不吞成成功。

## 4. 当前路线 v2.5–v2.10

### 4.1 重排依据与假设

**用户原话（2026-10-27）**：

- 核心目标：agent 生成交易计划，我来复查并实施计划；agent 交易计划可基于时间链路反思 + 补充信号。
- 问题：我不能了解系统运行原理；我的预期是我的交易能力能够跟随系统进化。

**对现状的判断**（2026-10-27 仓库核对，见 [Agent 轨道](../features/agent-track.md)、[每日计划](../features/daily-plan.md)、[复盘](../features/review.md)）：

- Agent 现在只在信号日批处理里给一次 `agent-1`，之后不再更新；规则 `plan-1` 是主计划，Agent 是并列挑战者。能更新计划的能力在旧排序里要到 v2.8 才有，由新信号触发的更新更远。
- 「看懂」已有一半：v2.3「数据」菜单能看数据从哪来，v2.4 推导链能看 `plan-1` 怎么算。缺的是三件事：今天整个批处理跑了什么、每个概念是什么意思、Agent 为什么这么建议。
- 「我的能力进化」没有任何交付对应。旧 v2.6 的概念卡解决「这个指标是什么」，旧 v2.8 的沉淀经验是喂给 Agent 的记忆。没有一环把「这笔为什么对、为什么错」讲给用户，也没有一环检验用户自己的判断。
- 旧 v2.7 运行时切换是最大的纯基础设施块，和删除智谱绑在一起，不直接服务上面任一目标。

**假设**（用户未逐条确认，默认成立；推翻任一条就改对应版本）：

| # | 假设 | 影响 |
|---|---|---|
| A1 | 基线是 2026-10-27 早先确认的 v2.5–v2.9（决策 #25–#44）。同日另两份未提交草稿——「压缩路线」（v2.5-lite / v2.8-core / v3-agent-loop）与「Agent 主导投研总纲」（R0–R5）——作为参考输入：前者的取舍逐条在 #53 说明，后者的远期部分摘入 §5 | 文档 |
| A2 | 「Agent 生成交易计划、我复查」= Agent 计划成为「今日」与推送里的**默认复查对象**；`plan-1` 照常计算、并列展示、影子跟踪，作为**规则基线**。不是用 Agent 替换规则，也不宣称 Agent 有效 | v2.5 |
| A3 | 「基于时间链路反思」= 同一单元的 Agent 计划有**版本链**：信号日首版 → 之后每个交易日对有效计划复查 → 有新信号或你补充了信息就出新版，每版写明相对上版改了什么、为什么；旧版不改、各版截止时间各自固定 | v2.5 |

### 4.2 顺序理由

- v2.5 先做，因为它直接交付用户的核心目标，且只用现有数据族、现有工具层和现有运行时，不等任何基础设施。
- v2.6 紧随其后，因为 v2.5 之后 Agent 计划变多、变长、有版本，不配解释层用户更看不懂；v2.6 的概念卡又是 v2.7「我的知识」挂靠的对象。
- v2.7 放第三，因为复盘卡需要 v2.5 的版本链（预期是哪一版的预期）和 v2.6 的概念卡（教训挂在哪个概念上）；放得更晚则 v2.5 起积累的交易没有复盘。
- v2.8 放第四：v2.5–v2.7 让每天的批处理更长、调用更多，运行记录里的失败也随之显形（2026-10-28 核对：3 次定时运行 1 次失败，失败那次因外部接口挂起跑了 2 小时 41 分，而记录的耗时只有 138 秒）。先把链条做成一张可续跑、看得见的图，再往上加数据源和研究范围，否则后两版加进来的失败同样看不见。模型层在这一版一起切到 ChatGPT 订阅，因为 v2.7 之后 Agent 的调用面（提议、反方、复查、解读、复盘卡、讨论）已经定型，切一次就够。
- v2.9 多数据源放 v2.8 之后：v2.8 的失败明细会说明哪个数据族、哪类错误最常见，备源按这个证据加，不凭感觉。
- v2.10 主动研究是扩张范围，等前面闭环跑过真实交易日再定。

### 4.3 计划时间线（v2.5）

**Agent 计划结构**（版本号由 spec 定；现 `agent-1` 的输出只有动作、价位、理由、风险提示）：

| 字段 | 内容 | 校验 |
|---|---|---|
| 动作与价位 | 入场区间、止损、T1，照旧每个价位引用价格类工具调用 | 沿用 `citations.py`，失败整条作废 |
| 论点 | 1–3 条「为什么现在值得做」，每条带引用 | 引用必须存在 |
| 关键反证 | 反方产出，逐条对应论点 | 不改价位 |
| 失效条件 | 可由程序检查的条件，如「收盘跌破 X」「财报前未到入场区」「区制转防守」 | spec 定可检查的条件集合 |
| 下次复查条件 | 什么事发生就该重新看；默认「下一交易日」 | — |
| 相对上版变化 | 首版为空；修订版列出改了哪些字段、为什么、引用新证据 | 修订版必填 |

**默认复查对象**：「今日」计划卡 Agent 计划在前，`plan-1` 折叠为「规则基线」一行，可展开、可切换回旧布局；推送同样 Agent 行在前、规则行在后。决定时执行依据三选一照旧（规则 / Agent / 自定），三方对比 `tracks-1` 不变。Agent 失败或作废时显示失败原因和规则基线，不伪装成有 Agent 计划。证据状态「未验证」常驻。

**版本链**：

- 版本 0 由信号日批处理生成（现有 `agent` 阶段）。每个新版 `supersedes` 指向上一版；旧版不改。
- **每日复查**：批处理新增一个阶段（`stage_runs` 注册表从 7 行变 8 行，`stages-1` → 新版本号），对象是所有**有效的 Agent 计划**（未过期、未作废）加**关联持仓的计划**。输入 = 上一版全文 + 自上版截止时间以来的新数据（同一套工具层，截止时间 = 本次运行）+ 新的用户输入。输出三选一：维持（写一行原因）、修订（走完整的提议 + 反方 + 校验生成新版）、作废（写原因）。复查是单阶段调用，只有修订才触发完整流程，控制调用量。
- **系统信号触发**：不另建事件系统。复查阶段里按规则判断是否「应修订」：新 8-K、`abnormal_move`、止损或 T1 触及、临近到期（到期前 1 个交易日）、区制变化。这些条件作为复查提示词的一部分给模型，也写进复查记录供回看。
- **用户输入触发**：「标的」页和计划页可贴入文本（研报要点、新闻、你的判断），存为带时间戳的只追加记录，引用形式 `user:<id>`；贴入后可点「重新复查」立即跑一次，截止时间 = 点击时刻。用户输入只是证据，不授予权限、不改规则。
- **截止时间**：每一版的截止时间 = 生成时刻，写进版本记录；工具层照旧只读截止时间之前的数据。

**影子跟踪**：对象是**版本**，不是单元。每版从生成时刻起算，不回溯到信号日。汇总时「首版」和「最新版」各算一条，防止事后修订把结果修好看；三方对比里 Agent 轨道取「你决定时看到的那一版」。

**推送**：新计划段照旧；新增「计划更新」段，只推修订与作废，维持不推。

**预算**：复查对象数小（有效计划 + 持仓，通常个位数）；沿用每单元尝试上限、批处理时间预算、每日 token 上限，超限记 `skipped` 并写原因。

**退出条件**：

- 连续 10 个交易日，每份有效 Agent 计划每日恰有一条复查记录，`stage_runs` 每次运行恰好 8 行。
- 至少一次由系统信号触发、一次由用户输入触发的修订版，「相对上版变化」可读且引用成立。
- 每个版本有自己的影子跟踪行；三方对比能指出决定用的是哪一版。
- 你确认：连续两周，只读 Agent 计划（不展开规则基线）就能做决定。

**不做**：盘中、新数据族、运行时切换、无信号的研究、对话式问答（v2.7）。

### 4.6 每日工作流（v2.8）

**要解决的问题**（2026-10-28 从真实库核对，见 #58）：

- **跑得久、常出错**：`job_reports` 里 `workbench` 定时运行 3 次 1 次失败，手动运行 13 次 3 次失败。失败的定时运行 `workbench-20261027225217` 从 06:52 跑到 09:33，其中采集阶段 2 小时 35 分：Yahoo 财报接口的 curl 挂到 17.5 分钟才超时、连续两次，另有代理 503、SEC 的 TLS 断开、FRED 走代理失败；`stage_runs` 记的采集耗时却只有 138 秒，因为现有计时只累计部分子步骤。Agent 的失败全部是智谱 90 秒请求超时，三次后记 `max_attempts`，当天这只股票不再运行。
- **运行记录看不懂**：「工具 → 运行记录」的详情就是把 `summary` 整个 `JSON.stringify` 进一个 `<pre>`；而 v2.4 起每次运行已有 8 行阶段证据、v2.3 起每个数据族有逐目标的 `data_fetch_runs.detail`，只是没有页面展示。
- **接口异常多且无界**：外部请求没有统一的紧超时与重试策略，单个目标失败会拖住整条链。

**一张图、一天一次**（#59、#60）：

- 现有三个定时任务 `workbench`（06:30）、`workbench_review`（08:00）、`filings`（09:30）合成一张 LangGraph `StateGraph`，任务名 `daily`，**北京 11:30、周二至周六**运行一次。挪到 11:30 是因为美股收盘后的披露可提交到美东 22:00（北京 10:00 夏令时 / 11:00 冬令时），SEC 采集排在链首就必须等这个窗口关闭；你在北京 21:30 美股开盘前复查，上午 11 点多出计划时间够用。
- 节点与顺序（`stages_version = stages-3`，每次运行恰好 10 行 `stage_runs`）：`sec_monitor`（原 `filings` 任务：SEC 下载器 / 监控）→ `collect`（日线、资讯、池内 SEC、FRED、成分股；族内顺序与锁不变）→ `screen` → `regime` → `signals` → `plan` → `agent` → `review`（每日复查）→ `push`（每日计划推送）→ `retro`（原 `workbench_review`：周 / 月复盘与复盘推送，只在该做的日子生成，其他日子记 `skipped: not_due`）。`retro` 排在 `push` 之后，复盘出错不耽误当天的计划推送。
- 纽约休市日沿用现在的做法：`push` 之前的节点全部 `skipped: not_trading_day`，`push` 只发休市一行，`retro` 照常判断是否到期。
- 旧任务从注册表与 `scheduled_jobs` 删除；`job_reports.task` 的历史值保留只读，运行记录页按任务筛选时仍能看到旧名字。
- 图的形态是**扁平的**：节点就是阶段，节点函数包现有的阶段函数；`agent` 节点内部照旧按单元顺序调用现有的提议 → 校验 → 反方子图（子图保留自己的检查点）。不用 `Send` 把单元并行展开（额度、截止时间、尝试次数四道闸是跨单元共享状态，并行要重写 Agent 阶段，而订阅额度也不鼓励并发）。

**检查点与续跑**（#61）：

- 检查点用现有的 PostgresSaver，`thread_id = run_id`，节点边界即检查点。
- **自动重试两层**。外部请求一层：每个数据源请求连接 10 秒、总计 30 秒超时；网络错误、5xx、429 按目标重试 2 次（退避 2 秒、8 秒），4xx 不重试；再失败记该目标失败、继续后续目标，族状态 `partial` / `failed`，节点不因单个目标失败而失败。节点一层：节点函数抛异常时等 60 秒自动重试 1 次；再失败该节点记 `failed`，其后未执行的节点记 `skipped: upstream_failed`，运行状态 `failed`，任务外壳照旧发失败通知。
- **手动续跑**：运行详情页在失败节点上给「从此节点继续」（`POST /api/jobs/daily/resume`，body `{run_id, node}`），从检查点续跑，已完成节点不重跑；`agent` 节点续跑时已完成单元由现有 `already_completed` 守卫跳过。续跑沿用原运行的 `session` 与截止时间；若当时已过下一个交易日的纽约 17:00，拒绝续跑（会读到截止时间之后的数据），只能作为新运行整次重跑。
- Agent 单元三次失败后的 `max_attempts` 保留，但从「当天永久作废」改为可在详情页与计划页手动重新运行（计数清零、新一组尝试）。
- Agent 时间预算从「批处理开始起 1500 秒」改为「`agent` 节点开始起 1500 秒」，采集节点的重试不再吃掉 Agent 的预算。
- 每节点的 `duration_ms` 改为按节点真实起止时间算；外部请求的等待全部计入所在节点。

**运行详情页**（#62）：

- 入口：「工具 → 运行记录」每一行，以及「今日」运行一览的标题。
- 顶部：整次运行的一句话（沿用 `run_overview` 的 `headline` 口径）与**节点状态图**（每个节点一格，颜色即状态，依次相连）。可视化在自己的页面画，不接 LangGraph Studio（要另起开发服务器和认证，而要看的只是哪个节点卡了、为什么）。
- 点一个节点展开三块：①做了什么——输入 / 产出计数、耗时、跳过与降级原因（人话模板沿用 `run_overview`）；②拉取详情——按数据族列出目标清单，每个目标成功 / 失败、失败原因原文、拿到的行数与最新时点（来自 `data_fetch_runs.detail`）；③结果详情——该节点产出的对象列表并可点进去：`screen` 列入选标的，`signals` 列候选，`plan` 列 `plan-1`，`agent` 列每个单元的状态、尝试次数、token 与计划链接，`review` 列每条复查，`push` / `retro` 列发了几条到哪个频道。失败节点在这里放「从此节点继续」。
- 原来的整段 JSON 保留在页面底部的折叠里，叫「原始摘要」，排错时用。
- 数据来自一个只读接口 `GET /api/runs/{run_id}/detail`，只读 `job_reports`、`stage_runs`、`data_fetch_runs` 与阶段证据里已记录的产出引用，不调用外部数据源。

**模型层：Agent 走你的 ChatGPT 订阅**（#63、#64）：

- 用 [Sign in with ChatGPT](https://developers.openai.com/siwc) 的「ChatGPT 计划用量」能力。它不是要依赖的 SDK，而是一份协议：标准 OAuth（PKCE、`127.0.0.1` 回环回调、首次以 `dynamic_agent_client` 动态注册得到 `client_id`，无需向 OpenAI 申请或审核），之后以 Bearer access token 调公开的 Responses API `https://api.openai.com/v1/responses`；官方文档直接给出 Python `openai` SDK 示例。本项目是在本机运行的个人开源项目，在允许范围内；Plus / Pro 可用。
- **无人值守**：access token 1 小时，refresh token 30 天且每次刷新换新的 30 天；每天一次运行即每天刷新，连接不会过期。一次性登录在运行服务的这台 Mac 的浏览器里完成（回调只能回到开浏览器的那台机器），之后由服务自己刷新。
- **接入方式**：继续用 `langchain-openai` 的 `ChatOpenAI`，切到 Responses API 模式（`use_responses_api=True`、`store=False`、`streaming=True`、`temperature=None`、`max_retries=0`），四张子图（提议、反方、复查 / 解读、复盘卡 / 讨论）与 `ToolNode` 循环、`citations.py` 判定一行不改。硬限制：每次请求必须 `store: false`、`stream: true`；禁用 `temperature`、`max_output_tokens`、`user`、`previous_response_id`、system 角色（系统提示改走 `instructions` / developer 消息）；函数工具支持，托管 MCP / 文件搜索不支持（本项目用不到）。
- **开工前核查（你来做）**：用一次性脚本走完登录、`GET /v1/models`、一次带函数工具的 `ChatOpenAI` 调用，记下被拒字段、`usage` 形态、可见模型清单、额度用尽的真实错误文本，写进 spec。若 `langchain-openai` 夹带被禁字段且 `disabled_params` 关不掉，退到备选：用 `openai` SDK 自写带函数工具循环的薄客户端（放弃 `ToolNode`）。
- **连接与存储**：「设置 → Agent 连接」页：连接 ChatGPT（后端起回环监听、返回授权 URL，前端新标签打开）、显示已连接账号与到期状态、断开（撤销 refresh token）、选择模型（清单来自 `GET /v1/models` 中 `visibility = list` 的项，不写死）。`client_id`、`host_id`（`urn:uuid:` 一次生成持久保存）、access / refresh token、过期时间、账号邮箱、scopes、所选模型存数据库表 `agent_connections`（与现在 `.env` 里的密钥同一安全级别；不进日志、不经接口回显、刷新用行锁防并发、先写后用）。
- **错误分类**：`subscription_sharing_usage_limit_exceeded` → `quota_exhausted`（本次运行其余单元跳过，同现在）；刷新失败（`invalid_grant`、`refresh_token_*`）→ `agent_unavailable: not_connected`，设置页红条 + 失败通知各一次；`model_not_found` → `agent_unavailable: model_unavailable`；429 与网络错误 → `model_error`，走现有尝试次数闸。`usage` 从 `response.completed` 读，输入 / 缓存 / 输出 token 照旧写 `agent_runs`，每日 token 上限保留。
- **删除智谱**（#64）：`zhipu` provider、`ZHIPU_API_KEY`、`WORKBENCH_AGENT_BASE_URL`、`WORKBENCH_AGENT_MODEL`、默认模型 `glm-5.3`、额度错误码 `1113 / 1308 / 1310` 分类一并删除；`WORKBENCH_AGENT_PROVIDER` 只剩 `chatgpt` / `off`。已有运行记录与计划的 `provider` / `model` 字段保留只读。不保留智谱作第二 provider：两套错误码与配置的维护成本高于「ChatGPT 不稳时的退路」的价值；真要退路时在设置页断开再连另一个 ChatGPT 账号。
- **不做**：本地 CLI 适配器（`claude-code` / `codex` / `pi`）、MCP 服务、禁用自带工具的测试、按「用途 × 阶段」配多运行时、自动换模型或降级。[v2.8 运行时可行性报告](v2.8-runtime-feasibility.md)保留为历史依据，不再是 v2.8 的输入。

**不做**：新数据源或备源（v2.9）、新数据族、盘中、LangGraph Studio、并行 Agent 单元、改任何计算口径或 Agent 提示词（接入 ChatGPT 必需的 `instructions` 搬运除外）。

**退出条件**：连续 10 个交易日 `daily` 定时运行无需人工介入（允许降级，不允许失败）；手动造一次节点失败并从该节点续跑成功，续跑后 `stage_runs` 仍是 10 行且已完成节点未重跑；没有任何外部请求的真实耗时超过 2 分钟（含重试），每节点 `duration_ms` 与起止时间之差一致；你任选 3 天打开运行详情，都能回答「哪个数据源对哪个目标没拿到、为什么、卡在哪个节点」；Agent 单元在 ChatGPT 上完成且通过同一套引用校验，`agent_runs` 有 ChatGPT 的模型名与 token；智谱代码、配置与文档引用已删除，`grep -ri zhipu` 只剩 CHANGELOG 与冻结文档。

### 4.7 多数据源与降级（v2.9，大纲）

只定方向，spec 时再定交付与退出条件：

- **目标**：单一数据源故障不再让当日采集失败。每个数据族（日线、资讯、财报 / 基本面、SEC、FRED、成分股）定义主源与至多一个备源；主源超时、报错或返回空时切备源；选择与降级逻辑在宿主代码，不交给模型。
- **证据先行**：以 v2.8 积累的 `data_fetch_runs` 逐目标失败明细为依据，先给失败最多的族加备源，不是一次全加。
- **可见性**：每条拉取记录写 `source_used` 与是否降级；备源与主源的口径差异（如复权方式、时区、延迟）在数据菜单与运行详情里可见；备源数据同样受截止时间约束。
- **参考**：[HKUDS/Vibe-Trading](https://github.com/HKUDS/Vibe-Trading) 的数据源适配层，写 spec 时再读。
- **不做**：用历史数据调参、自动选「更好看」的源、盘中源。

### 4.8 主动研究（v2.10，大纲）

只定方向，spec 时再定交付与退出条件：

- **入口**：你指定一只股票或一个问题；持仓出现新披露；无买入信号但你想看的标的。
- **研究档案**：问题、标的与期限、触发来源、优先级、证据截止时间、状态（待研究 / 研究中 / 等待证据 / 已形成结论 / 已结束）、预算消耗、结论版本、下一次复查条件；内容至少回答论点、事实与来源（正式披露 / 价格事实 / 用户观点 / 模型推断分开）、催化与时间、反证与替代解释、价格与情景、下一步。「研究完成」不要求产生买入建议，有证据的放弃和有条件的等待都是有效产出；数据取不到只能记为阻塞或覆盖不足，不能写成不存在机会。
- **与 v2.5 的关系**：研究档案形成计划时走同一套 Agent 计划结构与版本链。
- **数据范围**：先复用现有日线、财季、指引、SEC、资讯和市场环境；缺的按已支持来源补查或保留缺口（基本面的[已知限制](../features/fundamentals.md#已知限制)）。补采后由宿主开新一轮证据快照、记新截止时间，再生成新版结论；模型不能自行移动截止时间；新资料不塞回旧研究或旧影子计划。研究范围由任务宿主分配：单标的任务只读相关公司和基准；比较任务才获授多个标的。外部材料正文只作为证据，不授予工具权限。

### 4.9 验收方式

- 每版走 DoD（spec → plan → 自动化测试 → 手动触发验收 → 连续 N 日定时验收），验收证据各自追加到 `v2.x-acceptance.md`。
- v2.5 强调「每日复查行完整 + 版本截止时间与引用成立」的自动校验，以及你「只读 Agent 计划即可决定」的使用验收；v2.6 以你的使用验收为主（能解释、能回答）；v2.7 强调「知识受截止时间约束」的自动校验 + 复盘卡与知识回看的使用验收；v2.8 强调「定时运行连续 10 个交易日不需人工介入」的自动证据 + 一次人为失败的续跑演练 + 你「看详情页就能说出哪里没拿到数据」的使用验收；v2.9、v2.10 spec 时定。
- 以上「你确认」类条件，没有记录就不算过；工程完成不代替使用验收。

## 5. 远期：Agent 主导投研

> 摘自 2026-10-27 的「Agent 主导投研总纲」草稿；是方向建议，不排期。§4 的 v2.5–v2.10 是通向它的前半段。

**最终状态**：你打开「今日」先看到四件事——①已有持仓要不要处理 ②哪些新机会值得看、有什么反证、什么条件成立才行动 ③合在一起能不能实施（持仓、现金、待决定计划一起考虑后的冲突与先后）④今天哪些结论不能给（缺什么数据、哪个任务失败、哪些标的未研究）。每条建议先给结论和相对上次的变化，展开后有证据、推导、风险和历史版本。数据、知识、运行一览保留为核查入口。

**三方职责**：

| 工作 | Agent | 程序 | 你 |
|---|---|---|---|
| 研究范围与风险预算 | 提出调整建议 | 保存版本并检查限制 | 设定或修改约束 |
| 今天研究什么 | 在约定范围内选题、排序、安排补查 | 去重、调度、限时、限制成本 | 可补充问题 |
| 数据与证据 | 判断还缺什么，调用允许的工具 | 保存原文、来源、时间、覆盖及失败状态 | 可提供材料和纠错 |
| 投资判断 | 写论点、催化、反证、情景和不行动理由 | 验证引用和数值，保留版本 | 阅读、追问、决定采纳与否 |
| 价位与仓位 | 提出有依据的情景、方法与参数 | 按已支持的方法重算并检查单笔和组合限制 | 决定实施方案 |
| 交易与实际账户 | 给出行动建议，等待成交反馈 | 区分建议、决定、成交和持仓 | 自行下单，录入成交与资金 |
| 持仓跟踪 | 检查原论点和失效条件，提出修订 | 按约定频率采集、触发检查、保存变更 | 决定是否调整持仓 |
| 学习与改进 | 自动整理观察、起草经验和流程改进 | 保存证据与实验版本 | 审定正式经验、策略和风险参数变更 |

**能力阶段与版本的对应**：

| 阶段 | 用户能力 | 对应 |
|---|---|---|
| R0 结果看得懂、问题查得到 | 看清数据状态、单份计划推导、当日处理过程 | v2.3、v2.4、v2.6 |
| R1 Agent 稳定执行并回答问题 | 可读知识、可引用个人判断、可靠执行、讨论和修订计划 | v2.5、v2.7、v2.8 |
| R2 Agent 主动完成研究 | 不必逐只派工；自动排题、补证据、提出与反驳论点，生成研究档案 | v2.10 |
| R3 Agent 交付默认行动简报 | 每天一份结合持仓和现金的优先级清单（组合检查：持仓、现金、单票与总风险、行业集中、待决定计划；互斥方案标明替代关系） | 不排期（§6.1） |
| R4 Agent 持续负责跟踪 | 更多事件源、只突出有意义的变化、本地服务延误可见 | 不排期；日频与批处理内的事件判断已在 v2.5 |
| R5 Agent 复盘并提出改进 | 周 / 月复盘同时检查研究判断、计划设计、实际实施；Agent 可提出规则、提示词、工具的改进，不能自行改风险预算或上线新策略 | 不排期；人侧复盘已在 v2.7 |

**切换默认入口前的门槛**（v2.5 把 Agent 设为默认复查对象时沿用）：保留切回旧布局的入口与全部历史；Agent 故障时显示失败与规则基线，不伪装成 Agent 已完成，也不自动切换运行时；`coverage.missing` 为空不等于全部成功，没有候选的空跑不替代非空研究验收；收益比较以前向记录为主，统一期限、决策时间、候选范围和成本假设；关闭联网不消除模型预训练中可能知道的后续信息，历史重跑只能声称「所引用证据受截止时间约束」。

## 7. 交付标准与状态用语

**交付标准（DoD）**——每个阶段的每项交付同时满足四条：

1. **手动入口**：自动任务有手动触发路径（API、CLI 或前端按钮至少其一）。
2. **验证入口**：结果可查（`job_reports`、前端状态或 CLI 输出至少其一）。
3. **功能说明 + 如何验证**：文档或页面写清做什么、怎么手动验证一次。
4. **离线测试**：pytest 离线可跑，数据库、网络、LLM 全部 mock 或注入。

**状态用语**：

| 用语 | 含义 |
|---|---|
| `engineering_done` | 代码和入口在仓库里 |
| `runtime_unverified` | 尚未经真实库、HTTP 或页面验收 |
| `gate_hold` | 证据不够，不能当作有效规则 |
| `user_acceptance_pending` | 工程结果不能代替使用验收 |

没有新证据时，不把状态改成完成。

### 8.8 v2.8 重定义为每日工作流（2026-10-28）
