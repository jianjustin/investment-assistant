## 1. 最终目标与成功标准

**最终目标**（用户 2026-10-27）：Agent 生成交易计划，你复查并实施；Agent 的计划能沿时间链路反思、吸收后来的信号出新版；系统把它做了什么、为什么讲给你听；你的交易能力随系统一起进化。

**你的角色**：阅读 Agent 的计划与理由，决定是否下单、何时止盈止损，自己下单并录入成交，审定复盘得出的经验。
**Agent 的角色**：从规则候选出发给出可复查的计划，每日复查并修订，计划结束后起草复盘；远期扩展到主动研究（§5）。
**程序的角色**：数据、计算、校验、风险限制、记录；判定始终在宿主代码，不交给模型。

**主指标：月度账户收益率**

| 档位 | 月度收益率 |
|---|---|
| 非常优秀 | > 20% |
| 优秀 | 10% – 20% |
| 可行 | 0% – 10% |
| 需关注 | < 0% |

- 口径：（本月末资金快照 − 上月末资金快照 − 区间净出入金）÷ 上月末资金快照；同一行显示同月 SPY。
- **流程复查触发**：滚动 3 个月复合收益 < 0 **且**跑输 SPY。
- 优先级：收益 > 纪律 > 认知 > 省时间。一年约几十笔交易，第一年做到「收益口径算得准、算得诚实」，不以「已证明跑赢」为验收。

**主线（v2.5–v2.9 完成后）**：扫描 `screen-1` → 规则候选 → **Agent 计划（默认复查对象）+ `plan-1`（规则基线）** → 你复查、决定、自己下单 → **每日复查与版本更新** → 计划结束后**复盘卡讲给你听** → 你审定的经验进「我的知识」→ 被后续 Agent 引用、被影子结果检验。

**成功标准**：

| # | 标准 | 版本 |
|---|---|---|
| 1 | 每个买入单元，你只读 Agent 计划就能决定做不做：计划有论点、证据、反证、失效条件、价位依据、下次复查条件 | v2.5 |
| 2 | 每份有效 Agent 计划每个交易日有一条复查记录（维持 / 修订 / 作废）；新信号或你的输入能产生新版，差异可读；所有版本可回放，截止时间各自固定 | v2.5 |
| 3 | 不读仓库文档，在系统里能看懂：今天批处理跑了什么、任一概念是什么意思、任一份 Agent 计划的每个字段和数字从哪来 | v2.6 |
| 4 | 每笔结束的交易有复盘卡（预期 vs 实际、三条轨道的 R、你的决定与纪律判定、教训草稿）；教训经你审定进「我的知识」；每条知识被引用后能回看表现 | v2.7 |
| 5 | Agent 可在 ≥ 2 个本地 CLI 运行时下运行，引用校验结果一致，截止时间与工具记录的保证不变 | v2.8 |

## 2. 原则与边界

**沿用原则**（自 v1 [00](../archive/roadmap-v1/00-principles-and-direction.md) 起有效）：

1. **闭环优先于回测**：价值在「计划、执行、结果」的归因，不在小样本上的组合回测。
2. **证伪优先于建设**：规则和 Agent 都要有影子跟踪证据，没有证据不宣称有效。
3. **诚实优先于漂亮**：统计带样本量；区分「没算」和「无信号」；不用历史反推参数。
4. **人在环路**：系统出计划，人决定是否下单；不接券商、不自动下单。
5. **只追加写入**：按时点可还原，更正用新记录指向旧记录。
6. **截止时间覆盖一切 Agent 输入**：工具数据、概念卡、我的知识、用户输入，都只能看到截止时间之前的内容；新经验不回填到旧计划。

**边界**：

- 不接券商、不自动下单、不做盘中自动交易；只做美股波段；本地单进程运行。
- 价位是规则或算术结果并标注证据状态；所有规则都未经验证（Phase 0 Gate HOLD），推送里如实标注。**Agent 成为默认复查对象不等于 Agent 有效**：`plan-1` 继续计算、影子跟踪、三方对比；不因界面默认展示 Agent 解除 Gate HOLD；不做自动晋升。
- **版本只追加**：旧版计划、当时的决定和成交不改写；修订版指向旧版并列出差异；影子跟踪按版本记录，汇总时首版与最新版分开。
- 证据不够时停住：数据缺失、计划超限、Agent 引用无效，都显式标出，不写成「无信号」。
- 每版 spec → plan → DoD；真实库迁移先 `pg_dump` 备份并单独授权；push 单独授权；与 #投研-工作（Team B）不衔接。
- 凭据只从环境变量或各 CLI 自身的登录态读取，系统不保存、不进报告；错误文本脱敏。
- 工程纪律：路由层薄封装（`api/routes` → `services` → `db` / `tasks`）；外部失败结构化返回，不吞成成功。

## 4. 当前路线 v2.5–v2.9

### 4.1 重排依据与假设

**用户原话（2026-10-27）**：

- 核心目标：agent 生成交易计划，我来复查并实施计划；agent 交易计划可基于时间链路反思 + 补充信号。
- 问题：我不能了解系统运行原理；我的预期是我的交易能力能够跟随系统进化。

**对现状的判断**（2026-10-27 仓库核对，见 [Agent 轨道](../features/agent-track.md)、[每日计划](../features/daily-plan.md)、[复盘](../features/review.md)）：

- Agent 现在只在信号日批处理里给一次 `agent-1`，之后不再更新；规则 `plan-1` 是主计划，Agent 是并列挑战者。能更新计划的能力在旧排序里要到 v2.8 才有，由新信号触发的更新更远。
- 「看懂」已有一半：v2.3「数据」菜单能看数据从哪来，v2.4 推导链能看 `plan-1` 怎么算。缺的是三件事：今天整个批处理跑了什么、每个概念是什么意思、Agent 为什么这么建议。
- 「我的能力进化」没有任何交付对应。旧 v2.6 的概念卡解决「这个指标是什么」，旧 v2.8 的沉淀经验是喂给 Agent 的记忆。没有一环把「这笔为什么对、为什么错」讲给用户，也没有一环检验用户自己的判断。
- 旧 v2.7 运行时切换是最大的纯基础设施块，和删除智谱绑在一起，不直接服务上面任一目标。

**假设**（用户未逐条确认，默认成立；推翻任一条就改对应版本）：

| # | 假设 | 影响 |
|---|---|---|
| A1 | 基线是 2026-10-27 早先确认的 v2.5–v2.9（决策 #25–#44）。同日另两份未提交草稿——「压缩路线」（v2.5-lite / v2.8-core / v3-agent-loop）与「Agent 主导投研总纲」（R0–R5）——作为参考输入：前者的取舍逐条在 #53 说明，后者的远期部分摘入 §5 | 文档 |

| A3 | 「基于时间链路反思」= 同一单元的 Agent 计划有**版本链**：信号日首版 → 之后每个交易日对有效计划复查 → 有新信号或你补充了信息就出新版，每版写明相对上版改了什么、为什么；旧版不改、各版截止时间各自固定 | v2.5 |
| A4 | 「补充信号」两类：系统采到的（新日线、新财报、资讯、区制变化、止损或 T1 触及、临近到期）和你贴进来的（用户输入）。不新增数据族、不做盘中 | v2.5 |
| A5 | 「了解系统运行原理」分三层，都在系统内看，不靠读仓库文档：①今天跑了什么（运行一览）②这个概念、这个数字什么意思（概念卡 + 已有推导链）③Agent 为什么这么建议（可读的论点结构与工具调用顺序） | v2.6 |
| A6 | 「交易能力跟随系统进化」= 闭环的人侧：每笔结束的交易有讲给你听的复盘卡；你的判断写进系统、被 Agent 引用、再被影子结果检验；每周有一段「你学到了什么」。这与给模型喂记忆是两件事，本文把人侧放在前面 | v2.7 |
| A7 | Agent 的入口仍是规则候选（`screen-1` → 规则 v1 → 买入单元）。无买入信号也能研究、用户指定标的或问题的研究，留到 v2.9 | 范围 |

| A9 | 多 agent 对抗 `agent-2` 进 backlog；原 v2.9 的版本号改给主动研究 | 范围 |
| A10 | 不写周数估计。v2.0–v2.4 五天完成，工程不是瓶颈；每版实际耗时由「连续 N 个交易日」的验收决定 | 排期 |

### 4.2 顺序理由

- v2.5 先做，因为它直接交付用户的核心目标，且只用现有数据族、现有工具层和现有运行时，不等任何基础设施。
- v2.6 紧随其后，因为 v2.5 之后 Agent 计划变多、变长、有版本，不配解释层用户更看不懂；v2.6 的概念卡又是 v2.7「我的知识」挂靠的对象。
- v2.7 放第三，因为复盘卡需要 v2.5 的版本链（预期是哪一版的预期）和 v2.6 的概念卡（教训挂在哪个概念上）；放得更晚则 v2.5 起积累的交易没有复盘。
- v2.8 放第四：它不改变用户看到的任何东西；可行性验证提前，真正的切换等前三版把调用量和成本暴露出来再做。
- v2.9 是扩张范围，等前面闭环跑过真实交易日再定。

### 4.3 计划时间线（v2.5）

**Agent 计划结构**（版本号由 spec 定；现 `agent-1` 的输出只有动作、价位、理由、风险提示）：

| 字段 | 内容 | 校验 |
|---|---|---|
| 动作与价位 | 入场区间、止损、T1，照旧每个价位引用价格类工具调用 | 沿用 `citations.py`，失败整条作废 |
| 论点 | 1–3 条「为什么现在值得做」，每条带引用 | 引用必须存在 |
| 关键反证 | 反方产出，逐条对应论点 | 不改价位 |
| 失效条件 | 可由程序检查的条件，如「收盘跌破 X」「财报前未到入场区」「区制转防守」 | spec 定可检查的条件集合 |
| 下次复查条件 | 什么事发生就该重新看；默认「下一交易日」 | — |
| 相对上版变化 | 首版为空；修订版列出改了哪些字段、为什么、引用新证据 | 修订版必填 |

**默认复查对象**：「今日」计划卡 Agent 计划在前，`plan-1` 折叠为「规则基线」一行，可展开、可切换回旧布局；推送同样 Agent 行在前、规则行在后。决定时执行依据三选一照旧（规则 / Agent / 自定），三方对比 `tracks-1` 不变。Agent 失败或作废时显示失败原因和规则基线，不伪装成有 Agent 计划。证据状态「未验证」常驻。

**版本链**：

- 版本 0 由信号日批处理生成（现有 `agent` 阶段）。每个新版 `supersedes` 指向上一版；旧版不改。
- **每日复查**：批处理新增一个阶段（`stage_runs` 注册表从 7 行变 8 行，`stages-1` → 新版本号），对象是所有**有效的 Agent 计划**（未过期、未作废）加**关联持仓的计划**。输入 = 上一版全文 + 自上版截止时间以来的新数据（同一套工具层，截止时间 = 本次运行）+ 新的用户输入。输出三选一：维持（写一行原因）、修订（走完整的提议 + 反方 + 校验生成新版）、作废（写原因）。复查是单阶段调用，只有修订才触发完整流程，控制调用量。
- **系统信号触发**：不另建事件系统。复查阶段里按规则判断是否「应修订」：新 8-K、`abnormal_move`、止损或 T1 触及、临近到期（到期前 1 个交易日）、区制变化。这些条件作为复查提示词的一部分给模型，也写进复查记录供回看。
- **用户输入触发**：「标的」页和计划页可贴入文本（研报要点、新闻、你的判断），存为带时间戳的只追加记录，引用形式 `user:<id>`；贴入后可点「重新复查」立即跑一次，截止时间 = 点击时刻。用户输入只是证据，不授予权限、不改规则。
- **截止时间**：每一版的截止时间 = 生成时刻，写进版本记录；工具层照旧只读截止时间之前的数据。

**影子跟踪**：对象是**版本**，不是单元。每版从生成时刻起算，不回溯到信号日。汇总时「首版」和「最新版」各算一条，防止事后修订把结果修好看；三方对比里 Agent 轨道取「你决定时看到的那一版」。

**推送**：新计划段照旧；新增「计划更新」段，只推修订与作废，维持不推。

**预算**：复查对象数小（有效计划 + 持仓，通常个位数）；沿用每单元尝试上限、批处理时间预算、每日 token 上限，超限记 `skipped` 并写原因。

**退出条件**：

- 连续 10 个交易日，每份有效 Agent 计划每日恰有一条复查记录，`stage_runs` 每次运行恰好 8 行。
- 至少一次由系统信号触发、一次由用户输入触发的修订版，「相对上版变化」可读且引用成立。
- 每个版本有自己的影子跟踪行；三方对比能指出决定用的是哪一版。
- 你确认：连续两周，只读 Agent 计划（不展开规则基线）就能做决定。

**不做**：盘中、新数据族、运行时切换、无信号的研究、对话式问答（v2.7）。

### 4.4 看懂系统（v2.6）

| 交付 | 内容 | 数据来源 |
|---|---|---|
| **运行一览** | 「今日」顶部一段：今天批处理 8 个阶段各一句人话（扫了多少只、触发几只、几份计划、Agent 跑了几个单元、复查了几份、推了几条）+ 计数 + 跳过原因；可选日期查往日 | 已有 `stage_runs`，不画节点图、不另建表 |
| **「原理」页** | 「知识」菜单下一页：系统每天怎么跑的叙述，规则 v1 八条、`plan-1` 公式、Agent 流程、复盘口径都在；每一步链接到概念卡和当天的阶段行 | 仓库内 Markdown 源文件，系统读取并渲染（与概念卡同一机制） |
| **概念卡 + 就地展开** | 源文件是仓库内版本化 Markdown，随代码改（代码改了口径就同提交改卡）；「知识」菜单可浏览、按数据族 / 指标 / 规则项分组、互链；「数据」菜单、推导链、「标的」页、计划卡上的概念名可就地展开摘要，一跳到完整卡。概念范围：数据族、指标、规则项、`plan-1` 字段、Agent 计划字段（论点、反证、失效条件、复查条件）、复盘指标（R、纪律四项、三方对比状态）。引用形式 `concept:<id>@<版本>` | 仓库 Markdown |
| **Agent 推理阅读视图** | 计划卡展开后按时间顺序读：提议者读了什么（工具调用的参数与返回值，用概念卡解释字段）→ 论点 → 反方 → 回应 → 校验结果；版本链上的每一版都能这样读 | 已有 `agent_runs`、`agent_tool_calls` |
| **「标的」页重排 + K 线标注** | ①信号与计划（今日触发、有效计划及版本链、持仓）→ ②关键数据（推导链所需输入）→ ③背景（基本面、下次财报日、行业强弱、区制）→ ④历史（K 线上标候选、各版本价位、你的成交）；与推导链互相链接；不新增数据，只重排与收敛 | 已有数据 |
| Agent 工具 `get_concept(id)` | Agent 读概念卡；概念卡随代码版本走，不按时点回读（写明这一例外） | — |

**退出条件**：每个数据族、指标、规则项、`plan-1` 字段、Agent 计划字段、复盘指标都有概念卡且系统内可读；运行一览的计数与 `stage_runs` 逐项一致；你验收：不读仓库文档，能向第三人解释一份 Agent 计划的每个字段与每个数字从哪来；「标的」首屏能回答「今天该关注什么、为什么」。

**不做**：workflow 节点图、历史某日回放界面（§6.1）；「数据」菜单导出。

### 4.5 我的成长闭环（v2.7）

| 交付 | 内容 |
|---|---|
| **复盘卡** | 触发：计划结束（止损、T1、过期、作废）或持仓平仓。Agent 单阶段起草：预期 vs 实际（引用当时版本的价位与之后的日线）；三条轨道的 R（取自 `tracks-1`）；你的决定（采纳 / 否决 / 自改）与纪律判定（追高、过早止盈、死扛、计划外）；教训草稿（带引用、写明适用范围与反例）。你审定（可改）后进「我的知识」；未审定的草稿不被任何 Agent 引用。「复盘」页新增复盘卡列表 |
| **我的知识** | 数据库只追加，修改 = 新版本指向旧版本，归档 = 状态记录；挂到概念或标的（可多挂），带写入时间；「知识」菜单写、改、归档、看版本；「标的」页显示挂在该标的上的知识；引用形式 `know:<id>@<版本>`。Agent 工具 `get_knowledge(ticker 或 concept)` 受截止时间约束：为信号日 T 复查或生成计划时只看到 T 之前写入的条目（自动校验）。Agent 计划记录引用了哪些知识，点开看引用时的版本 |
| **知识表现回看** | 每条知识 → 引用它的计划版本 → 这些版本的影子结果；样本量常驻，少于 5 个不给均值。这是检验你自己判断的机制，与检验规则、检验 Agent 同一口径 |
| **就此计划讨论** | 从计划卡、「标的」页、复盘卡进入，带计划上下文。能问「怎么来的」（Agent 读推导链、`agent_runs`、概念卡，给带引用的解释，不改任何东西）；能在对话里起草或改写经验；补充信息走 v2.5 的用户输入。对话历史与阶段记录持久化。旧 v2.8「对话生成新版计划」合并到 v2.5 的「重新复查」，不单独做 |
| **周度「你学到了什么」** | 周度复盘 `review-5` 加一段：本周纪律四项、本周复盘卡摘要、本周被检验的知识；随周度推送 |

**退出条件**：自 v2.7 上线起每笔结束的交易都有复盘卡；至少 2 条教训经你审定进「我的知识」，且后续至少一份 Agent 计划引用并在卡上显示；至少 1 条知识有表现回看；你验收：读一周的复盘，能说出自己哪类决定在亏、下周要改什么。

### 4.6 运行时可切换（v2.8）

- **分层**：编排（阶段顺序、分支、代码校验节点、检查点）保留在 LangGraph `StateGraph` + PostgresSaver；单阶段执行从 LangGraph `ToolNode` + 智谱改为本地 CLI 运行时适配器 `run_phase(提示词, 工具范围) → 输出 + token 用量`；工具层同一组函数另以本地 stdio MCP 服务暴露；判定（引用、价位、基本校验，`citations.py`）始终在宿主代码。
- **适配器**：`claude-code`（`claude -p` + MCP 配置）、`codex`（`codex exec` + MCP）、`pi`（pi 不内置 MCP，通过扩展注册同一组工具）。三者都是本地 CLI，用各自的登录态 / 订阅。以后按 token 计费的 API 模型（含智谱等）统一在 pi 里配置 provider，系统侧只认 `pi` 一个适配器。
- **宿主注入、模型不可改**：截止时间、允许查询的标的范围、`run_id` / 阶段写进 MCP 服务的启动参数；每次调用照旧写 `agent_tool_calls`（参数、返回值、SHA-256）。
- **关掉运行时自带能力**：CLI 自带的 shell、文件读写、联网、网页搜索一律禁用，只允许本 MCP；否则模型能绕过截止时间读到「未来数据」。spec 里逐个运行时写清禁用方式，并有测试证明禁用生效。
- **配置**：按「用途 × 阶段」各配一个运行时（及可选模型名）：提议、反方、复查、复盘卡、对话。配置是唯一选择方式，**不做自动降级**。单元级失败（CLI 不可用、未登录、超时、订阅额度用尽）记 `error` / `skipped` 并写明原因，不换运行时重试；你可以改配置，或在「重新运行 Agent」时手动指定运行时再跑。运行记录新增运行时与模型字段。
- **可行性验证提前到 v2.5 期间**：逐个运行时核实①无人值守运行（LaunchAgent 环境下登录态可用）②禁用自带工具 ③接上本工具集 ④报告 token 用量 ⑤在批处理时间预算内完成。只出报告，不合并代码。不满足的运行时留 backlog。
- **删除智谱**：至少两个 CLI 运行时通过验证后才删 `zhipu` provider、`ToolNode` 循环、`ZHIPU_API_KEY` / `WORKBENCH_AGENT_BASE_URL` 等配置与额度错误码分类；已有运行记录与计划保留只读。此前 v2.5–v2.7 照旧用智谱。
- **检查点粒度**：CLI 运行时只能在节点边界续跑，不能从一次 CLI 会话中途恢复；接受这一代价。
- backlog 的 Agent 工具 `get_fundamentals` 并入本版工具集。

**退出条件**：同一单元在 ≥ 2 个运行时下跑出的计划都通过同一套引用校验；批处理按配置选运行时，失败按单元记原因、不自动换；至少两个 CLI 运行时通过可行性验证且智谱代码与配置已删除；连续 5 个交易日 `coverage.missing` 为空。

### 4.7 主动研究（v2.9，大纲）

只定方向，spec 时再定交付与退出条件：

- **入口**：你指定一只股票或一个问题；持仓出现新披露；无买入信号但你想看的标的。
- **研究档案**：问题、标的与期限、触发来源、优先级、证据截止时间、状态（待研究 / 研究中 / 等待证据 / 已形成结论 / 已结束）、预算消耗、结论版本、下一次复查条件；内容至少回答论点、事实与来源（正式披露 / 价格事实 / 用户观点 / 模型推断分开）、催化与时间、反证与替代解释、价格与情景、下一步。「研究完成」不要求产生买入建议，有证据的放弃和有条件的等待都是有效产出；数据取不到只能记为阻塞或覆盖不足，不能写成不存在机会。
- **与 v2.5 的关系**：研究档案形成计划时走同一套 Agent 计划结构与版本链。
- **数据范围**：先复用现有日线、财季、指引、SEC、资讯和市场环境；缺的按已支持来源补查或保留缺口（基本面的[已知限制](../features/fundamentals.md#已知限制)）。补采后由宿主开新一轮证据快照、记新截止时间，再生成新版结论；模型不能自行移动截止时间；新资料不塞回旧研究或旧影子计划。研究范围由任务宿主分配：单标的任务只读相关公司和基准；比较任务才获授多个标的。外部材料正文只作为证据，不授予工具权限。

### 4.8 验收方式

- 每版走 DoD（spec → plan → 自动化测试 → 手动触发验收 → 连续 N 日定时验收），验收证据各自追加到 `v2.x-acceptance.md`。
- v2.5 强调「每日复查行完整 + 版本截止时间与引用成立」的自动校验，以及你「只读 Agent 计划即可决定」的使用验收；v2.6 以你的使用验收为主（能解释、能回答）；v2.7 强调「知识受截止时间约束」的自动校验 + 复盘卡与知识回看的使用验收；v2.8 强调各运行时下引用校验一致、自带工具禁用有测试；v2.9 spec 时定。
- 以上「你确认」类条件，没有记录就不算过；工程完成不代替使用验收。

## 5. 远期：Agent 主导投研

> 摘自 2026-10-27 的「Agent 主导投研总纲」草稿；是方向建议，不排期。§4 的 v2.5–v2.9 是通向它的前半段。

**最终状态**：你打开「今日」先看到四件事——①已有持仓要不要处理 ②哪些新机会值得看、有什么反证、什么条件成立才行动 ③合在一起能不能实施（持仓、现金、待决定计划一起考虑后的冲突与先后）④今天哪些结论不能给（缺什么数据、哪个任务失败、哪些标的未研究）。每条建议先给结论和相对上次的变化，展开后有证据、推导、风险和历史版本。数据、知识、运行一览保留为核查入口。

**三方职责**：

| 工作 | Agent | 程序 | 你 |
|---|---|---|---|
| 研究范围与风险预算 | 提出调整建议 | 保存版本并检查限制 | 设定或修改约束 |
| 今天研究什么 | 在约定范围内选题、排序、安排补查 | 去重、调度、限时、限制成本 | 可补充问题 |
| 数据与证据 | 判断还缺什么，调用允许的工具 | 保存原文、来源、时间、覆盖及失败状态 | 可提供材料和纠错 |
| 投资判断 | 写论点、催化、反证、情景和不行动理由 | 验证引用和数值，保留版本 | 阅读、追问、决定采纳与否 |
| 价位与仓位 | 提出有依据的情景、方法与参数 | 按已支持的方法重算并检查单笔和组合限制 | 决定实施方案 |
| 交易与实际账户 | 给出行动建议，等待成交反馈 | 区分建议、决定、成交和持仓 | 自行下单，录入成交与资金 |
| 持仓跟踪 | 检查原论点和失效条件，提出修订 | 按约定频率采集、触发检查、保存变更 | 决定是否调整持仓 |
| 学习与改进 | 自动整理观察、起草经验和流程改进 | 保存证据与实验版本 | 审定正式经验、策略和风险参数变更 |

## 7. 交付标准与状态用语

**交付标准（DoD）**——每个阶段的每项交付同时满足四条：

1. **手动入口**：自动任务有手动触发路径（API、CLI 或前端按钮至少其一）。
2. **验证入口**：结果可查（`job_reports`、前端状态或 CLI 输出至少其一）。
3. **功能说明 + 如何验证**：文档或页面写清做什么、怎么手动验证一次。
4. **离线测试**：pytest 离线可跑，数据库、网络、LLM 全部 mock 或注入。

**状态用语**：

| 用语 | 含义 |
|---|---|
| `engineering_done` | 代码和入口在仓库里 |
| `runtime_unverified` | 尚未经真实库、HTTP 或页面验收 |
| `gate_hold` | 证据不够，不能当作有效规则 |
| `user_acceptance_pending` | 工程结果不能代替使用验收 |

没有新证据时，不把状态改成完成。
