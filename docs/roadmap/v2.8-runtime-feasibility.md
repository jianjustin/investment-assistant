# v2.8 运行时可行性报告

[roadmap](roadmap.md) §4.6 要求在 v2.5 期间先核实三个本地 CLI 运行时（`claude-code`、`codex`、`pi`）能否替换 Agent 单阶段执行（假设 A8：只出报告，不合代码）。本报告逐个运行时核实五项：①无人值守运行 ②禁用自带工具 ③接上本工具集 ④报告 token 用量 ⑤在批处理时间预算内完成。

- 验证日期：2026-10-28，本机（macOS，用户 `chenjianrui`）。
- 版本：`claude` 2.1.311、`codex-cli` 0.164.0、`pi` 1.4.0。三个都已安装。
- 被替换的对象：[Agent 轨道](../features/agent-track.md)的单阶段调用（LangGraph `ToolNode` + 智谱），工具层是 `investment_assistant/workbench/agent/tools.py` 的八个函数。批处理整体预算 1500 秒，单元最多尝试 3 次。
- 所有验证只用极小提示词，没有碰真实数据库，没有改系统、shell 或 LaunchAgent 配置，没有安装软件。命令输出已脱敏：不含密钥、令牌、账号邮箱。

## 0. 先看结论

三个运行时在本机都能无人值守跑通、能关掉自带工具只留指定 MCP 工具、能接上最小 MCP 工具集、能拿到 token 用量，单次最小调用都在几十秒以内。差别在「禁用有多干净」和「有哪些坑」：

- **`claude-code`**：最干净。`--tools ""` 把内置工具全部移除，初始化消息里能直接读出实际工具清单。坑：本机登录态不是订阅 OAuth，而是 `~/.claude/settings.json` 里指向本机网关的环境变量；用户级 hooks / 插件会进入上下文。
- **`pi`**：干净，且**自带 MCP**（路线文档里「pi 不内置 MCP」在 1.4.0 不成立）。坑：`pi` 是 node 脚本，node 不在 LaunchAgent 的 PATH 里；没有操作系统沙箱，禁用完全靠「不声明工具」；MCP 配置只能走文件。
- **`codex`**：能禁到只剩 MCP，但是**黑名单式**，且有残留：`apply_patch` 工具关不掉（靠 `read-only` 沙箱兜底拒写），所有工具都经一个 JS 隔离区 `exec` 调用，子代理工具仍在。默认推理强度下一次三步任务跑了 268 秒，每次调用固定约 2 万输入 token。

建议 `claude-code` + `pi` 作为 v2.8 首批（满足「至少两个 CLI 运行时通过验证」才删智谱），`codex` 带条件，详见[第 5 节](#5-对-v28-spec-的建议)。

## 1. 验证方法

- **最小环境**：`env -i HOME=$HOME PATH=/opt/homebrew/bin:/usr/bin:/bin:/usr/sbin:/sbin` 外加 LaunchAgent plist 里的代理变量（`http(s)_proxy` 指向本机 1082，`no_proxy` 为本机地址）。这是 plist 里 `EnvironmentVariables` 的子集；plist 本身没有改。
- **真实 launchd 环境**：`launchctl submit -l tmp.feasibility.<名字> -- <脚本>` 起临时任务，跑完 `launchctl remove`。launchd 给的 PATH 是 `/usr/bin:/bin:/usr/sbin:/sbin`（比 plist 少 `/opt/homebrew/bin`），也没有代理变量，比 plist 更严。`launchctl submit` 的任务退出后会被重启，所以脚本里用标记文件保证只跑一次。
- **最小 MCP 服务**（原型在会话 scratchpad，不在仓库）：约 50 行 Python，stdio、换行分隔的 JSON-RPC；暴露 `get_price_bars(ticker, lookback)` 与 `get_trigger()` 两个只读工具，返回固定数据（两根日线，最后一根 `close = 104.25`）；`--ticker`、`--cutoff`、`--run-id`、`--log` 由宿主通过启动参数注入，模拟路线文档里「截止时间、标的范围、`run_id` 写进 MCP 服务启动参数」；每次收到 RPC 与工具调用都追加一行日志，用来证明 CLI 确实启动了服务并调用了工具。
- **禁用证明**：同一条提示词让模型依次①调用 `get_price_bars` ②读一个含金丝雀字符串的文件 ③访问 `https://example.com`，最后列出可用工具。每个运行时各有一次「对照组」（不禁用、能读到金丝雀 / 能联网）和一次「禁用组」。模型自述的工具名不可信（见 1.2），以 CLI 自己给出的工具清单和事件流为准。

## 2. `claude-code`

### 2.1 五项结论

| # | 项 | 结论 | 一句话 |
| --- | --- | --- | --- |
| 1 | 无人值守运行 | 通过（有条件） | `claude -p` 一条命令跑完；launchd 下可用；登录态来自 `~/.claude/settings.json`，可执行文件不在 LaunchAgent PATH 里要用绝对路径 |
| 2 | 禁用自带工具 | 通过 | `--tools ""` + `--strict-mcp-config`，初始化消息里只剩两个 MCP 工具；读文件、联网实测失败，对照组成功 |

| 4 | 报告 token 用量 | 通过 | 结果 JSON 的 `usage` 与 `modelUsage` |
| 5 | 批处理预算内完成 | 通过 | 无工具 4–5 秒；一次 MCP 调用（两轮）21.6 秒 |

### 2.2 证据

**1. 无人值守。**

```bash
env -i HOME=$HOME PATH=/opt/homebrew/bin:/usr/bin:/bin:/usr/sbin:/sbin <代理变量> \
  /Users/<用户>/.local/bin/claude -p "只回复一个词：ok" --output-format json --tools "" \
  --strict-mcp-config --mcp-config mcp.json --no-session-persistence </dev/null
```

退出码 0，5.1 秒，`result: "ok"`，`is_error: false`。`launchctl submit` 的临时任务（PATH 为 `/usr/bin:/bin:/usr/sbin:/sbin`，无代理变量）同样通过，`duration_ms` 5200。

三个需要写进 spec 的事实：

- `claude` 在 `~/.local/bin/claude`，**不在** LaunchAgent PATH（`/opt/homebrew/bin:/usr/bin:/bin:/usr/sbin:/sbin`）里，适配器必须用绝对路径或在环境里补 PATH。
- **登录态的来源是 `~/.claude/settings.json` 的 `env`**（`ANTHROPIC_BASE_URL` 指向 `127.0.0.1` 的本机网关、`ANTHROPIC_AUTH_TOKEN`、`ANTHROPIC_DEFAULT_*_MODEL` 等），不是 Keychain：`security find-generic-password -s "Claude Code-credentials"` 查不到条目。证明：加 `--setting-sources project`（不读用户设置）后返回 `is_error: true`、`Not logged in · Please run /login`、退出码 1。所以 `--bare`（只认 `ANTHROPIC_API_KEY`、不读 Keychain）和 `--setting-sources` 不含 `user` 的写法在本机都不可用；模型名也受这份设置里的映射影响（`--model haiku` 实际落到网关映射的模型），适配器应显式传完整模型名。
- 未登录或失败时 `claude -p` 退出码为 1，结果 JSON 带 `is_error: true`。

**2. 禁用自带工具。**

```bash
claude -p "<提示词>" --output-format stream-json --verbose \
  --tools "" \
  --strict-mcp-config --mcp-config mcp.json \
  --allowedTools "mcp__ia__get_price_bars,mcp__ia__get_trigger" \
  --permission-mode dontAsk --disable-slash-commands --no-session-persistence
```

`mcp.json`：

```json
{"mcpServers": {"ia": {"command": "/opt/homebrew/bin/python3",
  "args": ["mini_mcp.py", "--ticker", "AAPL", "--cutoff", "2026-10-27", "--run-id", "r1", "--log", "calls.log"]}}}
```

- `--tools ""` 去掉全部内置工具（含 Bash、文件读写、WebFetch、WebSearch）；`--strict-mcp-config` 让用户级 / 项目级 / 插件自带的 MCP 服务都不加载；`--permission-mode dontAsk` 让任何需要询问的调用直接拒绝。
- `stream-json` 的 `system/init` 消息给出权威清单：`tools = ['mcp__ia__get_price_bars', 'mcp__ia__get_trigger']`，`mcp_servers = [{name: ia, status: connected}]`。
- 禁用组：模型回复 `CANNOT_READ`、`CANNOT_FETCH`；没有出现 Bash / Read 的 `tool_use`；`permission_denials` 为空（工具根本没声明）。
- 对照组（`--tools "Read" --allowedTools Read`）：初始化清单是 `['Read']`，模型调用 `Read`，返回金丝雀字符串。
- 模型自述的「可用工具」里出现了 `deferredToolPlaceholder` 这种并不存在的名字，说明**不能用模型自述做测试依据**，要读 `init.tools`。
- 限制：`--safe-mode` 会同时关掉 `--mcp-config` 指定的服务（实测 `mcp_servers = []`），不能用来瘦身；用户级 hooks、插件、`CLAUDE.md` 仍会加载进上下文（最小调用的缓存写入就有 3947 token，随用户配置变化）。用 `--system-prompt` 换系统提示词 + `--disable-slash-commands` 后，最小调用的缓存写入从 3947 降到 2682 token。没有 `--max-turns`，只有 `--max-budget-usd`。

**3. 接上本工具集。** 服务日志（宿主注入的参数生效）：

```text
rpc initialize → rpc notifications/initialized → rpc tools/list → rpc tools/call
call get_price_bars {"ticker":"AAPL"}   run_id=claude-t1
```

模型报告「最后一根 close 为 104.25」，与固定数据一致。CLI 里的工具名是 `mcp__<服务名>__<工具名>`。CLI 还会先发一个非标准的 `server/discover` 请求，服务端要容忍未知方法（返回 `-32601` 即可）。

**4. token 用量。** 结果 JSON（`--output-format json`，或 `stream-json` 的最后一条 `type: "result"`）：

```text
usage.input_tokens / usage.output_tokens
usage.cache_creation_input_tokens / usage.cache_read_input_tokens
modelUsage.<模型>.{inputTokens, outputTokens, cacheReadInputTokens, cacheCreationInputTokens, costUSD}
total_cost_usd, num_turns, duration_ms
```

最小调用：`input_tokens 0`、`cache_creation_input_tokens 3947`、`output_tokens 3`。**`input_tokens` 不含缓存**，总输入 = `input_tokens + cache_creation_input_tokens + cache_read_input_tokens`；多轮调用时 `usage` 是累计值（两轮那次：12122 / 48022 / 40442，输出 311）。

**5. 耗时。** 无工具最小调用 4.7–5.1 秒；带一次 MCP 工具调用（两轮、默认用户上下文）21.6 秒；`--safe-mode` 无工具 4.7 秒。

## 3. `codex`

### 3.1 五项结论

| # | 项 | 结论 | 一句话 |
| --- | --- | --- | --- |
| 1 | 无人值守运行 | 通过 | `codex exec --json`；登录态是 `~/.codex/auth.json`（ChatGPT 订阅模式），launchd 下 18 秒通过；需 `--ignore-user-config` |
| 2 | 禁用自带工具 | 通过（有残留） | 关 shell、联网、文件读取、连接器后只剩 MCP；但 `apply_patch` 关不掉，只能靠 `read-only` 沙箱拒写，且是黑名单式 |
| 3 | 接上本工具集 | 通过 | `-c mcp_servers.ia.*` 命令行注入，工具调用返回 104.25 |
| 4 | 报告 token 用量 | 通过 | `turn.completed.usage` |
| 5 | 批处理预算内完成 | 通过（有风险） | 最小调用 16–43 秒；默认推理强度下三步任务 268 秒；每次约 2 万输入 token |

### 3.2 证据

**1. 无人值守。**

```bash
env -i HOME=$HOME PATH=/opt/homebrew/bin:/usr/bin:/bin:/usr/sbin:/sbin <代理变量> \
  /opt/homebrew/bin/codex exec --ignore-user-config --ignore-rules --skip-git-repo-check \
  --ephemeral --json -s read-only -C <空目录> -m gpt-6-astra "只回复一个词：ok" </dev/null
```

- 退出码 0；事件流 `thread.started → turn.started → item.completed(agent_message "ok") → turn.completed`。`codex` 在 `/opt/homebrew/bin`，在 LaunchAgent PATH 上。
- 登录态：`~/.codex/auth.json` 的 `auth_mode` 为 `chatgpt`（订阅登录，令牌在 HOME 下的文件里）。`--ignore-user-config` 不读 `~/.codex/config.toml`，但认证仍读 `CODEX_HOME`。不加它会载入用户 config 里启用的插件、computer-use、notify 钩子，不适合批处理。
- `launchctl submit` 临时任务（PATH `/usr/bin:/bin:/usr/sbin:/sbin`，二进制用绝对路径）：18 秒，事件流完整，退出码 0。
- 失败形态：用一个空 HOME（无登录态）运行，40 秒后退出码 1，事件流末尾是 `{"type":"turn.failed","error":{"message":"unexpected status 401 Unauthorized ..."}}`。
- 网络：多次出现 `responses_websocket ... tls handshake eof`（经代理的 websocket 握手失败），CLI 自动重连或降级，事件流里可见 `{"type":"error","message":"Reconnecting... 2/5 (request timed out)"}`，最终仍成功，但把一次最小调用拖到 43 秒；同样的调用另外三次是 15.7、15.9、22.6 秒。适配器要容忍这类中间 `error` 事件，以 `turn.completed` / `turn.failed` 为准。
- 提示词参数给了之后，stdin 若是管道，其内容会被追加进提示词（`codex exec --help` 所述），批处理应显式 `</dev/null`。

**2. 禁用自带工具。** 默认配置下的对照组：模型通过 `command_execution`（`/bin/zsh -lc 'cat <文件>'`）读到金丝雀字符串，通过 `web_search` 的 `open_page` 动作打开了 `https://example.com`，工具清单里还有 ChatGPT 账号的连接器 `mcp__codex_apps__...`。**不禁用就会绕过截止时间。**

禁用组命令（`-c` 与 `--disable` 的组合）：

```bash
codex exec --ignore-user-config --ignore-rules --skip-git-repo-check --ephemeral --json \
  -s read-only -c 'approval_policy="never"' -c 'model_reasoning_effort="low"' -c 'web_search="disabled"' \
  --disable shell_tool --disable unified_exec --disable apps --disable plugins --disable multi_agent \
  --disable memories --disable view_image --disable image_generation --disable browser_use \
  --disable browser_use_external --disable computer_use --disable goals --disable skill_search \
  --disable tool_suggest --disable hooks \
  -c 'mcp_servers.ia.command="/opt/homebrew/bin/python3"' \
  -c 'mcp_servers.ia.args=["mini_mcp.py","--ticker","AAPL","--cutoff","2026-10-27","--run-id","r1","--log","calls.log"]' \
  -c 'mcp_servers.ia.enabled_tools=["get_price_bars","get_trigger"]' \
  -m gpt-6-astra "<提示词>"
```

实测结果：

- **工具清单（权威）**：让模型在 `functions.exec` 里执行 `text(JSON.stringify(Object.keys(tools)))`，返回 `["apply_patch","clock__curr_time","list_mcp_resource_templates","list_mcp_resources","mcp__ia__get_price_bars","mcp__ia__get_trigger","read_mcp_resource"]`。`exec_command`（shell）、`web_search`、连接器都已消失。
- 读金丝雀文件：`CANNOT_READ`；联网：`ReferenceError: fetch is not defined`（`exec` 是「没有 Node、没有文件系统、没有网络」的 V8 隔离区，工具描述里这样写）。
- `apply_patch` 仍在清单里。让模型用它新建文件，返回 `patch rejected: writing is blocked by read-only sandbox`，文件没有创建。也就是说**它没被禁用，是被 `-s read-only` 拒绝**。
- `read_mcp_resource` 只能读 MCP 服务暴露的资源，对本地文件无效（实测 `server must be provided`）；`list_mcp_resources` 返回空。
- `functions.exec` 是所有嵌套工具（含 MCP 工具）的唯一入口：`--disable code_mode_host` 后 MCP 工具一起失效（`Code Mode is unavailable because code-mode host is disabled ... will fail closed`）。所以 `exec` 不能关。
- `collaboration.spawn_agent` 等子代理工具仍在清单里（`--disable multi_agent` 没有去掉）。**未验证子代理是否继承禁用设置。**
- `-c include_apply_patch_tool=false` 无效（CLI 提示 `is ignored`）。没有找到去掉 `apply_patch` 的开关。
- `codex debug prompt-input` 渲染的「模型可见输入」不随 `--disable` 变化，也不展开嵌套工具，**不能**拿它做禁用测试。

**3. 接上本工具集。** 服务日志显示 `initialize → notifications/initialized → tools/list → tools/call`，参数 `{"ticker":"AAPL"}`；事件流里是 `item.completed` / `item.type = "mcp_tool_call"`，字段 `server`、`tool`、`arguments`、`result.content[0].text`、`status`。模型报告 close 为 104.25。工具名 `mcp__ia__get_price_bars`。`enabled_tools` 可限定服务里暴露哪些工具。

**4. token 用量。** `turn.completed` 事件：

```json
{"type":"turn.completed","usage":{"input_tokens":20075,"cached_input_tokens":0,"cache_write_input_tokens":0,"output_tokens":5,"reasoning_output_tokens":0}}
```

`cached_input_tokens` 是 `input_tokens` 的子集（一次多步任务里 `input_tokens 92543`、`cached_input_tokens 70912`，按数值判断是包含关系）。**最小调用也要约 2 万输入 token**（系统提示词和工具定义）。

**5. 耗时。** 最小调用 15.7 / 15.9 / 22.6 / 43.2 秒；launchd 18 秒；低推理强度 + 一次 MCP 调用 23 秒；低强度下的多步任务 36–87 秒；**默认推理强度**下同样的三步任务 268 秒，用了 92543 输入 token。批处理要显式 `-c model_reasoning_effort="low"` 或按阶段配置。

## 4. `pi`

### 4.1 五项结论

| # | 项 | 结论 | 一句话 |
| --- | --- | --- | --- |
| 1 | 无人值守运行 | 通过（有条件） | `pi -p --mode json`；LaunchAgent PATH 下找不到 `node`，补上 `~/.local/bin` 后 launchd 通过 |
| 2 | 禁用自带工具 | 通过 | `--tools 'mcp__ia__*'`；读文件、联网实测失败，对照组成功；无 OS 沙箱 |
| 3 | 接上本工具集 | 通过 | 1.4.0 自带 MCP（`builtin:mcp`），也验证了 `pi.registerTool` 扩展路径 |
| 4 | 报告 token 用量 | 通过 | `message_end.message.usage`，每条助手消息一份，要累加 |

### 4.2 证据

**1. 无人值守。**

```bash
env -i HOME=$HOME PATH=/Users/<用户>/.local/bin:/opt/homebrew/bin:/usr/bin:/bin:/usr/sbin:/sbin <代理变量> \
  pi -p --mode json --no-session --approve --no-extensions -e builtin:mcp --no-skills \
  --no-prompt-templates --no-themes --no-context-files --tools 'mcp__ia__*' "<提示词>" </dev/null
```

- **`pi` 是 `#!/usr/bin/env node` 脚本，`node` 在 `~/.local/bin/node`，不在 LaunchAgent PATH 里**：用 plist 的 PATH 运行报 `env: node: No such file or directory`；`launchctl submit` 临时任务里同样复现，脚本里把 `~/.local/bin` 加进 PATH 后通过，`pi` 返回 `104.25`，9 秒。`pi` 本身在 `~/.npm-global/bin`，也不在 PATH 上，要用绝对路径。
- 登录态：`~/.pi/agent/auth.json`，里面有 `openai`（OAuth，订阅）和 `zai-coding-cn`（API key，智谱 coding plan）两个 provider，都是 HOME 下的文件。
- 项目内的 `.pi/mcp.json` 只有在项目被信任时才读；非交互运行用 `--approve` 信任本次运行。不加则 `pi mcp list` 提示「`.pi/mcp.json` is ignored because the project is not trusted」。
- 失败形态：一次运行里 OAuth 刷新失败（`OAuth refresh failed for openai: fetch failed`），事件流出现 `auto_retry_start`（`maxAttempts 3`，延迟 2/4/8 秒），前三条助手消息 `stopReason = "error"`、用量全 0，第四次成功。**整个过程退出码仍是 0**，成功与否要看最后一条助手消息的 `stopReason` 和 `agent_settled`。全部重试都失败时的退出码**未验证**。

**2. 禁用自带工具。** 对照组（默认工具）：模型调用 `read` 读到金丝雀字符串，调用 `bash` 执行 `curl -L https://example.com` 取到页面。禁用组：

- `--tools 'mcp__ia__*'`：允许名单；一旦出现 `mcp__` 开头的条目，MCP 工具也受过滤，`read` / `bash` / `edit` / `write` 都不再声明。
- `--no-extensions` 会连内置 MCP 一起关掉，要显式写 `-e builtin:mcp`（实测不写则服务根本没启动）。
- `--no-skills --no-prompt-templates --no-themes --no-context-files` 避免外部内容进入上下文。
- 结果：模型报告 `CANNOT_READ`、`CANNOT_FETCH`，工具只有 `mcp__ia__get_price_bars` 与 `mcp__ia__get_trigger`；事件流里只出现 `mcp__ia__get_price_bars` 的 `tool_execution_*`。
- 注意：官方文档（`security.md`）明确 pi 没有操作系统级沙箱，工具权限就是进程用户的权限。这里的「禁用」只是「不声明这些工具」，不像 codex 有 `read-only` 沙箱兜底；也不要启用 `codemode`（它让模型写脚本批量调用工具，本次未验证其隔离性）。

**3. 接上本工具集。** 两条路径都验证了：

- **内置 MCP（推荐）**：`.pi/mcp.json`（或 `~/.pi/agent/mcp.json`）

  ```json
  {"mcpServers": {"ia": {"command": "/opt/homebrew/bin/python3",
    "args": ["mini_mcp.py", "--ticker", "AAPL", "--cutoff", "2026-10-27", "--run-id", "r1", "--log", "calls.log"],
    "exposure": "direct", "description": "只读日线与触发规则查询"}}}
  ```

  **必须写 `"exposure": "direct"`**：默认是 `codemode`，工具不会声明给模型，模型回答「没有 get_price_bars 工具」，服务也不会被拉起。服务日志与调用返回和另两个运行时一致（104.25）。工具名同样是 `mcp__ia__get_price_bars`。
- **扩展注册（备选）**：一个 TypeScript 扩展里 `pi.registerTool(defineTool({name, parameters: Type.Object(...), execute}))`，用 `-e <文件> --tools get_price_bars` 加载；实测模型调用成功并返回 104.25，读文件仍是 `CANNOT_READ`。代价是工具层要用 TypeScript 重写，或再包一层去调 Python，不如直接用 MCP。
- **配置限制**：pi 没有「指定 MCP 配置文件」的命令行参数，只有用户级文件和项目级 `.pi/mcp.json`。每个单元的注入参数（`run_id`、截止时间、标的）要么每次写一份临时工作目录下的 `.pi/mcp.json`（`-C` 式换目录运行），要么用扩展的 `pi.registerMcpServer(name, config)` 在会话内注册（文档有，**未实测**）。

附带验证：同一套命令加 `--provider zai-coding-cn --model glm-5.1`，工具调用成功（15 秒），与路线文档「以后按 token 计费的 API 模型统一在 pi 里配置 provider」一致；`glm-5.3` 本次没有测。

**4. token 用量。** `--mode json` 的 `message_end` 事件里 `message.role = "assistant"` 的 `usage`：

```json
{"input":161,"output":46,"cacheRead":1408,"cacheWrite":0,"reasoning":8,"totalTokens":1615,
 "cost":{"input":0.000644,"output":0.00092,"cacheRead":0.000563,"cacheWrite":0,"total":0.002127}}
```

- 一次运行里每个助手消息一份，**要对所有助手消息累加**；失败重试的消息用量为 0。
- `input` **不含**缓存（上面 161 + 46 + 1408 = 1615 = `totalTokens`）。`message.model`、`message.provider`、`message.stopReason` 同在。
- 最小调用（无工具）：`input 477`、`output 5`，是三个运行时里系统提示词最小的（几百 token，对比 codex 的约 2 万）。

**5. 耗时。** 无工具最小调用 23.5 秒（含三次自动重试等待共约 14 秒）、带 MCP 的调用 14 秒；智谱 `glm-5.1` 带一次 MCP 调用 15 秒；launchd 下 9 秒。

## 5. 对 v2.8 spec 的建议

### 5.1 汇总表

| 运行时 | ①无人值守 | ②禁用自带工具 | ③接上本工具集 | ④token 用量 | ⑤预算内完成 |
| --- | --- | --- | --- | --- | --- |
| `claude-code` | 通过（用绝对路径；登录态来自 `settings.json` 环境变量） | 通过 | 通过 | 通过 | 通过 |
| `codex` | 通过（需 `--ignore-user-config`） | 通过，有残留（`apply_patch` 靠只读沙箱兜底；黑名单式） | 通过 | 通过 | 通过，有风险（默认强度 268 秒；固定约 2 万输入 token） |
| `pi` | 通过（PATH 要补 node 目录） | 通过（无 OS 沙箱） | 通过（自带 MCP；需 `exposure: direct`） | 通过（逐消息累加） | 通过 |

### 5.2 每个运行时的禁用方式

| 运行时 | 禁用写法 | 怎么证明生效 |
| --- | --- | --- |
| `claude-code` | `--tools ""`、`--strict-mcp-config --mcp-config <文件>`、`--allowedTools mcp__<服务>__*`、`--permission-mode dontAsk`、`--disable-slash-commands`；不要用 `--bare` / `--safe-mode` / 不含 `user` 的 `--setting-sources` | `stream-json` 的 `system/init` 里 `tools` 必须恰为允许集合 |
| `codex` | `--ignore-user-config --ignore-rules -s read-only -c approval_policy="never" -c web_search="disabled"`，加 `--disable shell_tool / unified_exec / apps / plugins / multi_agent / memories / view_image / image_generation / browser_use / browser_use_external / computer_use / goals / skill_search / tool_suggest / hooks`，MCP 用 `-c mcp_servers.<名>.*`（含 `enabled_tools`） | 让模型在 `exec` 里 `Object.keys(tools)`，结果必须恰为 `{apply_patch, clock__curr_time, list_mcp_resource_templates, list_mcp_resources, read_mcp_resource, mcp__*}`；再让它 `apply_patch` 写一个文件，必须被只读沙箱拒绝 |
| `pi` | `--no-extensions -e builtin:mcp --tools 'mcp__<服务>__*' --no-skills --no-prompt-templates --no-themes --no-context-files --no-session`，MCP 配置写 `exposure: direct` | 事件流里只允许出现 `mcp__<服务>__*` 的 `tool_execution_*`；对照组提示词（读文件、联网）必须失败 |

codex 和 pi 的「禁用」是黑名单式或声明式，CLI 升级后可能多出新工具，所以 spec 里的「禁用生效测试」不能只测一次：每个运行时升级后、以及批处理第一次启动时，都应跑一次上表的「怎么证明生效」检查。对 codex，`codex debug prompt-input` 不反映嵌套工具，不能代替这一步。

### 5.3 适配器接口的可行形态

`run_phase(提示词, 工具范围) → 输出 + token 用量` 对三者都可行，建议形态：

```python
run_phase(
    prompt: str,
    tool_scope: ToolScope,        # 允许的工具名 + 宿主注入的 ticker / cutoff / run_id / 阶段
    *, runtime: str, model: str | None, effort: str | None, deadline_s: float,
) -> PhaseResult(output_text, input_tokens, cached_tokens, output_tokens, reasoning_tokens,
                 runtime, model, status, error_kind)
```

- **进程管理**：宿主用 `subprocess` 起 CLI，绝对路径、显式 `env`（`HOME`、含 node 目录的 `PATH`、代理变量）、空的临时工作目录、`stdin=DEVNULL`、进程级超时。`claude` 没有最大轮数参数，`pi` 失败也可能退出码为 0，所以超时必须由宿主控制。
- **MCP 服务**：每次 `run_phase` 为本次调用生成启动参数（`--ticker`、`--cutoff`、`--run-id`、阶段），写入各运行时的配置（claude 的 `--mcp-config` 文件、codex 的 `-c`、pi 的临时 `.pi/mcp.json`）。工具调用的记录（`agent_tool_calls`、SHA-256）由 MCP 服务进程写库，与现有 `call()` 同一套。服务进程怎么拿数据库连接（环境变量能否传到 MCP 子进程）**本次没有验证**，见第 6 节。
- **token 口径统一**（三者定义不同，适配器要换算成同一口径）：

  | 目标字段 | `claude-code` | `codex` | `pi` |
  | --- | --- | --- | --- |
  | 总输入 | `input_tokens + cache_creation_input_tokens + cache_read_input_tokens` | `input_tokens`（已含缓存） | 各助手消息 `input + cacheRead + cacheWrite` 累加 |
  | 其中缓存命中 | `cache_read_input_tokens` | `cached_input_tokens` | `cacheRead` |
  | 输出 | `output_tokens` | `output_tokens` | `output` 累加 |

- **失败分类**（按「不自动换运行时、按单元记原因」）：`claude` 看退出码与 `is_error`；`codex` 看退出码与 `turn.failed`，中间的 `error` 事件（重连）不算失败；`pi` 退出码不可信，看最后一条助手消息的 `stopReason` 与 `agent_settled`。额度用尽、超时、未登录各自的真实错误文本本次没有拿到，需要在 v2.8 实现时用真实响应核对（与[智谱额度错误码](../features/agent-track.md#已知限制)同样的做法）。

### 5.4 不满足的项与 backlog 建议

没有哪个运行时在五项上完全「不通过」，但有限制，建议如下（取舍由你定）：

- **v2.8 首批：`claude-code` + `pi`。** 两者禁用干净、系统提示词开销小、token 字段清楚，满足「至少两个 CLI 运行时通过验证后才删智谱」。
- **`codex`：条件通过，建议放 v2.8 之后或 v2.8 末尾。** 三个理由：①`apply_patch` 关不掉，安全边界依赖 `read-only` 沙箱，而不是「根本没有这个工具」；②工具全部经 `exec` 隔离区，子代理工具仍在，其继承关系未验证；③默认推理强度下延迟大、每次固定约 2 万输入 token，对 1500 秒批处理预算偏紧。解除条件：验证子代理继承禁用、确认 `-s read-only` 在批处理里一直生效，并把推理强度固定为低或中。
- **需要改的路线文档表述**：§4.6 括号里「pi 不内置 MCP，通过扩展注册同一组工具」，在 pi 1.4.0 应改为「pi 自带 MCP，配置走 `.pi/mcp.json` 或扩展注册」；「用各自的登录态 / 订阅」对 `claude-code` 在本机成立的前提是 `~/.claude/settings.json` 里的网关配置，而不是 Keychain 里的订阅登录。
- **运维配套**：LaunchAgent 的 PATH 只有 `/opt/homebrew/bin:/usr/bin:/bin:/usr/sbin:/sbin`，而 `claude`（`~/.local/bin`）、`pi`（`~/.npm-global/bin`）和它依赖的 `node`（`~/.local/bin`）都不在其中；适配器用绝对路径并自己补 PATH，比改 plist 稳妥。这条应写进 [local-service.md](../operations/local-service.md)（v2.8 实现时）。

## 6. 本报告未验证的事项

- **真实单元规模**：只用了几十 token 的提示词；提议 + 反方各若干次工具调用的真实耗时、token 量，以及是否在 1500 秒预算内跑完一批单元，都没有测。
- **`claude-code` 的订阅（OAuth / Keychain）登录态**：本机走的是 `~/.claude/settings.json` 里的本机网关，订阅登录在 launchd 下能否读 Keychain 没有验证；网关或订阅额度用尽时的错误形态也没有拿到。
- **三个运行时的额度用尽、限流、超时的真实错误文本和退出码**：只验证了「未登录」（claude、codex）。
- **`pi` 全部重试失败时的退出码**；多个 `pi` 进程同时刷新同一份 OAuth 令牌会不会互相覆盖 `auth.json`；批处理并发度。
- **`codex` 的 `spawn_agent` 子代理是否继承禁用设置**；`workspace-write` 沙箱下 `apply_patch` 的行为（本次一直用 `read-only`）。
- **MCP 服务进程如何拿到数据库连接**：本次所有注入都走命令行参数，没有验证各运行时的 `env` 字段（claude 的 `mcpServers.<名>.env`、codex 的 `mcp_servers.<名>.env`、pi 的 `env`）能否把环境变量传给 MCP 子进程，也没有验证运行时是否会把宿主环境里的凭据泄漏给模型可调用的东西。
- **八个真实工具**：只用了两个固定数据的工具；`tools.py` 里带参数校验、截止时间、`call()` 记录的真实函数没有接，大结果（pi 会把超过 20 KB 的结果截断中段）也没有测。
- **LaunchAgent 真实配置**：没有改也没有重启 `local.investment-assistant`；launchd 环境用 `launchctl submit` 临时任务模拟，它没有 plist 里的代理变量，PATH 也比 plist 少 `/opt/homebrew/bin`（对 `codex` 是更严的条件，对 `claude`、`pi` 无差别，因为它们本来就不在 plist 的 PATH 上）。长时间运行后登录态过期、刷新是否仍可用没有观察。
- **`pi` 的 `pi.registerMcpServer` 会话内注册**、`glm-5.3` 在 pi 里的表现、`codex` 的非订阅（API key）模式。
- **输出格式稳定性**：模型能否稳定输出现有校验要求的 JSON（`citations.py` 的输入）不在五项之内，没有测。
